# AI Lessons & Design Decisions

このファイルは、AIが過去のセッションで学んだエラーの解決策や設計判断を記録し、同じミスを繰り返さないための「外部記憶」です。
AIはタスク開始前に必ずこの内容を確認してください。

## 記録テンプレート
新しい知見を追加する際は、以下のフォーマットを使用すること：

```markdown
### [YYYY-MM-DD] 事象の短いタイトル
- **発生した事象**: （何が起きたか、どのようなエラーが出たか）
- **根本原因**: （なぜそれが起きたか、技術的・論理的な理由）
- **解決策・パターン**: （どのように解決したか、再利用可能なパターン）
- **今後のルール**: （今後、同様のケースで守るべき具体的なアクションや制約）
```

### [2026-05-24] Vesperリブランディング、NotebookLM一括パッキング機能、およびPWA化
- **発生した事象**: 他人のアイデアである「つゆみ」から卒業し、オリジナルブランド「Vesper」へ刷新。NotebookLMのソース数制限（最大50個）によるインプット漏れと、スマートフォンからのオフライン閲覧・専用アプリ化の課題を同時に解決する必要があった。
- **根本原因**: 情報の収集は自動化されたが、下流の「知性の拡張（NotebookLM RAG）」と「日常的な消費（スマホUX）」の連携部分にまだ摩擦（フリクション）が残っていたため。
- **解決策・パターン**: 
  1. **未読・High限定一括パッキング**: `sync.js` に `generateNotebookMaster` を実装し、未読かつ最重要（High）の記事（最大50件）の要約と本文を1つのMarkdown（`data/notebooklm_master.md`）に自動結合・統合出力する。
  2. **高級ブランドVesperへの刷新**: マットチャコールブラック（`#121214`）と艶やかなローズゴールド（`#c8968c`）を組み合わせた、シックでモダンなプレミアムデザインにダッシュボードを完全リニューアル。
  3. **依存関係ゼロのPWA化**: `manifest.json` と `sw.js` (Service Worker) を新規実装し、アセットをキャッシュ。AI画像生成（`generate_image`）でデザインに調和する高級アイコンを作成。
- **今後のルール**: 外部ライブラリに頼る前に、ブラウザ標準機能（Web API）やピュアなNode.jsスクリプトで解決可能かを常に検討し、メンテナンス性と「No Extra Dependencies」を両立させる。下流ツール（NotebookLM等）の物理的制約をあらかじめ考慮し、パイプライン側で結合や選別（パッケージ化）などの前処理を行う。

### [2026-05-03] フェーズ3統合と判定精度の向上
- **発生した事象**: 統合スクリプト `scripts/sync.js` での一括処理時に Gemini API (Free Tier) の1日20リクエスト制限に到達。また、優先度判定が High に極端に偏り、タグの表記揺れも発生した。
- **根本原因**: API制限の考慮漏れ、および判定プロンプトの基準が「AI関連」という広すぎる定義であったこと。
- **解決策・パターン**: 指数バックオフによるリトライ、およびプロンプトへの「具体的パレート分布目標（High 10-20%）」と「否定条件」の明記。タグ正規化マップ（`TAG_MAP`）の実装。
- **今後のルール**: バッチ処理は1日上限を意識し進捗を永続化する設計にする。主観判定には数値目標と厳格な必須条件を設ける。

### [2026-05-01] プロジェクトの初期構築：Gemini-Native方針の決定
- **発生した事象**: 外部ツール（Antigravity等）に依存した複雑なワークフローが提案されたが、Gemini CLIの能力を最大限活かす方向に軌道修正した。
- **根本原因**: 依存関係を増やすことは、AIによる自律的なメンテナンスを困難にする可能性があるため。
- **解決策・パターン**: Gemini CLIの標準ツール（web_fetch等）と「Skills」を組み合わせた構成を採用。
- **今後のルール**: 実装は極力Gemini CLIの機能で完結させ、外部スクリプトの作成は最小限に留める。

### [2026-05-07] サンドボックス環境におけるNode.js fetchの制限とcurlによる回避
- **発生した事象**: Node.js (v20) の組み込み `fetch` を使用した外部API（Raindrop.io, Gemini API）やウェブサイトへのアクセスが `fetch failed` で失敗した。`--dns-result-order=ipv4first` フラグでも解消しなかった。
- **根本原因**: サンドボックス環境のネットワーク制限またはDNS設定が、Node.jsの組み込み `fetch` 実装と互換性がない可能性がある。一方で、システム標準の `curl` コマンドは外部アクセスが許可されていた。
- **解決策・パターン**: 通信処理を Node.js の `fetch` から `child_process.execSync` を利用した `curl` コマンド実行に置き換えた。JSONの送受信やヘッダー指定も `curl` の引数として構成することで、従来のロジックを維持しつつ接続性を確保した。
- **今後のルール**: 環境依存のネットワークエラー（fetch failed）が発生した場合は、速やかに `curl` での疎通を確認し、必要に応じて通信ロジックを `curl` ベースに切り替える。特にバッチ処理や外部API連携を行うスクリプトでは、最初から `curl` を選択肢に含める。

### [2026-05-09] 大量バッチ処理時のGemini APIレート制限（429エラー）
- **発生した事象**: 20件の連続処理中にGemini APIで429エラー（Quota exceeded）が発生。指数バックオフによるリトライを行うも、最終的に一部の記事で解析に失敗した。
- **根本原因**: Gemini 3 Flash (Free Tier) の制限（特に短時間での連続リクエスト数、または1日の合計リクエスト数）に達したため。エラーメッセージには `limit: 20` との記載があった。
- **解決策・パターン**: 処理に失敗してもスクリプトを停止せず、次の記事へ進むようにエラーハンドリングを強化。また、一度に大量の処理を行うのではなく、10〜15件程度のバッチに分けて実行する。
- **今後のルール**: 連続処理は最大10件程度を目安とし、429エラーが頻発する場合は時間を置いてから再開する。`sync.js` の `SLEEP_MS` を必要に応じて延長（15s -> 20s等）することを検討する。

### [2026-05-12] curlユーティリティのエラー検知とGemini APIリトライの実装
- **発生した事象**: `scripts/sync.js` で20件のバッチ処理中に429エラー（Quota exceeded）が発生。当初の60秒待機だけでは回避できず、また `curl` ユーティリティが常に `ok: true` を返していたため、リトライロジックが機能せずに処理が中断した。
- **根本原因**: `curl -s -L` はAPIがエラーを返しても終了コード0を返すため、レスポンスJSONの中身を検証せずに `response.ok` を判断していたことが原因。また、無料枠の制限が一時的に厳しくなり、固定待機では不十分な場合があった。
- **解決策・パターン**: `getSummary` 関数内で `responseJson.error` を直接チェックし、エラーコード（429等）に基づいた指数バックオフ（40s, 70s, 100s）を伴うリトライを実装した。また、致命的なエラー以外では `break` せず `continue` で次の記事へ進むようにループ構造を改善した。
- **今後のルール**: 外部API（特にGemini）と連携するスクリプトでは、レスポンスJSONの `error` フィールドを必ず検証し、レート制限に対する自律的なリトライロジックを標準で組み込む。固定の待機時間（SLEEP_MS）に頼りすぎず、APIのレスポンスに応じた柔軟な待機を行う。

### [2026-05-23] 既存レコード更新時のフィールド維持
- **発生した事象**: `scripts/sync.js` で既存の記事を再処理（更新）する際、ユーザーがダッシュボード上で変更した既読ステータス（status）が常に `unread` に上書きされてしまっていた。
- **根本原因**: 新しく生成したオブジェクト（`newArticle`）で `status: 'unread'` を固定値として持たせ、それを `Object.assign` で既存オブジェクトにマージしていたため。
- **解決策・パターン**: オブジェクト作成時に `status: existing ? existing.status : 'unread'` のように、既存データがある場合はその値を優先するようにロジックを修正した。
- **今後のルール**: 既存のJSONデータを更新する際は、ユーザーが手動で変更した可能性のあるフィールド（ステータス、フラグ、手動修正タグなど）を安易に上書きせず、明示的に維持するロジックを組み込むこと。

### [2026-05-24] CI環境での堅牢性とエラー検知の改善（決定版）
- **発生した事象**: GitHub Actions での同期処理が「Rejected」または認証エラーで失敗。AIエージェント（私）が「修正完了」と誤報告（ハルシネーション）し、混乱を招いた。
- **根本原因**: 
  1. **環境変数のスコープ**: `.env` ファイルにのみ依存し、GitHub Secrets (`process.env`) を無視していた。
  2. **Gitプッシュ競合**: AIエージェントと Actions が同時にファイルを触ることで、Action 側が `rejected (fetch first)` でクラッシュ。
  3. **不完全な空振り処理**: 変更がない時に Git操作をスキップするガードレールが不十分だった。
  4. **APIレスポンス検証の甘さ**: HTTP 200 でも JSON 内でエラーを返しているケースを捕捉できていなかった。
- **解決策・パターン**: 
  1. **`dotenv` の導入**: `require('dotenv').config()` を冒頭で呼び出し、`process.env` を最優先とする堅牢なキー取得。
  2. **Git競合回避**: `sync.yml` に `git pull --rebase origin main` を追加。
  3. **条件付きコミット**: `git diff --staged --quiet` による変更有無の事前判定。
  4. **詳細なデバッグログ**: JSON 解析失敗時にレスポンスの生データを出力する例外処理。
- **今後のルール**: CIスクリプトは必ず `exit 1` を投げて失敗を可視化すること。環境変数は物理ファイルに依存せず `process.env` をベースに設計する。

### [2026-05-24] 差分同期（Incremental Sync）の実装による最適化
- **発生した事象**: ブックマーク数が増加するにつれ、全件取得（Full Fetch）による API 制限リスクや Actions 実行時間の増加が懸念された。
- **根本原因**: 取得件数が固定（最大200件）であり、すでに同期済みのデータに対しても毎回 API リクエストを行っていた。
- **解決策・パターン**: 
  1. `sort=-created` の特性を活かし、取得した記事の中に「既存かつMarkdownファイルが存在する」ものを発見した時点でフェッチループを中断（`break`）するロジックを導入。
  2. これにより、差分データのみを取得・処理する Incremental Sync を実現。
- **今後のルール**: 外部データの同期処理では、データの並び順を考慮した「早期中断（Early Break）」パターンを検討し、API 制限の回避と効率化を優先する。

### [2026-05-24] GitHub Pages 公開と Jekyll 回避
- **発生した事象**: GitHub Pages の自動デプロイが Jekyll のパースエラーにより失敗した。
- **根本原因**: Jekyll がリポジトリ内の Markdown や JSON を誤って処理しようとしたため。
- **解決策・パターン**: ルートディレクトリに `.nojekyll` ファイル（空ファイル）を配置し、Jekyll ビルドを無効化。
- **今後のルール**: GitHub Pages で静的ファイルをそのまま配信する場合は、必ず `.nojekyll` を配置すること。

### [2026-08-16] 大量追加時のEarly Breakによる取りこぼし防止とGemini APIの超軽量化
- **発生した事象**: Raindrop に一度に10件以上のブックマークを追加した場合、初回実行で上限（10件）まで処理された後、次回実行時に先頭記事が「処理済み」と判定されて Early Break（即時中断）が発動し、残りの新規記事が永久に取りこぼされる重大なリスクがあった。また、Gemini API の要約・理由出力が使われておらず、トークンコストと実行時間を圧迫していた。
- **根本原因**: 差分同期の早期中断条件を「1件でも処理済み記事を検知したら終了」と短絡的に設計していたこと、および使用していない長文テキスト（要約・今読む理由・後回し理由）を高価な出力トークンで毎回生成させていたこと。
- **解決策・パターン**:
  1. **未処理記事の全量スキャン＆キュー化**: 複数ページ（最大500件）を走査し、`bookmarks.json` または `.md` ファイルが存在しない未処理記事を漏れなく抽出。「連続25件処理済み」が続いた場合のみ安全にスキャンを終了する。
  2. **Gemini APIの軽量化**: 要約出力を全廃し、プロンプトを「重要度スコア（0〜100）とタグ分類」のみに特化。出力トークンを約90%削減し、高速化と429エラー回避を実現。
  3. **本文ソース（Markdown）の独立性確保**: AI用ソース（本文抽出）はローカルの Readability で生成（Gemini API コスト 0円）。
- **今後のルール**: バッチ同期処理で早期中断（Early Break）を導入する場合は、未処理記事の取り残しが発生しないよう「連続一致閾値」や「未処理キュー走査」を必ず組み合わせる。LLMの出力要件はユーザーの実利用に合わせて最小限に絞り、トークンコストと処理時間を常に最適化する。
