## 本文
会社辞めてフリーな生活をしているようで日々個人開発に追われているVtuberの「ぷらむらいす」です。
突然ですが、Webフロントエンドの開発はずるいと思いませんか？
ブラウザにはDOMがあります。Playwrightなら、画面上の座標を人間のように推測しなくても、getByRole("button", { name: "Start Game" })のようにUIの意味を使って操作できます。Vitest Browser Modeのように、実際のブラウザ環境でコンポーネントを動かして検証する仕組みもあります。
そしてAIにもPlaywright MCPを渡せば、実装した画面をAI自身に開かせて、ボタンを押させて、表示結果を確認させられます。
これ、ゲームライクな環境でも使いたい！！！！
UIテストを書きたいし、AIにコーディングを任せたい。AIにはコードを書くだけで満足せず、ゲームを実際に起動して、自分の実装が動くところまで確認してほしい。
しかしゲームのUIには、ブラウザのDOMに相当する共通の観測面がありません。そこで個人開発として作り始めたのが、ゲーム向けのランタイムUIオートメーションプロトコル「Gua」です。
ちなみに「Gua」は、Game UI Automationの頭文字から取っています。そのままと言えばそのままですが、何をする道具なのかは一度覚えれば忘れにくい名前です。
導入方法や使い方をすぐ見たい方は、Gua公式リファレンスも公開しています。Godotへの導入、UIの実装、テスト、Inspector、MCPからの操作まで、日本語で順番に確認できます。

 Guaとは
Guaは、実行中のゲームから意味のあるUIツリーを取り出し、テストコードやAIエージェントからUIを観測・操作するための小さな橋渡しです。
たとえば、タイトル画面に「Start Game」というボタンがあるとします。画像認識だけに頼る場合は、スクリーンショットからそれらしい領域を探し、その座標をクリックすることになります。画面サイズやレイアウトが変われば壊れやすく、似たボタンが並べば判別も難しくなります。
Guaでは、ゲーム側のUIを次のような情報として公開します。

ID

buttonやtextといった役割
表示テキスト
表示・有効状態
画面上の領域

これにより、オートメーション側は座標ではなくUIの意味を使えます。たとえば、まずUIツリーからStart Gameというボタンを探し、そのノードに対してクリックを要求し、次のフレームでLoading...が表示されたかを待てます。
目指している体験は、PlaywrightでWeb UIをテストするときの感覚を、ゲームのランタイムにも持ち込むことです。

 なぜ画像認識だけでは足りないのか
AIはスクリーンショットを見られます。なら、画像を見せてクリックさせれば十分ではないか？と思うかもしれません。
もちろん、見た目の確認にスクリーンショットは重要です。しかしスクリーンショットだけでは、次のような情報を安定して判断できません。

その要素が本当にボタンなのか
現在クリック可能なのか
同じ文言の要素が複数ある場合、どれが対象なのか
透明・非表示のUIが残っていないか
操作後にどの状態へ遷移したのか

人間向けの見た目と、機械向けの意味情報は別物です。
Webでは、スクリーンショットとDOMの両方を使えます。Guaも同じように、スクリーンショットを捨てるのではなく、UIツリー、ノード状態、ログ、スクリーンショットを組み合わせて観測できる形を目指しています。

 実行中のゲームをInspectorで覗く
Guaには、実行中のゲームへ接続する「Gua Inspector」があります。
Inspectorからは、主に次の情報を確認できます。

UIツリー
選択したノードの詳細と状態
ゲーム画面のスクリーンショット
ランタイムログ
クリックやキー入力などのコマンド

ゲームを起動しながら「現在、オートメーション側には何が見えているのか」を確認できます。テストが失敗したときに、ブラックボックスのまま悩む必要を減らすための道具です。
これはゲームエディターをAIから操作するためのMCPではありません。Guaが対象にしているのは、エディターではなく、いま実行されているゲームのUIです。

 GodotのUIを意味のあるツリーにする
現在のGuaが正式に対象としているのは、Godot 4.7のGDScriptプロジェクトです。
Godotアドオンは、実行中のシーンにある標準的なControlをたどり、ButtonなどのUIをGuaの意味ツリーへ反映します。ノードのIDにはgua_id、またはGodotのNodePathを利用できます。
外部からクリック要求が届いた場合も、ゲームの状態を無理やり書き換えるわけではありません。アダプターが要求を受け取り、Godotの通常のボタンシグナルを通して操作します。
この「実際のゲームと同じ経路を通す」ことを重要視しています。テストだけが内部状態を書き換えて成功しても、プレイヤーが操作したときに動かなければ意味がないからです。
これなら「シーンファイルが存在する」「GDScriptに構文エラーがない」で終わらず、ゲームを起動し、開始ボタンを押し、次の画面が表示されるところまで確認できます。

 AIにゲームを触らせる
私が特に欲しかったのは、ここです。
Guaには、同じランタイムブリッジへ接続するMCPサーバー「gui-mcp」があります。MCPクライアントから起動すると、AIエージェントは次のようなツールを利用できます。

get_ui_tree
click_node
press_key
wait_for_node
get_screenshot
get_logs
run_test

bunx gui-mcp@latest mcp
これでAIは、コードを編集したあとにゲームへ接続し、UIツリーを読み、目的のボタンを探し、操作後の表示やログを確認できます。
つまり、AIへの依頼を「このコードを書いてください」から、次のような形へ変えられます。

タイトル画面に設定ボタンを追加してください。実装後はゲームを起動し、設定ボタンを押して、設定画面へ遷移することを確認してください。

AIコーディングで面倒なのは、コードを書かせることではありません。書いたコードが本当に動いたかを人間が毎回確認し、失敗を説明し直すことです。
Guaは、その確認ループをAI自身へ渡すための観測面になります。

 現在対応しているもの
2026年7月時点で、利用対象としている環境はGodot 4.7（GDScript）のみです。そのうえで、次のものを組み合わせて使います。

Godot 4.7用GDScriptアダプターとGDExtension
実行中のGodot UIを公開するランタイムブリッジ
UIツリー、ノード状態、スクリーンショット、ログを確認するGua Inspector
AIエージェントから操作するためのMCPサーバーgui-mcp


リポジトリには他環境に向けた実験的なコードもありますが、現時点では正式なサポート対象として扱いません。特にImGui連携はまだ仮実装の段階です。
UnityやUnreal Engineを含む、あらゆるゲームエンジンですぐ使える完成品でもありません。まずはGodot 4.7のGDScriptプロジェクトで、ゲームUIを観測・操作する体験を固めています。
まだ若いプロジェクトです。だからこそ、Godot 4.7とGDScriptでUIテストを書きたい人、AIにゲームを操作させたい人には、試してフィードバックをもらえると非常に助かります。

 Guaが目指すもの
Guaはゲームエンジンではありません。
ゲームエディターを遠隔操作するMCPでも、画面の見た目だけで頑張る画像認識QAボットでもありません。
実行中のゲームと、テストランナーやAIエージェントの間に置く、小さな橋です。
実行中のゲーム
  ↓ UIツリー・状態・ログ・スクリーンショット
Gua Runtime Bridge
  ├─ Gua Inspector
  └─ MCP経由のテスト・AIエージェント
ブラウザ開発では、UIを意味で探し、クリックし、結果を待ち、期待値を検証することが当たり前になっています。
ゲーム開発でも、それを当たり前にしたい。
そして最終的には、AIに「実装して」と頼んだら、AI自身がゲームを起動し、操作し、壊れていれば直し、動作確認まで終えてほしい。
そんな欲望から作っているのがGuaです。
