## 本文
はじめに
Claude Code を長く使っていると、CLAUDE.md が太ります。過去の失敗パターン、ワークフロー、ツールの使い方を書き足すたびに、ファイルが肥大化していきます。
気づいたら 2000 行近くまで育ち、どんな小さな作業でも毎セッションで全文を読み込ませていました。タスクに取りかかる前から、過去の注意書きだけでコンテキストの大部分を使っている状態でした。
この記事では、そこから 起動時のコンテキスト消費を約 83% 削減 するまでの試行錯誤を書きます。結論だけなら「rules/ と skills/ に切り分けた」ですが、2 ヶ月かけて行きつ戻りつしながら削った記録の方が実用的なので、そちらを中心に書きます（実測値は後半）。

 最初はこうだった（失敗の出発点）
過去の commit ログを掘り返すと、2 月時点で以下のような状態でした。


SuperClaude Framework が提供するモジュールを取捨選択せず全部有効にしていて @import が 12 個。フラグ、原則、モード、MCP 設定などがセッション起動時に全部展開されていました

スキルを作るたびに足していて 24 個。目的の重なるものまで並立していました（レビュー系だけで 3 つなど）

rules/ は存在したが chezmoi 管理外で直置き。複数マシンで同じファイルを別々に編集していて、片方だけルールが古いまま、という状態が起きていました

小さな作業でも「過去に決めた何か」が毎回コンテキストに乗ってくる感覚がありました。/compact の頻度が上がり、コンテキスト枯渇による打ち切りも体感で増えていました。

 どこで何を間違えたか

 1. Claude が既に知っている原則を書き並べていた
SOLID、DRY、KISS、YAGNI を並べたファイルを @import していました。ある日読み返して「これ、Claude が既に知ってるやつだ」と気づきました。コンテキストに入れる価値がない文書を毎セッション読ませていたことになります。削除して特に困ることはありませんでした。

 2. ルールに冗長な例示を書きすぎた
各ルールに「✅ Right: ... / ❌ Wrong: ...」を何行も書いていました。ルール本体だけ残して例示を削ったら半分以下になりました。精度は落ちませんでした。

 3. 似たスキルを並立させていた
「PR レビュー」を目的とするスキルが 3 つありました。後から作ったものが前のを置き換えていたのに、古いファイルを消していませんでした。1 つに統合しました。

 4. rules/ を chezmoi 管理外で直置きにしていた
rules/ を ~/.claude/rules/ に直接書いていた時期が長かったです。複数マシンで別々に編集した結果、片方だけルールが古いまま動いている状態が起きました。chezmoi 配下に移して、ホスト別テンプレートで出し分けるまでに 1 ヶ月かかりました。

 解決アプローチ: 3 層構造
剥がし終えた結果、以下の 3 層に落ち着きました。


CLAUDE.md: エントリーポイント。フレームワーク参照と最重要ルールだけ

~/.claude/rules/*.md: 日常的に効かせたい恒常ルール。ドメイン別に分割

~/.claude/skills/<name>/SKILL.md: 呼び出されたときだけコンテキストに入るワークフロー

測定コード（Python / tiktoken）
import tiktoken
from pathlib import Path
import glob

enc = tiktoken.get_encoding("cl100k_base")

def count(paths):
    return sum(len(enc.encode(Path(p).read_text())) for p in paths if Path(p).exists())

BASE = Path.home() / ".claude"
print("CLAUDE.md    :", count([BASE / "CLAUDE.md"]))
print("rules/       :", count(glob.glob(str(BASE / "rules/*.md"))))
print("skills/      :", count(glob.glob(str(BASE / "skills/**/*.md"), recursive=True)))

 どう使い分けるかのフロー
新しいルールを足したくなったら、以下のフローチャートで判断しています。
新しいルールを足したい
  │
  ├─ 全作業の前提？（textlint、Git 安全）
  │   └─ CLAUDE.md
  │
  ├─ 日常的に効かせたい恒常ルール？
  │   └─ rules/<topic>.md
  │
  └─ 明示的に呼ぶワークフロー？
      └─ skills/<name>/SKILL.md
ワークフローっぽいものは全部 skills/ に寄せるのが効きます。起動時のトークン消費に影響しないので、気軽に足せます。

 さらに効かせている工夫
3 層構造とは別軸で、コンテキスト消費を抑える方法も併用しています。どちらも本題からは外れるので折りたたんでおきます。
サブエージェントへの探索委譲（補足）
コードベース横断の調査やレビューは Explore / general-purpose エージェントに投げて、要約だけメインに返させます。生ログはサブ側のコンテキストで消費され、メインには結論と関連ファイルパスが返ってきます。
たとえば「このリポジトリ全体で gh api の使い方を調べて」と直接やるとメイン側で grep 結果を全部読むことになります。サブエージェントに投げれば数千行の結果が 200 語の要約に圧縮されて返ります。
ただし、削減量そのものはまだ定量計測していません。体感で「明らかに軽い」止まりです。

SessionEnd / PreCompact フックによる自動メモリ化（補足）
SessionEnd と PreCompact フックでトランスクリプトから会話を抜き出し、プロジェクト別メモリに自動で書き出すスクリプトを置いています。
# dot_claude/hooks/executable_auto-memory.sh（抜粋）
TRANSCRIPT="${CLAUDE_TRANSCRIPT_PATH:-}"
CONVERSATION=$(jq -r '...' "$TRANSCRIPT" | head -c 50000)

次セッションで「前回何話したっけ」を長文で再展開せずに済みます。メモリ側は要点のインデックスだけになるので軽いです。

 おわりに（正直な現在地）
2 ヶ月かけて、だいたい以下を学びました。


CLAUDE.md と @import に全部詰める構成は、拡張性・保守性ともに破綻します

本命は skills/ への切り出しです。起動時ロードに乗らないのでいくら増えても重くなりません

rules/ はファイル分割だけでは減りません。chezmoi のホスト別出し分けと組み合わせて初めて効きます

一方で、残っている課題も多いです。


rules/ は 15 本で微妙に太り気味です。「recently-referenced なもの」だけ自動で読む仕組みがあると良いですが、今は全ロードです

一度削った @import がいつの間にか戻ってきています。SuperClaude の更新を取り込んだ際に diff を確認せずマージしたため、@FLAGS.md / @MODE_*.md / @MCP_*.md が復活していました。自分の棚卸し不足です

サブエージェント委譲と auto-memory の削減量を測っていません。「体感で軽い」止まりで、再現性のある数字が出せていません

skills/ の発火条件（自動 vs 明示）をちゃんと把握していません。description のキーワードで勝手に発火するケースがあり、意図しないロードが起きている疑いがあります

要するに「3 層に分けて楽になった」ところで止まっていて、次の削減フェーズに進めていません。次は rules/ の間引きと、削減効果の定量化をやりたいです。

 おまけ：自分の環境を見てみるプロンプト
自分でもこんなプロンプトを Claude Code に貼って現状把握をしました。同じことをやりたい人向けに置いておきます。
~/.claude/CLAUDE.md と、そこから @import されているファイルを全部読んで、以下を出して。

1. 各ファイルの行数と推定トークン数（1行≒4tokensで概算）
2. 起動時に毎回読まれている総トークン数
3. 以下の基準で切り分け提案を表にする
   - 全作業の前提（textlint、Git安全）→ CLAUDE.md に残す
   - 日常的に効かせたい恒常ルール → rules/ に移動
   - 明示的に呼ぶワークフロー → skills/ に切り出し
   - Claude が既に知っている知識（SOLID、DRY等）→ 削除候補
   - 冗長な例示（Right/Wrong パターン）→ 圧縮候補
4. 提案通りに切り分けた場合の推定削減率
