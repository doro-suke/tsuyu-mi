## 本文
AI に任せたコードが、回すたびにじわじわ壊れていく。そんな経験はないでしょうか。
仕様書を書いて AI にコード化させ、問題が出たら仕様を直してまた回す。コードはできるだけ見ない。そういう進め方を試したら、かえってコードがどんどん悪くなった、という話があります。
その違和感を真正面から扱った講演が、AI Engineer というカンファレンスで Matt Pocock さんが話した It Ain't Broke: Why Software Fundamentals Matter More Than Ever です。この記事では、その講演の流れを追いながら、AI にコードを任せても壊れない人が何をやっているのかを整理していきます。

 specs to code を試したら、コードが壊れていった
Matt Pocock さんは Total TypeScript や「Claude Code for real engineers」というオンラインコースを運営している講師です。
そのカリキュラムを組むなかで、Matt さんは最近の流行をひとつ試してみました。specs to code（スペックスツーコード） と呼ばれる手法です。
仕組みはシンプルです。

まずアプリの仕様書をしっかり書く
その仕様書を AI に渡してコードに変換させる
問題が見つかったら、コードではなく仕様書のほうを直す
もう一度コンパイラ（AI によるコード生成）を回す
コードそのものは、できるだけ見ない

「これは新しいパラダイムだから、古いルールはぜんぶ捨てよう」というノリの運動でした。
ただ、Matt さんが実際に試したらこうなったそうです。

コードを見ないようにしようと思っていたけれど、結局見てしまった。最初は普通のコードが出てきて、もう一度回したらちょっと悪くなって、また回したらもっと悪くなって、気づいたら、ただのゴミができあがっていた。

会場で「同じ経験をした人」と挙手を求めると、たくさんの手が挙がったそうです。
Matt さんの結論は明快です。コードを無視して AI に丸ごと管理させるという発想は、結局のところ vibe coding（AI にフィーリングで書かせるやり方）の言い換えにすぎない。仕様書だけを直し続けても、コードはむしろ劣化していく。
ここから Matt さんは逆方向に向かいます。「AI を信じてコードから手を引く」のではなく、「AI が真価を出せるコードベースとは何か」を、古い設計の本に立ち返って考え直していきます。

 古典に書かれていた「変えられないコード」の話
Matt さんがまず引っ張り出してきたのは A Philosophy of Software Design という本です。著者はジョン・オースターハウト。スタンフォード大学でコンピューターサイエンスを教える教授で、Tcl/Tk というプログラミング言語の生みの親としても知られています。
そこには「複雑さ」の定義が書いてあります。

Complexity is anything related to the structure of a software system that makes it hard to understand and modify the system.

訳： ソフトウェアシステムの構造に関連する、システムを理解しづらく、変更しづらくしているもののすべて、それが複雑さです。
つまり、悪いコードベースとは何か、と聞かれたら、答えは「変えにくいコードベース」だ、ということになります。

バグを生まずに変更できないコードは、悪いコードである
変更が容易なコードは、良いコードである

シンプルですが強い基準です。
次に Matt さんが手に取ったのは『達人プログラマー』でした。そこには「ソフトウェアエントロピー」という章があります。エントロピーというのは、放っておくとシステムは秩序を失ってバラバラになっていく、という物理の概念です。
ソフトウェアもまったく同じ性質を持ちます。ひとつ変更を加えるたびに、目の前の変更だけを考えてシステム全体の設計を考えないでいると、コードベースは少しずつ確実に劣化していきます。
そして Matt さんは気づきます。specs to code でコンパイラ（AI）を何度も回していたとき、自分が見ていたのはまさにこのエントロピーそのものだった、と。設計を考えずに変更だけを積み上げていく。その結果が、ゴミの山だったわけです。

 「コードは安い」は嘘だった
specs to code を支えるスローガンに code is cheap という言葉があります。「もうコードは安い、いくらでも生成できる、だから人間がコードに注意を払う必要はない」という空気です。
Matt さんはここに正面から異議を唱えます。

コードは安くなんかない。むしろ、悪いコードはこれまで以上に高くついている。

理由はシンプルです。AI は良いコードベースのなかではきわめて優秀に働きます。ただ、変更しづらいコードベースのなかに放り込まれると、AI も人間と同じように壊し始めます。
つまり、コードベースの質が低いほど、AI から得られる恩恵は小さくなる。
良いコードベースこそが AI の燃料で、それを保つにはソフトウェアの基礎が要る、というわけです。ここから Matt さんは、自分が遭遇した 5 つの失敗モードを順に潰していく構成に入ります。

 失敗 1 ── AI が意図したものを作らないとき
最初の失敗は、誰でも一度は経験しているはずです。「自分の頭のなかにはちゃんとしたイメージがあったのに、AI が出してきたものは、まったく違うものだった」というやつです。
Matt さんがここで持ち出すのは、フレデリック・ブルックスの The Design of Design に出てくる design concept（設計コンセプト） という概念です。ブルックスは IBM でメインフレーム OS の開発を率いた伝説的なエンジニアで、『人月の神話』の著者でもあります。
二人以上で何かを設計するとき、両者の間にはふわっとした「つくろうとしているものの理念」が漂っています。マークダウンに書ける形にはなっていない、目に見えないけれど確かに存在する共通理解。それが設計コンセプトです。
AI と仕事がうまくいかないとき、何が起きているか。人間と AI のあいだで、設計コンセプトが共有できていない。
Matt さんの解決策は、たった数行の指示を AI に渡すことでした。スキルの名前は grill-me。「徹底的に問い詰めろ」という意味の名前です。
中身はこんな短い指示です。

この計画のあらゆる側面について、共通理解に達するまで、容赦なく私にインタビューせよ
設計の枝分かれを一つひとつ歩き、決定どうしの依存関係を順に解いていけ

これだけで、AI は 40 問、60 問、ときには 100 問もの質問を投げ返してきます。
Matt さんが公開したスキルのリポジトリ mattpocock/skills は、執筆時点で GitHub のスター数 2 万を超えています。それくらい刺さっている人が多いということです。このやり取りで生まれた会話は、そのまま PRD（プロダクト要件定義書）にも、Issue にも変換できます。
Matt さんはここで、Claude Code の標準機能である plan モードに小さな批判を加えています。「plan モードはアセットを作りたがりすぎる」。すぐに「計画書」というドキュメントをアウトプットしようとしてしまう、という指摘です。それよりも、共有された設計コンセプトに先にたどり着くほうが大事だ、という主張になります。

 失敗 2 ── AI が冗長になるとき
二つ目の失敗は、もう少し地味ですが厄介です。「AI が出してくる文章やコードがやたらに長くて、自分との会話が噛み合わない感じがする」という違和感です。
Matt さんはこの感覚を、ベテランの開発者ならよく知っているはずだ、と話します。ドメインエキスパート（業務知識を持っている依頼主）と仕事をするときの、あの「言葉の壁」と同じです。
たとえば半導体まわりのアプリを依頼されたとして、開発者は専門用語をうまく咀嚼できません。専門家のほうも、開発者が書いたコードはわからない。両者のあいだで、言葉そのものがズレています。
ここで Matt さんが引っ張ってくるのが、DDD（ドメイン駆動設計）の ubiquitous language（ユビキタス言語、共有言語） という考え方です。
ユビキタス言語とは、開発者の会話、コードのなかの表現、そして業務の専門家との会話、そのすべてが同じ用語で動く状態のことを指します。
それを AI とのやりとりに適用したらどうなるか。Matt さんが作ったのは、コードベースを走査して、出てくる用語を集めてマークダウンの表にまとめてくれるスキルです。そうしてできた用語表を AI に渡し、自分でも開いておく。
AI の思考のログを読んでいると、こんな変化が見えたそうです。

計画の質が上がる
AI 自身の思考が冗長でなくなる
計画と実装のズレも小さくなる

人間と AI で、まず使う言葉を揃える。そのうえで設計を話し合う。これだけで、出力の精度はだいぶ変わるという話です。

 失敗 3・4 ── 動かない、テストしづらい
三つ目の失敗は「ちゃんと作ったはずのものが、なぜか動かない」です。Matt さんの処方は王道です。

TypeScript（型のある JavaScript）のような静的型を使う
フロントエンドなら、AI にブラウザを触らせて挙動を確認できる環境を用意する
自動テストを書く

ただ、ここで Matt さんは LLM（Large Language Model、大規模言語モデル）の悪い癖を指摘します。AI はせっかくフィードバックループ（型エラーやテスト結果といった、即座に返ってくる確認の仕組み）があるのに、それをうまく使いきれない。一気に大量のコードを書いてしまい、最後になって「あ、型チェックしていなかったな、テストも回しておくか」と思い出すような働き方をしがちなのです。
『達人プログラマー』にぴったりの表現があります。

ヘッドライトの先を走ってしまう。

夜道で、自分が照らせる範囲よりも速いスピードで走ってはいけない。フィードバックの速さが、そのままあなたの速度の上限 。これが Matt さんの強調するポイントです。
四つ目の失敗は、その自然な続きです。「テストを書こうにも、テストすること自体が難しい」。テスト設計には、ユニットの大きさをどうするか、何をモックするか、どんな振る舞いを検証するか、たくさんの相互依存した判断があります。
Matt さんの経験則はシンプルです。良いコードベースは、テストしやすいコードベースである。
ではテストしやすい構造とは何か。ふたたびオースターハウトの本に戻ります。そこに deep module（ディープモジュール、深いモジュール） という考え方が出てきます。
ディープモジュールとは、中身に多くの機能を抱えながら、外から見える窓口（インターフェイス）はとても小さい部品のことです。逆にシャローモジュールは、中身がそれほどないわりに窓口だけがやたら複雑な部品を指します。

AI に任せると、放っておいてシャローモジュールだらけのコードができあがりやすい。小さな部品がたくさん散らばっていて、それぞれが互いに薄く絡みあっている状態です。そういうコードベースを AI に探索させると、目的のロジックにたどり着く前に迷子になる。依存関係を理解できず、勝手な変更を入れる。結果としてバグが増える。
ディープモジュールで構成されたコードベースは違います。中身は太く、入り口は細い。テストはその細い入り口に対して書けばいい。中身がどう変わっても、入り口が変わらないなら振る舞いは保証されます。
Matt さんはここでも、シャローからディープにコードベースを整える専用のスキルを作っています。

 失敗 5 ── 脳が追いつかないとき
ここまでの失敗を片づけても、最後にもうひとつ、いちばん深い問題が残ります。人間の脳のほうが、追いつかなくなる 。これが五つ目の失敗です。
「これまでで一番疲れている」と感じている人はいないでしょうか、と Matt さんは会場に問いかけます。たくさんの手が挙がりました。Matt さん自身も同じだそうです。
書けるコードの量が増えれば、レビューしなければならない量も増えます。AI と人間がいっしょに、コードベース全体を頭のなかに保持しようとしてしまう。
ディープモジュールが効くのは、ここでもです。中身が一定の太さでまとまっていると、人間はそれを gray box（グレーボックス） として扱えます。グレーボックスとは、中身を完全に見るわけでもなく、完全に無視するわけでもなく、外側の振る舞いを確かめれば中身は AI に任せていい、という扱い方のことです。

私はインターフェイスを設計する。実装は AI に任せる。

これが Matt さんの五つ目の失敗への答えです。もちろん、金融処理のように壊せない領域はこの限りではありません。ただ、多くのモジュールではこの分業が成立します。人間の脳を救うのは、設計の節度である 、というわけです。

 設計に毎日投資する、それだけ
最後のメッセージは、ケント・ベックの言葉でした。ケント・ベックは TDD（テスト駆動開発）やエクストリームプログラミングを広めたことで知られるエンジニアで、現代のソフトウェア開発のスタイルに大きな影響を与えた人物です。
そのケント・ベックがこう書いています。

Invest in your design every day.

訳： システムの設計に、毎日投資せよ。
Matt さんは specs to code の問題を、この言葉でひと言にまとめます。specs to code は、設計から手を引いている。divest（投資の引き上げ）している。それは投資の真逆だ、と。
Matt さんはこの講演を、ひとつの比喩で締めくくりました。

AI を、現場で実際にコードを書いてくれる、戦術担当の有能な兵卒だと考えてほしい。兵卒の上には、戦略を考える人間が必要だ。そしてそれはあなただ。

戦略を担うために必要なのは、20 年以上前から使われ続けてきたソフトウェアの基礎スキルです。

良いコードベースの定義（変更しやすいこと）
共通言語（ubiquitous language）
TDD（テスト駆動開発）
ディープモジュール
毎日の設計投資

どれも、新しい話ではありません。新しい話ではないからこそ、AI 時代でも揺るがない、という結論になります。
ここまでの内容を振り返ると、こうまとめられます。

specs to code に違和感があるなら、その勘は正しい。コードを見ないという発想は、設計から手を引くことと同じ
AI が壊さないコードベースをつくるための知恵は、すでに古典のなかにある。複雑さの定義、共通言語、ディープモジュール
「設計はあなたが、実装は AI が」という分業を意識すると、人間の脳の負荷も下がる

ソフトウェアの基礎は、AI 時代になって陳腐化したわけではありません。むしろ、こうしたスキルを持っている人ほど AI を強く使いこなせる、という話です。元の動画も短くて熱量があるので、ぜひ見てみてください。
