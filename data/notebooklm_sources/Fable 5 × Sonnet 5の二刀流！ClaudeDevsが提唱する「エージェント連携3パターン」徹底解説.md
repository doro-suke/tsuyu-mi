## 本文
Naです。普段はAIツール、特にClaude Codeや様々なMCPサーバーなどを組み合わせて、日々の開発ワークフローをどうやってハックするか試行錯誤しています。
私自身、最近は自分専用のコーディングエージェントを自作して動かしているのですが、ちょっと複雑な作業をさせようとすると、文脈（コンテキスト）が膨らみ、毎ターンのAPI利用料金がびっくりするような額になってしまいます。おまけに、賢いモデル（OpusやFableクラス）を毎ターン呼び出していると、応答を待つ時間も長くなり、開発のテンポが悪くなってしまうのが悩みでした。
そんな中、先日ClaudeDevsの公式X（旧Twitter）で、非常に興味深いポストのツリー（スレッド）が投稿されていました。

ここで紹介されているのは、次世代モデル（仮定の Fable 5 と Sonnet 5）を組み合わせた 「エージェント連携パターン」 です。
単に1つの強力なモデルを回すのではなく、役割やフェーズに応じてモデルを使い分けることで、「知能レベル（推論力）」 と 「コスト・速度」 のトレードオフを劇的に解消するアプローチです。
今回は、このスレッドで言及されている 3つの設計パターン について、Claude Codeでの具体的な実用例を交えて徹底的に解説します！


 提唱されている3つの連携パターン
公式スレッドでは、Fable 5（高知能・高価格）とSonnet 5（高速・低価格）を組み合わせるアプローチとして、主に以下の3つのパターンが紹介されています。

Advisor（アドバイザー）パターン
Orchestrator（オーケストレーター）パターン
Fable Sandwich（サンドイッチ）パターン

それぞれの仕組みとメリットを詳しく見ていきましょう。


 パターン1: Advisor（アドバイザー）パターン
まずは、最も基本となる「相談役」としての活用パターンです。

エージェントシステムの中の役割を 「Executor（実行役 / Sonnet 5）」 と 「Advisor（相談役 / Fable 5）」 の2つに完全に切り離して協調させます。


Executor (Sonnet 5): メインループを回し、すべてのステップで毎ターン実行されます。ファイルの読み書き、ローカルコマンドの実行、テストの実行、基本的なコード書きといった「手を動かす作業」を高速かつ低コストで愚直に行います。

Advisor (Fable 5): 常時ループで動くのではなく、必要なときにだけオンデマンドで呼び出されます。複雑なエラーの根本原因特定や設計方針の決定など、「頭を使う高度な判断」に特化します。


 なぜ強力なのか？
全体の9割以上の作業ループを安価な Executor で回し、「本当に知恵が必要な瞬間」にだけ Advisor をツール経由で呼び出すため、「大半のトークン消費は低コストなExecutorレートで課金されつつ、全体の知能レベルは最高峰のAdvisorと同等に保つ」 ことができます。

 🛠️ Claude Codeでの設定例
実は、公式の Claude Code にはこのAdvisor機能がネイティブで備わっています。セッション内で以下のコマンドを入力することで、アドバイザーモデルを固定できます。
# アドバイザーモデルに Fable 5 を設定する
/advisor fable
このように設定しておくと、メインで動く Sonnet 5 が作業中に壁にぶつかった際、自動的に Fable 5 へ助言を仰ぐようになり、コンテキストとAPI費用を抑えながら難問を突破できるようになります。


 パターン2: Orchestrator（オーケストレーター）パターン
2つ目は、Fable 5を「司令塔（プランナー）」としてトップに据え、Sonnet 5を「作業員（ワーカー）」として従わせるパターンです。



Orchestrator (Fable 5): ユーザーから受け取った巨大なタスクを解析し、アーキテクチャの設計や、矛盾のない実行プランを作成します。その後、タスクを小さく分割し、下位のワーカーに指示を出します。

Worker (Sonnet 5): 指示された単一のサブタスク（例: 「この関数のユニットテストを書く」「CSSのスタイルを修正する」など）に集中してコードを書き、Orchestratorに結果を報告します。


 メリット
メインコンテキストをOrchestratorが管理するため、作業中に発生する「エージェントが何をやっていたか忘れて迷子になる現象（コンテキストロス）」を防げます。また、並列で複数の Worker（Sonnet 5）を走らせることで、全体のタスク処理時間を大幅に短縮できます。


 パターン3: Fable Sandwich（サンドイッチ）パターン
3つ目は、開発プロセスのフェーズごとにモデルを交互に入れ替える、3ステップの信頼性重視パターンです。

開発の「最初」と「最後（の関門）」だけ高知能モデルを配置し、作業の大部分を標準モデルで挟むことから、コミュニティでは「サンドイッチ」と呼ばれています。


Phase 1: Explore（探索）: まず安価で高速な Sonnet 5 がリポジトリ全体を巡回し、関連するコードや依存関係、エラーログなどを徹底的に集めて整理します。

Phase 2: Plan & Review（計画・査読）: 整理されたコンテキストを Fable 5 に渡し、最も頭を使う「修正方針の決定」と「リスクチェック（セキュリティやパフォーマンスへの影響）」を行います。

Phase 3: Execute（実行・実装）: Fable 5 が立てた確実なプランに沿って、再び Sonnet 5 が具体的なコード書き換えとローカルテストの実行を担当します。


 メリット
最初から Fable 5 にソースコードを探索させると、探索中の読み込みトークンだけで膨大な費用がかかります。探索（泥臭い作業）は Sonnet に任せ、最も思考力が必要な「設計・チェック」のポイントだけで Fable 5 を通過させることで、最高精度の成果物を最も安価に得られます。


 まとめ
改めて、今回のエージェント連携パターンの要点を整理します。
今回は、ClaudeDevsが紹介した「Fable 5を活用する3つの連携パターン」を紹介しました。
まとめの要点:


Advisorパターン: Sonnet 5がメインで走り、行き詰まったときだけFable 5に助言を求める。

Orchestratorパターン: Fable 5がプランを立ててタスクを分解し、複数のSonnet 5に並列で実行させる。

Fable Sandwichパターン: 探索（Sonnet）→ 計画・査読（Fable）→ 実行（Sonnet）と、フェーズごとにモデルをバトンタッチする。

AIエージェントを現場で実用化・プロダクション導入するにあたって、単一モデルの性能向上を待つのではなく、「モデルの組み合わせによって限界を突破する」 というのがこれからのトレンドになりそうです。
