 説明編の振り返り
説明編では、AIエージェント活用における開発者体験の課題と、TREアプローチによる解決策の基本概念について説明しました。
シンプルなプロンプトで高品質な結果を得るために、暗黙知をルールとしてパイプラインに埋め込むアプローチの重要性をご理解いただけたかと思います。

 TREパイプラインの構造
TREパイプラインは、人間の認知プロセスを3段階に分解し、それぞれにルールを定義したものです。
マルチエージェント環境では、各セル内でT（Translator）、R（Realization）、E（Executor）の3つのロールが順番に実行されます。ロール間はYAML形式のインターフェース契約で接続され、タスクがパイプライン的に流れます（T→R→E）。並列化は、複数のセルがそれぞれT→R→Eパイプラインを持つことで実現しています。

 全体像
各段階は明確に定義されたインターフェース契約で接続されており、前段の出力形式が後段の入力形式と一致します。
品質ゲートを通過しない場合は前段に戻り、修正が行われます。
ロール間のYAMLインターフェース契約により、各ロールは独立して動作しながらも、全体として一貫した処理フローを実現しています。
これにより、マルチエージェント環境での並列処理と品質保証を両立しています。

 Translator（ダッシュボード画面の構造化ルール）
Translatorは、自然言語の指示を構造化仕様に変換するルールセットです。入力として自然言語の指示を受け取り、構造化されたYAML仕様を出力します。
このプロセスでは、ドメイン知識や制約条件のチェックリストといったルールが適用されます。
先ほどの「ダッシュボード画面を作って」という例で見てみましょう。
実際のルール例:
# Webアプリ用構造化ルール
domain_knowledge:
  - "認証・認可機能が必要"
  - "ユーザー権限に応じた表示制御"
  - "データの可視化（グラフ・チャート）"

ui_patterns:
  - "検索・フィルタリング機能"
  - "一覧表示とカード表示の切り替え"
  - "ページネーション"

technical_constraints:
  - "レスポンシブデザイン対応"
  - "3秒以内の表示速度"
  - "HTTPS通信必須"

output_format:
  requirement:
    summary: "機能概要"
    primary_functions: []
    secondary_functions: []
    ui_requirements: []
  constraints:
    technical: []
    business: []
    performance: []
  acceptance_criteria: []

 Realization（結線ルール）
Realizationは、構造化仕様を実装可能な計画に結線するルールセットです。入力として構造化されたYAML仕様を受け取り、実装計画（コンポーネント構成、依存関係、実装順序）を出力します。
このプロセスでは、アーキテクチャパターンや技術選定基準、依存関係の解決といったルールが適用されます。
先ほどのダッシュボード画面の例を続けて見てみましょう。
実際のルール例:
# アーキテクチャ選定ルール
architecture_patterns:
  data_heavy: "React + Chart.js + 仮想化"
  simple_crud: "React + Table"
  real_time: "React + WebSocket"

component_rules:
  - "データ表示は表示ロジックと取得ロジックを分離"
  - "共通UIコンポーネントは再利用可能に設計"
  - "非同期処理は適切なローディング表示"

dependency_resolution:
  - "UI → データ取得 → API連携の順で実装"
  - "共通コンポーネントを先に実装"
  - "テストは各コンポーネント完成後"

output_format:
  architecture: "技術スタック"
  components: []
  api_integration: []
  implementation_order: []

 Executor（実行ルール）
Executorは、実装計画に従って実際のコードを生成するルールセットです。入力として実装計画を受け取り、実行可能コード、テスト、ドキュメントを出力します。
このプロセスでは、コーディング規約や品質基準、テスト戦略といったルールが適用されます。
ダッシュボード画面の例では、前段で決定されたReact + TypeScript + Chart.jsの構成に基づいて、実際のコンポーネントが生成されます。
実際のルール例:
# 実装ルール
coding_standards:
  - "TypeScript strict mode"
  - "ESLint + Prettier"
  - "関数型コンポーネント使用"

quality_gates:
  - "単体テストカバレッジ80%以上"
  - "ESLintエラー0件"
  - "TypeScriptエラー0件"

test_strategy:
  - "各コンポーネントに対応するテストファイル"
  - "APIモックを使用した結合テスト"
  - "E2Eテストは主要フローのみ"

output_format:
  - "src/components/*.tsx"
  - "src/components/*.test.tsx"
  - "README.md"

 ルール設計の勘所
TREパイプラインを実際に構築する際の実践的なポイントを説明します。

 YAMLルールの適用メカニズム
YAMLで定義されたルールがAIエージェントにどのように適用されるかは、実装上の重要な要素です。
実際の運用では以下の3つの方式を組み合わせています。
まず、システムプロンプトへの組み込みでは、各ロール（T/R/E）起動時に基本的なYAMLルールをシステムプロンプトに読み込みます。
これにより、エージェントは常に一貫したルールセットを参照できるようになります。
次に、ファイルベースの参照では、タスクYAMLにルールファイルパスを記載し、実行時に動的に読み込みます。
これはRAGのような外部知識参照形式で、タスク固有のルールを適用する仕組みです。
実際の運用では、ハイブリッド方式を採用しています。
基本ルールはシステムプロンプトに組み込み、タスク固有ルールはタスクYAMLで指定することで、再利用性とカスタマイズ性を両立しています。
この多層的なルール適用により、汎用性を保ちながら個別要件にも対応できる柔軟な仕組みを実現しています。

 出力フォーマットの固定
最も効果的なのは、各段階の出力フォーマットを固定することです。YAML形式を採用することで、構造化された情報の表現が可能になり、人間にも機械にも読みやすく、バリデーションが容易になります。
また、階層構造を使うことで情報の整理が自然になり、段階的な詳細化が可能になって認知負荷の軽減にもつながります。

 品質ゲートの設計
品質ゲートは「何を通すか」ではなく「何を通さないか」で定義するという設計アプローチが極めて有効であるという知見を得ました。このアプローチを採用することで、判定の精度を劇的に向上させています。
実際の品質チェックは以下の3つの手段を組み合わせて実現しています。
AIエージェントによる自動チェックでは、rejection_criteriaに基づいてAIエージェント自身が出力内容を検証し、基準を満たさない場合は自動的に前段に戻ります。
YAMLスキーマによるバリデーションでは、出力されたYAMLファイルが定義されたスキーマに準拠しているかを機械的にチェックし、構造的な不備を検出します。
そして、重要なタスクや複雑な要件の場合には、人間による確認をオプションとして設け、ビジネス要件との整合性を検証しています。
これらの多層的なチェック機構により、品質の安定性を確保しています。
Translator品質ゲート:
rejection_criteria:
  - "primary_functionsが空"
  - "acceptance_criteriaが測定不可能"
  - "constraintsにtechnical要素がない"
Realization品質ゲート:
rejection_criteria:
  - "循環依存が存在"
  - "実装順序が依存関係と矛盾"
  - "アーキテクチャが要件と不整合"
Executor品質ゲート:
rejection_criteria:
  - "テストカバレッジ80%未満"
  - "Lintエラーが存在"
  - "実装計画との乖離"

 ドメイン知識の埋め込み
ドメイン知識はチェックリストとしてルールに埋め込みます：
Webアプリ用チェックリスト:
domain_checklist:
  security:
    - "認証・認可の適切な実装"
    - "XSS・CSRF対策"
  usability:
    - "直感的なUI/UX設計"
    - "アクセシビリティ対応"
  performance:
    - "適切なキャッシュ戦略"
    - "効率的なデータ取得"

 粒度調整
タスクの複雑さに応じて、各段階の深さを調整することも重要です。
シンプルなタスクの場合は、
Translatorでは軽量な構造化を行い、
Realizationでは基本的な結線を、
Executorでは標準的な実装を行います。
一方、複雑なタスクの場合は、
Translatorでは詳細な要件分析を行い、
Realizationでは複雑な依存関係の解決を、
Executorでは高度な品質管理を実施するようにしています。
