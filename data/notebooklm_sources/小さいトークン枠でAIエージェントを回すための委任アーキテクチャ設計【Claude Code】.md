## 本文
はじめに
Claude Code のような AI コーディングエージェントを定額プランで常用していると、次の問題に必ずぶつかります。

数時間の作業でトークン枠を使い切り、リセット待ちで作業が止まる
メインエージェントがファイル全文読みや長大なログ出力でコンテキストを浪費する
「とりあえず全部メインモデルにやらせる」運用でコストが青天井になる

本記事では、メインエージェントを「判断と統合」に専念させ、トークンを消費する作業を外部ツールや安価なモデルに委任するアーキテクチャ設計と、その際の判断基準（break-even ルール）・検証規律を紹介します。特定の製品構成に依存しない、汎用的な設計パターンとしてまとめます。

 ベースとなるアーキテクチャ
                 ┌─────────────────────────┐
                 │  オーケストレーター      │
                 │  （メインLLM・高単価）   │
                 │  判断・分解・統合・検証   │
                 └─────┬──────┬──────┬─────┘
        委任           │      │      │
   ┌──────────────┐ ┌──┴───┐ ┌┴─────────┐
   │ LSPツール     │ │実装用 │ │調査用     │
   │（LLM不使用）  │ │別CLI  │ │別CLI      │
   │構造把握・編集 │ │(安価) │ │(Web検索)  │
   └──────────────┘ └──────┘ └──────────┘
処理の流れはシンプルです。オーケストレーターはタスクを分解し、トークンを大量消費する作業（コード読解・大量生成・Web調査）を下流に委任し、返ってきた要約（digest）だけを受け取って統合・検証します。

 設計原則1: メインモデルのコンテキスト消費自体をコストと見なす

 問題
エージェントがファイルを Read するたび、そのファイル全文がコンテキストに載り、以降の全ターンで課金対象になります。1万行のファイルを読んでから10ターン作業すれば、実質10回分読んだのと同じコストです。

 解決策
Step 1: コード構造の把握は LSP ベースのツールに委任する
LSP（Language Server Protocol）を使うツール（Serena など）なら、LLM を介さずシンボル一覧を取得できます。
NG: Read main.py（3000行全文がコンテキストに載る）
OK: get_symbols_overview main.py（クラス/関数名の一覧だけ ≒ 数十行）
    → 必要なメソッドだけ find_symbol で本体取得
Step 2: 編集もシンボル単位で行う
diff を LLM に書かせるのではなく、replace_symbol_body（メソッド丸ごと置換）を使えば、前後のコードをコンテキストに載せずに済みます。


 設計原則2: break-even（損益分岐）判断を毎回行う

 問題
「委任すれば節約になる」は常に正しいわけではありません。委任には仕様の言語化＋往復＋結果検証という固定オーバーヘッドがあり、小さいタスクを委任すると往復コストが節約分を上回る純損失になります。

 解決策
委任判断を次の3分類で機械的に行います。



タスクの性質
判断
理由




1ファイルの小修正・変数リネーム
自分でやる
往復コスト > 節約分


大量スキャフォールド・テスト網羅生成・機械的移行
委任する
生成量が大きく digest で受け取れる


設計判断・トレードオフ検討・最終採否
委任しない
判断の質＝オーケストレーターの存在意義



さらに委任先もタスクで使い分けます。実装は安価なコーディング特化 CLI、Web 調査は検索グラウンディング付きの CLI、分類・フォーマットなどの単純作業は最安モデルのサブエージェント、という**モデル階層化（tiering）**です。
<!-- ルールファイルへの記述例 -->
| 作業 | 委任先 |
|------|--------|
| 新規実装・機能コーディング | 実装特化CLI（安価モデル） |
| Web検索・大規模調査 | 検索付きCLI |
| 単純なパターン処理・分類 | 最安モデルのサブエージェント |
| 進行管理・最終採否・テスト実行 | オーケストレーター直接（委任しない）|

 設計原則3: digest で受け取り、生ログを二度と読まない

 問題
委任しても、委任先の生出力を全部コンテキストに貼り戻したら意味がありません。また過去ターンの巨大なツール結果が残り続けるのも同じ問題です。

 解決策
Step 1: 委任時に「要約形式で返せ」を仕様に含める
依頼テンプレート:
- タスク: XXX を実装せよ
- 出力: 変更ファイル一覧＋各変更の1行要約＋実行したテスト結果のみ
- 禁止: 変更コード全文の貼り付け（diff は git で確認する）
Step 2: 結果確認は diff で行う
生成物の中身はコンテキストに載せず、git diff --stat → 気になるファイルだけ部分 diff、の順で確認します。
Step 3: 大きなツール結果は圧縮退避する
コンテキスト圧縮ツール（Headroom など）で過去の大きな出力を退避し、必要箇所だけ取り出す運用にすると、長時間セッションでの「コンテキスト固定費」を抑えられます。

 設計原則4: 委任先を信用しない（検証はオーケストレーターの責務）

 問題
委任先のエージェントは「GREEN です」「テスト通りました」と自己申告で成功を主張します。実際には依存をモックに差し替えてテストを通す、環境自体を書き換えるといった挙動が観測されており、自己申告をそのまま信じると壊れたコードがマージされます。

 解決策
書き手と検証者を分離します。

委任結果のテストは、オーケストレーター自身がクリーンな状態で再実行する
「passing」の根拠は委任先の報告文ではなく、自分で実行したコマンドの出力のみ
重要な変更は別ベンダーのモデルにクロスレビューさせる（同系モデルは同じ盲点を共有しがち）



 設計原則5: 状態をコンテキストではなくディスクに置く

 問題
長時間タスクの途中でトークン枠が尽きたりセッションがクラッシュすると、コンテキスト上の進捗は全部消えます。再開時にゼロから状況説明をやり直すのは最悪のトークン浪費です。

 解決策
進捗・計画・ブロッカーを常にファイルに永続化します。
<!-- HANDOFF.md の例 -->
# Goal
バッチ処理のリトライ機構追加

# Progress
- [x] 設計確定（指数バックオフ・最大3回）
- [x] retry_handler.py 実装済み
- [ ] 統合テスト未実行 ← 次はここから

# Blockers
- テスト用DBの接続情報が未設定
再開時は全履歴ではなく HANDOFF.md ＋直近履歴だけをコンテキストに入れれば、安価に続きから着手できます。

トークン節約の本質は「安いモデルを使うこと」ではなく、高いモデルのコンテキストに何を載せるかを設計することです。オーケストレーターの仕事を「判断と検証」に絞り込めば、小さいプランでも長時間の自律作業が現実的になります。
