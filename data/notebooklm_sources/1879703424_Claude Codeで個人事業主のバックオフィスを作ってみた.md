## 本文
はじめに
2026年6月に開業届を出し、10月から実際の業務を始めています。仕事の内容は、AI活用開発手法の導入と開発プロセス改善です。
準備を始めてすぐに分かったのは、本業以外の仕事が思ったより多いことでした。屋号を決める、開業届を出す、インボイス登録を判断する、事業用口座を作る、ロゴを作る。どれも一度きりか年に数回の作業で、毎回調べ直すことになります。
そこで、準備を始めた4月に、これらをまとめて任せる仕組みを Claude Code で作りました。リポジトリ名は company です。メインの Claude が窓口になり、調査・経理・企画・営業・法務・デザインの6部署（サブエージェント）へ仕事を振ります。
この記事では、このシステムの構成と、4月から約半年の運用でぶつかった課題、そのたびに足してきた機能を時系列で紹介します。コードはほとんどなく、中身は Markdown の指示書と少しの設定です。

 全体像
私（代表）
   ↓ 相談・指示
[コンサルタント / 代表秘書（メインClaude）]
   ↓ 受付 → 分析 → 分解 → 並列アサイン → 集約 → 報告
   ├── research   調査部（税制・制度・市場・法令の一次調査）
   ├── accounting 経理部（帳簿／確定申告）
   ├── planning   企画部（事業計画／価格戦略／収益見通し）
   ├── sales      営業部（自己紹介／サービス資料）
   ├── legal      法務部（商標・利用規約などの法的リスクの確認）
   └── design     デザイン部（ロゴ／アイコン／ブランドガイド）
使い方は、このリポジトリで claude を起動して日本語で相談するだけです。

「インボイス登録した方がいいか整理して」と頼むと、調査部が制度を確認し、企画部が経営への影響を見て、メインの Claude が1本の回答にまとめます
「法務部だけで」のように部署を指名することもできます

ファイル構成は次のとおりです。
company/
├── CLAUDE.md              # メインClaude（窓口役）への指示
├── README.md              # 人間（私）向けの使い方
├── .claude/
│   ├── agents/            # 部署ごとのサブエージェント定義（6本）
│   ├── skills/status/     # 現状報告スキル /status
│   └── settings.json      # Stopフック
├── state/                 # 会社の状態（確定事項・決定ログ・残タスク）
└── deliverables/          # 各部署の成果物
CLAUDE.md には、窓口役の動き方を6ステップで書いています。


受付：何が欲しいのかを把握する。曖昧なら1〜2問だけ確認する

分析：必要な専門領域を特定する

分解とアサイン：部署ごとのサブタスクに分け、独立なものは並列で起動する

集約：各部署の結果を統合し、矛盾や抜けを補う

報告：1本にまとめた回答を返す。部署の生レポートは貼らない

記録：そのターンで確定した事実・決定・宿題を state/ に書いてから終える

最初の版にあったのは 1〜5 だけです。6 は運用の途中で足しました。経緯は後で書きます。
各部署の定義は .claude/agents/<名前>.md に置いた Markdown です。担当範囲、仕事の進め方、レポートの書式、成果物の保存先を書いています。たとえば調査部には「国税庁や e-Gov などの一次ソースを優先し、数字・締切・条件には出典URLと参照日を必ず付ける。個人ブログは裏取りに使わない」と指示しています。


 何に使ってきたか
準備の期間を含めた半年で、実際に任せた仕事を挙げます。


屋号の決定：10案について商標・既存事業者・ドメイン・SNSハンドルの空きを調査し、1案に絞った

開業手続き：開業届・青色申告承認申請・インボイス登録申請の準備と、登録日をいつにするかの検討

ブランド：配色（日本の伝統色がベース）、ロゴ、デザインシステム、名刺の入稿データ

事業計画と打ち出し：事業定義の整理、紹介Webサイトの文面

社内規程の整備：情報分類、機密情報の取扱い、パスワード運用、インシデント対応の各規程と、資産台帳

口座・税理士：事業用口座の比較、税理士候補の調査

一人でやると、調べものと書類作成が交互に来て頭が切り替わりません。部署に分けておくと、調査と下書きが並行で進み、私は判断だけすれば済みます。

 課題と、足してきた機能
ここからが本題です。最初の版はコミット1つ、487行の Markdown でした。そこから14回のコミットを重ねて今の形になっています。変更のほとんどは、運用で困ったことへの対処です。

 1. 調査結果をそのまま信じてよいのか（4月）
屋号の調査をさせていて、調査レポートの正しさを誰が確かめるのかが気になりました。そこで調査部に「レビューモード」を足しました。既存のレポートを渡すと、次の3軸で検証して A〜C の総合評価を返します。

事実の裏付け：数値や制度の説明が一次ソースと一致するか
論理の飛躍：結論が根拠から導けるか
代替解釈・見落とし：検討されていない選択肢やリスクはないか

調査した本人とは別のコンテキストで検証させるのが要点です。

 2. 成果物をGitHubに置きたくない（5月）
成果物には申請書類などが入ります。private リポジトリでも GitHub には置きたくないので、実体をネットワークドライブへ移し、リポジトリ内の deliverables はそこへのシンボリックリンクにしました。.gitignore で追跡対象から外しています。
サブエージェントの定義は deliverables/<部署>/ という相対パスを参照しているので、リンクに変えても何も書き換えずに動きます。

 3. 部署が足りない（6月）
ロゴと配色が必要になり、デザイン部を新設しました。部署の追加は、.claude/agents/design.md を1本書いて CLAUDE.md の部署一覧に1行足すだけです。
デザイン部の成果物の中心は「デザインシステムの正典」となる Markdown と SVG のソースです。名刺、スライド、Webサイトの配色は、すべてこの正典から派生させています。

 4. 毎回「記憶して」と言うのが面倒（7月）
運用して2か月ほどで、いちばん大きな問題がはっきりしました。決めたことが次のセッションに引き継がれないことです。
当時は、屋号や開業日などの前提を CLAUDE.md に直接書いていました。何かを決めるたびに「これを記憶して」と指示する必要があり、言い忘れると次回は古い前提で話が進みます。CLAUDE.md も膨らむ一方でした。事業定義を変えたときには、CLAUDE.md・README・部署定義の計8ファイルを書き換えることになりました。
そこで state/ ディレクトリを作り、役割の違う3ファイルに分けました。



ファイル
役割
更新のしかた




state/company.md
確定事項の現在値
事実が変わったら上書き


state/decisions.md
決定ログ（決定・理由・却下案）
追記のみ


state/open-loops.md
未完了・保留のタスク
追記し、完了したら削除



company.md と open-loops.md は CLAUDE.md から @state/company.md の形でインポートしているので、毎セッション自動でコンテキストに載ります。決定ログは必要なときだけ読みます。
合わせて、次のルールを決めました。


ターン終了前に記録する：フローに第6ステップ「記録」を足し、「言われたら記録する」から「記録してから終える」に変えた

書き込むのはメインの Claude だけ：サブエージェントは読み取り専用にした。各部署はレポートの末尾に【状態差分】という節を付けて変更候補を返し、メインが検証してから反映する

事実とルールを分ける：company.md には事実だけを書き、運用ルールは CLAUDE.md に書く

3つ目は、導入した当日にレビューさせて見つかった問題への対処です。同じルールが CLAUDE.md と company.md の両方に書かれていて、将来食い違う原因になる状態でした。
決定ログに却下案も残すようにしたのは、効果が大きかった点です。「なぜこの口座にしたのか」「なぜ商標出願を保留したのか」を後から聞いても、当時の理由と捨てた選択肢がそのまま返ってきます。現在、決定ログは約90件あります。

 5. ルールを書いても記録が漏れる（7月）
「ターン終了前に記録する」と書いても、守られないことがあります。そこで Claude Code の Stop フックを使い、仕組みで担保することにしました。
.claude/settings.json に prompt 型のフックを置いています。ターンが終わるたびに別のモデル呼び出しが会話を見て、記録漏れがあればターンの終了を差し戻します。
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "prompt",
            "prompt": "あなたは「記録漏れチェッカー」です。（中略）\n(1) このターンで新たに確定した事実・下した決定・発生または完了した宿題があるか\n(2) あるにもかかわらず state/ 配下のファイルが更新されていないか\n\n(1)(2)の両方が明確にYESの場合のみ {\"ok\": false, \"reason\": \"...\"} を返してください。\n\n次の場合は必ず {\"ok\": true} を返す：質問への回答・調査・レビュー・提案だけで何も確定していないターン／state/ が既に更新されているターン／判断に迷うケース／入力の stop_hook_active が true の場合。",
            "timeout": 30
          }
        ]
      }
    ]
  }
}
工夫したのは「迷ったら通す」と明記したことです。質問に答えただけのターンで差し戻されると、使い勝手が悪くなります。stop_hook_active が true のときに通すのは、差し戻しが無限に続くのを防ぐためです。
同じタイミングで、現状報告スキル /status も作りました。state/ の内容から「今どこにいるか」「待ちになっているもの」「私のボール」「次にやれること」を20行以内でまとめます。数日ぶりに開いたときに、まずこれを打ちます。
一方、このとき見送ったものもあります。Agent Teams はコストが大きく実験的だったので採用していません。CLAUDE.md を .claude/rules/ に分割する案も、当時90行しかなかったので不要と判断しました。

 6. 状態ファイルをGitHubに置いてよいのか（8月）
state/ は当初 git で管理し、「個人情報は書かない」というルールで運用していました。しかし会社の状態を書くファイルに個人情報を書けないのは不便です。方針を変えて、state/ も成果物と同じくネットワークドライブ上の実体とシンボリックリンクにしました。GitHub に出るのは CLAUDE.md・README.md・.claude/ だけです。

 7. 引っ越しで参照が全滅した（8月）
同じ月に、保存先のドライブを別のサービスへ乗り換え、ホームディレクトリのパスも変わりました。その結果、あちこちに書いてあった絶対パスが一斉に壊れました。
いちばん危なかったのは、部署サブエージェントの定義にあった state/company.md への参照です。絶対パスで書いていたので6部署すべてで読めなくなっていました。読めなくてもエラーにはならず、前提知識なしで作業が進んでしまいます。
対処として、絶対パスをなくしました。

ドキュメントには実体パスを書かない。保存先は一般的な呼び名だけで書き、実際の場所は ls -l state deliverables で確認する
部署定義からの参照は相対パスにする
成果物を生成するスクリプトは、スクリプト自身の位置を基準にパスを解決する（__file__、import.meta.url）

実体パスを知っているのはシンボリックリンクだけ、という状態にしたわけです。これでドライブの乗り換えは、フォルダを移してリンクを張り替えるだけで済みます。
mv <現在の実体パス> <新しい実体パス>
ln -sfn <新しい実体パス> ./state
ls -l ./state
この引っ越しでは、/tmp に置いていた依存パッケージも消え、事業計画書の PDF を再生成できなくなりました。これを受けて、Python の実行は uv に統一しました。スクリプトの先頭に PEP 723 のインラインメタデータで依存を書いておけば、どのマシンでも uv run script.py だけで動きます。

 振り返り

 うまくいっていること
窓口が1つで、判断だけに集中できる。 どの部署に頼むかを私が考える必要がありません。複数の領域にまたがる相談でも、返ってくる回答は1本です。
決定の理由が残る。 半年前に決めたことの理由を、自分で覚えていなくて済みます。
仕組みが薄い。 中身は Markdown の指示書と、フックの設定1つ、スキル1つです。Claude Code のバージョンが上がっても、モデルが変わっても、ほぼそのまま動いています。

 残っている課題
状態ファイルが育ちすぎている。 company.md は毎セッション自動で読み込まれるので、簡潔に保つ決まりです。しかし実際には事実が増えるたびに膨らんでいます。決定ログも100KB近くになりました。古い事実の整理や、ファイルの分割が必要になってきています。
シンボリックリンクの先が見えないと前提を失う。 新しいマシンでドライブのマウントが認証エラーで切れていたとき、調査部は state/company.md を読めないまま調査を終えました。このときはレポートの末尾に「読めなかった」と書いてきたので気づけましたが、起動時にリンク先を確認する仕組みはまだありません。
フックは毎ターン、モデルを1回余分に呼ぶ。 記録漏れは減りましたが、差し戻しの指摘が細かすぎることもあります。判定の基準はまだ調整の余地があります。
定型業務の自動化はこれから。 月次の定期実行と部署ごとの永続メモリは、検討を保留しています。

 おわりに
振り返ると、足してきた機能のほとんどは「AI に何をさせるか」ではなく、状態をどこに置き、誰が書き、どう引き継ぐかに関するものでした。記憶の置き場所、書き込み権限、機微な情報の境界、パスの持ち方。人間の組織で情報管理と呼んでいるものと同じです。
部署に分けること自体は初日にできます。その後の半年は、その「会社」が昨日のことを覚えていて、機微な情報を外に出さず、引っ越しても壊れないようにする作業でした。
同じような仕組みを作るなら、次の3つを最初から入れておくことをおすすめします。

確定事項・決定ログ・残タスクを分けた状態ファイル
書き込みは窓口役だけ、という単一ライターの原則
絶対パスを書かないこと
