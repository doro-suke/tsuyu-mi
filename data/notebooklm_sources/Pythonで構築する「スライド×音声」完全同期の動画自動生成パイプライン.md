## 本文
Pythonで構築する「スライド×音声」完全同期の動画自動生成パイプライン：制作コストを激減させる技術選定と実装戦略

 1. はじめに：動画制作における「品質の壁」と自動化の戦略的意義
技術解説動画の制作において、多くのエンジニアやクリエイターが直面するのが「品質と工数のトレードオフ」という壁です。初期の試みではNotebookLM等を利用した自動生成も検討しましたが、生成される動画には特有の「解説調の硬さ」や視覚的な単調さが残り、視聴者のエンゲージメントを高めるには限界がありました。
この「品質の壁」を突破する戦略的解法として、NotebookLMで作成したスライド資産をベースに、Canva等でデザインされたリッチなスライドを動画形式への転換を選択しました。しかし、視覚的品質の向上と引き換えに、新たなボトルネックが浮上します。「スライドの切り替え」と「合成音声のナレーション」をミリ秒単位で手動同期させる作業は、極めて非創造的かつ膨大な工数を要する「苦行」と化してしまったのです。
バックエンドエンジニアの視点に立てば、これは単なる編集作業ではなく、スライド（画像）と台本（音声データ）という「非構造化データのマッピング問題」です。本稿では、これらの個別資産をステートレスに処理し、プログラムによってタイムラインを動的に構築する動画生成パイプラインの実装戦略を詳解します。

 2. 技術スタックの選定理由と各コンポーネントの役割
本パイプラインでは、PDF処理・TTS（Text-to-Speech）・動画レンダリングという異なるドメインの技術をPythonで統合しています。単なる自動化スクリプトではなく、各ライブラリの特性を活かしたデータ駆動型ワークフローを構築しました。

PDF処理
pdf2image / Pillow
PDFをフレーム画像（PNG）へラスタライズしつつ、解像度の適応リサイズ・センタークロップも担う。

pdf2imageの動作にはシステム側への外部バイナリ「Poppler」の導入が必要。


音声合成
VOICEVOX API
台本から人間味のある高品質なナレーションを生成。HTTPリクエストベースで処理を抽象化できるため、パイプラインへの組み込みが容易。
ローカルサーバーを事前に起動しておく必要あり。接続確認は/versionエンドポイントで実施。


動画編集
MoviePy
スライド・ナレーション・BGMを統合し、コードでタイムラインを定義する非線形編集（NLE）を実現。各クリップのdurationを音声長に動的に設定して完全同期を達成する。
MoviePy v2系でAPIが変更（set_duration → with_duration等）されており、バージョン依存に注意。


音声処理
pydub
BGMのループ・カット・ゲイン調整（dB指定）とフェード処理を担う。
BGM音量はデフォルト**−10dB**。settings.jsonのbgm_volume_reduction_dbで調整可能。



これらを疎結合に連携させることで、入力データ（PDF・台本・BGM）が最終的なMP4へと変換される一気通貫のパイプラインを実現しています。

 3. プロジェクト構成：マルチプロジェクト対応の設計
一度構築したパイプラインを複数の動画制作プロジェクトで使い回せるよう、以下のフォルダ構造を採用しています。
movieMaker/
├── main.py           # 全プロセス実行スクリプト
├── settings.json     # 話者ID・音質・クレジット等のグローバル設定
├── inputs/           # 入力ソース（プロジェクト単位）
│   └── project_A/
│       ├── slides.pdf      # スライド
│       ├── script.txt      # ページごとの台本
│       └── bgm.mp3         # BGM（任意）
├── temp/             # 中間生成物（処理完了後に削除可）
│   └── project_A/
│       ├── images/   # PDFから抽出した画像（page_001.png ...）
│       └── audio/    # 合成したナレーション（audio_001.wav ...）
└── outputs/          # 完成動画
    └── project_A.mp4
inputs/以下にプロジェクトフォルダを追加するだけで新しい動画制作が始められます。settings.json一つで話者・速度・クレジット等をプロジェクト横断的に管理できるのがポイントです。

 script.txt の書き方
台本は「数字 ---」区切りでスライド単位に分割します。PDFのページ数と台本ブロック数が一致していないと後段で不一致エラーが発生するため、バリデーションを実装しています。
1 ---
こんにちは。1枚目のスライドの台本です。
2 ---
続いて2枚目です。
3 ---
最後のスライドです。ご視聴ありがとうございました。

 4. 自動化パイプラインの6ステップ：設計の全容
本システムは入力アセットを最終的なビデオストリームへ変換するまでの工程を、以下の6ステップで管理しています。

 Step 1：PDFからフレーム画像への変換（pdf2image）
pdf2image.convert_from_path()でPDFの各ページを独立したPNGへとラスタライズします。
So What?： PDFという文書形式を動画編集エンジンが扱える「フレームデータ」へ標準化し、元のデザイン精度を維持したままプログラム制御可能な状態にします。

 Step 2：台本テキストの解析
正規表現 \d*\s*---\s* で台本ファイルをスライド単位のブロックに分割します。

 Step 3：ナレーション生成（VOICEVOX API）
各台本ブロックを2段階のAPIコールで音声化します。


POST /audio_query → 発話クエリJSONを取得

POST /synthesis → WAVバイナリを取得・保存

settings.jsonのspeed_scale（デフォルト1.1）でナレーション速度を調整でき、VOICEVOXの話者キャラクター（speaker_id）も自由に切り替え可能です。

 Step 4：映像と音声の合成（MoviePy）
本プロジェクトの技術的ハイライトはここにあります。各WAVファイルをAudioFileClipとして読み込み、その.duration属性（秒単位の浮動小数点数）をImageClip.with_duration()に直接注入します。
audio_clip = AudioFileClip(str(wav_path))
img_clip = ImageClip(img_array).with_duration(audio_clip.duration)
img_clip = img_clip.with_audio(audio_clip)
解像度の自動適応： 最初の画像のアスペクト比を判定し、横長なら1920×1080、縦長なら1080×1920をターゲット解像度として自動選択。Pillowでアスペクト比を維持したままリサイズ後、中央をセンタークロップして各スライドを統一解像度に正規化します。これにより、縦動画（ショート・リール）と横動画（YouTube）の両フォーマットに対応できます。
タイムラインのドリフト防止： TTSが生成する音声の長さはテキスト量によって動的に変化します。各クリップのdurationを実計測値から設定することで、後半で映像と音声がずれる「タイムラインのドリフト」が一切発生しません。

 Step 5：BGMのミキシング（pydub）
pydubでBGMを読み込み、bgm_volume_reduction_db（デフォルト**−10dB**）で減衰させた後、動画尺に合わせてループ・カット。MoviePyのCompositeAudioClipでナレーションと合成します。

 Step 6：エクスポート
libx264（映像）+ aac（音声）、24fpsでMP4を書き出します。
final_clip.write_videofile(
    str(out_file),
    fps=24,
    codec="libx264",
    audio_codec="aac"
)
出力先はoutputs/{プロジェクト名}.mp4として自動生成されます。

 5. 実装のポイント：ステートレス性と部分実行オプション
本パイプラインの重要な設計思想がステートレス性です。実行のたびに中間ファイル（画像・音声）をフラッシュしてから再生成するため、入力変更後の再実行でも常にクリーンな状態から処理が始まります。
さらに、試行錯誤を効率化するための部分実行オプションを実装しています。
# 全工程を実行（通常の使い方）
python main.py project_A

# PDFの画像化のみ（スライドを確認したいとき）
python main.py project_A --only-pdf

# 音声生成のみ（台本を修正したとき）
python main.py project_A --only-audio

# 動画合成のみ（BGMだけ変えたいとき）
python main.py project_A --only-video
台本を1行修正するたびに全工程を再実行するのは非効率です。--only-audioで音声だけ再生成し、--only-videoで合成する、というワークフローにより反復サイクルを大幅に短縮できます。

 6. ボーナス機能：クレジットオーバーレイの自動生成
最後のスライドに、VOICEVOXのキャラクター名・BGM素材提供元のクレジットを半透明のオーバーレイとして自動合成する機能も実装しています。
// settings.json
"credit": {
    "enabled": true,
    "position": "top_right",
    "margin_px": 80,
    "font_path": "resources/font.ttf",
    "font_size": 36
}
enabledをtrueにするだけで、PillowのRGBA合成（Image.alpha_composite）を使い半透明の黒背景矩形+縁取りテキストをスライドに上書き保存します。権利表記の記載漏れという凡ミスをコードでゼロにするのが狙いです。

 7. 結論：コンテンツクリエイター中心のワークフローへの転換
本パイプラインの構築により、動画制作の本質的な価値は「編集作業」から**「企画・台本の設計」**へとシフトしました。制作時間を「数時間から数分」へ短縮できたことは、単なる効率化以上の意味を持ちます。それは、クリエイターが非創造的な同期作業という低レイヤーなタスクから解放され、より高次な「何を伝えるか」という設計に全リソースを投入できる環境が整ったことを意味します。
エンジニアにとって、動画制作はもはや「表現」という抽象的な営みではなく、Pythonで最適化可能な「インフラストラクチャ」の問題です。技術によって創作活動のボトルネックをハックし、表現のデリバリー速度を最大化すること。それこそが、自動化アーキテクトとしての醍醐味と言えるでしょう。
さらに付け加えると、GoogleのAIプロダクトにおける全方位戦略によって、競合するプロダクトは非常に苦しい戦いを強いられているのではないかと推察します。一方で、個人開発者にとっては巨人の肩に乗る戦略を取ることも一つの方法だと思いますので、このパイプラインではNotebookLMによって最もコストがかかる部分をアウトソースすることにも成功していると思います。
私はあえて、AI活用を間接的な手法（直接APIを叩かずに、プロダクト経由にする）にする戦略を取っておりますが、コスト面を考えると常にAIのAPIを叩き続けるよりも、トップランナーのプロダクト経由やAIで自前の実装に落とし込んで活用する方がリーズナブルかつサステナブルであると考えます。
