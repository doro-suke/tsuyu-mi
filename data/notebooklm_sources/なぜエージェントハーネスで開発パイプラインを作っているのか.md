## 本文
クロステック・マネジメントでは docker-agent を使い、エージェントハーネスで開発パイプラインを構築しています。現時点の設計では、プロダクトオーナーやプロダクトマネージャーが要求仕様書を Markdown で記述すると、それを受け取って、要求を満たす Web アプリケーションの Pull Request を生成する、という流れです。

 何を作っているのか
私たちが作っているのは docker-agent の外側となるハーネスの部分で、全体像は以下のようになります。

図の中の各工程は、別々のエージェントが非同期に分担するマルチエージェント構成になっています。次の段階へ進めるかどうかは、スクリプトが機械的に判定します。大きく分けると設計ステージと実装ステージの二つがあり、各ステージの内部はさらに細かい工程に分かれていて、一部は並列に、一部はシーケンシャルに進みます。
設計ステージでは、要求仕様書を詳細な設計書に落とし込みます。仕様駆動開発を想像してもらうと分かりやすいと思います。成果物は Markdown と YAML のファイル群で、例えば Mermaid で書いた ER 図やシーケンス図、OpenAPI 形式の API 定義、Gherkin 書式の受け入れテストなどをアーティファクトとして書き出します。この設計書を基に実装ステージが自動で進み、Pull Request の作成まで到達する設計です。
すべての工程を一度に、ワンショットで実行することもできます。工程の間には品質のゲートと監査があり、この流れを無人で回せるように仕組み化したものが、私たちの作っているハーネスです。
設計までは無人で動きますが、人間がどこで介入するかはこれから決めます。全体はまだ構築中で、運用には入っていません。

 なぜ内製しているのか
このハーネスを開発している理由は二つあります。一つ目は、人によるレビューの限界です。組織は業務ドメイン知識の文章化に積極的で、要求仕様書から開発を駆動させる文化があります。その文化のもとで実際に仕様駆動で開発を自動化させてみると、AI による実装速度の向上に対して、人によるレビューがボトルネックになります。開発が速くなった分、レビュー待ちのコストなどが相対的に大きくなってしまいます。メンバーが入れ替わっても一定の基準でコードレビューを行い、質を担保したいのですが、プロジェクトの量や件数が増えるほど、人手のレビューでそれを保つのは難しくなります。
今後、エージェンティックコーディングによって開発はさらに加速します。ここから導かれるのが、コードレビューの負荷をなるべく減らすように開発の前提を作り変えるという、私たちが取り組んでいる課題です。人間がコードレビューをしなくていい状態を作るために鍵となるのが、品質の担保と、その責任をどう仕組み化するかです。
二つ目は、今後の開発規模です。学校 DX や AI を活用した学習支援に関する複数のプロダクトを開発しています。今後、各プロジェクトで要求や制約が具体化していくと見込んでおり、プロダクト数によっては必要な役割や人数が不足する可能性があります。これに備えて、組織の目標として内製のハーネス構築に、プロダクト開発と並行して取り組んでいます。プロダクトを作り切ってからハーネスを整備するのでは遅いと考えているためです。
こうした理由から組織の開発フローを分析した結果、工程を設計と実装の二つに分け、各段の通過を仕組みで検証する今の形になりました。レビューのボトルネックを解消するために、開発パイプラインの中で実際にコードが書かれる段階に、ループでレビューを繰り返すゲートと監査を備えています。アーキテクチャレベルでは組織が備えた ADR(Architecture Decision Records) との照合、そのほかコード規約、セキュリティ要件、デザインコンポーネントの利用ルールもここに入ります。パイプラインを通過した時点で、これらが AI によって自動的に解決されている状態にしたいと思っています。また、これらを自動化・無人化するにあたって、監査要求に耐えられるログ基盤も用意します。
このような開発パイプラインの構築は、グローバル企業でも行われています。Stripe や Ramp、Shopify がその代表例です。各社のプロジェクトを見ていくと、私たちと同じように、特定の問題やボトルネックを解消するために独自に作ったという背景が分かります。ただし、問題領域は違います。各社では、コードベースやリポジトリの規模が大きくなり、開発環境をリモートに移して統一する必要が先に来ていました。私たちの場合は規模ではなく、人間のレビュー工程が先に詰まりました。

 なぜ docker-agent を基盤とするのか
ハーネスを作る以外の選択肢として、既存のコーディングエージェントを使って、各エンジニアの作業にレバレッジを効かせて最大化するという戦略もあります。これは今も続けています。組織内では Claude Code を標準で利用しており、スキルやフックの設定を共有しています。また、パイプラインから外部のエージェントプロセスを呼び出すことにも対応しているので、連携の選択肢にもなっています。
ただし、既製ツールを人が操作する戦略では、使えるエンジニアの数がスケールの制約になり得ると見ています。
この見立てをもとに、パイプラインに採用するコーディングエージェントを、ハーネスとしてカスタマイズできる範囲を軸に比較しました。候補は OpenHands SDK、pi、Claude Agent SDK などです。その中から docker-agent を選びました。理由は、特定のモデルに依存せずマルチモデルで動くこと、権限・サンドボックス・ログがランタイムの標準機能として備わっていること、細かくカスタマイズできることです。候補の中では新しいフレームワークですが、私たちの目的に適しています。工程ごとにエージェントが分かれているので、例えば設計は推論の強いモデル、定型的なチェックや修正は軽量なモデルと、モデルを使い分けてコストを抑える最適化もできます。ハーネスのレイヤーに投資しておけば、モデルやエージェント本体の性能向上は後から取り込めます。


 内製だから使える組織の資産
ハーネスを自分たちで作り込むことで、組織にある豊富な資産を前提に使えます。対象の Web アプリケーションのスタックは組織内でほぼ固定されているので、それに根ざしたパイプラインになっています。サーバーサイドは Go の API、フロントエンドは Next.js と TypeScript、それにビルド環境、リポジトリ構成、アーキテクチャが決まっていて、今後はインフラも固定化されてここに含まれます。
ただし、パイプライン化したことで、人間向けの開発フローとエージェントに適した開発フローが違うことが徐々に明らかになってきました。AI エージェントは基本的に、制約の中でテストが最も安く通る実装に解決してタスクを完了させがちです。指示していないことは省略します。これは普段対話でコーディングしている皆さんもご存知の性質だと思います。パイプラインの中でそれを使うために、繰り返し強制的にガードや監視をすることが必要になりました。
例えば、最上位の要求仕様書と UI デザインのガイドラインが食い違うことがあります。人間ならそもそも要求仕様書側を書き直す判断をしますが、AI はそれをせず、用意したデザインコンポーネントを使わずに独自実装をして解決してしまいます。こうした学びから、要求仕様書のフォーマットと含まれるべき情報を、パイプラインに合わせて整備することになりました。
内部で文書化された資産も、エージェントに読み込ませるだけでは機能しません。パイプラインのエージェントに必要なタイミングで読ませ、それが守られたことを別のエージェントで確認して、フィードバックしてループする仕掛けが要ります。人間が開発とレビューを進めていた頃は、仕様の漏れを人が補ってプロジェクトを進めていたので、衝突がなかったのだと思います。そのため、人間はより厳密に上流工程を管理する必要があります。作業者にも、具体的な実装作業から、抽象的に広く多くを解決する発想が求められます。


 どこまでを自作するのか
私たちは docker-agent をベースにハーネスを構築していますが、docker-agent の標準装備の機能にすべて沿ったものではありません。自分たちの要望に合わせてカスタマイズしたり、機能の一部を外部のミドルウェアに任せたりしています。また、docker-agent 本体側に足りない機能をコントリビュートして追加することも行いました。

例えば、権限のチェックは docker-agent の外でガードできるよう、自前の判定プロセスに投げ、判定には Microsoft の Agent Governance Toolkit を使っています。ログの構築も監視の構築も、docker-agent の外側で自作して、自分たちで保存し分析するようにしています。

現在の実行環境は Cloud Workstations のリモートマシンで、その上に Docker コンテナを使った開発環境が作られています。隔離のためにこの中間へ Docker Sandbox で VM を挟むかどうかは、今検証中でまだ判断していません。


 今後の課題
課題はまだ豊富にあります。まず、最初の入力となる要求仕様書の検査が定まっていません。一番上位の要求仕様書は下流工程のコーディングやセキュリティのガイドラインに強く作用するので、そこをチェックし、必要なら人間が判断するという機能設計も、議論に上がっています。その場合、対話的なコーディングエージェントに組み込まれる形で、人間と AI が一緒に要件定義をする工程を追加するアイデアもあります。また、それらをもとにバックグラウンドで、仕様書に対して形式手法などの検査が走るレイヤーを挟んで自動チェックする案も出ています。
次に、コアだけがある状態で、そこに開発者やプロダクトマネージャーがどう接するかがまだ決まっていません。今の入口は要求仕様書の Markdown ですが、これも今後変わるかもしれません。例えば、私たちの作っているパイプラインと似たもので、Slack ボットなどから話しかけて開発を始められるツールもあります。対話や人間の関与をどの段階でどこまで入れるかというのも、私たちが内製している理由です。すべてを無人化してワンショットで完成するのが良いのではなく、必要としている品質や開発目標が満たされることが重要です。
さらに、使ってみて自己改善ループを走らせる段階にはまだ行っていません。本来ならドッグフーディングとして、サイドプロジェクトで使ってみたいところです。実行環境のインフラの設計もこれからで、より広く活用するために並列実行への対応や、開発環境のライフサイクルの最適化が必要です。また、最終成果物としてできた Pull Request を、誰がどう開発フローとして扱い、責任の所在を担保するかという決定も未定義です。
