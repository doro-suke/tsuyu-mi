## 本文
特定のプロジェクト（言語およびアーキテクチャのリプレイス開発）のフローを前提に組んでいた Claude Code の commands を、skills と役割分担しながら、複数のチームで使える形に整備し直した話です。
「自分のチームのフローに最適化してコマンドを組んだら、他チームでは逆に使いにくくなった」——同じ経験をしている、あるいはこれからやりそうな人に向けて書きました。

 整備前 ── リプレイス開発を前提に組んだコマンド群
もともとこの仕組みは、リプレイス開発をスピーディに進めるために作ったものでした。仕様書を開発と並行して揃えたかったので、リプレイス前の実装を playbooks に書き起こし、そこからリプレイス後の仕様を確定・仕様書化し、それを元に実装する、という流れを前提にしていました。
具体的には、次のようなコマンド群を用意していました。

元実装を playbooks に書き起こす（このとき API 分割案も提示）
API 分割やリプレイス後の仕様を修正する
playbooks を元に、API とフロントの仕様書を作成する
API を実装する（OpenAPI 定義 → 本実装）
フロントを実装する

さらに、あるフェーズの作業が終わったら次のフェーズのコマンドを案内する導線も整えていました。コマンドに沿って進めれば、リプレイス開発が一本道で流れていくイメージです。

 つまずき① ── 他チームのフローに合わなかった
このコマンド群は「playbooks をまず作る」「仕様書を先に固める」という前提の上に成り立っていました。リプレイス開発にはぴったりでしたが、裏を返すと、その前提から外れる開発には合いません。
たとえば、わざわざ playbooks に書き起こすほどでもない保守開発や、API だけを作るような開発。こうした他チームのフローには、用意したコマンドがうまくはまりませんでした。結果として コマンドが使われないケースが増え、実装コードの一貫性があちこちで損なわれていきました。

 つまずき② ── ちょうど skills が台頭してきた
プロジェクトごとにフローが違うのは、考えてみれば当然のことです。だからこそ、フローの違いはそのままに、最低限のアーキテクチャや決まり事だけは先に揃えられるようにしたい——そう考えるようになりました。
ちょうど方針に迷っていたこの時期に、Anthropicが提唱してオープンスタンダードとなった Agent Skills（以降skillsとする） が台頭してきます。skills を使えば、コマンドを明示的に呼び出さなくても、フローに依存せず、実装するときにコーディングルールが自然に守られる。そういう仕組みが作れるのではないか。そこで、skills 中心の開発フローへとシフトすることにしました。

 commands と skills の役割をどう分けたか
シフトにあたって決めたのは、commands と skills の役割分担です。基準はシンプルで、「今から何をするかを、人間が意図的に宣言したいもの」だけを command に残し、それ以外はすべて skills に集約しました。
command として残したのは、たとえば次のようなものです。

これから API を実装するのか、batch を実装するのか
同じフロントリポジトリの中で、管理画面を実装するのか、サービス画面を実装するのか
ADR を作成する

いずれも実装ロジックそのものではなく、「これから何をやるか」という作業コンテキストの宣言です。（とはいえ、実質ほとんどskillsで十分であることがわかって来ている状態なので、commandsは使われていない。）
逆に、コーディングルールやアーキテクチャの決まり事のように、フローに関係なく常に守られてほしいものは、すべて skills に寄せました。以下はAPIのアーキテクチャを遵守できているかをチェックするskillsの例。

api-structure-checker/SKILL.md
---
name: api-structure-checker
description: API構成をチェックするツール。新規API追加後や既存APIの構成確認に使用。「APIの構成をチェック」「API構成を確認」「check api structure」などのリクエストで起動する。(project)
---

# API Structure Checker

APIのディレクトリ構成、ファイル構成をチェックする。

## チェック項目

1. **ディレクトリ構成**: `application/`, `presentation/`, `pkg/` の存在
2. **サブディレクトリ**: `presentation/http/handler/`, `pkg/ogen/`, `pkg/di/`
3. **wire関連ファイル**: `pkg/di/wire.go`, `wire_gen.go` の存在と同期状態
4. **想定外ディレクトリ**: 規約外のディレクトリがないか

## 使い方

```bash
# 単一APIをチェック
./scripts/check_api_structure.sh web

# 全APIをチェック
./scripts/check_api_structure.sh
```

## 出力

- `[OK]` 緑: チェック成功
- `[WARN]` 黄: 警告
- `[ERROR]` 赤: エラー

終了コード: 0（エラーなし）、1（エラーあり）

## API構成の規約

```text
api/
├── application/
│   ├── usecase/        # ユースケース（任意）
│   ├── service/        # サービス（任意）
│   ├── query/          # クエリ（任意）
│   └── dto/            # DTO（任意）
├── presentation/
│   └── http/
│       ├── handler/    # ハンドラー（必須）
│       └── middleware/ # ミドルウェア（任意）
...
```

## Scripts

- `scripts/check_api_structure.sh` - ディレクトリ構成チェック


「人間が明示的に宣言したいかどうか」——この一線で振り分けると、迷うことはほとんどありませんでした。

 なぜ playbook まで skills に寄せたのか ── commands と skills の違い
そもそも commands と skills は、トリガーの仕組みが根本的に違います。


command（slash command）は、人間が /xxx と明示的に呼び出して初めて効く。呼ばなければ何も起こりません。

skills は、Claude がリクエストの文脈と skills の説明（description）を照らし合わせ、関連していれば自動で読み込んで使う（model-invoked）。

ここに、つまずき①の答えがありました。playbook 作成を command のままにしておくと、そのコマンドを使わないチームでは一切効きません。一方 skills に寄せておけば、明示的に呼ばなくても、関連する作業をしているときに Claude が自動で参照してくれる。「コマンドが使われないと一貫性が崩れる」問題そのものに、skills の自動起動が効くわけです。
加えて、skills ならではの利点が2つあります。


段階的な読み込み（progressive disclosure） — 普段は説明文だけをコンテキストに置き、使うときに本体を読み込む。大きな playbook を常駐させずに済み、効率的です。

起動方法を frontmatter で制御できる — disable-model-invocation: true を付ければ「手動でしか呼べない（＝宣言系）」に、付けなければ「自動で効く（＝規約系）」にできる。つまり「宣言は command、作法は自動の skills」という役割分担を、設定ひとつで表現できます。

これが、playbook という"特定フロー前提の手順"まで skills に寄せた理由です。

参考: Extend Claude with skills - Claude Code Docs


 整備後 ── skills 中心で、フローに依存せず品質を守る
役割分担を決めたことで、開発の前提が変わりました。これまでは「コマンドを順番に呼び出す」ことが品質担保の入り口でしたが、整備後は skills が実装時に自動で効くことで、どのフローで開発していても、コーディングルールやアーキテクチャの決まり事が守られる——という形を目指しました。
skills 側には、フローに関係なく常に効かせたいものを集約しました。大きく3種類です。


構造・依存のチェッカー — レイヤー依存やディレクトリ構造、命名規約が崩れていないかを機械的に検証する

レイヤー別のコード生成 — ハンドラやユースケース、クエリなどを"決まった作法"で生成する

仕様・設計まわり — 仕様書テンプレートや OpenAPI のレビュー基準

おもしろいのは、もともと command 側にあった「元実装を playbook に書き起こす」処理も、この skills 側へ移したことです。特定フロー前提の手順すら、"作法"として skills に寄せられると気づいたタイミングでした。
コマンドは「今から何をするか」を宣言したいときだけ使えばよく、保守開発でも API 単体の開発でも、フローを問わず最低限の一貫性が保てるようになります。

 苦労したこと ── skills が「必ず起動する」仕組みがまだ作れていない
正直なところ、移行そのものは大変ではありませんでした。難しいのはその先です。
skills は実装時に自動で起動して効いてくれる想定でした。ところが、どうしてもうまく起動しない場合がある。しかもそれが、PR のコードレビューの段階になって初めて表に出てくる。本来なら実装中に防げていたはずのものを、レビューで指摘されて気づくわけです。
技術的には、skills が起動するかどうかは、その説明文（description）のキーワードが作業中の文脈にマッチするかに左右されます。skills が増えてくると説明文がコンテキストの予算内に収まらず切り詰められ、マッチに必要なキーワードが落ちてしまうこともあります（/doctor で状況を確認できます）。
skills を 必ず起動させる仕組み、ここがまだ作りきれていない、というのが今の正直な現在地です。

 これからの課題 ── レビューまで含めて品質を一貫させる
この「必ず効かせる」をどう実現するかが、これからの課題です。
具体的には、コードレビューまで含めて一貫して質の高い実装を完遂できる仕組みづくりに取り組もうとしています。その手段として注目しているのが TAKT（TAKT Agent Koordination Topology） です。複数の AI エージェントの協調や、人間が介入するポイント、何を記録するかを YAML で定義できる OSS で、レビューループやガードレールを組み込めます。これを使ったフローを確立できれば、skills が効かなかった部分もレビュー段階で確実に拾えるはず、と考えています。


 まとめ
最初は「自分たちのチームのフローを速く回すこと」だけを考えてコマンドを組みました。でも、その最適化がそのまま他チームには足かせになる。振り返ると、これは AI 駆動開発に限らず、特定の文脈に最適化したツールを横展開するときに必ずぶつかる壁だったように思います。
もし今、特定のプロジェクト前提でコマンドや skills を組んでいるなら、「これはフローに依存する宣言なのか、フローに関係なく常に守りたい決まり事なのか」 を一度切り分けてみてください。その線引きが、複数チームで使える基盤への第一歩になるはずです。
skills を必ず効かせる仕組みは、まだ道半ばです。進展があれば、また書こうと思います。
