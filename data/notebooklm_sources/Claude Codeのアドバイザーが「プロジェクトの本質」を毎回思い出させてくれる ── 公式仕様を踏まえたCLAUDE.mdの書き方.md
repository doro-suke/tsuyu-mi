## 本文
この記事で言いたいこと
長いセッションでコーディングを任せていると、メインのモデル（実行モデル / executor）はだんだん「このプロジェクトが本来何を大事にしていたか」を見失います。スケールしない前提のツールに勝手にキャッシュ層を足したり、依存を増やしたくないのにライブラリを追加したり。コンテキストの後半になるほど、目先のタスクに引っ張られて全体の方針からズレていく、という経験は多くの人にあるはずです。
ここで効くのが Claude Code の アドバイザー（advisor） です。アドバイザーは重要な局面で自動的に呼び出され、しかも会話の全履歴を読みます。であれば、アドバイザーに直接宛てて「このプロジェクトの本質はこれだ」と書いておけば、呼び出されるたびに実行モデルの仕事をその本質に照らしてレビューしてくれる ── つまり、忘れっぽい実行モデルに対する「毎回のリマインダー」として使える、という話です。
そしてこの「アドバイザーに直接宛てて書く」やり方には、公式ドキュメントに根拠があります。本記事はそこを参照しながら、実際に使える CLAUDE.md のサンプルまで落とし込みます。

 前提：アドバイザーは何を見て、何を見ないのか
アドバイザーツールはベータ提供中の機能です（ツール識別子 advisor_20260301、ベータヘッダ advisor-tool-2026-03-01）。Claude Code では /advisor コマンドで実行モデルより賢いモデル（例：Sonnet 実行に対して Opus）を相談相手に指定でき、実行モデルが重要な判断のとき（アプローチを固める前、行き詰まったとき、完了を宣言する前など）に自動で相談します。呼び出すタイミングは実行モデルが決めます。
仕組みのうち、今回の本題に直結する性質が2つあります。公式の Advisor tool ドキュメントに明記されています。なお Claude Code での利用には v2.1.98 以降が必要です。課金形態は問わず、Pro / Max などのサブスクリプションでも、API 課金アカウントでも使えます（サブスクの場合、アドバイザー利用はプランの使用量にカウントされ、Claude チャットと共有のプールから消費されます）。バックエンドは Anthropic 直接の基盤で動くため、Amazon Bedrock / Google Vertex AI / Microsoft Foundry では使えません。実験的・ベータ機能なので、挙動や価格、提供範囲は変わりうる点に注意してください。


アドバイザーは executor の全トランスクリプトを受け取る。 システムプロンプト、すべてのツール定義、これまでの全ターン、すべてのツール実行結果を見ます。

アドバイザー呼び出しに引数は渡せない。 server_tool_use の input は常に空で、executor が input に入れた内容はアドバイザーには一切届きません。サーバー側が「全履歴」からアドバイザーの視界を自動構築します。

ここから分かるのは、「アドバイザー専用の入力欄」は存在しないということです。「アドバイザーにだけ別ファイルを渡す」「呼び出し時に個別のプロンプトを添える」といったことはできません。アドバイザーへの指示は、あくまで executor が見ているコンテキスト（システムプロンプトやユーザーメッセージ、そして CLAUDE.md）の中に書いておくしかない。そしてそれで十分に届く、というのがポイントです。

参照：Advisor tool — Claude API Docs


 公式の根拠：「アドバイザーに直接呼びかける指示」は効きが違う
同じドキュメントの Best practices（アドバイザー出力を短くする節）に、本記事の主張の土台になる一文があります。要約するとこうです。

アドバイザーはシステムプロンプトとユーザーメッセージの両方を「executor のタスクに関する引用文脈」として読む。そのため、アドバイザーに直接呼びかける指示は、三人称で書かれた記述よりもはるかに確実に従われる。 Anthropic がテストした中で最も効果的だった配置は、ユーザーメッセージ内に置く一行で、形式は次のとおり。

(Advisor: please keep your guidance under 80 words — I need a focused starting point, not a comprehensive plan.)
ここで2つ、正確に押さえておきたいことがあります。
その1：これは「構文」ではなく「作法」です。 Advisor: という単語やコロンをシステムが特別にパースしているわけではありません。アドバイザーが会話全体を読む以上、宛て名を明示した平文が（三人称の説明文より）よく効く、という性質を利用しているだけです。だから魔法のキーワードを探す必要はなく、要は「アドバイザー、あなたへ」と二人称で語りかける形にする、というだけのことです。
その2：公式が直接挙げている用途は「出力の長さ制御」です。 上の例も「80語以内で答えて」という長さの話です。本記事でこれから紹介する「プロジェクトの本質を伝える」用途は、この 「直接呼びかける方が確実に従われる」という公式の知見を別の目的に応用したもの であって、その用途そのものが公式に明記されているわけではありません。技法としては筋が通っていますが、効果は自分のワークロードで検証してください ── という温度感で読んでください。

 筋書き：なぜ「本質のリマインダー」として機能するのか
整理すると、こういう連鎖になります。

実行モデルはセッションが長くなるほど、直近のタスクに引きずられて全体方針を見失いがち（recency bias / コンテキストドリフト）。
アドバイザーは「アプローチを固める前」「行き詰まったとき」「完了を宣言する前」といった重要な節目で自動的に呼ばれる。
アドバイザーはそのとき会話の全履歴を読む。つまり CLAUDE.md に書いた内容も、システムプロンプト相当の文脈として届く。
そこに アドバイザー宛ての二人称で「このプロジェクトの本質はこれ。executor の手を本質に照らして見てくれ」 と書いておけば、節目ごとに「で、そもそもの狙いからズレてない？」というチェックが自動で入る。

実行モデル自身に「本質を忘れるな」と書く（三人称・自分向けのルール）よりも、判断の節目で必ず登板するアドバイザーに、二人称で本質の番人を任せる方が、ドリフトに対しては効きやすい構図です。実行モデルが忘れても、アドバイザーが思い出させる。役割分担になっているわけです。

 CLAUDE.md サンプル
ここでは例として「オフラインファーストの個人用ツール」を題材にします。この手のプロジェクトは、実行モデルが放っておくと「一般的なベストプラクティス」に引き戻されて、ネットワーク同期やテレメトリ、スケール対応の抽象化を勝手に足しがちです。まさに「本質を忘れる」が起きやすい題材です。
CLAUDE.md に次のように書きます。アドバイザー向けブロックは二人称で、実行モデル向けブロック（いつ相談するか）は executor への指示として、役割を分けて書くのがコツです。
# プロジェクト概要

これは「ひとりのユーザーが自分のために使う」オフラインファーストの個人用ツールです。
スケールやマルチユーザーは目的ではありません。明快さと、外部依存の少なさが最優先です。

## Advisor へ（毎回、これに照らして executor の判断を見てください）

Advisor: あなたは、このプロジェクトの「本質の番人」です。相談を受けたら、まず
次の3点に照らして executor のアプローチを評価し、ズレていれば最初に指摘してください。

1. オフラインファースト：ネットワーク通信・外部API・テレメトリを足していないか。
   「あったら便利」は理由になりません。デフォルトはオフライン完結です。
2. 依存を増やさない：標準ライブラリで足りるものに新規パッケージを足していないか。
3. 単一ユーザー向けの明快さ：スケール・並行処理・将来の拡張性を理由に、
   いま不要な抽象化やキャッシュ層を導入していないか。

この3点と、目先のタスクの都合が衝突したときは、本質（この3点）を優先してください。
助言は要点だけで構いません（長い設計書は不要です）。

## Advisor 活用ルール（実行モデル向け：いつ相談するか）

- 実装に着手する前に、まず Advisor に方針・設計を相談すること。
- 複数ファイルにまたがる変更や、新しい依存・通信を入れる判断の前には必ず相談すること。
- 同じエラーを2回繰り返したら、自力で粘らず Advisor に相談すること。
- 完了を宣言する前に、成果物を保存・コミットしたうえで最終相談すること。

## コーディング規約

（プロジェクト固有の規約をここに。テスト、フォーマッタ、コミット規約など）
ポイントを補足します。


二人称の宛て名（Advisor:）で書いているブロックが、公式が言う「直接呼びかける指示」に相当します。三人称で「アドバイザーは～すべき」と書くより、こうして「あなたは番人です」と語りかける形にしておきます。

「Advisor 活用ルール」は executor 向けです。これはアドバイザーへの命令ではなく、実行モデルに「いつアドバイザーを呼ぶか」を指示するもの。アドバイザーは呼ばれるタイミングを自分では決めきれない（executor が呼ぶ）ので、登板の頻度を上げたいならこちらで促します。公式にも、呼び出し回数を強制する設定はなく頻度は指示文で誘導する、と書かれています。
CLAUDE.md はセッション開始時にコンテキストへ読み込まれ、アドバイザーはその会話履歴ごと受け取ります。だから アドバイザー専用ファイルを別に用意する必要はありません。本質は CLAUDE.md に集約できます。



 出力長の制御も併用する
「本質に照らして指摘して」と頼むと、アドバイザーは饒舌になりがちです。コスト面でも、アドバイザー出力は最大のコストドライバーで、トップレベルの max_tokens では制限されません。公式の手法と合わせて、長さの制約も同じ「直接呼びかけ」で添えておくと収まりがよくなります。先ほどのブロック末尾に入れた「助言は要点だけで構いません」がそれにあたります。
ハードな上限が欲しい場合は、ツール定義側の max_tokens（最小1024、推奨の出発点は2048あたり）で物理的に制限する手もあります。プロンプトでの依頼はソフトな制約、ツール定義の max_tokens はハードな天井、という使い分けです。

 まとめ

アドバイザーには専用の入力欄がない。指示は executor のコンテキスト（CLAUDE.md 含む）に書くしかなく、それで届く。
公式 Best practices によれば、アドバイザーに直接（二人称で）呼びかける指示は、三人称の記述より確実に従われる。ただし公式が挙げる用途は「出力長の制御」で、「本質の伝達」はその応用。
アドバイザーは重要な節目で自動登板し、全履歴を読む。だから 二人称で「本質の番人」を任せておくと、実行モデルが忘れた方針を毎回思い出させる役割を担わせられる。
CLAUDE.md には「Advisor 宛て（二人称・本質）」と「実行モデル宛て（いつ呼ぶか）」を分けて書く。

最後にもう一度だけ。効果はタスク依存です。本記事の「本質リマインダー」用途は公式の保証ではなく応用なので、自分のプロジェクトで実際に効くかは試して確かめてください。
