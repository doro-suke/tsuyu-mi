## 本文
はじめに
株式会社GENDA 開発部エンジニアの奥山です。
先日 Claude Fable 5 が公開され、Opus を上回る Mythos 級の性能が一般提供で使えるということで話題になりました。
公式のベンチマークでも、コーディングを含む各分野で最高水準のスコアが示されています。
一方で、性能が上がった分だけ価格も上がっています。
この水準の単価のモデルに確定した仕様をコードに落とす作業や grep して片っ端からファイルを読むような単純な作業まで任せるのは適切ではないと感じました。
以前から作業をサブエージェントに委譲する仕組み自体は運用していたのですが、これを機に改めてメンテナンスし「メインセッションは上位モデルのまま、実装や調査はサブエージェント経由で Sonnet / Opus に委譲する」という運用ルールとして設計し直しました。


 コストの構造
委譲ルールを作る前に、まずモデルごとの価格を比較しておきます。

 コスト = トークン数 × モデル単価
課金は「消費トークン数 × モデル別単価」で決まります。
API 価格(2026-06-11 時点、$/1M トークン)は次のとおりです。

同じトークン数を処理した場合、Opus は Fable の 半分、Sonnet は 30%、Haiku は 10% のコストになります(比率は Input / Output とも同じです)。
サブスクプラン(Max 等)の quota 消費もモデルごとに重み付けされているため、同じ方向に効きます(正確な比率は公開されていません)。

 トークナイザによるコスト差
価格表だけでは見えない要素としてトークナイザの差があります。
公式の価格ページによると、Opus 4.7 以降のモデル(Fable 5 を含む)は新しいトークナイザを採用しており、同じ内容が従来モデル比で最大35%ほど多くトークン化されるとのことです。

Opus 4.7 and later use a new tokenizer compared to previous models, contributing to their improved performance on a wide range of tasks. This new tokenizer may use up to 35% more tokens for the same fixed text.

Sonnet 4.6 は従来のトークナイザなので、(内容にもよりますが)同じファイルを読むのに必要なトークン数自体が最大で Fable 5 の 3/4 程度まで少なくなります。
単価(Fable 比 30%)と掛け合わせると、同じ作業のコストは概算で実質 1/4 前後になる計算です。「大量のファイル読み込みを伴う作業」を委譲する効果が特に大きいのはこのためです。
なお、Opus 4.8 は Fable 5 と同じトークナイザのため、Opus への委譲で効くのは単価が半分になる分のみです。

 effort によるコスト差
コストに影響するもう一つの要素として、thinking の深さを調整するパラメータである effort(low / medium / high / xhigh / max。対応レベルはモデルにより異なる)があります。
effort を下げると thinking が浅くなり、ツールコールが統合され output トークンが減ります。ただし単価は変わりません。
モデル変更が「単価」を変えるのに対し、effort は「トークン量」を変える、という整理です。
モデル自体のデフォルトは Sonnet 4.6 / Opus 4.8 とも high です(なお、Haiku に effort の概念はありません)。
基本はデフォルトのままで良いと思いますが、コストを気にする場合は仕様が明確な単純タスクの委譲先に限って下げる選択肢もあります。
effort は後述するサブエージェント定義の frontmatter effort フィールドでエージェント単位に指定でき、未指定の場合はセッションの effort を継承します。

 役割ベースのモデル使い分け
方針はシンプルで、タスクの役割ごとに担当モデルを固定するというものです。
賢さが結果を左右する仕事はメインセッション(Fable)に残し、手数が多いだけの仕事はサブエージェントに逃がします。

実装だけでなく調査も委譲対象にしているのは、「探索的なファイル読み込み」こそメイン文脈を圧迫する最大の要因だからです。
逆に、原因の切り分けから必要なデバッグを能力の足りないモデルに投げるとリトライと回り道でかえってトークンを消費するため、Sonnet に出すのは仕様が確定したタスクのみに絞り、デバッグは Opus に出します。
同じ理由で、最安の Haiku にコードを書かせることはしていません。
ただし「テストを実行して合否の要約だけ返す」ような用途には十分なので、テスト実行専用の test-runner だけ Haiku を割り当てています。長大なテスト出力をメイン文脈に入れずに済むため、単価の安さ以上に文脈の節約として効いています。
また、サブエージェントの呼び出しにもコストはかかるため、ツールコール数回で終わる小タスクは委譲の往復の方が高くつきます。そこで、規模の目安と委譲時の作法もルールに入れています。


委譲する: 複数ファイルの読み込み・編集や試行錯誤が見込まれる、ある程度規模の大きい自己完結したタスク

委譲しない: 1〜2ファイルの小さな編集はメインセッションが直接行う

まとめて渡す: 小タスクが複数ある場合は1エージェントにタスクリストごと渡す(呼び出しを1回に圧縮)

再説明を避ける: 指示は plan ファイルやタスクリストのパスを渡し、メインセッションが長文を書き下ろさない

この規模感の線引きは体感ベースの暫定的なもので、運用しながら調整していく予定です。
なお、委譲内容によってはトークンの総量は増えることもあります。それでも目的がコスト(quota 消費)の削減であれば問題ないと考えています。
大半のトークンを Sonnet / Opus 単価に移すこと自体が節約の本体だからです。
委譲先は .claude/agents/ 配下のカスタムエージェントとして定義します。
frontmatter の model: で委譲先モデルを構造的に固定できるため、「Sonnet を使うこと」と文章で指示するより確実です。
前述の effort もここで指定できます。
---
name: implementer
description: Implementation agent for well-specified coding tasks
model: sonnet
effort: medium
---

(エージェントへの指示。報告形式の制約などをここに書く)

 委譲判断の置き場所
エージェント定義を用意しただけでは Claude が毎回それを使ってくれるとは限りません。
「どんなタスクが来たら委譲するか」という判断基準を、すべてのタスクで毎回効かせる仕掛けが別に必要です。
Claude Code で指示を仕込める場所は複数あり(CLAUDE.md、Rules、Skill)、どれが適切かを検討しました。
採用したのは、委譲基準をまとめたファイルを作成し、CLAUDE.md から @ で読み込む方法です。
セッション開始時にロードされるため、タスクの種類を問わず毎回判断基準が効きます。
構成は次のようになりました。
~/.claude/
├── references/
│   └── role-based-model-selection.md   ← 委譲基準(CLAUDE.md から @ 参照)
└── agents/
    ├── code-explore.md       ← model: sonnet(広範なコード調査・構造分析)
    ├── implementer.md        ← model: sonnet(仕様が明確な実装・機械的編集)
    ├── heavy-implementer.md  ← model: opus(複数ファイル実装・デバッグ)
    └── test-runner.md        ← model: haiku(テスト実行・合否の要約)
CLAUDE.md 側には、次のように @ で参照する行を書くだけです。
# Personal Claude Code Instructions

@references/role-based-model-selection.md

 Skill を採用しなかった理由
委譲ルールを Skill にまとめる方法も検討しましたが、Skill を呼び出すかどうかは Claude 自身の判断で決まります。
「判断基準がコンテキストに載っている」ことを構造的に保証したかったため、今回は不採用としました。

 Rules との比較
Claude Code には ~/.claude/rules/ に置くだけで自動ロードされる Rules があり、「CLAUDE.md + @ import」とどちらが良いかも調べました。
Rules の実質的な強みは frontmatter の paths:(glob)による条件付きロードで、マッチしたファイルを触るときだけルールが効きます。
逆に言うと、常時適用のルールに限れば無条件の Rules と @ import は機能的にほぼ等価で、差は保守性くらいです。
今回の委譲ルールはタスク種別ベースの常時適用で paths の恩恵がないため、既存の @ import パターンを継続しました。
パススコープ化したいルールが出てきた時点で、Rules への移行を検討すれば十分と考えています。

 運用の工夫

 Plan ファイルへの owner 注記
計画段階で plan ファイルを書く際に、各実装ステップへ担当を注記させるようにしておきます。
## 実装ステップ
1. API エンドポイント追加 (owner: implementer)
2. 認証まわりのリファクタリング (owner: heavy-implementer)
3. 統合確認・レビュー (owner: main)
また、委譲時は「plan ファイルのパス + ステップ参照」を渡すだけにすることで、メインセッションが指示文を長々と書き下ろさずに済みます。

 報告契約
サブエージェントの最終報告はメイン文脈に戻ってくるため、ここが長いと委譲の意味が薄れてしまいます。
エージェント定義に「報告は変更ファイル一覧・主要な判断・検証結果のみ。コード全文や読んだファイルの内容を貼らない」という制約を入れて、往復コストを抑えています。
調査エージェントについては「発見は file_path:line_number 参照で返す」と決めておくと、メインセッションはそこだけをピンポイントで読めます。

 おわりに
Claude Fable 5 の公開をきっかけに、サブエージェント活用ルールを見直した過程を紹介しました。
モデルやハーネスの性能向上は目覚ましく、深く考えなくても「任せておけば動く」場面が増えています。
だからこそ、今回の見直しはコスト面を一度立ち止まって整理する良い機会になりました。
便利さに甘えず改善できそうな部分は今後も積極的に改善を回していきたいと考えています。
効果測定はこれからなので、ccusage などで消費量を観測しながら粒度基準を調整していく予定です。
本記事が Claude Code のコストに悩む方の一助になれば幸いです。
