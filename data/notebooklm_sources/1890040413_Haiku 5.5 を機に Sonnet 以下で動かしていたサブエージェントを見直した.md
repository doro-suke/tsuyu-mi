## 本文
はじめに
株式会社GENDA 開発部エンジニアの奥山です。
Claude Haiku 5.5 が出ました。

Haiku で effort を指定できるのは 5.5 が初めてで、単価は Haiku 4.5 のちょうど 1/10 になっています。

価格は公式の料金ページより。
Haiku 5.5 はプロンプトが 100,000 トークンを超えると $0.50 / $2.50 に上がります。
私は Claude Code のサブエージェントを .claude/agents/ に置いていて、そのうち 3 つを Sonnet 以下のモデルで動かしています。
テスト実行役の test-runner、調査役の code-explore、実装役の fast-worker です。
これだけ安くなったのだから、この 3 つを Haiku に下げられないかを考えました。
役割ごとに Haiku との相性を ◎ ◯ △ で評価し、そのうえで見直した結果を書き残しておきます。


 役割ごとの Haiku との相性

 test-runner（テスト実行役）: ◎
テストを実行し、合否と失敗の要点だけを返す役割です。
出力が長くても必要なのは状態と件数と失敗箇所だけで、判断を含みません。
Haiku 5.5 のプロンプトガイドには、low は短いツール作業向けで長いプロンプトでは途中で止まりやすいという注意があります。

low is the cheapest and fastest level. Use it for chat, short tool tasks, and simple, high-volume requests. In long agent prompts, the model is more likely to skip a search, stop early, or skip a check at this level.
— Prompting Claude Haiku 5.5

テスト実行役の定義は短く、やることも 1 つなので、この条件には当てはまりません。
Haiku / low に切り替えました。

 code-explore（調査役）: ◯
読み取り専用でコードを調べ、結果を file_path:line_number 付きで返す役割です。
tools は Read / Grep / Glob だけです。
この役割は Haiku と Sonnet をそれぞれ effort medium と high で動かし、4 つの構成を並べて試しました。
対象は 100 ファイル弱の Terraform リポジトリと、TypeScript をはじめ複数の言語が使われている数千ファイル規模の社内モノレポです。
依頼は、普段この役割に頼んでいるものから種類を分けて用意しました。


列挙: ある DB 処理の実行箇所と、その呼び出し元を言語をまたいで全部挙げる

場所探し: ある API のハンドラがどこで定義されているか

フロー追跡: 画面での入力から結果の表示までの経路

存在しないことの確認: 呼び出し元が 0 件の DB 処理について、名前のよく似た既存の処理と誤認して「呼ばれている」と答えないか

比較: 新旧の実装で、同じ DB 処理の呼び方がどう違うか

さらに、名前を grep するだけでは答えが揃わない依頼も足しました。
ORM のスキーマ変数経由でしか参照されないテーブルの読み書き箇所、別の DB 処理の中からしか呼ばれない DB 処理への到達経路、関数注入や動的 import を数段たどらないと分からない「ある DB 処理に到達する HTTP エンドポイント」の列挙です。
正解は事前に自分で grep とコードの読み込みで作っておき、各構成の報告と照らし合わせました。
結果として、答えの質は Haiku と Sonnet で変わりませんでした。
grep をすり抜ける依頼でも、Haiku は Sonnet と同じ箇所を拾っています。
ただ、速くはなりませんでした。
Haiku は調べる範囲を広げる傾向があり、ツールを呼ぶ回数が増えます。
そのぶんトークンは Sonnet より多く、所要時間も同じか長めでした。それでも金銭面では安くなります。
トークンは多いといっても Sonnet の 2 倍には届かない程度です。
単価が 1/20 なので、API 換算の費用は大まかに 1/10 以下に収まる計算です。
ただし Haiku 5.5 はプロンプトが 100,000 トークンを超えると単価が 5 倍になります。
大きなリポジトリで長く調べさせる場合は、この線を越えていないかを見ておく必要があります。

Claude Haiku 5.5 is priced by prompt length: a prompt of over 100,000 tokens pays higher prices.
— Pricing - Long context pricing

Haiku の利点は費用の安さに集約されます。
私はサブスクリプションで使っていて、調査役はメインセッションが結果を待つ役割です。
そのため速さを優先して Sonnet のままにしました。
API の従量課金で使っているなら、質が同じで費用が大きく下がる Haiku を選ぶ理由は十分にあります。
どちらを優先するかで答えが変わるので ◯ です。

 fast-worker（実装役）: △
仕様が決まった実装を任せる役割です。
こちらは試していません。
公式の発表を見るかぎり、測るまでもないと感じたためです。

Sonnet 5.5 and Opus 5.5 remain better choices for complex agentic coding tasks like those measured by Terminal-Bench 4.0.
— Introducing Claude Haiku 5.5

同じページの Terminal-Bench 4.0 の数字は、Haiku 5.5 が 39.2%、Sonnet 5.5 が 70.6% です。
調査役と違って、実装は仕様とコードの食い違いに気づいて止まる判断や変更後の確認まで含みます。
プロンプトガイドにも、low や medium では確認を省いて完了と報告することがあるという注意があります。

At low and medium effort, Claude Haiku 5.5 sometimes reports a code change as done without running a check.
— Prompting Claude Haiku 5.5

実装役は Sonnet / high のまま据え置きました。

 外から effort を指定する旨み
Haiku 5.5 とほぼ同じ時期に、Claude Code の Agent ツールでもサブエージェントの呼び出し時に effort を指定できるようになりました。

Added an effort parameter to the Agent tool, so Claude runs a sub-agent at the effort level you ask for
— Claude Code CHANGELOG v2.1.292

上の比較でも、定義ファイルは変えずにこの機能で model と effort を切り替えました。
比較には便利でした。
ただ普段の運用で、定義に書いた effort とは別に呼び出しのたびに変える旨みは今のところ思いついていません。
後述のとおり調査役で medium と high を比べても差が見えなかったこともあり、effort は役割ごとに定義へ固定しておけば足ります。

 ついでに定義を書き直した
評価のために 3 つの定義ファイルを読み直したところ、モデルとは関係なく直したい点がいくつか見つかりました。
自前の定義を置く意味は、tools や model の制限を構造で保証すること、報告の形を固定すること、毎回同じ指示を依頼文から外すことにあります。
その観点で、3 つとも書き直しました。

 test-runner → command-runner
テスト実行役の価値は「長い出力をメインセッションに流さない」ことで、これはテストに限りません。
lint、型チェック、ビルド、terraform plan も同じです。
そこで名前を command-runner に変え、確認系のコマンド全般を受け持つようにしました。
外部に影響するコマンド（apply、deploy、push）と、入力を待つコマンドは対象外と明記しています。
あわせて、報告の先頭に決まった形のブロックを置かせるようにしました。
Command: <COMMAND>
CWD: <CWD>
Exit code: <code, or "none" if it did not run>
Status: PASSED | FAILED | DID NOT RUN | TIMED OUT
Summary: <counts or the tool's summary line>
特に効いているのが DID NOT RUN です。
コマンドが起動しなかった、依存が足りなかった、テストが 0 件だった、といった状態を「失敗」と区別させています。
これがないと、何も確認できていないのに「失敗した」と報告されたり、逆に 0 件実行が「成功」になったりします。

 code-explore → Haiku が利用できる形で試験運用
調査役の定義には、もともと次の一文がありました。

The orchestrator treats your report as ground truth for decisions it will not re-verify — completeness of the answer outranks economy of reading.

呼び出し元は報告を再検証しないので、読む量より網羅性を優先せよという指示です。
この前提のまま運用を続けることもできます。
評価の節で書いたとおり、この定義のままでも Haiku は Sonnet と同じ箇所を拾っていました。
調査役の報告をそのまま信じて次の判断に使いたいなら、網羅性を最優先にする元の形が合っています。
一方で、呼び出し元の側で裏取りをする運用に変えると、Haiku を採用しやすくなるかもしれません。
報告を検証しないと言い切ると、Haiku は際限なく読む範囲を広げがちです。
呼び出し元の側にも、検証を怠る理由を与えてしまいます。
そこで前提を「呼び出し元は引用された根拠を抜き打ちで確かめてから使う」に変え、報告の形も「呼び出し元が確かめやすい形」に揃えました。
### Reporting

Put the answer first and keep the whole report under about 60 lines;
drop detail before dropping sections. Use these sections, in this order:

1. Answer — one to three sentences.
2. Evidence — `file_path:line_number` and a one-line fact, only for code you read.
3. Inferences — each conclusion that goes beyond the evidence, naming the evidence it rests on.
4. Search log — the patterns and scopes you used. Mandatory for any negative claim.
5. Not covered — what you did not read or could not check.
6. Noticed (optional, at most 3) — risks outside the question in code you already read.
ポイントは 2 つです。

事実と推論を分ける。呼び出し元は推論の部分だけを判断し直せます
「見つからない」という主張には検索パターンを必ず付けさせる。呼び出し元は見落としを探し直すのではなくパターンの抜けを見るだけで済みます

effort は high から medium に下げました。
Sonnet の medium と high を同じ調査で比べたところ、答えの質に差が見えない一方で high はトークンと時間を目に見えて多く使っていたためです。
この形にして Haiku で試しましたが、答えの質は落ちず、調べる範囲が広がりすぎることもなくなり、トークンは旧定義のときより減っています。
評価の時点では速さを優先して Sonnet のままにしましたが、新しい形では Haiku のトークンも減り、費用の差を考えると速さの差を受け入れる価値があるかを実運用で確かめたくなりました。
調査役は、この形のまま Haiku に変えてしばらく運用してみます。

 fast-worker → spec-coder
fast-worker という名前はモデルの性質（速い）を表していて、役割を表していませんでした。
実際には Sonnet / high で動いていて、特に速いわけでもありません。
それ以上に問題なのは、「速いからこっちに投げる」という誤った動機を呼び出し元に与えることです。
この役割の本当の前提は、仕様が具体的に書けていることです。
そこで名前を spec-coder に変え、description に前提を書きました。
仕様には、触るファイル、従うパターン、決定済みの事項が含まれていること。
そこまで書けないなら、先に調べるか、メインセッションで実装すること。
報告には「やらなかったこと」の欄を足しました。
1. Changed files — each path with a one-line summary.
2. Not done — anything in the spec you skipped, deferred, or did only partly,
   with the reason. Write "none" if nothing.
3. Deviations — where you departed from the spec, and where the code contradicted it.
4. Verification — each command you ran with its result, or the check you could not run and why.
黙って飛ばされた作業をレビューで見つけるより、自己申告させる方が安く済みます。
tools は編集と Bash に絞り、仕様に書かれていない限り git の状態を変えないルールも足しました。

 おわりに
Haiku 5.5 をそのまま当てはめられたのは、結果を決まった形に写すだけのテスト実行役でした。
判断を含む実装役は Sonnet のままにしています。
調査役は評価の時点では Sonnet を選びましたが、呼び出し元が裏取りをする形に定義を書き換えて Haiku を試すことにしました。
モデルを差し替えるだけで済む役割もあれば、調査役のように呼び出し元との役割分担を変えて初めて安いモデルが活きる役割もあります。
どちらの場合も定義に置くのは制限と報告の形と依頼の型で、モデルはその中の 1 項目として差し替えます。
本記事がサブエージェントの役割設計の一助になれば幸いです。
