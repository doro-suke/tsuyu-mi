## 本文
「もうClaudeにプロンプトを送っていない。私が持っているのはループだ。プロンプトを送って次に何をするか考えるのは、そのループの方。私の仕事はループを書くことだ」
これは Claude Code を作った Boris Cherny が、2026年6月2日のイベント(WorkOS Acquired Unplugged)で言った言葉です。

I don't prompt Claude anymore. I have loops that are running. They're the ones that are prompting Claude and figuring out what to do. My job is to write loops.

奇妙なことに、まったく別の人物が、ほぼ同じことを言っています。OpenClaw の作者 Peter Steinberger です。彼の言い方はこうです。「coding agent に手で毎回プロンプトを送るのはやめろ。agent にプロンプトを送るループを設計しろ」。
ツールも立場も違う2人が、別々に同じ結論に辿り着いた。プロンプトを磨く時代は終わり、ループを書く時代が来ている、と。
この記事では、その「ループを書く」の中身を整理します。Claude Code の /loop と /goal という2つのコマンドが何をしていて、何がそんなにすごいのか、どう使うのか。自分の運用も交えて書きます。

 「ループを書く」とは何か
Boris は、自分の働き方の変化を3段階で説明しています。


手で書く + 補完: IDEがコードを補完してくれる段階。主役は人間。

並列セッション + 手動プロンプト: 複数のClaudeを同時に走らせるが、プロンプトは毎回人間が打つ。

ループがpromptを出す: 人間はループを書き、ループがClaudeにプロンプトを送り続ける。

3段階目に入ったとき、Boris はIDEをアンインストールしたと明かしています。コードを自分で書かなくなったからです。2025年末のひと月で、彼はIDEを一度も開かず、259本のPRをすべてClaude Codeに書かせたそうです。
ここで言う「ループ」は、難しい仕組みではありません。プロンプトが「一回叩いて一回返ってくる」ものだとすれば、ループは「条件を満たすまで、あるいは止めるまで、勝手に回り続ける」ものです。違いは、いつ次の一手が始まり、いつ止まるかの主導権が、人間から仕組みへ移る点にあります。
Claude Code はこの「回り続ける」を、性格の違う2つのコマンドで提供しています。/loop と /goal です。

 /loop -- 時間で回す
/loop は 時間で回る ループです。一定の間隔ごとに、同じプロンプトを繰り返し実行します。
# 5分ごとに deploy が終わったか確認する
/loop 5m check whether the deploy finished

# 間隔を省略すると、Claude が自分でペースを決める(self-pace)
/loop check CI and address review comments
間隔を省略すると面白いことが起きます。Claudeがタスクの性質を見て、次にいつ走るかを自分で決める。CIが動いている間は短く、静かなときは長く。そして仕事が無くなったと判断したら、自動で止まります。
Boris が実際に回しているループを見ると、用途がよく分かります。
/loop 5m /babysit          # PRのレビュー対応・auto-rebase・PRの世話
/loop 30m /slack-feedback  # Slackのフィードバックから自動でPR作成
/loop /post-merge-sweeper  # 見落とされたレビューコメントを拾ってPR化
/loop 1h /pr-pruner        # 古い不要なPRを閉じる
どれも「定期的に様子を見て、あれば対応する」型です。/loop はポーリング。監視と定期メンテナンスに向いています。

 /goal -- 完了するまで回す
/goal は、時間の代わりに 完了条件 で回ります。達成したい状態を1つ書くと、それが満たされるまでClaudeがターンを回し続けます。
/goal all tests in test/auth pass and the lint step is clean
これだけで、テストが全部通ってlintがきれいになるまで、Claudeは勝手に次のターンを始めます。プロンプトを毎回打つ必要はありません。
ここからが本題です。いつ「終わった」と判定するのは、誰か。
公式ドキュメントの一文が、すべてを言っています。

completion is decided by a fresh model rather than the one doing the work.
（完了の判定は、作業をしているモデルではなく、別の新鮮なモデルが下す）

/goal は毎ターンの後に、作業役とは別の小型モデル(デフォルトはHaiku) に「条件は満たされたか?」を聞きます。満たされていなければ、その理由を添えて次のターンへ。満たされて初めて、ゴール達成として終了します。
なぜこれが発明なのか。AIエージェントには「やったつもりで止まる」という持病があるからです。自分で書いて、自分で「できました」と言う。人間が確かめると、半分しかできていない。作業者に完了判定をさせる限り、これは消えません。/goal は判定を別の役者に渡すことで、これを構造的に潰しました。効いたのは賢いプロンプトの工夫ではありません。役割を分けたことです。
良い完了条件には3つ揃っている、とドキュメントは言います。


測れる終了状態: テスト結果、buildのexit code、ファイル数、空のキュー

証明の仕方: 「npm test がexit 0」「git status がクリーン」など、Claudeの出力で示せること

守るべき制約: 「他のテストファイルは変更しない」など

/loop と /goal の違いは、公式の比較表が一番分かりやすいです。




次のターンが始まる
止まる条件




/goal
前のターンが終わったとき
モデルが条件達成を確認したとき


/loop
時間間隔が経過したとき
自分で止める、またはClaudeが完了と判断



時間で回すか、完了で回すか。監視なら /loop、達成なら /goal。トリアージ・リサーチ・検証のような繰り返し作業は、この2つを組み合わせると回しやすくなります。

 もう一人の作者も、同じ結論に
冒頭で名前を出した Peter Steinberger は、PDF SDKの PSPDFKit を創業・経営し、2021年に€100M規模(約160億円)のInsight Partnersの出資を受けて第一線を退いた人物です。2025年にOpenClawという個人用AIエージェントを作り始め、GitHubのスターは数ヶ月で20万を超えました。2026年2月には本人がOpenAIに採用されています。
そのOpenClawも、中心にあるのは自律ループです。設計思想は「brains and muscles」。頭脳(Claude や GPT、ローカルのOllamaなどのLLM)と、筋肉(ローカルのファイルシステムやTelegram・Discord連携)を分ける。そして徹底して local-first です。「自律エージェントが強力になるほど、それを中央集権の企業に全部握らせるのは危険だ」というのが、ローカルにこだわる理由です。
ゴールの扱いも Claude Code とよく似ています。OpenClawのエージェントには get_goal というツールがあり、現在のゴール・目的・使ったトークン・トークン予算まで読めます。ゴールを1つ与えると、エージェントは plan → act → test → review → iterate を、数時間から数日、達成するまで回します。
そして興味深いのが、OpenClawの自己改善です。エージェントが自分のコードを書き換える、という危ういことをやるのですが、その対処が面白い。変更を提案するエージェントと、それを評価する別のエージェントに分ける、という**敵対的(adversarial)**な設計が説明されています。
気づいた方もいると思います。/goal が「作業役と判定役を分けた」のと、同じ発想です。判定を作業者から切り離すという考え方は、ループ設計のあちこちに顔を出します。

 何がすごいのか -- 判定を、外に出す
2つのツール、2人の作者を並べると、すごさの正体が見えてきます。
これまでのAIの使い方は「何をするか」を人間が指示するものでした。プロンプトを磨くとは、指示の精度を上げることです。
ループを書くというのは、そこから一段ずれています。人間が設計するのは「何をするか」ではなく、「いつ次を始め、いつ止まるか」という仕組みの方です。やるべきことの発見と、終わったかどうかの判定を、AI側の仕組みに委ねる。
その鍵が、判定者を作業者から切り離したことです。/goal は別モデルに、OpenClawの自己改善は別エージェントに、停止と承認の判断を渡しました。自分の答案を自分で採点させない。言われてみれば当たり前の話ですが、これが長時間の自律運用を初めて現実的にしました。作業者だけだと「やったつもり」で止まり、嘘の完了を返すか、永久に回る。判定者がいると、止まるべきところで止まれる。
プロンプトエンジニアリングが「いい質問の仕方」だとすれば、これは「いい止め方の設計」です。

 どう使うか -- 私の場合
偉そうに書いていますが、私自身もうこの世界の住人です。27本のcronで、コンテンツ運用の調査から品質チェックまでを自動で回しています。これはまさに「ループを書く」側の運用です。
使い分けはシンプルです。


監視・定期メンテナンスは /loop: 「公開予約が発火したか」「数字に変化はあるか」のような、定期的に様子を見るタスク。

完了させたい仕事は /goal: 「移行が終わって全テストが緑になるまで」のような、明確なゴールがあるタスク。

/goal は非対話でも使えます。これが地味に効きます。
claude -p "/goal CHANGELOG.md に今週マージした全PRのエントリがある"
claude -p に /goal を渡すと、条件を満たすまでのループが一回の呼び出しの中で完結します。cronから叩く自動化と、完了駆動のループが、そのまま繋がる。(ループを回し続ければ当然トークンも食うので、その原価の話は別記事「claude -p の『使い放題』が終わった日」に書きました。)
ただし長く回すなら、もう一つBorisの習慣を真似する価値があります。Claudeが間違えたら、その場で言い直すのではなく、CLAUDE.mdに書く。会話で直すと、次のセッションでまた同じ間違いをします。ルールとして書けば、エラーは時間とともに減っていく。ループを長く回せるかどうかは、ここで決まります。
Boris が挙げる、Opusを何時間も何日も自律で回すための5点はこうです。


Auto mode -- ツール実行の許可を自動化する

Dynamic workflows -- 状況に応じてやり方を変える

/goal か /loop -- 完了まで止めない

クラウドで回す -- ラップトップを閉じてもループが続く

end-to-endで自己検証する -- 自分で確かめる

最後の「自己検証」が、結局 /goal の判定モデルと同じ話に戻ってきます。回し続けるには、止め方を仕組みにすること。

 まとめ -- ループを書く側へ
「もうプロンプトは書かない、ループを書く」。Boris Cherny の一言は、誇張抜きで、いまのAIの使い方の重心がどこに移ったかを正確に指しています。同じ結論にOpenClawの作者も別ルートで辿り着いた。/loop で時間に回し、/goal で完了に回す。そして両者の本当の発明は、賢いプロンプトではなく、判定を作業者の外に出したことでした。
プロンプトを磨くのは、もちろん今も無駄ではありません。でも、それは一手の精度の話です。これからの伸びしろは、「いつ止まるか」を仕組みにできるかどうか、つまりループを書く側に回れるかどうかにあります。
あなたは今、AIに何をさせていますか。そろそろ、それを回し続けるループを書いてみませんか。
