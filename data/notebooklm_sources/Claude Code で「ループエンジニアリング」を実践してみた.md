## 本文
Claude Code で「ループエンジニアリング」を実践し、Maker-Checker構成で本物のバグを検出できた話

 はじめに
てつどんです。データエンジニアとして 日々業務をこなしております。
最近、バズワードのように、いろんなところで「ループエンジニアリング」というのを聞くことが多くなりました。
そこで、今回、ループエンジニアリングというのはなんなのか、どういう使い方をするのかというのをClaudeと壁打ちして、実践してみました。
正直、全くよく分かってない状況なので、認識として間違ってるかもしれないですが、やったことを残してみます。
2026年6月にGoogleのエンジニアリングリーダー Addy Osmani 氏が名付けた概念で、こう表現されています。

Loop engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead.
（あなたがエージェントにプロンプトを打つ人であることをやめ、代わりにそれを行うシステムを設計する）

今回、実践してみたことは
「Cloud Loggingのエラーを検知して、原因を調査し、仕様書・コードを修正し、レビューを通して、pushする」というフローを、AIエージェント自身に自律的に繰り返させる仕組みです。今回、これを実際に構築し、本物のバグを検出・修正するところまで実践できたので、その記録です。


 まず区別しておきたい「2つのAI活用」
学習を始めてすぐに気づいたのですが、「AIを使った自動化」には性質の異なる2種類があります。
① AIを使ったバッチ処理：
Pythonで書いたコードをCloud Schedulerで定期実行し、
その中でGemini APIを1回呼び出す
→ 主導権は「人間が書いたコード」
→ 今まで学んできたGemini API・Cloud Runの延長

② ループエンジニアリング：
Claude Code自身が「何を直すか」「どう直すか」
「pushするか」を全部自律的に判断する
→ 主導権は「AIエージェント自身」
比喩で言うと、①は「決まった手順書を実行するロボット（途中で専門家に意見を聞く瞬間はある）」、②は「あなたの代わりに考えて判断して作業してくれる人を定期的に働かせ続ける」というイメージです。この記事は②の実践記録です。


 Maker-Checker パターン：自己採点バイアスを防ぐ
ループエンジニアリングを調べる中で、重要な設計原則に出会いました。
LLMは「合格させたい」方向に評価を歪める傾向がある

対策：モデルが言い逃れできない決定的なゲート
（pytest / mypy のような、人の主観が入らない自動判定）
をループに置くこと

さらに、実装エージェント（Maker）と検証エージェント（Checker）
を完全に別のコンテキストで動かすことで、
「本当に他人がチェックしているような」検証ができる
Claude Code のサブエージェント機能を使うと、この Maker-Checker を実装できます。サブエージェントは独立したコンテキストウィンドウで動作し、結果の要約だけを親会話に返すという特性があり、これが「fresh context（記憶を共有しない）」を自然に実現してくれます。


 Step 1：既存の Skills をループ対応に作り直す
いきなり本命を作る前に、以前作っていた /spec-review・/code-review（Skills）を、Maker-Checkerの部品として使えるように作り直しました。

 共通の設計方針
① 「High指摘が0件」になるまで繰り返す（終了条件）
② 「要確認」に分類されたHigh指摘が1件でもあれば
   即座にループを中断し、人間にエスカレーションする
   （試行回数を使い切る前でも最優先で停止する）
③ 上限回数を設ける
④ サブエージェント（reviewer）は「判定のみ」、
   呼び出し元（メインのClaude Code）が「修正」を行う
spec-reviewer サブエージェントはこう定義しました。
---
name: spec-reviewer
description: docs配下の仕様書を独立した視点でレビューする。過去のレビュー履歴や修正履歴は一切参照しない。
tools: Read, Grep, Glob
model: inherit
---
ポイントは tools に Write・Edit を含めていないことです。 これによりサブエージェントは物理的に修正ができず、「判定のみ」の役割に固定されます。判定と実行が同じ主体だと、自分の判定に沿った甘い実行をしてしまうリスクがあるためです。
code-review はさらに pytest・mypy という機械的ゲートをループに組み込みました。
以下のいずれかが1つでも真であれば、High指摘ありとみなす：
- pytest が1件でも失敗している
- mypy が1件でもエラーを検出している
- code-reviewerが「自動修正可能」なHigh指摘を返している
なお code-reviewer は当初 src/ 固定で作っていましたが、プロジェクトによって構成が異なる（app/・pipeline/ 等）ため、CLAUDE.mdの「プロジェクト構成」から対象ディレクトリを自動判定する設計に修正しました。


 Step 2：検証用の題材を用意する
Maker-Checkerを試すには、意図的にエラーを起こしやすい題材が必要です。今回は openBD（ISBNから書籍情報を取得できる無料API、APIキー不要）を使った、シンプルな書籍価格チェッカーを新規に作りました。
9784873119045   → 正常に価格が表示される
123             → invalid_isbn_format（形式不正）
0000000000000   → isbn_not_found（該当なし）
ここで重要な整理をしておきました。 この2種類のエラーは「バグ」ではなく「正しく動作しているバリデーション・異常系ハンドリング」です。AIエージェントがこれらを「バグだ」と誤判定して不要な修正を繰り返さないよう、判定ロジックを明示的に設計する必要がありました。


 Step 3：Cloud Logging のハマりポイント
ローカルCLIから実行しているため、Cloud Run等の自動検出が効かず resource.type が "global" にフォールバックし、resource.labels には project_id しか入らないことに気づきました。
検討した2つの解決策：

(a) entry.labels に service_name を追加する
    → log_struct 呼び出しに1行追加するだけ、シンプル

(b) monitored resource を generic_task に変更する
    → job/task_id/namespace の組み立てが必要で複雑
(a) を採用しました。 理由は、将来 Cloud Run Jobs にデプロイすれば自動的に resource.labels.job_name が入るようになるため、ローカル実行主体の今の段階で複雑な作り込みをする必要はないと判断したためです。
logger.log_struct(
    payload,
    severity="ERROR",
    labels={"service_name": "book-price-checker"}
)
また、以前検討していた「Cloud Logging → GitHub連携でコードを取得する」という設計も、今回は不要と判断しました。サブエージェントはローカルのファイルシステムを直接 Read・Grep できるため、同じマシン上で完結する検証ではGitHub経由の取得工程がまるごと省略できます。


 Step 4：incident-maker / incident-checker の実装
いよいよ本命です。
incident-maker：
① Cloud Loggingからエラーログを取得する
② Step 0：想定内の異常系か、本当のバグかを判定する（最重要）
③ 本当のバグの場合のみ、原因調査・コード修正に進む
④ 修正が必要なら /code-review でHigh指摘0件まで確認する

incident-checker：
incident-makerの「判定」と「修正」の両方を、
独立した視点で再検証する
incident-maker の性質判定部分はこう設計しました。
## Step 1：エラーの性質を判定する（最重要）

### 想定内の異常系（バグではない）と判定する条件
- error_type が invalid_isbn_format（バリデーションエラー）
- error_type が isbn_not_found（データが存在しないだけ）

### 本当のバグ・改善余地ありと判定する条件
- error_type が openbd_api_error で、かつ頻発している
- ハンドリングされていない例外
- ログから明らかにコードのロジックミスと分かるもの

想定内の異常系と判定した場合は、修正フローには進まず
「対応不要」と報告して終了する。
厳守事項として「想定内の異常系を『バグだ』と誤判定して不要な修正をしない」ことを最も注意すべき点として明記しました。


 実践①：バグなしケースでの検証
まず先ほど仕込んだ2種類のエラー（形式不正・該当なし）で incident-maker を動かしました。
結果は「6件すべて想定内の異常系」という正しい判定でした。特に印象的だったのが、NOTAREALISBN という文字列に対する挙動です。
「文字種エラーではなく桁数エラーになる」点を
incident-maker 自身が一度疑い、isbn_validator.py を確認し、
「長さチェックが文字種チェックより先に実行される設計」であることを
docs/ の仕様と突き合わせて確認した上で、仕様通りと結論づけた
指示していた判定基準を上回る丁寧さで、一見おかしく見えるが実は仕様通り、という誤検知しやすいケースを正しく処理できていました。
続けて incident-checker にこの判定結果を再検証させたところ、報告を鵜呑みにせず以下をすべて独立してやり直していました。
① gcloud logging read を再実行し、ログ内容の完全一致を確認
② isbn_validator.py を読み、設計を実装レベルで再確認
③ 実際に curl で openBD API を再度叩き、[null] を実地確認
④ 仕様書と実装の整合性を確認
⑤ pytest を再実行し全パスを確認
「incident-makerが言っていたから信じる」のではなく「独立して同じ手順を踏んで、同じ結論に至った」という、Maker-Checkerの本質的な価値が発揮された瞬間でした。


 実践②：本物のバグを検出
ここからが今回一番の収穫です。全角数字（９784873119045 のような文字列）でテストしてみたところ、エラーが起きませんでした。仕様書と照らし合わせると、これは矛盾でした。実際に incident-maker に調査させたところ、本物のバグを正しく検出・修正してくれました。

 検出したバグ
isbn_validator.py の文字種チェックで Python 組み込みの str.isdigit() を使っていたため、全角数字も True と判定されてしまい、バリデーションを素通りしていました。
"９784873119045".isdigit()
# → True（半角と誤認）
仕様書（docs/02_functional_design.md）には「半角の数字・ハイフン・スペース以外は invalid_character として弾く」と明記されていたにもかかわらず、実装がそれを満たしていませんでした。結果として、全角数字入りのISBNが openBD API まで素通りし、isbn_not_found として誤分類されてログに残っていました。

 修正内容
def _is_ascii_digits(value: str) -> bool:
    return value.isascii() and value.isdigit()
という半角限定チェックを追加し、ISBN-13・ISBN-10双方の文字種判定をこれに置き換え。さらに tests/test_isbn_validator.py に回帰テストを2件追加（全角数字混入・全角小文字x混入）しました。

 検証結果
pytest 63件全パス
修正後の実機テストでも、全角数字ISBNが正しく
invalid_isbn_format として弾かれるようになった
（修正前は isbn_not_found として誤って openBD まで到達していた）


 incident-maker からの正直な申し送り
修正後、incident-maker から2点の申し送りがありました。
① /code-review が未実施だった
「このagentには Agent ツールがなく code-reviewer サブエージェントを呼べなかった」という報告でした。incident-maker.md の tools 設定にサブエージェントを呼び出すための Agent ツールが含まれていなかったのが原因でした。追加後、改めて /code-review を正式に実行し、High指摘0件を確認しました。
② mypy エラー2件をスコープ外と判断
「今回のインシデントとは無関係なのでスコープ外とした」という報告です。これは正しい判断でした。1つのインシデント対応で無関係な問題まで一緒に直そうとすると、変更範囲が広がりすぎてレビューが困難になります。「合格基準は先に凍結し、通すために緩めない」という原則にも合致します。


 得られた知見

 ① fresh context の原則が実際に機能した
incident-checker が incident-maker の報告を参考情報としてではなく、ゼロから同じ調査（ログ取得・API問い合わせ・コード確認・テスト実行）をすべて自分でやり直していました。判定と検証を分離し、Checkerに独立したコンテキストを持たせるという設計が、狙い通りに機能した証拠です。

 ② 「エラー＝バグ」ではないという判定が最重要だった
もし性質判定のステップがなければ、正常なバリデーションエラーを「バグだ」と誤判定して不要な修正・コミットを繰り返していた可能性があります。ループエンジニアリングでは「直すこと」より先に「本当に直すべきか」を判定するステップが不可欠だと実感しました。

 ③ サブエージェントの権限制限が役割分離を担保する
spec-reviewer・code-reviewer・incident-checker はいずれも tools に Write・Edit を含めていません。「判定はできるが修正はできない」という制約が、物理的に役割分離を保証してくれます。

 ④ ローカル検証では GitHub 連携は不要だった
サブエージェントがローカルファイルシステムを直接読める場合、Cloud Logging → GitHubリポジトリ特定 → コード取得、という工程はまるごと不要になります。GitHub連携が必要になるのは、本番のコードとローカルの開発コードが乖離している可能性がある場合です。

 ⑤ 実際に動かしてみて初めて見つかる問題がある
incident-maker の tools に Agent が抜けていたことは、座学や設計段階では気づけませんでした。実際にサイクルを回してみたからこそ発見できた運用上の不備でした。


 今回の構成の位置づけ：プロジェクト専用版であること
ここで1点、今回作った incident-maker の設計について正直に書いておきます。今回の incident-maker.md は「対象プロジェクト：book-price-checker」とプロジェクト名を直書きしており、あくまで単一プロジェクト専用の検証版です。
本来の実務運用としては、こういう形が理想だと考えています。
① サービス名（Cloud Loggingのlabels.service_name等）と
   プロジェクトのパス（またはGitHubリポジトリ）の
   マップ（レジストリ）を持つ

② incident-makerは、エラーの service_name から
   レジストリを引いて対象プロジェクトを動的に特定する

③ 1組のincident-maker/incident-checkerが、
   登録された複数プロジェクトを横断して面倒を見る
これは以前 BigQueryで検討していた「監視対象パイプラインの登録簿」という考え方を、そのままループエンジニアリングの文脈に持ち込んだものです。プロジェクトごとの固有ルールは各プロジェクトのCLAUDE.mdから都度読み込み、incident-maker自体は「進め方の手順」だけを持つ、という役割分担にすれば汎用化できます。
さらに視野を広げると、複数リポジトリ・チームで承認フローを含めて継続的にエージェントを走らせる段階になると、Claude Code単体の機能だけでなく外部オーケストレーターを検討する領域に入っていくようです。
① 単一タスクの分業        → サブエージェント（今回の構成）
② 1台のマシンで並列作業   → Agent Teams（Proプランでは過剰と判断）
③ 複数リポジトリ・チーム  → 外部オーケストレーター
今回はまだ検証段階なので単一プロジェクト専用のままにしていますが、次に複数のパイプラインを横断して監視したくなったタイミングで、レジストリを持たせる形に拡張していきたいと考えています。


 まとめ
今回の実践を通じて、ループエンジニアリングの本質を体感できました。
✅ Maker-Checker構成が自己採点バイアスを防げること
✅ 「エラー＝バグ」ではなく、性質判定が正しく機能すること
✅ 逆に見逃されがちな本当のバグも、深い検証
   （仕様書照合・実際の言語挙動の確認）によって
   正しく検出できること
✅ 座学だけでは見えない運用上の不備は、
   実際に動かして初めて見つかること
CLAUDE.md・Skills・MCP という「ハーネス」の先にある「ループ」の世界は、正しく設計すれば本当に信頼できる自動化になり得る、という手応えを得られました。次は修正後の git push・PR作成の自動化や、Cloud Schedulerでの定期実行への発展を試していきたいと思います。
