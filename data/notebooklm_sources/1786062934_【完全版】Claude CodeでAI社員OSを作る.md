    完全自動化は、1つの巨大プロンプトでは作れません。


    仕事を7つのレイヤーに分けると、何を作ればよいかが見えます。


    1つ目は、記憶です。プロジェクトのルール、禁止事項、出力形式を置きます。


    2つ目は、技能です。毎回同じ判断をする仕事をSkillsへ分けます。


    3つ目は、担当者です。調査、実装、レビュー、テスト、営業、記事制作のようにSubagentsへ分けます。


    4つ目は、外部接続です。MCPでSlack、GitHub、Figma、Notion、DBなどへ接続します。Playwrightでブラウザ操作も任せます。


    5つ目は、安全制御です。Hooksとpermissionsで、危険コマンド、公開前チェック、テスト、lintを強制します。


    6つ目は、反復です。短期なら `/loop`、再利用する作業ならスクリプト、長めの並列作業ならDynamic workflowsを検討します。


    7つ目は、経営判断です。AIに何を任せ、何を人間が見るかを決めます。


    この7つを混ぜると崩れます。


    たとえば、MCPで外部ツールへ接続しても、担当者と安全制御がなければ事故ります。


    Subagentsを作っても、Skillsがなければ毎回判断がズレます。




    
    
    


    最初に作るべきものは、AI社員ではありません。


    仕事のルールです。


    Claude Code公式Docsでは、Skillsは `SKILL.md` に手順やチェックリストを置き、必要な時だけ読み込む仕組みとして説明されています。


    長いルールを常に会話へ貼るのではなく、必要な時だけ呼び出せる点が重要です。


    分け方は簡単です。

            
                プロジェクト全体の恒久ルール: `CLAUDE.md`
特定作業の手順: `SKILL.md`
繰り返し使うテンプレ: skill配下の参考ファイル
実行スクリプト: skill配下のscripts
            

    たとえば、記事制作AI社員を作るなら、ルールはこう分けます。

            
                `CLAUDE.md`: 削除禁止、保存先、文章トーン、Git運用
`copy_note/SKILL.md`: note記事を書く手順
`copy_check/SKILL.md`: 公開前確認
`visual_thumbnail_note/SKILL.md`: サムネプロンプト作成
            

    これで、毎回「川合トーンで、定型文を入れて、保存先はここで」と説明しなくて済みます。


    AI社員化の第一歩は、プロンプトを増やすことではなく、作業ルールをファイルへ移すことです。




    
    
    


    Subagentsは、AI社員化の中心です。


    公式Docsでは、Subagentsは独自の文脈、system prompt、ツール権限、permissionsを持つ専門AIとして説明されています。


    重要なのは、何でもSubagentにすることではありません。文脈を分けたい仕事だけ切り出します。


    向いている担当はこれです。

            
                research-agent: 大量検索、動画調査、記事収集
browser-agent: Playwrightやブラウザ操作
review-agent: 事実確認、品質確認、危険操作検出
build-agent: 実装、修正、検証
sales-agent: 問い合わせ、提案文、営業フォロー
publishing-agent: note、X、サムネ、公開前チェック
            

    ここで大事なのは、ツール権限を絞ることです。


    調査担当に編集権限を渡す必要はありません。


    レビュー担当に外部投稿権限を渡す必要もありません。


    AI社員は「強いAIを1体作る」より、「弱くても役割が明確なAIを複数作る」方が安定します。


    これは人間の会社と同じです。




    
    
    


    完全自動化で一番分かりやすく効くのは、外部ツール操作です。ここで使う主役が、MCPとPlaywrightです。


    MCPは、Claude Codeを外部ツール、データベース、APIへ接続するための仕組みです。


    公式Docsでは、Issue tracker、monitoring、database、Figma、Slack、Gmail下書きなどの例が示されています。


    Playwrightは、ブラウザ操作の自動化に向いています。


    海外動画では、Claude Code + Playwright MCPで「ブラウザ操作をAIに任せる」方向の動画が目立ちました。


    低コストで始めるなら、最初の対象はこのあたりです。

            
                競合LPを開いて見出しを収集する
問い合わせフォームの入力項目を確認する
noteやブログのリンク切れを見る
管理画面のスクリーンショットを取る
GoogleスプレッドシートやNotionの入力を確認する
            

    ただし、最初から投稿、購入、送信、削除を自動化してはいけません。


    最初は「読む」「集める」「下書きする」までにします。


    AI社員化で事故が起きるのは、外部操作を早く渡しすぎる時です。


    最初は読み取り専用。


    次に下書き。


    最後に人間承認付き実行です。




    
    
    


    上級者向け自動化で一番重要なのは、Hooksです。


    派手ではありませんが、AI社員を安全に働かせる土台になります。


    Claude Code公式Docsでは、HooksはClaude Codeのライフサイクル上の特定タイミングで自動実行されるshell command、HTTP endpoint、LLM promptとして説明されています。


    たとえば、`PreToolUse` はツール実行前、`PostToolUse` は実行後、`Stop` は応答終了時に動きます。


    これは何に使えるか。

            
                `rm` や危険操作を止める
編集後にlintやtestを走らせる
公開前にURL、出典、画像パスを確認する
成果物の保存先を検査する
長文出力後に要約ログを保存する
AIが権限外の操作をしようとした時に止める
            

    完全自動化で必要なのは、AIを信じることではありません。AIが失敗しても止まる仕組みです。


    特に一人事業や小規模チームでは、AI社員に任せた作業を毎回すべて目視できません。


    だからこそ、Hooksで「必ず通す確認」を作ります。


    プロンプトはお願いです。


    Hooksは仕組みです。




    
    
    


    AI社員が1人なら、便利な作業者です。


    AI社員が複数なら、会社のように動かせます。


    Claude Code公式Docsでは、Dynamic workflowsはClaudeが書いた再実行可能なスクリプトから、多数のSubagentsを束ねる仕組みとして説明されています。


    また、Agent teamsは複数のClaude Codeセッションをチームとして協調させる仕組みです。


    ここまで来ると、作業の渡し方が変わります。


    単発依頼ではなく、仕事をチームへ投げます。


    例です。

            
                調査担当: 世界中の動画、記事、Docsを収集
分析担当: 共通パターンと怪しい主張を分離
実装担当: テンプレ、設定、スクリプトへ変換
レビュー担当: 出典、危険操作、誇張表現を確認
公開担当: note、X、サムネ、リンクを整える
            

    この構造は、人間の会社に近いです。


    AIに全部やらせるのではなく、AI担当同士の成果を人間が編集します。


    並列化の目的は、放置ではありません。人間が見るべき判断だけを残すことです。




    
    
    


    ここからは、そのまま使える設計テンプレです。最初から大きく作らず、1つの業務だけで試します。


    おすすめは、公開前チェック、競合調査、営業フォロー、記事制作のどれかです。


    理由は、失敗しても人間承認を挟みやすいからです。

    たとえば、競合LP調査ならこうです。


    
    
    


    この段階で、AI社員はまだ働いていません。でも、働く前の安全設計ができています。


    ここを飛ばす人ほど、自動化で失敗します。




    
    
    


    最後に、やってはいけないことを整理します。上級者向けほど、ここが重要です。


    1つ目は、外部送信をいきなり自動化することです。投稿、メール送信、フォーム送信、決済、削除は、人間承認を挟みます。


    2つ目は、MCPを増やしすぎることです。接続が増えるほど便利になりますが、権限と情報漏洩リスクも増えます。最初は、読むだけのMCPから始めます。


    3つ目は、Subagentsを増やしすぎることです。担当が多すぎると、誰が何をしたか追えません。最初は3体で十分です。


    4つ目は、Hooksなしで自動化することです。危険操作を止める仕組み、検証を強制する仕組み、保存先を確認する仕組みがないなら、完全自動化ではありません。ただの放置です。


    5つ目は、SNSで見た成功例をそのまま真似ることです。既存X記事DBには、Claude CodeでX記事制作、副業、AI社員、非エンジニア革命を扱う投稿が残っています。


    ただし、Xはログイン壁で本文や指標を確認できない投稿もあります。


    見える範囲のフックだけを参考にし、本文の根拠には公式Docsや再現可能な手順を置きます。


    今回の結論です。


    Claude CodeでAI社員OSを作る順番は、こうです。

            
                仕事を1つ選ぶ
ルールをCLAUDE.mdへ置く
反復手順をSkillへ置く
専門担当をSubagentへ分ける
読み取り専用でMCPまたはPlaywrightをつなぐ
Hooksで危険操作と検証を固定する
最後にDynamic workflowsやAgent teamsで並列化する
            

    最初からAI企業を作ろうとしなくていいです。まず1人のAI社員を、読み取り専用で作る。


    そこから下書き、検証、承認付き実行へ広げる。


    Claude Code完全自動化は、ここから始めるのが一番安全です。
