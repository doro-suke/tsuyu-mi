## 本文
ある日ブラウザを開くと、私のGitHubの通知欄に未レビューのPRが20件ほどたまっていました。
全部、Claude Codeが書いたPRで、私が1件を読み終えるあいだに、Claudeは次のPRを2件出してきます。
ある日、私は気づいてしまいました。
この勝負、人間は絶対に勝てない、、、
みなさんは、AIが出してくるPRを、ちゃんと全部読めていますか？
私は読めていませんでした。
読んでいるふりをして、LGTMを押していただけでしただけの無能です＞＜

 AIが書くコードを、人間が全部読むのはもう無理です＞＜

AIが書くコードを、人間が全部読んでコードレビューするのはもう無理です。
だから「読む」仕事の大部分は、AIや自動チェックに任せます。
人間は、危ない場所とそもそも作るべきかの判断に集中します。
責任と理解は人間が手放さない




 人間が全部読むコードレビューは破綻した
Claude Codeをチームで使い始めた当初、私はAIのPRを一行残らず読んでいました。
AIが書いたコードを人間が確認するのは当然だ、と思っていたからです。
ところが、PRの数はみるみる増えていきました。
1日に20件程度、1件あたり300行の差分です。
レビューは時間を取って、まとめて読むことになります。
2週間ほどで、私の読み方は「精読」から「流し読み」に変わっていました。
そして、ある週に事件が起きます。
私がLGTMを押したPRから、とある値の扱いを間違えたバグが本番に出ました。
あとで差分を見返すと、問題の行はちゃんとそこに書いてありました。
その箇所は私は絶対読んだはずなのに、まるで見えていなかったのです。
さすがに少し泣きたくなりました。
このとき学んだのは、人間のレビューは量が増えるほど質が落ちるということです。
AIと「読む量の勝負」をした時点で、人間の負けは決まっていたのだと思います。

 そもそもコードレビューは何のためにあるのか
ここで一度、コードレビューの意味を立ち止まって考えてみたいと思います。
コードレビューの目的は、大きく2つあります。

出荷する前に、問題を見つけて直すこと。
チームの中で、コードの理解を共有すること。

よく見ると、「人間がコードを全行を読むこと」はどこにも入っていませんし、誰もそんなこといってません。

人間が読むのは目的を果たすための手段のひとつにすぎず、目的そのものではないのです。
ここに気づいてから、私の考え方は大きく変わりました。

 料理長は、全部の皿を味見しない
あるレストランに、腕のいい料理長がいるとします。
厨房にはロボットの料理人が10台いて、1時間に1000皿の料理を作ります。
料理長が全部の皿を味見していたら、どうなるでしょうか。
まず、時間が足りません。
それに、100皿目あたりで舌がしびれて、味の違いがわからなくなります。
これが、さきほどの私の姿でした。
名づけるなら「全部味見する料理長」です。
では、本当に腕のいい料理長はどうするのか。
温度計とタイマーで、火の通りを機械的にチェックします。
副料理長に味見を任せて、怪しい皿だけ報告してもらいます。
アレルギー対応の皿だけは、料理長が自分の舌で確かめます。
新メニューは、まず従業員のまかないで出して様子を見ます。
お客さんから苦情が来たら、そのメニューをすぐに下げます。
これが「仕組みで味を守る料理長」です。
料理長は味見の量を減らしましたが、店の味に対する責任は一切手放していません。

 Anthropicも同じことをやっていた
先日、Anthropicが自社のコードレビューについての記事を公開しました。

この記事によると、Claude Codeのコードは約90%をClaude自身が書いています。
人間が全部読んでいたら、とても追いつかない量です。
そこでAnthropicは、次のように方針を決めました。

We didn't remove review. But we did move most of the reading to machines, optimized for human time and attention, and invested heavily in making it fast and easy to undo mistakes.

レビューをやめたわけではありません。
読む仕事の大部分を機械に移して、人間の時間と注意を節約し、間違いをすばやく取り消せる仕組みに投資した、ということです。
この記事の中身を見ると、まさに「仕組みで味を守る料理長」でした。
PRを出す前に、Claude自身がテストとビルドとリンターを実行し、その出力を見せます。
さらに、まっさらなコンテキストを持つ別のエージェントが差分をレビューします。
PRの上では、必須のCIが通らなければマージできません。
複数のエージェントが並列でバグを探し、別のエージェントたちがその指摘が本物かどうかを投票で確かめます。
セキュリティレビューも独立して走ります。
マージ後は、フィーチャーフラグで社内から先に使い、段階的にリリースし、問題があれば再デプロイなしでフラグを切ります。
温度計が必須CI、副料理長がAIレビュー、まかないが社内先行リリース、メニューを下げるのがロールバックです。
その結果、6月から9月にかけてマージされたPRは2倍以上に増え、差し戻しは40%以上減ったそうです。
仕事は速くなったのに、成果物の品質は壊れにくくなったのです。

 誰が書いたかではなく、コードの何を変えたかで決める
私がAnthropicの記事でいちばん感心したのは、リスクに応じて人間の承認の数を変えている点です。

低リスクの変更は、自動チェックが通れば人間の承認なしでマージできます。
通常の製品変更は、人間が1人承認します。
最もリスクの高いコードは、人間が2人承認します。

低リスクとは、ドキュメントや文言の修正、フィーチャーフラグで守られた追加的な変更などです。
そして、このリスクの判定は書いた人ではなく、変更の中身で決まります。

The change sets the tier, not the author.

料理でいえば、サラダの盛り付けとアレルギー対応の皿を同じ重さで扱わない、ということです。
ここで大事なのは、エージェントの承認は人間の承認として数えない、というルールです。
また、軽いレーンを使えるのは、その領域を持つ信頼されたチームの作者に限られています。
AIに指示を出した人は、自分で書いたのと同じように責任を負います。
コードを読まない範囲を広げても、責任の所在はぼかさないのです。

 コードを読まないのに、理解はどう保つのか
コードを読まなくなったら、チームの誰もコードを理解していない状態にならないでしょうか？
Anthropicの答えはシンプルでした。
理解が必要になったときに、Claudeにその部分の解説を書かせるのです。
数分で作れて、しかも今のコードを反映しています。
私もこれを真似するようになりました。
ある機能に手を入れる前に、「この処理の流れを、新しく入った人向けに説明して」とClaudeに頼みます。
過去のPRを一件ずつ読み返すより、ずっと早く全体像がつかめます。
コードの理解は、「全部を読んで覚えておく」から「必要なときに引き出す」 に変わったのだと思います。
もうひとつ大事なのが、レシピ帳にあたるCLAUDE.mdとREVIEW.mdです。
AIのレビューがバグを見逃したら、Anthropicは「モデルに何が見えていなかったのか」を問い、その答えをこれらのファイルやチェックに書き足しています。
失敗するたびに、仕組みのほうが賢くなっていくわけです。

 人間が全部読むレビューを否定したいわけではない
誤解のないように書いておきます。
人間がコードを読むことに価値がない、と言いたいわけではありません。
新しく入った人がコードを読んで学ぶのは、今でもとても大切なことです。
認証や課金のように、壊れたら取り返しがつかない場所は、これからも人間が読むべきだと思います。
「全部読む」と「読まない」は、対立関係ではありません。
0か100かではなく、徐々に機械に任せる部分のグラデーションが広がっているということです。
どこを機械に任せて、どこを人間が見るのか、その線引きの問題です。
これは「私はこう考えた」という話であって、どのチームにもこれが正解だと言うつもりはありません。

 明日からできる小さな一歩
Anthropicほどの仕組みがなくても、始められることはあります。
私は、まずこの4つから始めました。

CIでの機械的な静的チェックを充実させ、ブランチ保護でCIを必須にして、赤ならマージできない状態にしました(必須
自動E2Eテストを充実させ、PRの変更箇所に該当する箇所のみのE2Eを実行するCIを組みました
AIによる自動レビューを基本とし、認証や課金の処理などの重要な箇所の変更は人間の承認を必須にしました
低リスクのPRだけ、gh pr merge --autoで自動マージするようにしました

これだけでも、私が読むPRの数はかなり減りました。
そのぶん、本当に危ない変更を、落ち着いて読めるようになりました。

 PRの変更のリスクを測るためのSkill
PRの変更のリスクを定量的に数値化するスキルを公開しています


 PRの変更に関係あるe2eだけをフィルタする例(Jevとかで判断させる)
// e2e.config.ts
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { gateway } from 'ai';
import { decisionFilter } from '@e2e-dev/decision';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  filters: [decisionFilter({ model: gateway.decisionModel('typesafe-ai/jev') })],
} satisfies E2EConfig;

A person is accountable for every change that ships, whoever typed it.

AIの時代になっても、ここだけは変わらないのだと思います。
