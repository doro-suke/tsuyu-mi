## 本文
はじめに
AIコーディングエージェントを使っていると、こんな欲が出てきます。

1つのタスクをエージェントに投げている間、別のタスクも同時に進めたい。

人間が1つずつ順番に見ている限り、エージェントがどれだけ速くても待ち時間が生まれます。そこで効いてくるのが「複数のエージェントを並列で走らせる」というアプローチです。
この記事では、git worktree をベースにした claude --worktree と、複数セッションをまとめて管理する cmux を組み合わせた並列開発のやり方を紹介します。あわせて、並列で走らせても事故らないためのコツ（PRで触る領域をぶつけない・そもそも疎結合に保つ・シンプルさを大事にする）もまとめます。
対象読者:

Claude Code などのコーディングエージェントを日常的に使っている人
「1タスクずつ」の進め方に限界を感じている人
並列でやりたいが、コンフリクトやレビュー地獄が怖い人


 なぜ並列開発でハマるのか
ナイーブに「同じリポジトリで2つのエージェントを走らせる」と、すぐに問題が起きます。

2つのセッションが同じ作業ツリーを編集して、変更が混ざる
ブランチの切り替えが衝突して、どちらの作業か分からなくなる
片方がビルド中にもう片方がファイルを書き換えて壊れる

要するに、1つの作業ディレクトリを共有しているのが諸悪の根源です。ここを分離するのが git worktree の役割です。

 git worktree のおさらい
git worktree を使うと、1つのリポジトリから複数の作業ツリーを別ディレクトリに展開できます。それぞれが独立したブランチをチェックアウトできるので、作業が物理的に分離されます。
# 現在のリポジトリから、別ディレクトリに新しいworktreeを作る
git worktree add ../myproject-feature-a feature-a

# 一覧を確認
git worktree list

# 使い終わったら片付け
git worktree remove ../myproject-feature-a
.git 本体は共有しつつ、作業ツリーとチェックアウト中のブランチだけが分かれる——これが並列開発の土台になります。

 claude --worktree で1コマンド分離
Claude Code には、この worktree 作成を肩代わりしてくれる仕組みがあります。ワークツリー用のフラグを付けて起動すると、専用の worktree を自動で切ってその中でセッションを開始してくれます。
# 専用のworktreeを作ってその中でClaudeを起動する
claude --worktree

# タスクごとに複数起動すれば、それぞれ独立した作業ツリーで動く
ポイントは、セッションごとに作業ツリーが分かれていること。エージェントAが feature-a を、エージェントBが feature-b を、互いのファイルを踏まずに進められます。

起動フラグやオプションは変わることがあるので、claude --help で最新の指定方法を確認してください。


 cmux で複数セッションをまとめて操る
worktree でタスクを分離できても、ターミナルを何枚も開いて行き来するのはつらい。ここで cmux が効いてきます。
cmux は複数のコーディングエージェントのセッションを並列に立ち上げ、隔離された環境で走らせ、まとめて監視・比較できるツールです。各タスクを独立した作業空間で回し、ダッシュボード的にまとめて見られるので、「今どれが動いていて、どれがレビュー待ちか」が一望できます。
イメージとしてはこうです。
1つのIssue/タスク  →  1つのworktree  →  1つのエージェントセッション
                              ↑
                     cmux が束ねて管理
「タスク = worktree = セッション」を1:1:1で対応させるのが、混乱しないコツです。

 実際の進め方（最小構成）

タスクを独立して進められる単位に割る（後述のコツが超重要）
各タスクを別々の worktree / セッションで起動する
エージェントに投げたら、人間は別のタスクのレビューや設計に回る
出来上がったものから順にブランチを push、PR を作る
マージできたものから片付け、worktree を remove する

人間は「同時に手を動かす」のではなく、投げる→別のことをする→戻ってレビューするというループを回します。ボトルネックは常に人間側のレビューなので、レビューしやすい単位に割ることがスループットを決めます。

 コツ1: PR で触る領域をぶつけない
並列開発で一番痛いのがマージコンフリクトとレビューの絡み合いです。これを避ける最大のコツは、シンプルです。

同時に走らせるタスクは、触るファイル・ディレクトリが重ならないように割る。


タスクA: app/models/ 周り
タスクB: app/views/ と CSS
タスクC: ドキュメントとテスト

のように、縄張りが被らないように切ると、コンフリクトはほぼ起きません。逆に「同じ関数を2つのタスクが直す」ような割り方をすると、並列にした意味が消し飛びます。
タスクを割る前に一言、**「これは他のタスクと同じファイルを触らないか?」**と自問するだけで事故は激減します。

 コツ2: そもそも疎結合に保つ
コツ1が効くかどうかは、コードベースの結合度に大きく依存します。すべてが1つの巨大ファイルや神クラスに集中していると、どのタスクも同じ場所を触らざるを得ず、並列化できません。

関心事ごとにモジュール／ファイルを分ける
依存の向きを一方向に保つ（循環依存を作らない）
境界をインターフェース（型・関数シグネチャ）で握り、実装は隠す

疎結合な設計は、そのまま「並列開発のしやすさ」に直結します。並列で速く回したいなら、まず設計を疎結合に寄せる。これは人間にとってもエージェントにとっても優しい構造です。

並列化のボトルネックは、CPUでもエージェントの速度でもなく、コードの結合度であることが多い。


 コツ3: シンプルが大事
最後に、全体を貫く原則が「シンプルさ」です。


1タスク1目的にする。あれもこれも詰め込むと、レビューも分離も難しくなる

小さな PR にする。小さいほどレビューが速く、コンフリクト面も小さい
ツールを盛りすぎない。worktree と cmux という最小の道具立てで十分回る
迷ったらタスクを分割する。並列化は「大きな1つ」より「小さな複数」と相性が良い

複雑な並列オーケストレーションを組むより、シンプルなタスク分割の方が、結局は速くて壊れにくい。これはソフトウェア設計の原則そのままです。

 よくあるハマりどころ


worktree の消し忘れ: 使い終わったら git worktree remove で片付ける。放置するとディスクとブランチが散らかる

共有ファイルの奪い合い: package.json や設定ファイルなど「みんなが触る場所」は並列タスクで同時に変えない。変えるなら単独タスクとして先に片付ける

DB マイグレーションの衝突: 連番マイグレーションは並列と相性が悪い。走らせる順番を人間が握る

レビューの飽和: エージェントを増やしすぎると、人間のレビューが追いつかず結局詰まる。同時に走らせる数は、自分がレビューできる数まで



 まとめ


git worktree（＝claude --worktree）で作業ツリーを分離し、cmux で複数セッションを束ねて監視する
「タスク = worktree = セッション」を 1:1:1 で対応させると混乱しない
並列で事故らないコツは3つ:


PR で触る領域をぶつけない（縄張りを分ける）

そもそも疎結合に保つ（設計が並列化のしやすさを決める）

シンプルが大事（1タスク1目的・小さなPR・道具は最小限）


ボトルネックは常に人間のレビュー。同時に走らせる数は、自分がレビューできる範囲に収める

並列開発は魔法ではなく、疎結合でシンプルな設計という土台があって初めて速く回ります。まずは2タスクの並列から、気持ちよく回してみてください。
