## 本文
Fable に1月から取り組んだLLMを使った自動化の成果をまとめてもらいました。結構面白い内容だったので記事にしてもらいました。ではどうぞ。

Unityモバイルゲームのクライアントエンジニアとして、この1年のAIコーディングエージェント（Claude Code / codex ほか）の利用ログを棚卸ししてみました。手元に残っていたセッションログ約3,100件と、git・GitHub・Linearの1年分の履歴から「何をして、何がどう早くなったのか」を再構成した記録です。
結論から言うと、この1年は 「AIに作業を頼む」から「AIが回る工場を作る」への移行 でした。マージされるPRは月10件から90件へ約9倍になり、issueの滞留は数十日から4日に縮みました。この記事では、その過程で起きたことを数字と一緒に振り返ります。

 集計方法について
先に前提を書いておきます。

セッションログが現存するのは直近3ヶ月分（codex 2,965件＋Claude Code 169件）で、それ以前のAI利用はコミットの Co-Authored-By トレーラーと git / GitHub / Linear の履歴から復元しています。
本人の複数名義（個人アカウント・bot・自動化名義)はまとめて「本人の活動」として合算しています。ただしPR数の集計は個人アカウント名義のみで、bot名義のPRを含まない控えめな数字です。
PR数・コミット数は工数の代理指標です。AI導入後はPRの粒度が細かくなる傾向があるので、件数比がそのまま生産性比ではありません。ただし後述のとおり、issue完了数・滞留時間という成果側の指標も同じ方向に動いています。


 アウトプットの推移 — 導入と同時に段が変わった
まずマージされたPRの月次推移です。

AIの痕跡（Co-Authored-By: Claude）がコミットに現れるのは2026年1月からで、その月にPRは前月の2件から45件へ跳ね、以後一度も以前の水準に戻っていません。同じリポジトリで働く同僚の推移（オレンジの参照系列）がほぼ横ばいなので、この変化はプロジェクトの繁忙ではなく 働き方の変化 によるものだと切り分けられます。
issue管理側（Linear）でも同じ形が出ます。担当issueの完了数は2025年下半期の月2〜14件に対して、直近3ヶ月は月67〜76件。さらに効いているのが滞留時間で、issueが作られてから完了するまでの中央値は、2025年の18〜167日（月によって大きくばらつく＝積み残しがち）から直近3ヶ月は 4〜6日 に収束しました。「バグは登録されたらその週のうちに直ってマージされる」が定常状態になっています。
2026年1〜7月にマージされたPRのタイトルから数えると、延べ340件のissueに対応する修正・実装が本流に入りました。

 何をしてきたか — 4つのフェーズ
ログを時系列に読むと、移行は4段階に分かれていました。

 〜2025年末: 手作業期
PRは月2〜22件、コミットは月十数件。実装・ビルド・配布・conflict解消・進捗集計をすべて手でやっていた時期です。PRは即セルフマージ運用（作成→マージの中央値0.1時間）で、レビューゲートは実質ありませんでした。

 2026年1月〜4月: Claude Code導入 — 二人三脚期
1月からコミットに Co-Authored-By: Claude が出現し、PRが月45件へ。3月にはbotアカウントやAI用のGitHub Actions（AI PR作成・自動調査・自動monkeyテスト）が整い始めます。まだ「人がAIと並走して1件ずつ片付ける」段階です。

 2026年5月〜6月: codex導入と仕組み化
codexの利用を開始。当初は「PR #1324 をpullしてUnity Editorを開いて」「urgentのissueを3並列で全部実装して」のような長文指示をコピペする運用でしたが、繰り返す手順をスキル（再利用可能な手順書。マージ、PR作成、テスト配布など計29個）へ切り出していきました。5月下旬には最初の常駐オートメーション「動作確認OKの自動マージ」が稼働。日報・メール整理・QA所感シートの転記も定期実行化されました。

 2026年7月: 分業の確立と無人運転
上旬に役割分担を明文化しました。Claudeが調査・設計・レビューを担い、実装はcodex（GPT-5.6）/ devin / cursorへ委譲する という体制です。AIが実際にゲームをプレイして修正を検証する「実装フリート」、敵対的レビューを行うCI、Rust製の常駐ビルダーを構築。月末には人間の指示が「ISSUE-2305 これ対応して。PR作成して『ビルド作成予約』タグ」の1〜2行に圧縮され、人間の発話ゼロで発火するセッション（ビルド失敗の要約・自動修正）がログに現れ始めました。
セッションの冒頭プロンプトを時系列で並べると、この変化がよく分かります。

2026-05-22（手作業期の典型）
「PR #1324 これpullしてUnity Editorを開いて」— 環境準備すら1件ずつ口頭で依頼していた


2026-07-28（同じ種類の仕事の現在形）
「ISSUE-2305 これ対応して。PR作成して『ビルド作成予約』タグ」— 実装からテスト配布ビルドまでがこの1行で完了する


2026-07-27（人間の発話ゼロ）
「Unity Androidの自動ビルドが失敗しました。以下のログ抜粋から失敗原因を要約してください」— 自作の常駐ビルダーが機械的に発行したプロンプト


 作った工場 — 開発サイクルの各段が自動化された
直近3ヶ月のcodexセッション2,395件のうち、約7割（1,822件）は定期実行の自動化 で、人が起点のセッションは残り3割でした。しかもその両方が毎月伸びています。自動化が人の依頼を置き換えたのではなく、人の指示1件あたりの射程が伸びた上に、裏で工場が回っている という構図です。

常駐AIの稼働は直近3ヶ月で1,611回・のべ411時間。この工場は夜も動きます。コミットの時刻分布には、developマージと早朝ビルドが走る朝4時台に139件のピークがあり、2025年にはほぼ存在しなかった時間帯が稼働しています。


 速度と同じくらい効いたもの — AIを疑う仕組み
振り返って重要だったのは、速度への投資と同時に AIを信用しすぎないための仕組み を作っていたことです。

AIの手抜き検証（ソースをgrepして「直ったはず」と報告する類）をゲートで機械的に弾く検証ハーネス。実装フリートには「AIが実際にゲームをプレイして確認する」工程を入れています。この工程では、検証したと自己申告させるのではなく、検証の証拠（スクリーンショット・テスト結果）を機械側で確認します。
レビューCIへのプロンプトインジェクション対策。PR本文やdiff中の指示文でレビューAIが乗っ取られないよう、入力のサニタイズと権限分離を設計しました。
2025年の「PR作成→マージ0.1時間」は実はレビューなしの即セルフマージの反映で、現在の6〜23時間はレビュー・ビルド確認ゲートを挟んだ結果です。この指標だけ見ると「遅くなった」ですが、実態はプロセス品質の向上で、悪化ではありません。指標は文脈込みで読む必要があります。


 まとめ

アウトプットはPRベースで約9倍、issue完了ベースで約15倍。issueの滞留中央値は数十日→4日。
変化は「AIに頼む」だけでは起きず、繰り返しをスキル化→定期自動化→常駐システム化と段階的に 工場を作った ことで起きた。
直近ではセッションの7割が自動実行。人間の役割は「1件やる」から「仕組みを設計して例外に対応する」へ移った。
速度と同時に、AIの検証を疑うゲートとレビューCIを整備した。ここを省くと、速くなった分だけ壊れたものが本流に入る。

次の課題は、この工場を属人化させないことです。オートメーションの登録・可視化を誰でもできるようにする仕組みに着手しており、「本人が休むと止まる」状態からの脱却が今後のテーマです。
