# 自分とAIだけで会社を設立した話とかを聞きます。副業でも個人事業主でもよいので、似たような事例を集めて学びたい。note, qiita, zennなどが好みですが、これは絶対ではない。

人間が意思決定などの重要な箇所のみを担当し、それ以外を各役割を担うAIが担当するというアプローチについて情報を収集したい。

結論から言うと、探しているテーマはすでに日本語圏でも **「AI社員」「一人会社」「AI-native company」「マルチエージェント運営」** という形で事例が出始めています。特に参考になるのは、単に「AIで作業を効率化した話」ではなく、**人間をCEO・プロデューサー・最終承認者に限定し、AIを部門や役割として配置する運用記録**です。

ただし、記事には実験・宣伝・誇張も混ざっています。以下では、事例を「再現性」「具体性」「収益実績」「仕組みの学び」という観点で整理します。

### 特におすすめ：ゲーム開発事例

どろどろしーさんの個人ゲーム開発志向に最も近いのは、Zennの「1人開発スタジオ」です。

この事例では、単一のAIチャットにすべてを任せるのではなく、次のように役割を分割しています。

- ストーリー・演出部門
- オーディオビジュアル部門
- システム部門
- 全体を管理するディレクター部門

各部門の担当ファイルや編集範囲を分離し、`docs/todos/`、`docs/logs/`、`AGENTS.md` などを介して情報を受け渡します。人間はプロデューサーとして、最終的な成果物の確認とGitへの反映を担当します。[^1_1]

重要なのは、AIを人格的な「社員」として扱うことより、**コンテキスト・権限・成果物の境界を設計していること**です。

## 実際に収益まで扱った事例

### YK Ventures型：コンテンツとデジタル商品の販売

YK Venturesの事例は、AI社員チームを使い、noteとBOOTHを同時に開始しています。

構成は以下です。

- 秘書：タスク整理、タグ、プロフィール整備
- PM：方針と公開スケジュール
- 経理：価格と採算の確認
- 開発：ツール制作や記事構成
- レビュワー：品質確認

初日に行った作業は、AI社員の定義、事業方針、noteとBOOTHの開設、市場調査、記事執筆、レビュー、投稿、Notionによる管理です。記事では、開始から初回記事公開までを約8時間で行ったとしています。[^1_2]

この事例の学びは、最初から大きなSaaSを作るのではなく、

1. 無料コンテンツで反応を見る
2. 需要が確認できたテーマを有料化する
3. デジタル商品やツールに展開する
4. データを見ながら継続・撤退を決める

という順番を取っている点です。

ただし、記事にある初期PVやスキ率は一時点の数字です。これだけで事業性が証明されたとは判断せず、継続期間、売上、リピート、制作コストまで追う必要があります。

### 11部門を運用して4部門に縮小した事例

より実務的で参考になるのが、1年間AIエージェントを運用した事例です。

当初は開発、マーケティング、営業、経理、法務、CS、人事、出版、コンサル、グロース、事業開発の11部門を作りました。しかし、最終的には次の4部門が売上と運用に重要だったと整理しています。[^1_3]

- 開発：自動化基盤を作る
- 出版：書籍や記事で信頼資産を作る
- コンテンツ：集客する
- コンサル：売上を作る

これに加えて、全体を統括するOrchestratorを置き、営業、法務、経理、CSなどは常設部門ではなく必要時に呼び出すユーティリティにしています。

この事例では、2026年3月の売上、AI運用コスト、自動化率、SNS配信数なども提示されています。ただし、これは個別事業者の自己申告による実践記録として扱い、一般的な再現性を保証する数字とは分けて考えるべきです。

特に重要な失敗は次の通りです。

- AIなら何でも作れるため、複数のSaaSを作りすぎた
- 営業メールを無承認送信して敬語事故が起きた
- ルールファイルを肥大化させ、指示が矛盾した
- AIに危険なGit操作をさせてしまった
- 市場のない仕事をAIに大量生産させた

つまり、AI導入の失敗は「AIが賢くない」ことより、**市場検証・権限管理・承認フローの不足**から起きています。

## 海外の先行事例

海外では、この考え方を「AI-native startup」や「one-person company」と呼ぶ例があります。

Forbesが紹介したGeneral Intelligenceは、問い合わせの監視、機能要望のコード化、レビュー依頼、デプロイ準備などをAIエージェントに担わせ、人間は最終承認を行う構想を掲げています。[^1_4]

また、AIエージェントを複数の役割に配置し、製品開発、顧客対応、マーケティング、営業、運用を一人の創業者が統括するという考え方も紹介されています。[^1_4]

Anthropicのエージェント開発に関するレポートでも、人間の役割は、すべての作業を確認することから、**戦略判断・例外処理・境界事例に集中すること**へ変わるという方向性が示されています。[^1_5]

ただし、「一人で数億円」「AIだけで会社運営」といった見出しは、以下を分けて確認してください。

- 法的に本当に一人なのか
- 業務委託や外注を含んでいないか
- 売上なのか利益なのか
- 一時的な調達額なのか
- AIが完全自律なのか、創業者が大量に手動修正しているのか
- プロダクト自体がAIエージェント基盤なのか、一般事業なのか

特に「AIだけで会社を運営」という表現でも、実際には人間が営業、法務、請求、顧客対応、最終品質確認を担当しているケースが多いです。

## 共通する設計パターン

複数の事例に共通しているのは、次の構造です。

```text
人間：目的設定・優先順位・最終判断・責任
  ↓
統括AI：依頼を分解・担当割り当て・承認待ち管理
  ↓
専門AI：調査・企画・制作・開発・分析
  ↓
検査AI：事実確認・品質確認・安全確認
  ↓
人間：公開・送信・契約・支払い・本番反映を承認
```


### 役割分担の例

| 役割 | AIに任せやすい仕事 | 人間の確認が必要な仕事 |
| :-- | :-- | :-- |
| リサーチ | 競合調査、情報整理、比較表 | 情報源の信頼性、最終解釈 |
| 企画 | アイデア出し、仮説作成 | 何を作るか、やめるか |
| 開発 | コード生成、テスト、修正案 | 本番反映、セキュリティ |
| コンテンツ | 構成、下書き、編集 | 事実性、著作権、公開判断 |
| 営業 | 見込み客抽出、提案書草案 | 送信、価格、契約 |
| 経理 | 売上集計、請求書草案 | 支払い、税務、契約 |
| CS | FAQ回答、問い合わせ分類 | クレーム、返金、個人情報 |
| 監査 | ログ確認、差分検出、ルール検査 | 重大事故への対応 |

## どろどろしーさん向けの現実的な構成

最初から「AI会社」を作るより、まずは **一つの小さな事業をAI部門制で運用する** 方が再現性があります。

例えば、次のような構成です。

### AI個人開発スタジオ

```text
Producer：自分
Director：AI統括
Researcher：市場・競合・ユーザー調査
Product：アプリやゲームの仕様作成
Developer：Python、Web、Godot実装
Content：note、Qiita、Zenn、SNS
Reviewer：品質、事実、表現、権利確認
Analytics：アクセス、反応、収益の分析
```

最初から常駐させるのは、次の4役で十分です。

1. 統括
2. 開発
3. コンテンツ
4. レビュー

経理、法務、営業、CSは、必要になったときだけ起動する形がよいでしょう。11部門の事例でも、最終的にはこのような最小構成に整理されています。[^1_3]

## 最初の実験案

どろどろしーさんの場合、次の3案が比較的相性がよいと思います。

### 案1：AI活用・個人開発の実践メディア

- AIを使ったWeb制作、ゲーム制作、分析を実践
- AIに調査・構成・下書き・校正を担当させる
- 自分はテーマ選定、検証、経験の追加、公開承認を担当
- note、Zenn、Qiita、YouTube Shortsへ展開
- 反応のよいテーマを教材、テンプレート、ツールにする

これは、実際の作業そのものがコンテンツになるため、開発と発信を同時に進めやすいです。

### 案2：小規模なWeb制作・LP制作事業

- リサーチAI：顧客業界・競合調査
- 企画AI：サイト構成・訴求案
- デザインAI：ワイヤー・デザイン案
- 実装AI：HTML、CSS、WordPress
- QA AI：表示崩れ・文言・アクセシビリティ確認
- 自分：ヒアリング、提案、価格、最終納品

ただし、顧客へのメール送信、見積もり、契約、公開は人間承認にすべきです。AIに営業を完全自動化した事例では、敬語や内容の事故が発生しています。[^1_3]

### 案3：競馬データ分析コンテンツ

- 収集AI：レース情報・過去データの整理
- 分析AI：特徴量、モデル比較、バックテスト
- 解説AI：予測根拠の文章化
- 検証AI：リーク、評価期間、過学習、再現性確認
- 自分：公開方針、賭けに関する表現、最終判断

この分野では、AIがそれらしい説明を作れてしまうため、予測精度よりも **データ期間、評価方法、再現性、損益の表示** を厳密に管理することが重要です。

## 実装時の重要ルール

最初に作るべきものは、AI社員の人格設定ではなく、次の4つです。

### 1. 会社方針ファイル

```text
MISSION.md
```

内容例：

- 何を作るか
- 誰に届けるか
- 何をしないか
- 品質基準
- 予算上限
- 公開基準
- 人間の承認が必要な操作


### 2. 権限表

```text
PERMISSIONS.md
```

例：

- 読み取り：許可
- 下書き作成：許可
- Gitブランチ作成：許可
- 本番公開：人間承認
- メール送信：人間承認
- 決済・契約：人間のみ
- `git push --force`：禁止


### 3. 成果物の受け渡し形式

```text
tasks/
drafts/
reviews/
approved/
logs/
archive/
```

AI同士を直接会話させるより、ファイルやIssueを介して成果物を渡す方が、履歴・再確認・差分管理がしやすくなります。ゲーム開発の事例でも、ToDo、日誌、アーカイブをファイルで管理していました。[^1_1]

### 4. 承認ゲート

```text
下書き → 自動レビュー → 人間確認 → 公開・送信・本番反映
```

AIに「勝手にやらせる」範囲は、次の条件を満たす仕事に限定すると安全です。

- 失敗しても元に戻せる
- 外部に公開されない
- 顧客や第三者に直接影響しない
- 金銭が動かない
- 個人情報を扱わない
- ログが残る

## 現時点での判断

このアプローチは、**「人間が重要な意思決定だけを行う」こと自体は十分現実的**です。ただし、現実に近い表現は「AIだけで会社を経営する」よりも、次のようなものです。

> 人間が目的・責任・最終判断を持ち、AIエージェント群が調査・制作・実行・監視を担当する、一人運営の業務システム。

成功のポイントはAIの人数を増やすことではありません。

- 売れるテーマを選ぶ
- 役割を分ける
- ルールを短く保つ
- 失敗を戻せるようにする
- 外部への作用には承認を置く
- 数字で継続・撤退を判断する

特に、どろどろしーさんの場合は、**「AI個人開発スタジオ」から始めて、Web制作・ゲーム開発・情報発信・データ分析のどれが最も反応を得られるかを検証する**のがよいと思います。最初の目標は「AI社員10人を作る」ではなく、「AI部門4つで30日間、1つの成果物を継続的に公開する」に置くのが現実的です。

# youtubeなどの動画投稿サイトを使用した収益化を事業とする場合は？

動画投稿を事業にする場合は、**AI動画を大量生産して広告収益を得る事業**ではなく、AIを制作部門として使いながら、人間が企画・独自性・品質・事業判断を担う「メディア事業」として設計するのが現実的です。

YouTubeはAI利用そのものを禁止していませんが、量産型・反復的・独自性の薄い動画は収益化対象外になり得ます。YouTube公式も、収益化にはクリエイター自身の制作物であり、視聴者に楽しさや有益性を提供するオリジナルコンテンツであることを求めています。[^2_1]

## 事業モデルの全体像

動画事業の収益源は、広告だけに限定しない方がよいです。


| 収益源 | 具体例 | AIの担当 |
| :-- | :-- | :-- |
| YouTube広告 | 長尺動画、Shorts、ライブ | 企画分析、制作、投稿補助 |
| ファン課金 | メンバーシップ、Super Thanks、Super Chat | FAQ、投稿案、コミュニティ運営補助 |
| アフィリエイト | 機材、ソフト、書籍、サービス | 商品調査、比較表、台本草案 |
| 自社商品 | テンプレート、教材、電子書籍、素材 | 企画、制作、校正 |
| 自社サービス | Web制作、AI導入支援、分析代行 | リード獲得、提案書、営業資料 |
| スポンサー | 商品紹介、タイアップ | 企業調査、提案書、進行管理 |
| 他媒体への展開 | note、Zenn、Qiita、TikTok、Instagram | 再編集、字幕、要約、投稿予約 |

YouTubeを「広告収益の場所」ではなく、**認知を集めて、自分の商品やサービスへ送る入口**と考えるのが重要です。

## 収益化条件

2026年9月時点で、YouTube広告収益を含む通常のYPP参加には、基本的に次のどちらかが必要です。

- チャンネル登録者1,000人以上、かつ過去12か月の有効な公開動画の総再生時間4,000時間以上。
- チャンネル登録者1,000人以上、かつ過去90日間の有効な公開Shorts視聴回数1,000万回以上。

YouTubeは条件を満たしただけで自動承認するのではなく、チャンネル全体を審査します。ポリシー違反、再利用コンテンツ、量産型コンテンツなどがある場合は承認されない可能性があります。[^2_2]

なお、YouTubeの公式ページ以外では、2027年2月以降に新規申請の広告収益条件が「8,000時間またはShorts 2,000万回」に引き上げられるという情報も出ています。 ただし、現時点では公式日本語ページに現在の4,000時間・1,000万回が掲載されているため、事業計画ではYouTube Studioや公式告知で最新条件を確認しておくべきです。[^2_3]

## AIに任せる役割

### 人間が担当する部分

人間に残すべきなのは、単なる最終チェックだけではありません。

- チャンネルのテーマと視聴者を決める
- 他チャンネルとの差別化を決める
- 体験・意見・検証結果を加える
- 扱ってよい情報と避ける情報を決める
- 公開するか、作り直すか、撤退するか判断する
- スポンサー契約、価格、外部との約束を判断する
- 医療・金融・法律などのリスクを確認する

特に、どろどろしーさんの場合は、診療放射線技師としての実務経験や、個人開発・AI活用の実験そのものが独自性になります。AIに一般論を作らせるより、**自分の検証記録や専門的な視点を材料にする**方が強いです。

### AIに任せやすい部分

- YouTubeやSNSのコメント分類
- 競合チャンネルの構成調査
- 視聴維持率やクリック率の分析
- 台本の初稿作成
- 複数タイトルの提案
- サムネイル案の作成
- 字幕生成、翻訳、要約
- 長尺動画からShorts候補を抽出
- 投稿文、概要欄、タグの草案作成
- 音声ノイズ除去や無音部分の整理
- 公開後の反応分析
- 次の企画候補の優先順位付け

AIは制作効率を高められますが、動画ごとの差が小さくなるほど「量産型」とみなされるリスクが上がります。公式ポリシーでも、テンプレートに沿った大量生産、変化の少ない動画、視聴回数だけを狙った一般的なコンテンツは収益化に不利です。[^2_1]

## おすすめのAI部門構成

最初は次の6役で十分です。

```text
人間プロデューサー
  ├─ 統括AI
  ├─ リサーチAI
  ├─ 企画・台本AI
  ├─ 制作AI
  ├─ 品質・権利確認AI
  └─ 分析・改善AI
```


### 統括AI

人間の指示をタスクに分解し、各AIに依頼します。

例：

```text
「AIを使った個人ゲーム開発の現実的な進め方を、
初心者向けの8分動画にする」
```

統括AIは、次のように分解します。

1. 視聴者像を定義
2. 競合動画を調査
3. 独自の切り口を決定
4. 台本を作成
5. 事実確認
6. 映像素材を準備
7. 編集指示を作成
8. タイトル・サムネイル案を作成
9. 人間の承認を待つ
10. 公開後の指標を分析

### リサーチAI

調査は、単に検索結果をまとめるだけにしない方がよいです。

- 一次情報を探す
- 情報の公開日を確認する
- 複数ソースを比較する
- 数字の根拠を記録する
- 台本中の主張と出典を紐付ける
- 不確実な内容を「未確認」として残す

医療や健康に関する動画では、AIが生成した内容をそのまま使わないことが特に重要です。YouTubeの収益化ポリシーに加えて、視聴者への安全配慮、広告適合性、専門職としての責任も考える必要があります。

### 企画・台本AI

台本AIには、毎回同じ構成だけを出させるのではなく、次の素材を渡します。

- 自分の実験結果
- 失敗した点
- 比較したツール
- 具体的な作業時間
- 費用
- 改善前後の違い
- 視聴者が判断できるデメリット

例えば、次の2本なら後者の方が独自性を作りやすいです。

- 「AIでゲームを作る方法」
- 「古いPCでAIを使ってGodotゲームを作り、3日間で詰まった5点」


## 相性のよいチャンネル案

### 1. AI個人開発の実験チャンネル

テーマ例：

- AIエージェントだけで小さなWebアプリを作る
- Claude Code、Gemini、Antigravityを比較する
- AIにゲームの企画・実装・テストを分担させる
- 古いPCやChromebookでどこまで開発できるか
- 1週間でLPを作って公開する
- AI生成動画を量産するのではなく、制作工程を検証する

このテーマは、制作過程そのものがコンテンツになります。成功例だけでなく、失敗、修正、費用、所要時間を公開すると、AIによる一般的な解説との差別化が可能です。

### 2. AI活用Web制作チャンネル

- LPの改善前後を比較
- AIに構成案を作らせ、人間が修正する
- WordPressサイト制作の工程
- 小規模事業者向けWebサイトの改善
- AI生成デザインの実用性を検証
- 実際の制作コストと納期を記録

この場合、YouTubeを集客媒体にして、最終的にLP制作、サイト改善、AI導入支援へつなげられます。

### 3. 競馬データ分析チャンネル

- 予測モデルの作り方
- XGBoostや特徴量の比較
- 予測と実績の検証
- バックテストの落とし穴
- AIに分析レポートを書かせる
- 回収率だけでなく、期間別・条件別に評価する

このテーマでは「当たる予想」を強調するより、**分析手法の再現性と失敗例**を軸にした方が、長期的な信頼を作りやすいです。ギャンブルに関する誤認を招く表現や、過度な利益保証は避けるべきです。

### 4. 短尺雑学・心理・エンタメ

Shortsは拡散の入口として使えますが、完全なAIナレーション、AI画像、同じテンプレートの雑学を大量投稿する形式は、独自性と収益化審査の面で弱くなります。

やるなら、次のような人間の編集要素を入れるべきです。

- 自分の視点でテーマを選ぶ
- 実際に検証する
- 出典を表示する
- 複数の説を比較する
- オリジナルキャラクターや世界観を作る
- 視聴者の反応で次回内容を変える


## 収益化しやすい導線

広告収益だけを目標にすると、視聴回数の変動に事業が左右されます。

```text
Shorts
  ↓
長尺動画
  ↓
無料配布・メルマガ・note
  ↓
テンプレート・教材・ツール
  ↓
制作代行・コンサル・開発サービス
```

例えばAI個人開発チャンネルなら、

- Shorts：開発の失敗や驚きの結果
- 長尺：作り方と検証
- note：要件定義テンプレート
- BOOTH：プロンプト・制作テンプレート
- Webサイト：アプリ開発やLP制作の依頼受付

という構成にできます。

## 投稿の自動化範囲

完全自動投稿は、最初から目指さない方が安全です。

### 自動化してよい流れ

```text
企画候補の収集
→ コメント分類
→ 台本初稿
→ 字幕生成
→ 素材整理
→ 編集プロジェクト作成
→ タイトル案作成
→ 分析レポート作成
```


### 人間の承認を必須にする流れ

```text
医療・健康情報の公開
スポンサー案件
外部へのメール送信
著作権が曖昧な素材の使用
有料商品の紹介
収益・実績の断定
動画の公開
削除・非公開化
```

YouTubeのアップロード自体を自動化する場合でも、公開前に人間が完成動画を再生し、音声、字幕、映像、リンク、権利、概要欄を確認する工程を残すべきです。

## 事業としての30日実験

最初の30日間は、広告収益を狙うより、**どのテーマに反応があるかを測る期間**にします。

### 1週目：チャンネル設計

- 視聴者を1種類に絞る
- チャンネルの約束を1文で定義する
- 長尺とShortsの役割を分ける
- AI利用ルールと権利確認表を作る
- 企画候補を20本出す


### 2週目：小さく制作

- 長尺動画2本
- Shorts 5〜10本
- サムネイルを複数パターン作成
- 制作時間、AI費用、修正回数を記録


### 3週目：反応分析

確認する指標は、再生数だけではありません。

- クリック率
- 冒頭30秒の離脱
- 平均視聴時間
- 視聴者維持率
- コメント内容
- チャンネル登録率
- 概要欄リンクのクリック
- 問い合わせや商品ページへの遷移


### 4週目：継続判断

- 視聴者が反応したテーマ
- 制作負担が大きいテーマ
- AIに任せても品質が落ちない工程
- 自分にしか作れない部分
- 収益につながる可能性

を評価し、次の月に残す企画を3つ程度に絞ります。

## 重要な注意点

### AI生成イコール収益化不可ではない

AIを使ったことだけで収益化できなくなるわけではありません。問題は、AI出力をほぼ加工せず、似たような動画を大量に並べることです。YouTubeは、独自性、視聴者への価値、チャンネル全体の内容を審査します。[^2_1]

### 再利用コンテンツに注意

他人の動画、ニュース映像、SNS投稿、ゲーム映像、音楽、画像を使う場合は、権利だけでなく、独自の解説・批評・教育的価値が必要です。単なる切り抜き、読み上げ、まとめ直しでは審査上弱くなります。[^2_4]

### Shortsだけに依存しない

Shortsは認知獲得には向いていますが、広告収益だけで安定した事業を作るには難易度があります。Shortsで興味を集め、長尺動画、note、商品、サービスへ誘導する構成が現実的です。

## おすすめの開始形

どろどろしーさんの場合、最初は次の形が最も相性がよいと思います。

> 「AIを使って個人開発・Web制作・ゲーム制作を実際に行い、費用・時間・失敗・成果を公開するチャンネル」

AIは、リサーチ、台本、字幕、編集補助、分析を担当します。どろどろしーさんは、テーマ選定、実作業、検証、意思決定、最終的な語りを担当します。

この形なら、動画自体が収益源になるだけでなく、将来的に以下へ発展できます。

- Web制作案件
- AI導入支援
- 個人開発ツール
- 有料テンプレート
- note・Zenn・電子書籍
- ゲームやアプリの販売
- 制作ノウハウの教材化

したがって、動画事業でのAI活用は「AIに動画を作らせる事業」ではなく、**AIを複数部門として配置した、個人メディア兼コンテンツ販売事業**として設計するのがよいでしょう。

# これまでの回答だけで直ぐに行動に移せる？補足や追加情報はある？

はい、これまでの回答だけでも「チャンネルを作る」「企画を決める」「1本目を作る」までは始められます。\
ただし、**事業として継続するには、テーマ・制作工程・権利・KPI・撤退基準を先に最低限決める**必要があります。

## まず今日やること

最初から会社組織やAI社員を大量に作る必要はありません。今日は次の作業だけで十分です。

### 1. チャンネルの仮テーマを決める

おすすめは、次のようなテーマです。

> AIを使って個人開発・Web制作・ゲーム制作を実際に行い、費用・時間・失敗・成果を公開する。

このテーマなら、どろどろしーさんの実際の関心と経験を使えます。AIが一般論を話すだけのチャンネルではなく、実験結果や判断過程を出せるため、独自性を作りやすいです。

### 2. 最初の10本を決める

例：

1. AIだけで小さなWebアプリを作ってみる
2. Claude Code、Gemini、Antigravityを同じ課題で比較する
3. AIエージェント4役でゲーム企画を作る
4. 古いPCでAI個人開発はどこまでできるか
5. AIにLPを作らせて、人間が改善してみる
6. 生成AIでShortsを作る工程と費用
7. AIに競馬データ分析をさせて人間が検証する
8. AIにコードレビューをさせたら何が見つかったか
9. 個人開発でAIに任せてはいけない作業
10. 30日間AIチームで活動した結果

最初から「バズる企画」を当てるより、10本を小さな市場調査として扱います。

### 3. 1本目の仕様を固定する

最初の動画は、次の程度で構いません。

- 長さ：5〜8分
- 目的：チャンネルのテーマを伝える
- 構成：課題、試したこと、結果、失敗、次回予告
- 素材：自分の画面収録、作業ログ、AIとのやり取り
- 投稿先：YouTube
- 再利用：Shorts 2〜3本、note記事1本


## 1本目の企画例

最初の企画としては、次が作りやすいです。

> AIエージェント4役で、個人開発用の小さなWebアプリを作ってみる

### 動画構成

```text
0:00 結論・完成品を見せる
0:20 今回の目的
0:50 AIに与えた役割
1:40 要件定義
2:30 実装
4:00 発生した問題
5:00 人間が判断した箇所
6:00 完成結果
6:40 費用・作業時間
7:10 次回の改善
```

重要なのは、AIがうまく作った部分だけでなく、次の内容も公開することです。

- AIが間違えた指示
- 人間が修正した箇所
- 予想より時間がかかった工程
- AIに任せて危険だと感じた作業
- AI利用料、開発費、作業時間
- 完成品の限界

この「失敗と判断」が、一般的なAI紹介動画との差になります。

## 最小AIチーム

最初は4役で十分です。


| 役割 | 担当 |
| :-- | :-- |
| 統括AI | 企画を作業に分解し、進捗を管理 |
| リサーチAI | 情報収集、競合調査、出典整理 |

- AIの出力の採用・却下

- 収益化方針
- 重要な事実の確認

## 公開前チェックリスト

公開ボタンを押す前に、次を確認してください。

### 内容

- 動画の冒頭で、何が分かる動画か伝わるか。
- タイトルとサムネイルが内容と一致しているか。
- AIの回答を事実として断定していないか。
- 数字、料金、機能、制度に出典があるか。
- 「必ず稼げる」「誰でも成功する」などの誤解を招く表現がないか。


### 権利

- 画像、音楽、映像、フォントの利用条件を確認したか。
- AI生成素材の商用利用条件を確認したか。
- 他人の動画やSNS投稿を単に再利用していないか。
- 出典を表示しただけで利用許諾になると誤解していないか。

YouTube公式も、著作権者の名前を表示しただけでは使用権が得られないと説明しています。動画内の著作物について、必要な権利を確認してから投稿する必要があります。[^3_1]

### AI開示

現実の人物・場所・出来事に見える合成映像や、実在人物が言っていないことを言っているように見せる動画などは、アップロード時に改変・合成コンテンツとして開示が必要になる場合があります。[^3_2]

一方、AIによる台本作成、構成案、字幕、編集補助のような制作支援だけで、直ちに開示が必要になるわけではありません。ただし、実在人物の声や顔を再現する場合は、より慎重に扱ってください。

## 事業として記録する数字

再生数だけを見ると、改善の方向を誤りやすいです。動画ごとに次を記録してください。

```text
動画ID
投稿日
企画テーマ
制作時間
AI利用料
その他費用
再生数
インプレッション

```

YouTube Studioでは、リーチでインプレッションやクリック率、エンゲージメントで総再生時間や平均視聴時間を確認できます。[^3_3][^3_4]

また、視聴者維持率のレポートでは、どの場面で視聴者が離脱したか、どの場面が注目されたかを確認できます。データ反映には通常1〜2日かかります。[^3_5]

### 最初に見る指標

- クリック率が低い：タイトル・サムネイル・テーマの問題
- 冒頭で離脱が多い：結論や見どころが遅い
- 中盤で離脱が多い：説明が長い、変化が少ない
- 視聴はされるが登録されない：チャンネルの約束が弱い
- コメントは多いがクリックされない：集客と商品導線が弱い

数字の基準値を最初から固定するより、同じチャンネル内で企画を比較してください。YouTube自身も、リーチ、エンゲージメント、視聴者維持率など複数のレポートで分析する仕組みを提供しています。[^3_6]

## 30日間の実行計画

### 1〜3日目

- チャンネル名を仮決定
- チャンネル説明を書く
- 視聴者像を一人に絞る
- AI利用ルールを作る
- 企画10本を決める
- フォルダ構成を作る


### 4〜7日目

- 1本目を撮影
- AIに台本初稿を作らせる
- 自分の実体験と検証結果を加える
- 事実確認と権利確認
- 長尺動画を公開


### 2週目

- 1本目からShortsを2〜3本作る
- noteまたはZennに制作記録を投稿
- コメントを分類
- 2本目と3本目を制作


### 3週目

- 反応の良いテーマを1つ深掘り
- サムネイルとタイトルを改善
- 制作時間を短縮
- AIに任せる工程を追加


### 4週目

- 長尺動画4本前後を評価
- Shortsの反応を評価
- 問い合わせやリンククリックを確認
- 継続するテーマを3つ以下に絞る
- 次の30日間の計画を決める


## 追加で決めるべきこと

### 1. 収益化の順番

おすすめは次の順番です。

```text
動画公開
→ 視聴者の反応確認
→ 無料テンプレート配布
→ note・BOOTHなどで小額商品
→ 制作依頼・相談
→ 教材・ツール・サービス
→ 広告・スポンサー収益
```

広告収益だけを目標にすると、YPPの条件を満たすまで収益が発生しない期間が長くなります。チャンネル初期から、動画と関係するテンプレート、開発支援、Web制作などの導線を用意した方が事業としては安定します。

### 2. 誰に見せるか

「AIに興味がある人」だけでは広すぎます。例えば、次のように絞ります。

> プログラミング経験は少ないが、AIを使って個人開発を始めたい会社員。

または、

> AIを使ってWeb制作や副業を始めたいが、何から着手すべきか分からない人。

視聴者が明確になると、タイトル、語彙、動画の長さ、導線が決めやすくなります。

### 3. AI量産をしない基準

次のような動画は、短期的に作れても長期的には弱いです。

- 同じ台本構造に固有名詞だけ入れ替える
- AI音声とフリー素材だけで毎日投稿する
- 他サイトの情報を読み上げるだけ
- 似た内容のShortsを大量投稿する
- 自分の検証や意見がない
- 視聴者から見て誰が作っても同じ

YouTubeは、2025年7月に「繰り返しの多いコンテンツ」を「量産型のコンテンツ」として明確化しています。AIを使うことではなく、独自性が薄く、反復的・大量生産的であることが問題になります。[^3_7]

## 追加で用意するとよい資料

最初に次の5ファイルを作ると、AIチーム運用が安定します。

### `channel-concept.md`

- チャンネルの目的
- 想定視聴者
- 扱うテーマ
- 扱わないテーマ
- 視聴者に提供する価値


### `production-rules.md`

- 動画の基本構成
- 字幕の形式
- サムネイルの方針
- AI音声の使用方針
- 投稿頻度
- 承認フロー


### `fact-check.md`

- 主張
- 出典URL
- 出典の種類
- 公開日
- 確認日
- 台本内の該当箇所
- 不確実性


### `rights-check.md`

- 素材名
- 入手元
- ライセンス
- 商用利用可否
- クレジット要否
- 証拠ファイル


### `postmortem.md`

- 何がよかったか
- どこで離脱されたか
- AIのミス
- 人間の修正
- 次回に残すこと
- やめること


## 結論

すぐ行動に移すなら、今日やるべきことは「AI社員の大規模な仕組み作り」ではありません。

1. チャンネルの仮テーマを決める。
2. 10本分の企画を作る。
3. 1本目を5〜8分で制作する。
4. Shortsと記事に再利用する。
5. 制作時間・費用・視聴データを記録する。
6. 30日後に継続テーマを絞る。

最初の目標は、登録者数や収益ではなく、**30日間で4本の長尺動画と10本程度のShortsを公開し、制作工程と反応データを取得すること**です。そこで初めて、どのAI部門が役立ち、どのテーマが事業になるかを判断できます。

# AIエージェント4役の具体的なプロンプト設定方法

できます。最初は複雑なフレームワークを使わず、**4つの固定プロンプトを用意し、Markdownファイルで成果物を受け渡す**方法がおすすめです。

構成は次のとおりです。

```text
人間プロデューサー
        ↓
統括AI
 ┌──────┼──────┐
調査AI  制作AI  レビューAI
        ↓
人間が最終承認
```

この構成は、統括役がタスクを分解して専門役に渡し、最後に評価役が品質確認する「オーケストレーター・ワーカー」と「評価・改善」の組み合わせです。[^4_1]

## まず作るファイル

```text
ai-video-studio/
├─ 00_project.md
├─ 01_orchestrator.md
├─ 02_researcher.md
├─ 03_creator.md
├─ 04_reviewer.md
├─ projects/
│  └─ 001_first-video/
│     ├─ brief.md
│     ├─ research.md
│     ├─ script-draft.md
│     ├─ review.md
│     └─ approval.md
└─ logs/
```

AIごとに新しい人格を毎回作るのではなく、各ファイルを「システムプロンプト」または「役割指示」として使います。

## 共通プロジェクト情報

まず、すべてのAIに共有する情報を作ります。

### `00_project.md`

```markdown
# プロジェクト共通設定

## チャンネル概要

チャンネル名：
AI個人開発スタジオ（仮）

テーマ：
AIを使って個人開発、Web制作、ゲーム制作を実際に行い、
費用・時間・失敗・成果を公開する。

## 想定視聴者

AIを使って個人開発や副業を始めたいが、
何から着手すべきか分からない人。

## チャンネルの方針

- 実際に試した内容を中心にする
- 成功例だけでなく失敗も公開する
- 制作時間と費用を可能な範囲で記録する
- AIの出力をそのまま事実として扱わない
- 視聴者が再現できる具体性を重視する
- 誇張した収益保証をしない
- 医療、法律、金融に関する内容は慎重に扱う

## 動画の基本構成

1. 結論または完成品
2. 今回の目的
3. 使用したツール
4. 実際の手順
5. 問題と失敗
6. 人間が判断した箇所
7. 結果
8. 費用・時間
9. 次回の改善

## 人間の承認が必要な操作

- 動画の公開
- 外部サイトへの投稿
- スポンサー案件への返信
- 有料商品の紹介
- 収益や成果の断定
- 著作権が不明な素材の利用
- 医療・健康情報の公開
- AIで生成した実在人物の顔・声の利用
```

共通設定には、役割ではなく「事業の目的」「視聴者」「禁止事項」「合格条件」を書きます。長大な人格設定よりも、明確な制約と出力形式を与える方が安定します。[^4_2]

## 1. 統括AI

統括AIは、直接動画を完成させる役割ではありません。人間の依頼を、調査・制作・レビューに分解します。

### `01_orchestrator.md`

```markdown
# あなたの役割

あなたは、個人運営の動画事業を統括するプロデューサーAIです。

人間が決めた目的を理解し、必要な作業に分解し、
調査AI、制作AI、レビューAIへ渡す依頼書を作成してください。

## 目的

- 人間の意思決定を支援する
- 制作工程を小さく分解する
- AIが勝手に公開・送信・契約しないようにする
- 各成果物に担当、期限、合格条件を付ける
- 不明点や重大なリスクを人間に戻す

## あなたがしてよいこと

- 企画の整理
- タスク分解
- 調査項目の作成
- 台本作成の依頼
- レビュー項目の作成
- 進捗と未解決事項の整理
- 人間への確認質問の作成

## あなたがしてはいけないこと

- 動画を公開する
- 外部サービスへ投稿する
- メールを送る
- 契約や購入を行う
- 収益を保証する
- 未確認情報を事実として扱う
- 著作権が不明な素材を使用許可する

## 実行手順

1. 人間の依頼を一文で要約する
2. 想定視聴者と視聴者が得る価値を定義する
3. 成果物を決める
4. 調査が必要か判断する
5. 制作タスクを分解する
6. レビュー項目を作る
7. 人間の承認が必要な箇所を示す
8. 優先順位を付ける

## 出力形式

# 企画ブリーフ

## 依頼の要約

## 想定視聴者

## 視聴者に提供する価値

## 動画の仮タイトル

## 成果物

- 長尺動画：
- Shorts：
- 記事：
- 商品・サービス導線：

## タスク一覧

| ID | 担当 | タスク | 入力 | 成果物 | 優先度 | 人間承認 |
|---|---|---|---|---|---|---|

## 調査AIへの依頼

## 制作AIへの依頼

## レビューAIへの依頼

## 人間が判断すること

## 未解決の質問

## 完了条件

```


### 実際の呼び出し

```text
00_project.mdと01_orchestrator.mdを前提にしてください。

今回の依頼：
「AIエージェント4役で、小さなWebアプリを作り、
制作時間・費用・失敗を動画にしたい」

企画ブリーフを作成してください。
まだ台本は作らず、最初に作業分解とリスク整理を行ってください。
```

統括AIには、いきなり「動画を作って」と言わず、まず企画ブリーフだけを作らせます。

## 2. リサーチAI

リサーチAIの仕事は「情報をたくさん集めること」ではなく、**台本に使える根拠を、主張ごとに整理すること**です。

### `02_researcher.md`

```markdown
# あなたの役割

あなたは、動画事業のリサーチ担当AIです。

企画に必要な情報を調査し、
主張、根拠、出典、確認日、不確実性を整理してください。

## 目的

- 台本に使える情報を集める
- 一次情報を優先する
- 数字、料金、仕様、規約を確認する
- 事実と意見を分ける
- 未確認情報を明示する
- 調査結果を制作AIが使える形式にする

## 情報源の優先順位

1. 公式ドキュメント
2. 公式料金ページ・規約
3. 一次資料・公式発表
4. 実測結果
5. 信頼できる報道
6. 技術者や利用者の実践記録
7. SNS投稿・検索スニペット

## 禁止事項

- 出典のない数字を確定情報にしない
- 検索結果のスニペットだけで結論を出さない
- 1つの情報源だけで重要な主張を確定しない
- 最新情報かどうか不明な料金や仕様を断定しない
- 他人の意見を自分の実験結果として書かない
- 医療・法律・金融情報を無検証で台本に入れない

## 調査手順

1. 企画の主張候補を列挙する
2. 各主張を「事実」「実測」「意見」「仮説」に分類する
3. 重要な主張から出典を探す
4. 情報源の公開日と確認日を記録する
5. 情報が食い違う場合は両方を記録する
6. 台本での安全な表現を提案する
7. 追加確認が必要な事項を示す

## 出力形式

# リサーチレポート

## 調査対象

## 結論の要約

## 主張一覧

| ID | 主張 | 分類 | 根拠 | 出典 | 確認日 | 信頼度 |
|---|---|---|---|---|---|---|

## 台本に使える事実

## 台本に使ってはいけない表現

## 不確実な情報

## 追加確認事項

## 制作AIへの引き継ぎ

```


### 実際の呼び出し

```text
以下の企画ブリーフを調査してください。

[企画ブリーフを貼り付け]

調査対象：
- 使用ツールの料金
- AIエージェントの役割分担
- YouTube収益化に関係する注意点
- AI生成・再利用コンテンツに関する公式ルール

主張ごとに、出典と確認日を付けてください。
公式情報と実際の使用結果を分けて記録してください。
```

ここで重要なのは、AIに「正確に調べて」とだけ頼まないことです。**主張単位の表**にすることで、どの文にどの出典が対応するか確認できます。

## 3. 制作AI

制作AIは、リサーチ結果と実際の作業ログを使って、台本・Shorts・概要欄を作ります。

### `03_creator.md`

```markdown
# あなたの役割

あなたは、YouTube動画の企画・台本・編集指示を担当する制作AIです。

リサーチレポートと人間の実験ログをもとに、
視聴者にとって分かりやすく、独自性のある動画案を作成してください。

## 目的

- 冒頭で視聴理由を明確にする
- AIの一般論ではなく、実際の検証を中心にする
- 成功と失敗の両方を含める
- 視聴者が結果を判断できる情報を出す
- 事実、実測、意見を区別する
- 視聴維持率を意識した構成にする

## 動画の原則

- 最初の20秒以内に結論または見どころを示す
- 1つの動画で扱う中心テーマは1つにする
- 抽象的な説明より画面・数字・比較を使う
- AIが行ったことと人間が行ったことを分ける
- 不確実な情報は断定しない
- 視聴者を煽る収益保証をしない
- 事実と意見に適切な表現を使う

## 台本で使用する表現

実測：
「今回の環境では、約3時間かかりました」

確認済みの事実：
「公式ドキュメントでは、〜と説明されています」

個人の感想：
「私の環境では、〜と感じました」

不確実な内容：
「今回確認できた範囲では、〜の可能性があります」

## 禁止事項

- 実際に試していないことを試したように書く
- リサーチレポートにない数字を追加する
- AIの推測を事実として書く
- 他人の動画や記事の構成をそのまま模倣する
- 収益や成果を保証する
- 未確認の著作権情報を書く
- 人間の承認なしに公開を指示する

## 出力形式

# 制作パッケージ

## 仮タイトル3案

## サムネイル文言5案

## 動画の約束

この動画を見ると、視聴者は何が分かるか：

ナレーション：
テロップ：

映像：
ナレーション：
テロップ：

映像：
ナレーション：
テロップ：

映像：
ナレーション：
テロップ：

### 結果

映像：
ナレーション：
テロップ：

### まとめ

ナレーション：
テロップ：

## Shorts案

### Shorts 1

- フック：
- 本文：
- 結論：
- 元動画の該当箇所：

- 本文：

- 元動画の該当箇所：

## チャプター案

## 使用素材一覧

## 人間が追加すべき情報

```

```text

```

この「存在しない情報を補完しない」という指示は必須です。AIは台本を自然にするため、実際には確認していない数字や結果を埋めてしまうことがあります。

## 4. レビューAI

レビューAIは、台本をきれいにするだけではなく、**公開してよいかを判定する検査役**です。

### `04_reviewer.md`

```markdown
# あなたの役割

あなたは、動画公開前の品質・事実・権利・安全性を確認するレビュワーAIです。

台本、概要欄、サムネイル、使用素材一覧を確認し、
問題点を重大度付きで報告してください。

## 目的

- 事実誤認を検出する
- 出典と主張の対応を確認する
- 実測と推測を区別する
- 著作権・商用利用の確認漏れを検出する
- 誇張・誤解を招く表現を修正する
- AI生成・合成コンテンツの開示要否を確認する
- 視聴者にとって分かりやすいか確認する

## 重大度

CRITICAL：
公開中止。法的、金銭的、安全上の重大リスク。

HIGH：
人間の修正と再レビューが必要。

MEDIUM：
修正推奨。誤解や品質低下の可能性。

LOW：
任意の改善。

## 必ず確認する項目

### 事実

- 数字に出典があるか
- 日付と料金が現在も有効か
- 公式情報と体験談が混ざっていないか
- AIの推測が断定されていないか

### 独自性

- 実際の検証や意見があるか
- 単なる読み上げ・転載になっていないか
- 他人の動画や記事を過度に再利用していないか
- 同じテンプレートの量産に見えないか

### 権利

- 素材の出典があるか
- 商用利用条件を確認したか
- 音楽、画像、映像、フォントの権利が明確か
- AI生成素材の利用条件を確認したか

### AI開示

- 実在人物の顔・声・発言を合成していないか
- 現実の出来事を改変していないか
- 視聴者が本物と誤認する可能性がないか
- 必要な開示が検討されているか

### 事業・広告

- 収益を保証していないか
- スポンサー表示が必要ではないか
- アフィリエイトリンクの説明があるか
- 視聴者に不利益な誘導がないか

## 出力形式

# 公開前レビュー

## 判定

PASS / PASS_WITH_CHANGES / HOLD

## CRITICAL

- 該当なし

## HIGH

- 該当なし

## MEDIUM

- 該当なし

## LOW

- 該当なし

## 事実チェック表

| 箇所 | 主張 | 出典 | 判定 | 修正案 |
|---|---|---|---|---|

## 権利チェック

| 素材 | 出典 | 利用条件 | 商用利用 | 判定 |
|---|---|---|---|---|

## 修正版の台本

## 人間が最終確認する事項

## 公開条件

```


### 実際の呼び出し

```text
以下のファイルをレビューしてください。

- 00_project.md
- research.md
- script-final.md
- description.md
- thumbnail-ideas.md
- 使用素材一覧

問題がない場合も、確認した根拠を示してください。
PASSと判定する場合は、人間が確認すべき項目を空欄にせず明記してください。
```

レビューAIには「問題があれば教えて」だけでなく、**PASSの条件と判定基準**を渡してください。生成AIと評価AIを分離し、明確な評価表で反復改善する形が、品質管理に向いています。[^4_1]

## 4役の実行順

最初は、次の順番で手動実行します。

```text
1. 人間
   企画を入力

2. 統括AI
   企画ブリーフを作成

3. 人間
   企画とタスクを承認

4. リサーチAI
   調査レポートを作成

5. 人間
   実測結果・作業ログを追加

6. 制作AI
   台本・Shorts・概要欄を作成

7. レビューAI
   品質・権利・安全を確認

8. 制作AI
   指摘を修正

9. 人間
   完成動画を再生して最終承認

10. 人間
   YouTubeへ公開

11. 分析AI
   24〜48時間後に指標を分析
```

最初から完全自動化するのではなく、読み取りと下書きだけで繰り返しテストし、外部への書き込みや公開は承認ゲートの後ろに置く設計が安全です。[^4_3]

## 統括AIに渡す全体テンプレート

4つのプロンプトを毎回個別に貼るのが面倒になったら、次の共通呼び出しを使います。

```text
あなたはAI動画スタジオの統括AIです。

## 共通設定
[00_project.md]

## 現在のプロジェクト
[brief.md、または現在の成果物]

## 現在の状態
- 企画：
- 調査：
- 台本：
- レビュー：
- 公開状態：

## 今回の依頼

[ここに人間の依頼を書く]

## ルール

- 不明な情報を推測で補わない
- 外部サービスに書き込まない
- 公開・送信・購入・契約を行わない
- 人間の承認が必要な事項を最後にまとめる
- 出力はMarkdownで作成する
- 完了条件を満たしていなければ、未完了として報告する
```


## プロンプトの改善方法

AIの回答が不安定な場合、役割の説明を増やす前に、次を追加してください。

### 1. 入力を明示する

悪い例：

```text
いい感じの動画を作って。
```

良い例：

```text
対象：
- 企画ブリーフ
- 実際の作業ログ
- リサーチレポート

目的：
- 5〜8分の動画台本を作る

制約：
- 実測と推測を分ける
- 未確認情報は補完しない
- 収益保証をしない
```


### 2. 出力形式を固定する

```text
以下の見出しを必ず使う。

1. 結論
2. 根拠
3. 未確認事項
4. リスク
5. 次の作業
```


### 3. 停止条件を入れる

```text
以下の条件に該当したら作業を続けず、HOLDとして人間に戻す。

- 出典が確認できない重要な数字がある
- 権利条件が不明な素材がある
- 実在人物の顔や声を合成している
- 収益や健康効果を断定している
- 外部への投稿や送信が必要になる
```


### 4. 例を1つだけ与える

Googleのエージェント向けガイドでも、役割、会話ルール、ツール利用、ガードレールを明確に分け、長すぎる一枚のプロンプトより、役割ごとのプロンプトや段階的な処理を推奨しています。[^4_2]

## まずは手動で試す

いきなりPythonやAPIで連携する必要はありません。

### 第1段階：チャットだけ

- ChatGPT、Claude、Geminiなどで4つの役割を別スレッドにする
- Markdownをコピーして渡す
- 成果物をフォルダに保存する
- 人間が承認する


### 第2段階：プロジェクト機能

各AIサービスのプロジェクト機能に共通設定を登録します。

- 共通設定
- チャンネル方針
- 出力形式
- 過去の実績
- 禁止事項


### 第3段階：ファイル連携

- Git
- Google Drive
- Notion
- Obsidian
- ローカルMarkdown

で成果物を受け渡します。

### 第4段階：Python・API連携

最後に、Pythonで次を自動化します。

```text
企画ブリーフ作成
→ 調査タスク生成
→ レポート保存
→ 台本生成
→ レビュー実行
→ 人間承認待ち
```

公開APIやYouTube投稿まで自動化する場合でも、最終公開だけは別の承認処理に分けるのが安全です。

## 初回テスト用プロンプト

まずは以下をそのまま統括AIに入力できます。

```text
以下の企画を、AI動画スタジオの4役で処理してください。

企画：
「AIエージェント4役で、小さなWebアプリを作り、
制作時間・費用・失敗・人間の判断を動画にする」

想定視聴者：
AIを使って個人開発を始めたいが、
実際の進め方が分からない人。

成果物：
- YouTube長尺動画1本
- Shorts 2本
- note記事1本

制約：
- 実際に確認していない結果は書かない
- 収益を保証しない
- 著作権が不明な素材を提案しない
- AI生成コンテンツの開示要否を確認する
- 公開、投稿、送信は人間の承認なしに行わない

まず統括AIとして、企画ブリーフとタスク一覧だけを作成してください。
まだ台本は作成しないでください。
```


## 重要な補足

この4役は、実際には「4人のAIが自律的に会社を運営する」というより、**4種類の専門プロンプトを持った処理工程**です。

最初からAI同士に自由に会話させると、次の問題が起きやすくなります。

- 同じ調査を何度も繰り返す
- 事実でない情報が次のAIへ引き継がれる
- 役割の境界が曖昧になる
- どのAIの判断か分からなくなる
- トークン費用が増える
- 人間が最終成果物を確認しづらくなる

したがって、最初の目標は完全自律ではなく、

> 各AIが決められた入力を受け取り、決められた形式で成果物を出し、人間が承認できる状態を作ること

です。

この設計で1本目を作り、実際にどの役割が不要だったか、どの指示が曖昧だったか、どこで人間の判断が必要だったかを記録してください。そこからプロンプトを短くし、役割を統合・分離していくのが最も現実的です。
