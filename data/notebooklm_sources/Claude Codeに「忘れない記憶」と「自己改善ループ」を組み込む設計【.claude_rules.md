## 本文
はじめに
Claude Code を使い込むと、必ずこの壁にぶつかります。

セッションを跨ぐと、前回学んだ環境固有の罠（このパスは遅い、このコマンドは死ぬ）を毎回ゼロから踏み直す
同じ指摘を何度もする羽目になる（「それさっきも言ったよね？」）
ルールを増やすほど毎ターンのトークン消費が膨らみ、CLAUDE.md が肥大化して逆に指示を守らなくなる
別のPCに環境を移すと、せっかく溜めた知見が一緒に来てくれない

この記事では、これらを「2層メモリ構造」と「自己改善ループ」という2つの仕組みで解決する設計を紹介します。要は Claude Code に永続的な記憶を持たせ、失敗から自動でルールを学ばせる という話です。



 全体像：2層メモリ + 自己改善ループ
設計の骨格はこの2つだけです。
┌─────────────────────────────────────────────┐
│ ① 2層メモリ                                   │
│   auto memory（環境固有・自動注入）            │
│   統合知見ベース（全環境共有・Git同期）        │
├─────────────────────────────────────────────┤
│ ② 自己改善ループ                              │
│   paths 遅延ロード（固定費を抑える）           │
│   失敗3回 → ルール昇格（同じミスを潰す）       │
│   候補自動生成 → 昇格（パターンを資産化）      │
└─────────────────────────────────────────────┘
処理の流れはシンプルです。セッション中に得た知見はまず環境固有のメモリに書き、他環境でも役立つものだけを Git 管理された共有知見ベースに「昇格」させる。そしてルール本体は普段ロードせず、関連ファイルを触ったときだけ読み込ませる。


 ① 2層メモリ構造
記憶を「環境固有」と「全環境共有」の2層に分けるのがこの設計の肝です。混ぜると破綻します。

 第1層：auto memory（環境固有・自動注入）
セッション開始時に自動でコンテキストへ注入される、その環境専用のメモリです。
格納場所はCWD（作業ディレクトリ）ごとにエンコードされたパス配下に置きます。
~/.claude/projects/<CWDをエンコードした文字列>/memory/MEMORY.md
MEMORY.md は「索引」です。1メモリ＝1ファイルにして、MEMORY.md には1行のポインタだけを書きます。本文をここに書くと毎ターン全部送られてトークンを食い潰すので厳禁です。
# Memory Index

- [遅延の原因はネットワークドライブ](network-drive-latency.md) — UNCパス上のDB初期化が遅い
- [Bashツールが死ぬ条件](shell-env-trap.md) — SHELL環境変数の汚染で全Bashツールが落ちる。再起動で復旧
- [このGUIツールの設計](sample-tool-arch.md) — tkinter + openpyxl、4モード構成

各メモリファイルはフロントマター付きの単一事実にします。
---
name: shell-env-trap
description: SHELL環境変数の汚染でBashツールが全滅する条件と復旧手順
metadata:
  type: project
---

Bashツールが「No suitable shell found」で全滅する。
User scopeのSHELLが正常でも、Process scopeに不正な値が混入すると発生する。

**Why:** Process scopeはセッション起動時に確定し、後から正しても効かない。
**How to apply:** Claude Code を再起動する。応急処置として別のシェル実行手段で代替する。

関連: [[network-drive-latency]]
ポイントは [[name]] でメモリ同士をリンクすること。まだ存在しない名前を書いてもエラーにはならず、「あとで書くべき知見」のマーカーになります。

 第2層：統合知見ベース（全環境共有・Git同期）
第1層は環境に紐づくので、別PCには来ません。そこで、他の環境でも有用な知見だけを Git 管理されたディレクトリに昇格させます。
~/.claude/memory/   ← Gitで全環境同期
├── plugins.md       # プラグインのインストール手順・罠
├── settings.md      # 設定値とその判断理由
├── workflow.md      # ツール委任・コンフリクト解決手順
└── environments.md  # OS固有の落とし穴
昇格の判断基準はこれだけです。



知見の性質
行き先




この環境でしか起きない一時的な作業記録
第1層（auto memory）に留める


他のPC・他のセッションでも再発しうる
第2層へ昇格



昇格したら git push、他環境は git pull で受け取る。これで 一度学んだ罠を全環境で二度と踏まない 状態になります。
# 昇格後
git -C ~/.claude add memory/environments.md
git -C ~/.claude commit -m "chore: add UNCパス遅延の回避策"
git -C ~/.claude push


 ② 自己改善ループ
メモリに知見が溜まっても、それが「ルール」として自動適用されなければ意味がありません。かといってルールを全部常時ロードするとトークンが爆発します。ここを3つの仕組みで解決します。

 改善1: paths 遅延ロードで固定費を抑える

 問題
~/.claude/rules/ 配下の .md は、paths フロントマターが無いと全ファイルが毎ターン常時ロードされます。ルールを書けば書くほど、会話が始まる前の「固定費」が膨らみます。実際、33ファイルで毎ターン55kトークン（コンテキストの14%）を食っていた、という事例があります。


 解決策
Step 1: 関連ファイルを触ったときだけ読むルールには、実globを書く
---
paths:
  - "**/*.py"          # Pythonファイル編集時だけロード
  - "**/*.ps1"
---
これで、ユーザーが .py を編集するときにだけ Python 用のルールが読み込まれます。
Step 2: ファイル編集に紐づかないルールはダミーglobで常時ロードから外す
ツール委任や運用フローのルールは「状況」で発動し、特定ファイルの編集を伴いません。これらは決してマッチしないダミーglobを指定し、CLAUDE.md のポインタ経由で必要時に読ませます。
---
description: GitHub操作・PR・Issue時に参照（いつ読むかの手がかり・メモ用）
paths:
  - "__manual_reference_only__/**"   # 自動ロードされない
---
Step 3: 常時ロードはコア原則だけに限定する
全セッションで必須な最小限のルール（言語設定・出力形式・トークン節約原則など）だけを _core/ に置き、paths を付けずに常時ロードします。それ以外は原則 paths で限定。これだけで前述の 55k → 5k 級の削減が効きます。


 改善2: 失敗3回 → ルールへ自動昇格（Compounding Engineering）

 問題
同じ種類のミス（同じ Bash コマンドの失敗、同じ環境の罠）を、セッションを跨いで何度も繰り返してしまう。

 解決策
「同じ失敗が3回起きたら、一般化したルールに昇格させる」というサイクルを組みます。
1. 失敗ログが一時ファイルに3回蓄積される（検知用のhookが監視）
2. 失敗パターンを分析して rules/ に追記
3. 次セッション以降は自動遵守 → 再発ゼロ
ルールに昇格させるときは、理由（Why）を1行添える のが効きます。背景があると遵守率が上がります。
# ❌ 理由なし
DB書き込みは必ずトランザクションで囲むこと。

# ✅ 理由あり
DB書き込みは必ずトランザクションで囲むこと。
# (Reason: 2024-11の本番障害 — 部分書き込みでデータ破損)
また、ルールは「客観的に検証可能」であることが重要です。抽象的だとモデルが逃げ道を見つけます。



❌ 抽象的
✅ 具体的（検証可能）




「効率的なコードを書く」
「N+1クエリを検出したら prefetch で解決する」


「セキュアに実装する」
「ユーザー入力は必ずパラメータバインディングで渡す。文字列連結禁止」



否定形（NEVER）は肯定形（prefer）より遵守率が高いですが、必ず代替案をセットにします。「するな」だけだとモデルが手詰まりになります。
# 段階1: 禁止
ユーザーパスをハードコードしない（例: C:\Users\foo\...）
# 段階2: 理由
# (Reason: マシンごとにユーザー名が違う)
# 段階3: 代替案
→ 環境変数を使う（$env:USERPROFILE / $HOME など）

 改善3: 候補の自動生成 → /promote-candidates で資産化

 問題
便利なコマンド列や繰り返し作業を「毎回手で再現」していて、再利用可能な資産になっていない。

 解決策
Bashコマンド・失敗・特定ドメインの作業が3回以上繰り返されたら、自動で「候補ファイル」を生成しておき、セッション終了前にまとめてレビュー・昇格する運用にします。
~/.claude/tmp/
├── skill-candidates/    # スキル化の候補
├── agent-candidates/    # サブエージェント化の候補
├── hook-candidates/     # hook化の候補
└── script-candidates/   # スクリプト化の候補
セッション終了前に候補をレビューするコマンドを1本実行するだけで、繰り返しパターンが恒久的なスキル/スクリプトとして定着します。「3回やったら自動化を検討する」を仕組みに落とし込むイメージです。


 仕組みを支える3つの設計原則
ここまでの仕組みは、根底にある3つの原則の上に成り立っています。

 原則1: ポインタ駆動で CLAUDE.md を薄く保つ
CLAUDE.md は毎ターン送信されます。1行足すと全セッションでトークンが増えます。100〜150行を超えると指示遵守率が落ち始める（絶対最大200行）ので、詳細は別ファイルに逃がしてポインタだけ書きます。
# CLAUDE.md（薄く保つ）
- アーキテクチャ詳細: `docs/architecture.md` を参照
- DB設計: `docs/schema.md` を参照
- ツール委任の基準: `rules/tools/delegation.md` を参照

 原則2: 定着したルールは削除する（Pruning）
モデルがそのスタイルを完全に習得し、ルールなしでも実践できるようになったら、そのルールは消します。「このルールは今も必要か？」を定期的に問い直すことで、コンテキストを節約しつつ自律判断を促せます。記憶は足し算だけでなく引き算も必要、ということです。

 原則3: 「次回の自分への手紙」として書く
ルールもメモリも、未来のセッション（＝記憶を持たない次の自分）への引き継ぎ書として書きます。「なぜこのルールがあるのか」が1行あるだけで、未来の自分は文脈ごと理解できます。
