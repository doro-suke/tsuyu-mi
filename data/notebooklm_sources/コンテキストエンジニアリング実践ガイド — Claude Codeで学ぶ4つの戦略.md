## 本文
CLAUDE.md を書いて、rules を整備して、agents も作った。それなのに Claude Code の出力精度が安定しない——そんな経験はないだろうか。原因は「プロンプトの書き方」ではなく、コンテキストの設計にある可能性が高い。本記事では業界で広く採用されている4つの設計戦略を、Claude Code の具体的な機能にマッピングしながら、「何を・いつ・どの粒度で渡すか」の判断基準を示す。


 なぜ「プロンプト」ではなく「コンテキスト」なのか
Andrej Karpathy（元 Tesla AI 責任者）は2025年6月、次のように述べた。

"Context engineering is the delicate art and science of filling the context window with just the right information for the next step."

彼の比喩はシンプルだ。LLM は CPU、コンテキストウィンドウは RAM。RAM に何をロードするかで、CPU の処理結果が決まる。2026年3月には Claude の 1M コンテキストウィンドウが GA になり、使える「RAM」は格段に広がった。しかし RAM が増えたからといって、設計なしに情報を詰め込めばよいわけではない——むしろ設計の重要性は増している。
「プロンプトエンジニアリング」が命令文の言い回しを最適化する技術だとすれば、「コンテキストエンジニアリング」はシステムプロンプト・RAG・ツール出力・会話履歴・メモリを含むウィンドウ全体の情報設計だ。Prompt Engineering はコンテキストエンジニアリングのサブセットにすぎない。

 現場の課題: CLAUDE.md に200行書いたのに出力が安定しない
この問題は「プロンプトが悪い」のではなく、コンテキストの設計が欠けていることが原因であることが多い。情報を「入れる」だけでは不十分で、「何を入れないか」「いつ入れるか」「どの粒度で入れるか」を設計する必要がある。
Chroma Research が18モデルを対象に実施した研究では、コンテキスト長が増加するとモデルの性能が劣化する傾向が観察されている（Context Rot）。また Stanford の研究（2023年、GPT-3.5/Claude 2世代が対象）では、コンテキストの中間部分の情報精度が15〜20ポイント低下する「Lost in the Middle」効果が報告されている。ただし劣化の程度はタスクやモデルによって異なり、最新モデルでは改善が進んでいる点には留意が必要だ。
加えて、コンテキストの肥大化はコスト面でも直撃する。LLM API はトークン単価で課金されるため、不要な情報をコンテキストに含めるだけで入力コストが膨らむ。マルチエージェント構成ではサブエージェントごとにコンテキストを消費するため、コスト乗数効果も無視できない。
つまり、CLAUDE.md にすべてを詰め込むことは、RAM を無関係なデータで埋め尽くすことと同じだ。

 4つの設計戦略と Claude Code のマッピング
LangChain が「Context Engineering for Agents」で体系化した4つの戦略がある。Anthropic も公式ブログで圧縮・選択的注入・サブエージェントといった類似の設計原則を論じている。ここでは各戦略を Claude Code の機能にマッピングするが、4戦略自体はツール非依存の汎用概念だ。Cursor、GitHub Copilot、Cline など他のツールでも同じ設計思想は適用できる。Claude Code 固有の機能名を覚えることよりも、背後の判断基準を理解することが重要だ。

マルチエージェント設計では、コンテキスト隔離が性能に大きく影響する。ルートエージェントが全履歴をサブエージェントに渡す設計は、Context Rot を加速させるアンチパターンだ。サブエージェントにはタスクに必要な最小限の情報だけを渡し、結果は要約して返すのが鉄則になる。

 設計判断フレームワーク: 5ステップ
新しいプロジェクトでコンテキストを設計するとき、以下の5ステップで判断する。
Step 1: プロジェクトの不変知識を特定する → CLAUDE.md（Write）
  「ビルドコマンドは？」「ディレクトリ構成は？」「命名規則は？」

Step 2: ファイル種別ごとのルールを整理する → rules/（Select）
  「テストの書き方は？」「APIの設計基準は？」「レビュー観点は？」

Step 3: コンテキスト予算を見積もる
  目標: 常時ロード情報を必要最小限に絞る（少ないほど精度が上がる）

Step 4: 長時間タスクの /clear ポイントを設計する（Compress）
  「このワークフローのどこでコンテキストをリセットすべきか？」

Step 5: 並列化可能なタスクを特定する → サブエージェント（Isolate）
  「独立して実行できるリサーチ・レビュー・テストはあるか？」

個人開発で rules/ を10ファイル作り込むのは過剰設計だし、10人チームで CLAUDE.md 1ファイルに全情報を集約するのは破綻する。自分のチームがどの段階にいるかを見極めてから設計に着手することが重要だ。

 現場で遭遇する4つの罠

 罠1: コンテキスト過積載
症状: CLAUDE.md にプロジェクトのすべてを書き込む。結果、重要なルールがコンテキストの中間に埋もれて無視される（Lost in the Middle 効果）。
対策: CLAUDE.md は簡潔に保つ（目安200行以内）。超過分は rules/ に分離し、ファイルパターンで Select 注入する。「全員が常に知るべきこと」だけを CLAUDE.md に残す。
ただし逆方向の罠もある。rules/ に追い出しすぎると、ファイルパターンに合致しないタスクでルールが適用されない「Select 漏れ」が起きる。この判断は可逆的なので、迷ったらまず分離してみて、漏れが発生したら CLAUDE.md に戻せばよい。

 罠2: コンテキスト矛盾
症状: CLAUDE.md で「テストは Jest」と書いているのに、rules/ で「Vitest を使用」と指示している。モデルの出力がセッションごとに異なる。
対策: 階層の優先順位を明確にする。Claude Code ではファイル固有ルール > プロジェクトルール > グローバルルールの順で適用される。同一トピックの指示は1箇所に集約する。

 罠3: コンテキスト腐敗
症状: 半年前に書いた CLAUDE.md の情報が古くなっているが、モデルはそれを「現在の事実」として扱い続ける。
対策: memory の定期レビューを習慣にする。auto-memory が書き出した MEMORY.md を月次で見直し、古くなった情報を更新・削除する。「この情報はいつ時点のものか」をメタ情報として記録するのも有効だ。

 罠4: 戦略間のトレードオフを見落とす
症状: 4戦略を個別に最適化した結果、戦略間で矛盾が生じる。たとえば Compress のために /clear した直後に、Write で書き残すべき情報が失われる。あるいは Isolate でサブエージェントを3並列起動した結果、総トークンコストが概ね3倍になっていることに気づかない。
対策: 4戦略は独立ではなく連動している。Compress するなら Write（ハンドオフ）を先に設計する。Isolate するならコスト乗数効果を見積もる。1つの戦略を強化するとき、隣接する戦略への影響を確認する習慣をつける。

 限界と向き合う
コンテキストエンジニアリングは「万能薬」ではない。
解決しない問題:

LLM のハルシネーション — コンテキストが完璧でも発生する。むしろ、コンテキスト矛盾やコンテキスト腐敗はハルシネーションのリスクを増幅させる。矛盾した情報を与えられたモデルは「つじつまを合わせる」ために事実を捏造しやすくなる
推論の不安定性（同一コンテキストでも出力が異なることがある）
ドメイン知識の欠如（コンテキストに含まれない専門知識は補えない）

コスト:

設計・保守に工数がかかる。CLAUDE.md / rules / agents の整備は「書いたら終わり」ではなく、プロジェクトとともに進化させる必要がある
過剰設計のリスク。小規模プロジェクトや個人開発では CLAUDE.md 1ファイルで十分なケースが多い

トークンコスト: コンテキストが大きいほど API 料金が増える。特にマルチエージェント構成では、各サブエージェントのコンテキスト消費を合算した総コストを見積もることが重要だ

ベンダーロックインのリスク:

CLAUDE.md / rules/ / skills の構造は Claude Code 固有だ。他ツールへの移行時にはこれらの設計資産を再構築する必要がある
ただし、4戦略の「判断基準」自体はツール非依存。設計思想を理解していれば、ツールが変わっても応用が利く

プライバシーの注意点:

CLAUDE.md に機密情報（API キー、社内 URL、顧客データ）を書かないこと。コンテキストに含まれた情報は LLM に送信される
auto-memory が個人情報や機密情報を自動保存するリスクにも注意が必要。MEMORY.md の内容は定期的にレビューする

設計しすぎない判断基準:

チームメンバーが少数 → CLAUDE.md だけで十分なケースが多い
タスクが単発（1セッションで完結） → rules/ は不要
並列処理するタスクがない → Isolate は不要


 まとめ: 今日からできる3つのアクション


CLAUDE.md を棚卸しする: 各行が Write / Select どちらに属するか分類し、Select に該当するものを rules/ に移動する

常時ロード vs オンデマンドを分離する: 「テスト規約」「レビュー基準」「デプロイ手順」など、特定タスクでしか使わない情報を rules/ や skills に切り出す

長時間タスクに /clear ポイントを設計する: ワークフローの Phase 境界を特定し、「ここでコンテキストをリセットする」というポイントを決める

コンテキストエンジニアリングの本質は、LLM に「何を知らせるか」ではなく「何を知らせないか」を設計することだ。情報を引き算する勇気が、出力の精度を安定させる。
