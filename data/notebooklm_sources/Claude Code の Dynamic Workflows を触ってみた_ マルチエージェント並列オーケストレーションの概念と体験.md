## 本文
本記事は 2026/5/29(日本時間)時点の公式ブログ[1]と公式 X 告知[2]に基づく初出時の内容です。当時 Dynamic Workflows はリサーチプレビュー段階でしたが、その後の GA 化に伴う仕様・利用条件の変更は下記の追記にまとめています
【2026-06-14 追記】 その後 Dynamic Workflows は GA(generally available)となり、対応プラン(Pro を含む 4 プランへ拡大)と既定値(Enterprise はデフォルト有効へ)が更新されました。該当箇所(「使える環境とプラン・注意点」)に時点付きで追記しています


 はじめに
2026/5/29(日本時間)、Claude Code v2.1.154 で Dynamic Workflows(動的ワークフロー)がリサーチプレビューとして追加されました。同じ v2.1.154 で Opus 4.8 も公開 されており、Opus 4.8 と同時の登場です[3]。
ひとことで言うと、Claude がオーケストレーション用のスクリプトをその場で書き起こし、1 つのセッションの中で数十〜数百のサブエージェントを並列で走らせて、大規模なタスクを最後まで遂行する 仕組みです。しかも結果はそのまま返ってくるのではなく、Claude 自身が検証してから 1 つの答えにまとめて返してきます。
公式の表現を借りると「四半期単位で計画するような規模の仕事が数日で終わる」[1:1]。
実例として挙げられているのが Bun の Zig → Rust 全面移植 です。Bun は高速な JavaScript ランタイムで、2025 年 12 月に Anthropic が買収 しています[4]。その Bun を Zig から Rust へ書き換えたことが 2 週間前に話題になっていましたが、今回のブログで それが Dynamic Workflows で行われた、という種明かし がされました。作者の Jarred Sumner 氏が Dynamic Workflows を使い、既存テストの 99.8% がパス・約 75 万行の Rust・最初のコミットからマージまで 11 日 で移植したとのことです[1:2]。しかも「各 .zig を挙動が同一の .rs へ移すワークフローでは、各ファイルに 2 人のレビュアーを付けて数百エージェントが並列で動いた」と、本機能の検証の手厚さがそのまま表れています[1:3]。
本記事では、まず Dynamic Workflows の概念を整理し、既存の並列・自動化手段(サブエージェント / バックグラウンド実行 / /loop / ルーチン)との違いを押さえた上で、実際に動かした体験レポートをまとめます。

 想定読者

Claude Code の最新機能をキャッチアップしたい方
サブエージェントやバックグラウンド実行を普段使っていて、Dynamic Workflows で何が変わるのか知りたい方
大規模リファクタやコードベース全体の調査を Claude に任せられないか検討している方


 Dynamic Workflows とは
従来の Claude Code でも、メインエージェントが必要に応じてサブエージェントへ委譲し、並列に走らせること自体はできました。ただ、それは Claude がその場の判断で行うもので、どれだけの規模で・どう分割し・どう検証するか を体系立てて組み上げる仕組みまではありませんでした。大規模な分割や多段の検証を狙うなら、プロンプトの工夫で都度お膳立てする部分が大きかったのが実情です。
Dynamic Workflows は、この 「分割と検証の段取り」自体を Claude がワークフロー(オーケストレーション用のスクリプト)として明示的に組み立てる のが新しいところです。公式ブログ[1:4]によると、Claude は次のように動きます。

タスクを受け取ると、オーケストレーション用のスクリプトを動的に生成 する
そのスクリプトが、1 セッション内で 数十〜数百のサブエージェントを並列起動 する
各サブエージェントの結果は、ユーザーに届く前に Claude 自身がチェック してから統合される

対象として想定されているのは、1 回のパスでは複雑すぎるタスクです。

コードベース全体にまたがるバグ調査
数千ファイルに及ぶ大規模マイグレーション
配信前に独立した検証が必要な重要タスク


 何がうれしいのか(4 本柱)
公式は Dynamic Workflows の特徴を 4 つ挙げています[1:5]。



柱
中身




並列処理
サブエージェントを逐次でなく同時に走らせ、完了までの時間を大幅に短縮する


独立検証
各結果は統合される前にチェックされ、ユーザーには調整済みの 1 つの答えが返る


進捗の永続化
実行中に進捗が保存され、中断されたジョブは最初からではなく途中から再開する

あるエージェントが独立した角度から問題に取り組み、別のエージェントがその発見を反証しようとし、答えが収束するまで反復する



特に重要なのは 独立検証 と 敵対的レビュー だと感じます。並列化そのものは既存のサブエージェントでもできますが、「複数の角度から攻めて、互いに反証し合って、収束するまで回す」という検証ループまで自動で組んでくれるのは、セキュリティ監査や大規模リファクタの安心感に直結します。
この敵対的レビューは、実は新しい発想ではありません。後述する エージェントチーム の公式ドキュメント[5]では、「one playing devil's advocate(デビルズアドボケイト役を立てる)」「互いの仮説を反証させる(try to disprove each other's theories, like a scientific debate)」という使い方が ベストプラクティスとして紹介 されていました。ただしエージェントチームでは、その役回りを 人間がプロンプトで明示 する必要がありました。Dynamic Workflows は、この反証ディベートを Claude 側が自動で組み込んで 収束まで回してくれる、という位置づけです。
進捗の永続化も地味に重要です。数百サブエージェントを長時間走らせる前提なので、途中で落ちても再開できる設計になっているのは実運用上ありがたいところです。

 起動方法
起動には 2 通りあります[1:6]。

 1. 直接お願いする
シンプルに Create a dynamic workflow(動的ワークフローを作って)と頼むパターンです。タスクの規模を見て、Claude がワークフロー化して走らせます。

 2. ultracode を選ぶ
ultracode は /effort(エフォート選択スライダー)に現れる選択肢です。low / medium / high / xhigh / max のさらに右、一番「Smarter」側に区切りを挟んで独立して置かれていて、サブラベルは xhigh + workflows。つまり xhigh の推論努力に Dynamic Workflows を組み合わせた モードだと、UI から読み取れます。
/effort スライダー右端に現れる ultracode(xhigh + workflows)

これを選ぶと effort が xhigh に上がり、ワークフローを適用すべきタイミングを Claude が自動で判断 するようになります。毎回明示的に頼まなくても、規模の大きいタスクで自動的にワークフロー化される、という位置づけです。ちなみに ultracode にフォーカスすると、スライダー全体に派手な紫のエフェクトが広がる演出付きでした。
なお、走らせた実行(runs)は /workflows コマンドで一覧できます[3:1]。また Opus 4.8 自体の default effort は high で、最難関タスクは /effort xhigh という位置づけです[3:2]。


 使える環境とプラン・注意点
公式ブログ[1:7]の記載をまとめます。


対応サーフェス: Claude Code CLI / Desktop / VS Code 拡張 / Claude API / Amazon Bedrock / Vertex AI / Microsoft Foundry

対応プラン: ローンチ時(2026-05-29 時点)は Max / Team / Enterprise のみで Pro 非対応でした。GA 更新(2026-06-14 時点)で Pro / Max / Team / Enterprise + Claude API に拡大 し、Pro は /config の Dynamic workflows 行から有効化、デフォルト有効は Max / Team / Enterprise + API です

Enterprise の既定値: ローンチ時はデフォルト無効でした。GA 更新(2026-06-14 時点)で Enterprise はデフォルト有効に変更 されています。組織全体で止める場合は管理者が managed settings の disableWorkflows で無効化できます

実行前の確認は権限モード次第: トークン消費が大きいため実行前に確認が挟まりますが、出る頻度は権限モードで変わります。default / acceptEdits では毎回、auto では初回のみです(GA 更新後の公式 docs で確認[6])

数十〜数百のサブエージェントを並列で走らせる以上、トークン消費が大きいのは当然です。「とりあえず全部 Dynamic Workflows で」ではなく、単一パスでは手に負えない規模のタスクに絞って使う のが基本方針になりそうです。

 既存の並列・自動化手段との違い
Claude Code には、これまでも並列・自動化の手段が複数ありました。Dynamic Workflows がどこに位置するのかを整理します。
複数のエージェントを並列に動かす手段は、サブエージェント → エージェントチーム → Dynamic Workflows と、規模と自動化の度合いを上げながら発展してきました。この系譜の中で位置づけると分かりやすいです。

 エージェントチームとの関係
一番近いのが エージェントチーム(CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 で有効化する実験的機能)です。エージェントチームも、1 つの lead セッションから並列の teammate を立ち上げて互いに協調させる機能で[5:1]、「複数エージェントを束ねて並列に動かす」点は Dynamic Workflows と同じです。
違いは、想定する規模と、オーケストレーションを誰が組み立てるか です。


エージェントチーム: 公式が「まずは 3〜5 体から」と勧める規模感で、役割分担(UX 担当・アーキ担当・デビルズアドボケイト役…)や検証の進め方を 人間がプロンプトで組み立てます。

Dynamic Workflows: 数十〜数百規模のタスクを前提 に、その複数エージェントのオーケストレーションを Claude 自身が動的に設計 し、反証ループ(デビルズアドボケイト)まで自動で内蔵します。

ひとことで言えば、Dynamic Workflows は「もともと大規模なタスクを、Claude 自身のオーケストレーションで一気に片付ける」ことを狙った仕組み です(公式の表現では「数十〜数百のサブエージェントをバックグラウンドでオーケストレーション」[1:8][3:3])。エージェントチームを無理に大きくしたものというより、最初から大規模前提の作業にそのまま適用する 性格の機能だと捉えると分かりやすいです。

 実際に動かしてみた(体験レポート)

 当社カンリーでの運用文脈
当社カンリーでは Claude Code を日常的に業務へ組み込んでおり、その一環として 社内で共通利用する Claude Code プラグインのマーケットプレイス用リポジトリ を運用しています。用途別のプラグインをまとめて配布し、チーム全体で同じスキルや規約を共有する狙いです。
このリポジトリ自体は、すでにかなり作り込んであります。具体的には次のような仕組みが回っています。

ドキュメント(README / 各プラグインの説明 / CLAUDE.md)
テスト(vitest)と linter(biome)、プラグイン定義やマーケットプレイス登録の整合性を検証するスクリプト
CI(lint / test / プラグイン検証 / セキュリティスキャン)

Claude Code 本体のバージョンアップに追従する仕組み(公式 CHANGELOG のスナップショットを監視し、上流の更新を拾う)

つまり「壊れていないか」を PR 単位で守る仕組みは一通り揃っています。それでも、リポジトリ全体を定期的に棚卸しして抜け漏れが無いかを見直す作業 は別途必要です。個々の自動チェックは回帰を防いではくれますが、「プラグインをまたいで見たときの不整合」や「上流に増えた機能をまだ取り込めていない」といった 横断的・俯瞰的な抜け漏れ は、全体を一度に見渡さないと気づきにくいからです。
この 定期的な全体点検 こそ、数十エージェントを並列で走らせて互いに検証させる Dynamic Workflows に向いていそうだ、と考えました。複数プラグイン × 複数観点(実装・テスト・登録・ドキュメント・上流追従)の突き合わせは、まさに想定ユースケースに合致します。

 依頼したタスク
別セッションで、対象リポジトリの Claude Code セッションに次のプロンプトを貼り、Dynamic Workflows に点検を依頼します。既存の自動チェックが担保する範囲を 先に読ませて除外 し、その網から漏れる横断的・俯瞰的な抜け漏れに集中させるのがポイントです。
dynamic workflow を作って、このリポジトリ全体の抜け漏れを定期棚卸しの観点で点検してほしい。
# 前提
- 社内共通の Claude Code プラグイン用マーケットプレイス。各プラグインは marketplace 定義に登録され、plugins/<name>/ に実体がある。
- テスト・linter・プラグイン検証スクリプト・整合チェック・CI・Claude Code 本体のバージョン追従(公式 CHANGELOG のスナップショット監視)は整備済み。
  「これらが無い」という指摘ではなく、これらの網から漏れている箇所を探すこと。
  まず検証スクリプトと CI 定義を読み、自動チェックが担保済みの範囲を把握してから、その範囲外(横断的・俯瞰的)に集中する。
# 探す抜け漏れ(プラグイン × 観点で横断)
1. 実装と登録の整合(登録漏れ / 記載と実体の不一致 / 孤立ディレクトリ)
2. テスト(実装に対するテストの有無 / 実装が消えてテストだけ残る片側残り)
3. ドキュメント(README・CLAUDE.md・frontmatter が実体と一致しているか / 陳腐化)
4. 上流追従(スナップショット以降の Claude Code 更新に対する陳腐化 / 取り込むべき新機能の取りこぼし)
5. 横断の一貫性(命名規約・必須ファイルがプラグイン間で揃っているか)
# 進め方
- プラグインごと・観点ごとにエージェントを並列化し、横断観点(全体の一貫性・上流追従)は別エージェントが担当。
- 各発見は別エージェントが「本当に漏れか、既存の仕組みでカバー済み/意図的か」を反証してから採用する(誤検知を潰す)。
- node_modules / coverage / dist / ロックファイルは対象外。秘密情報は値を出さず、場所と種別のみ報告。
# 出力(ファイルは変更せず、レポートのみ)
- プラグイン別に: 観点(1〜5) / 重大度(high・medium・low) / 根拠(path:line) / 推奨対応 を付ける。
- 「点検したが漏れなし」と確認できた箇所も明示する。
- 最後に、横断で見えた構造的課題(規約のばらつき・上流追従の遅れ)を 3〜5 点に要約。
「カンリーではこういう運用をしていて、このプロンプトを依頼した」という前提で、実際に回してみました。

数字から見えてくることがいくつかあります。


いきなり手を動かさず、まず 8 分かけて段取りを組む。点検対象の洗い出しとエージェントの割り当て(どのプラグインを誰が見るか / 横断観点を誰が担当するか)を先に設計してから、約 30 分の並列実行に入っていました。冒頭で触れた「オーケストレーションを動的に設計する」挙動が、計画フェーズとして体感できます。

約 40 分でひとつの全体レポートに着地。数十分かかるとはいえ、人間が複数プラグインを観点別に突き合わせる手間を考えれば、定期棚卸しを 1 回まるごと肩代わりしてくれる感覚です。

コストは軽くない。1 回の点検で 5 時間枠の 4 割強を使うので、2 回ちょっとで枠を使い切る規模です。「単一パスでは手に負えない、まとまった棚卸し」に絞って使う、という方針(前章)とそのまま一致しました。

それでいて、メインセッションのコンテキストはほとんど増えません。調査の実作業はサブエージェント側で行われ、メインに返ってくるのは集約済みのレポートだけなので、これだけ大きな調査を回しても 手元のメインセッションのコンテキストは数 % しか増えませんでした。レート制限(トークン)消費とコンテキストウィンドウ消費は別物で、重い調査を回してもメインの会話が膨らまない のは、長いセッションを続ける実運用で大きな利点です。


 ステップで見る実行の流れ

 ステップ 1: 計画と起動の確認
プロンプトを送ると、Claude はまず点検対象を洗い出して ワークフローの計画 を立てます。今回は対象を 21 ユニット(プラグイン 17 + 横断 4: 一貫性・上流追従・メタデータ drift・リポジトリ直下) に分け、Audit(監査)→ Verify(反証)の 2 フェーズの pipeline として設計していました。どのユニットを誰が見るかをここで割り当てている点に、「オーケストレーションを動的に設計する」性格がよく出ています。
計画フェーズ(21 ユニットを横断レーンとプラグイン単位に割り当て)

計画ができると、実行前に確認ダイアログが出ます。どんなフェーズで何をするか、そして 「大量のサブエージェントを並列に走らせるためトークン(使用量)を大きく消費する」「/workflows でいつでも停止できる」 という注意が明示されます。ここで Yes, run it を選ぶと走り出します(生成されたスクリプトを View raw script で確認したり、Tab で修正することもできます)。
確認ダイアログ(フェーズ構成とトークン消費の注意)


 ステップ 2: 数十エージェントが並列で走る
承認すると、計画した分のサブエージェントが一斉に立ち上がります。進捗ビューでは、各エージェントが Opus 4.8(1M コンテキスト) で動き、消費トークン・使用ツール数・経過時間がリアルタイムに更新されます。同時に走るのは一部で、残りは queued(順番待ち)として捌かれていきます。Audit フェーズ(21 エージェント)が終わると Verify フェーズに進み、最終的に 合計 40 エージェント が動きました。
並列実行の進捗ビュー(各エージェントが Opus 4.8 / 1M で稼働。プラグイン名は黒塗り)


 ステップ 3: 完了間際。メインのコンテキストはほぼ増えていない
完了間際(38/40 エージェント)のステータス行が象徴的でした。5 時間枠(5h)は 82% まで伸びているのに、メインセッションのコンテキスト(cx)は 9% にとどまっています。重い調査はサブエージェント側で行われ、メインに返るのは集約済みレポートだけなので、これだけ回してもメインの会話はほとんど膨らみません。
完了間際のステータス(38/40 エージェント / cx 9% = コンテキストはほぼ増えず / 5h 82%)


 反証ループの効果(誤検知の除外)
最後に届いたレポートの数字が、Verify(反証)フェーズの価値をはっきり示していました。


監査フェーズでの発見: 71 件 → 反証で 29 件(約 41%)を誤検知として除外 → 確定 42 件(high 0 / medium 18 / low 24)
あわせて、「漏れに見えたが自動化・意図でカバー済み」= 確認済みクリーン 143 項目 も明示

つまり、Audit フェーズが拾った発見のうち 4 割強は、別エージェントが「それは既存の仕組みでカバー済み / 意図的」と反証して落としてくれた わけです。冒頭で触れた敵対的レビュー(エージェントチームでは人手でデビルズアドボケイト役を立てていたパターン)が、誤検知のフィルタとして実際に働いていました。high が 0 だったのは、よく整備されたリポジトリらしい結果で、medium / low の棚卸し候補が手元に残りました。

 実際に回して感じた、エージェントチームとの差
前半では概念としてエージェントチームと比べましたが、実際に動かすと、規模以外にも挙動の差が具体的に見えました。


フェーズで分かれている: 今回は Audit(監査)→ Verify(反証)の 2 フェーズに明確に分かれて進みました。エージェントチームを手で組むときは「まず洗い出し、次に反証する」という段取りそのものを人間が指示しますが、Dynamic Workflows は計画フェーズでこの段取りごと設計してくれます。

エージェント同士は通信していない: エージェントチームの肝は teammate 同士が SendMessage で会話することでした。一方、今回の Dynamic Workflows では エージェント間の通信は見られませんでした。各サブエージェントは担当分を黙々と処理し、結果は司令塔(オーケストレーター)に集約されます。サブエージェントの素直な使い方、という印象です。

同時実行数は絞られている: 合計 40 エージェントが立ち上がりましたが、同時に動くのは 10 個程度 で、残りは queued(順番待ち)として順次捌かれていきました。一気に 40 並列ではなく、同時実行数を抑えながら流していく挙動です。

フェーズをまたいで先行できる(パイプライン): フェーズ 1(Audit)の全完了を待たず、監査が済んだユニットから先にフェーズ 2(Verify)へ流れて いきました。全部終わってから次へ進む硬いバリアではなく、準備できたものから次工程に送るパイプライン的な進行です。実際、Audit が 16/21 の時点で Verify が動き始めていました。

「人間が対等なチームを組んで会話させる」エージェントチームとは設計思想が異なり、司令塔(Claude)が段取りを決めて大量のサブエージェントを捌く という Dynamic Workflows の性格がよく出ていました。

 まとめ・所感
Dynamic Workflows は、Claude Code の使い方を「1 本のエージェントに順番にやらせる」から「オーケストレーションごと Claude に委ねる」へ一段引き上げる機能だと感じます。
これまでもサブエージェントで並列化はできましたが、大規模な分割や多段の検証まで体系立てて組むのはプロンプトのお膳立てに頼る部分が大きいものでした。そこを Claude が動的に設計し、敵対的レビューで収束まで回し、検証済みの 1 つの答えを返す。トークン消費は大きいものの、コードベース全体の調査や大規模マイグレーションのような「単一パスでは無理筋」だったタスクに正面から挑める手段が増えたのは大きい変化です。
どんなタスクにも万能というわけではなく、向き不向きがはっきりした機能 だと感じます。今回の体験と公式のユースケース[1:9]から整理すると、たとえば次のようなケースに向いていそうです。

コードベース全体を横断する調査(抜け漏れ点検・デッドコード洗い出し・依存関係の棚卸し)
数百〜数千ファイル規模の移行・リファクタ(レガシーのフレームワーク移行や言語移植)
検出した全項目に並列で検証をかけたいセキュリティ監査

共通するのは 「規模が大きい・横断的・検証が重い・単一パスでは無理筋」 という性質です。逆に、1〜数ファイルで完結する小さな修正や日常のちょっとした確認には、トークン消費の割に合いません。
当社カンリーでも、この見立てに沿って、長年手をつけられずにいたレガシー機能の移管 や セキュリティチェック に Dynamic Workflows を当てられないか検討しています。
初出時点ではリサーチプレビュー段階でしたが、冒頭の追記のとおりその後 GA へ移行しています。引き続き AI コーディングエージェントの動向を追い、業務への導入と外部発信を続けていきます。
