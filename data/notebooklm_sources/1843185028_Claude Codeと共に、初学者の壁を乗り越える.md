## 本文
みなさんこんにちは！株式会社TOKIUMでエンジニアをしている26卒の松本です。
早いもので、チーム本配属から1ヶ月が経ちました。実務の荒波に揉まれたこの1ヶ月間で、たくさんの壁に出会いました。そしてその度に自分なりの方法で壁を乗り越えようともがいたので、その軌跡を書いてみました！


 ① コードが読めず目が滑る、の壁
私が実務に配属されて、はじめにぶち当たった壁は、コードと睨めっこしても「目が滑ってしまう」現象です。いろいろ言葉を考えたのですが実体験からも「目が滑る」という表現がしっくりきます。
「目が滑る」現象を分解すると、読むための前提知識が足りなさすぎるということが大きな原因の一つだと思います。

ファイルの役割、呼び出し方といったルールが身についていない
瑣末な部分か重要な部分か、どうかを判断できない

結果として全ての行が同じ重みに見えてしまい、どこをどう読めばいいかわからず時間がいたずらに過ぎる。
この壁に対して自分がやったのは、いきなりコードを読もうとしないことでした。まず Claude Code に「このファイルは何をする係で、どこから呼ばれているのか、そしてそのファイルの中のこの部分は、ファイルの中でどんな役割を持つのか」を説明させて、全体の地図を先に描いてもらう。そのうえで、該当箇所の文法や、理解したいことを読み解いていくというやり方です。
最初に役割分解の地図が頭に入った状態だと、理解したい対象も少しとっつきやすくなるのです。


 ② 読めたことが定着しない、の壁
目が滑る壁を少し乗り越えたと思ったら、次の壁がすぐ来ました。
字面は追えるようになったけど、理解が定着せずに流れてしまう、という壁です。
自分なりにメモを取ったり、調べたりして「めっちゃ理解できた！」と感じたのに、いざ手を動かすと詰まる。
原因は単純で、理解できたのは抽象的な処理の流れであって、それを具体的にコードに翻訳することが定着していなかったのです。
では、①と②の壁は別物なのかというと、たどっていくと同じところに行き着きました。どちらも手元に照らし合わせるものが無いという話です。この部品は全体の中でどういう係なのか、この処理はどう書くのが定石なのか。そのどちらにも、当たりをつける材料が無い。
では逆に、経験者の方は何と照らし合わせているのでしょうか。仮説ですが、たぶん過去に見た似た形のコードなんだろうな、と思います。「このファイルは、前に見たあれと同じ作りだ」、「この処理は、前に書いたあれと同じ手順だ」。だから初見のファイルでも、全部読まずに当たりをつけられる。
自分はこの「似た形」のことを、型と呼ぶことにしました。そして、①で書いた「前提知識が足りない」の正体も、結局はこれなのではないかと思ったんです。
前提知識とは、プログラミングにおける「型」の数なのではないか。
「あ、これはあの型だ」と思えた瞬間、そのファイルは覚えるものではなく、思い出すものに変わります。だとすると、初学者の自分に足りないのは理解力ではなく、単純に型の在庫数なのではないか。経験と未経験の差も、この在庫の差にすぎないのかもしれません。
そしてこう考えたら、正直かなり気が楽になりました。それまでは「なぜこの形になっているのか」を毎回わかろうとしていたのですが、型に関しては、理由を考えたところで身につく気がしなかったんです。むしろ、考えるだけ無駄だなと感じる場面の方が多かった。
なので、そこは割り切ることにしました。型は理屈で理解するものではなく、接触回数で身につくものだと。そう置いてしまうと、やることは1つに絞れます。接触回数を、意志ではなく仕組みで増やせばいい。
幸いなことに①でも②でも、自分はずっと Claude Code に聞き続けていたので、詰まった瞬間も、勘違いしていた内容も、全部そのまま会話ログに残っていました。
なので、自分が学ぶ時には型カタログと思考ログを使って、蒸留し、ループを回していくという手法を考えました。

7月30日に「境界がわからなくなってる」と打ち込んだ1行が、いまは着手前に引ける型として手元にあります。次に似たようなタスクに取り組むときはこの型が2周目になります。
この仕組みで良かったと感じているのは、2つあります。
1個目は原文のまま残ること です。最初は要約して保存していたのですが、要約すると当時の切実さが消えてしまいます。原文で残すと当時の自分が何をわかっていなかったかが、そのまま再生できます。
2個目は想起が自動で起きること です。学びを貯めるだけでは、次なるアウトプットには繋がりにくい。かといって場面場面で、「あの時の学びを思い出そう」と意識し続けるのも難しい。今回の仕組み化で、タスク着手時に「昔やったあの型ですよ」と自動で想起されるので、ここが非常に効いています。②で書いた「型は接触回数で身につく」を、意志に頼らず積み上げられるようになりました。
このようにして、①と②の壁に出会ったことで、結果として自分に合う学習のループを構築できた、というのが、この1ヶ月の大きな進歩です。


 ③ 壁というより、気持ちの話
ところが、その学び方が回り始めた途端に、別のところに穴が空きました。「で、これは何のためにやってるんだっけ」です。
これは①②のように「できない」という壁ではありません。手は動くし、タスクも終わる。それでも引っかかる、という気持ちの話です。
学び方が定まるまでは、目の前のコードを読むだけで手一杯でした。そんなことを考える余裕が、そもそもなかったんです。少しだけ手が空くようになってはじめて、与えられたものをこなすだけ、という働き方に恐怖を感じるようになりました。
TOKIUMの志は「未来へつながる時を生む」です。入社を決めた理由の大きな部分は、この素晴らしい志に感銘を受けたことでした。それなのに、日々やっているのは目の前のタスクを片づけることで、そこと志がまったく繋がっていなかった。
今の自分の立場だと、まだお客様と直接接することがないので、自分のタスクのその先に誰がいるのかは、意識しないと一生見えないんです。
この引っかかりへの対策は超シンプルに2個考えました。
1個目は、PCの壁紙を志にすることです。本当にそれだけの対策ですが、それでもPCを開くたびに必ず目に入るので、「何のためにここに来たのか」を1日に何度も思い返すことができます。
2個目は、着手前ルーティンに「このタスクは誰の、どんな時を生むか」を問う一手を足した ことです。①②で出てきた永続メモリに、そのまま置いてあります。
たとえば、AI OCRまわりのタスクならこの問いを通すと、請求書がデータになるのを画面の前で待っている、ある経理の方のその待ち時間を減らして時を生む仕事に変わります。そうやって、自分の仕事の先にいるお客様を想像して、エンジンがかかった状態から始めるようにしました。
この意味づけは、正直こじつけでも構わないし、間違っててもいいと思っています。それでも、外から与えられた理由だけで動いているときより、自分で見つけた理由で動いているときの方が、はるかに長く、強く走れる。少なくとも私の場合は、そうでした。


 おわりに
書き終えてから気づいたのですが、3つとも向き合い方が同じ形をしていました。
①で地図をClaude Codeに描いてもらったのも、②で詰まりを自動で残して型を引いてもらうようにしたのも、③で志を壁紙にしたのも、結局は自分の頭だけでやろうとするのをやめて、外側に預けただけです。
これからも新たな壁に出くわした時には、またこうやって分解して、自分に合うやり方を探して、仕組みへ落としていきたいと思います。1ヶ月後には、まったく別の壁の話を書いているかもしれません。
