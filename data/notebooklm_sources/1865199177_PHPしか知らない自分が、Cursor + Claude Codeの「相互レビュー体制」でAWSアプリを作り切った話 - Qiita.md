## 本文
PHPしか知らない自分が、Cursor + Claude Codeの「相互レビュー体制」でAWSアプリを作り切った話

社内AI駆動ハッカソン(お題: チーム横断・部署横断のコミュニケーションを生むもの)の参加記録です。
普段はPHPでの開発がメインで、TypeScript・AWS CDK・DynamoDBはほぼ触ったことがない状態からのスタートでした。


この記事で言いたいこと

Cursor(実装担当)とClaude Code(設計・レビュー担当)に役割を分けて相互レビューさせると、専門外の技術スタックでも一人でプロダクションのAWSアプリを完成させられる
ただしAIに丸投げすると本番でしか出ないバグを量産する。そこを埋めたのはspec-workflow(requirements.md / design.md / tasks.md)による仕様の明文化と、実機・本番相当環境での動作確認を徹底したこと

良かった話ばかりではなく、平日にコツコツ進めるつもりが別システムの初回リリースと日程が丸かぶりして、まともに時間が取れない中でどう進めたかという裏話も書く


作ったもの
「大変だったこと発表会 〜笑ってもらえば全部チャラ〜」という、普段あまり接点のない部署間で「今月大変だったこと」を匿名で投票・コメントし合い、月末に結果発表(演出付き)をするという、ゆるい社内交流アプリです。

フロントエンド: Vite + TypeScript(フレームワークなし)
バックエンド: AWS Lambda(Node.js) + DynamoDB(シングルテーブル設計)
配信: S3(ブロックパブリックアクセスON) + CloudFront + OAC
CI/CD: Bitbucket Pipelines(OIDC、アクセスキーレス)

「AI活用の質」という評価軸に対しては、プロダクト自体にAI機能を組み込むのではなく、開発プロセスそのもの(後述の役割分担・相互レビュー)で応えることにしました。

裏話: 平日コツコツのつもりが、まったく時間が取れなかった
当初は「平日の空き時間にコツコツ進めよう」というくらいの気持ちで始めたのですが、ちょうど同じ時期に自分が主担当をしている別システムの初回リリースが控えていて、日中はほぼそちらに時間を取られる状況でした。
結果として、ハッカソンの想定工数(8時間)を確保したとは言いづらい状態です。正直に書きます。
ただこの「まとまった時間が取れない」という制約こそが、今回の体制(Cursor + Claude Codeの役割分担)が効いた理由でもあります。細切れの時間でも、
「今日はClaude Codeに設計だけ頼んで、明日Cursorに実装を投げる」
「レビューコメントだけ先に読んで、対応は空き時間にまとめて」
のように作業を分割・並列化しやすかったからです。

ポイントは、Claude Codeにレビューさせるとき「コードを読んで大丈夫そうです」で終わらせず、実際にサーバーを立てて叩かせる/ブラウザで操作させることを徹底した点です。理由は次の「実際に踏んだ地雷」を見てもらえれば分かると思います。

実際に踏んだ地雷(コードレビューだけでは見つからなかったバグ)
いずれも「コードとしては一見正しく見える」「ローカルのdocker-compose環境では問題が起きない」という共通点があり、実機・本番相当のAWS環境で動かして初めて発覚したものです。

1. CDKでSSMのSecureStringパラメータが作れない
cdk synth は通るのに cdk deploy だけが失敗する、というやつです。CloudFormationは AWS::SSM::Parameter の SecureString タイプ作成に未対応という既知の制約で、通常の String 型に変更し、値はデプロイ後に手動更新する運用に変えました。

2. CORSヘッダーの二重付与
Lambda Function URL自体のCORS設定と、アプリコード側で組み立てていた Access-Control-Allow-Origin ヘッダーが両方付与され、ブラウザ側で「同じヘッダーがカンマ区切りで2つ」という扱いになり拒否されていました。curlでは気づけず、Playwright(ブラウザ自動操作)でコンソールエラーを見て初めて発覚しました。

3. dynamodb:UpdateItem 権限の抜け
投票処理は TransactWriteItems でDynamoDBに書き込んでいたのですが、トランザクション内で Update 操作をするには TransactWriteItems の権限に加えて UpdateItem 権限も別途必要でした。ローカルの DynamoDB Local はIAMをそもそも見ないため、ローカルでは何度実行しても再現せず、本番でCloudWatch Logsを見て初めて AccessDeniedException に気づきました。

4. SameSite=Lax だとcrossoriginでCookieが飛ばない
フロントとAPIをローカルでも本番でも別オリジンにしていたため、SameSite=Lax のセッションCookieが fetch() に乗らず、ログイン直後から401になっていました。SameSite=None; Secure に変更し、ローカルの http://127.0.0.1 はChromiumの「信頼できるオリジン」特例で Secure Cookieも通ることを利用しました。

5. Bitbucket Pipelinesが古いプレースホルダページをデプロイし続けていた
cd frontend && npm run build の後に cd .. し忘れていたため、後続の成果物チェックが frontend/dist(空)を見てしまい、疎通確認用の仮ページがずっとデプロイされ続けていました。ビルド自体は毎回成功と表示されるため、パイプラインのログをスクリーンショットで見せて初めて気づけたバグです。

これらはすべて、「コードは正しそうに見える」→「実際に動かす」→「初めて壊れているのが分かる」の順で発覚しました。AIによるコードレビューは「読んで気づけるバグ」には強いですが、「実行して初めて分かるバグ」には無力です。ここを人間(というかレビュー担当のClaude Code)に実際に手を動かして確認させることが、この体制の一番のキモだったと思っています。


spec-workflow: requirements.md / design.md / tasks.md による仕様の明文化
Cursorに実装を丸投げすると、細部の仕様(「投票は何度でもできるのか」「削除できるのは誰か」等)がその場の判断で決まってしまい、後から「あれ、これで合ってたっけ」となりがちです。
そこで、機能ごとに .spec-workflow/specs/<feature-name>/ というディレクトリを切り、


requirements.md: 何を作るか、どんな絶対厳守ルールがあるか

design.md: どう作るか。あとから見返す用に、発生した不具合と対応も追記していく

tasks.md: 実装のチェックリスト。実施した動作確認も残す

という3点セットをClaude Codeに作らせ、それを見ながらCursorに実装させました。これにより、

「なぜこの実装になっているか」が後から追える
レビュー担当(Claude Code)も、requirements.mdに書かれた絶対厳守ルール(個人情報を含めない、他人のデータを消せないようにする等)と照らして具体的にレビューできる
途中でセッションが切れても、ドキュメントを読み直せば再開できる

という効果がありました。特に「絶対厳守ルール」(社内限定アクセスのみ、アクセスキー直書き禁止、S3のブロックパブリックアクセスは外さない、IAMに Action:*/Resource:* を書かない、他人のデータを消せないようにする、XSS対策)を最初に明文化しておいたのは効きました。AIは「動くもの」は作れても、明示的に言われないと安全側に倒してくれるとは限らないためです。

この返信、該当ファイルを実際に開いて行番号まで特定し、37個ある試験項目の一つひとつを実装と突き合わせて、優先度付きでまとめるという作業です。人間のレビュアーが同じ精度・網羅性でやろうとしたら、対象ファイルを何度も往復しながら数時間はかかる作業量だと思います。これがレビュー依頼を出してから数分で返ってきます。
もちろん指摘の中には「これは仕様通りで問題ない」という誤検知も混じるので、最終判断は人間が行う必要はありますが、「まず全項目を機械的に洗い出してもらい、人間は判断だけに集中する」という分業には十分な精度でした。

気を付けたこと・気を付けるべきこと


コードレビューだけで完了とみなさない: 「読んで大丈夫そう」と「動かして大丈夫」は別物。特にIAM権限・CORS・Cookie周りは実機で確認しないと分からない

絶対に譲れないルールは先に文章化する: 「個人情報を出力に含めない」「S3のブロックパブリックアクセスは外さない」等、AIが自発的に守ってくれるとは期待せず、requirements.mdやAGENTS.md的な指示ファイルに明記する

AIの指摘を鵜呑みにしない: レビューコメントには実装と食い違う誤検知も混ざる。最終的にどれを直すかは人間が判断する

役割を分けすぎて責任があいまいにならないようにする: 「設計はClaude Code、実装はCursor」で終わらせず、最終的に本番で動かして確認する担当(この場合は自分)を明確にしておく

専門外の技術でも、仕様さえ明文化されていれば実装・レビューはAIに任せられる: 逆に言うと、仕様が曖昧なまま進めると専門外の技術ほど「それっぽいが間違っている」実装に気づけない


おわりに
PHPしかほとんど触ったことがない状態から、TypeScript + AWS CDK + DynamoDBで一つのアプリをリリースまで持っていけたのは、Cursor/Claude Codeの実装力そのものより、「役割を分けて、仕様を文章化し、実機で確認する」という体制を作れたことが大きかったと感じています。
平日まとまった時間が取れない中でも進められたのは副産物です。細切れの時間でも「設計を頼む」「レビューを頼む」「対応する」を非同期に回せたので、思ったより無理なく完走できました。
