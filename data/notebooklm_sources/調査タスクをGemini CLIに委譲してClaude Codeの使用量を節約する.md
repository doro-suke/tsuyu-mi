## 本文
はじめに
Claude Codeは優秀なコーディングエージェントですが、使用量の制限が厳しいです。特に、複数ファイルを読んで現状を把握するような調査系のタスクは、難易度のわりに使用量を大量に消費します。
できればClaude Codeの容量は設計やコーディングなどの思考力が求められるタスクに温存しておきたいところです。そこで考えたのが、調査系のタスクを Gemini CLI に委譲するというアプローチです。Gemini CLIはGoogleが提供するコーディングエージェントで、Google Workspaceを契約している会社であれば契約済みであることが多いと思われます。思考力やコーディング能力では Claude Code に及びませんが、容量に余裕があります。
この特性を活かして、単純な調査はGeminiに任せ、Claude Codeの使用量を節約する方法を紹介します。

 まずは素朴にやってみる
Claude Codeに対して、以下のようなプロンプトを投げてみます。
@./syncable-api にて、devブランチに対して最もコミットがビハインドしているブランチはどれか調査してください。調査はgeminiに委譲して下さい。
Claude CodeはGemini CLIの起動自体はうまくやってくれます。以下のようなコマンドが生成されて実行されます。
gemini -p "このリポジトリで、origin/devブランチに対して最もコミットがビハインド（遅れている）しているリモートブランチを調査してください。git fetch originは既に実行済みです。git rev-list --count <branch>..origin/dev を使って各ブランチのビハインド数を算出し、上位10件をビハインド数の降順で報告してください。"
しかし、この素朴なやり方には以下の課題があります。

 gemini-3-pro-previewモデルで起動してしまう
Gemini CLIではモデルを選択できますが、モデルを指定しないとProモデルがデフォルトで選ばれます。Proモデルを使うと、必要以上に深くコードベースを読みに行こうとして動作が遅くなります。さらに、私の環境ではエージェントが無限ループにはまって処理が終わらないことも増えました。頻度は高くありませんが、調査のたびに気にするのはストレスです。Geminiに委譲するような調査タスクに求めるのは速さなので、Flashの方が適しています。

 Claude Codeが結果を待ちきれない
Claude Codeは外部コマンドをBashツール経由で実行します。このBashツールにはデフォルトで2分のタイムアウトが設定されており、Geminiの調査がそれを超えると、Claude Codeはタイムアウトと判断して自分で調査を始めてしまいます。これではトークンの節約になりません。

 Claude CodeのSkillsで解決する
これらの課題は、Claude Codeの Skills 機能を使うことで解決できます。Skillsとは、 .claude/skills/ ディレクトリにMarkdownファイルの入ったフォルダを配置することで、Claude Codeに特定のワークフローを教える仕組みです。
以下のようなskillを作成しました。全文を掲載します。

.claude/skills/gemini/SKILL.md
---
name: gemini
description: geminiにタスクを委譲するやり方が記載されたskill。調査を依頼された時、あるいはgeminiに委譲するように指示された時に発動する。
---

当スキルが起動された時、まずはユーザーにgeminiに委譲するか聞くこと。noという返答が返ってきた場合は、当スキルを終了し自分で調べること。yesという返答が返ってきた場合は、以下の手順でgeminiに委譲すること。

geminiとはgemini cliのことである。gemini cliは以下のコマンドで起動できる。プロンプトの部分はgeminiに指示したい内容を記載する。

```bash
cd <調査対象のディレクトリ> && gemini -sy --model flash -p "プロンプト" 2>/dev/null
```

- geminiの起動には時間がかかるため、geminiからの明確な応答があるまで次に進まないこと。Bashツールの timeout を必ず 600000（10分）に設定し、出力を待つこと。
- バックグラウンド実行時の注意
  - タイムアウトによりBashコマンドがバックグラウンドタスクとして継続された場合、途中の出力ファイルを読んで結果を判断してはならない。
  - 出力に429エラーやリトライログが含まれていても、それは処理の途中経過であり、最終結果ではない可能性が高い。
  - 必ずバックグラウンドタスクの完了通知を待ってから出力ファイルを読み、結果を報告すること。途中経過を見て失敗したと判断しないこと。

このskillのポイントは以下の通りです（なお、-s フラグはサンドボックスモード、-y フラグは確認プロンプトの自動承認を意味します）。


--model flash でFlashモデルを指定する：Proモデルで起動される問題を防ぎます
タイムアウトを最大に設定し、出力を待つことを明示する：Claude CodeがGeminiの応答を待たずに自分で動き出す問題を防ぎます

これにより、Claude Codeの使用量はGeminiからの応答を読む数百トークンだけで済むようになります。

 向いているタスク・向いていないタスク
すべてのタスクをGeminiに委譲できるわけではありません。使ってみた感触を整理します。

向いているタスク：

コードベースの調査全般（処理の概要を把握する、特定の処理がどこに書かれているか探す、ディレクトリ構成を確認するなど）


向いていないタスク：

設計の相談や方針の判断
コーディング（特に複数ファイル・複数クラスにまたがるもの）
どうするべきかといった論理的な判断が必要なもの




 実際に効果はあったのか
厳密に計測したわけではありませんが、体感としてClaude Codeの使用量に明らかに余裕ができました。調査のたびに使用量が削られる焦りが減り、本来使いたいタスクに集中して使えるようになりました。
一方で万能というわけではありません。GeminiはClaude Codeと比較すると調査が遅いことが多いですし、複雑な問題では結果が誤っていることも少なくありません。あくまで単純な調査の代行として割り切って使うのが良いです。また、正直なところ、Claude Codeの上位プランを契約するのが最もストレスのない解決策であることは変わりません。
ただ、チームの予算や契約の都合ですぐにはプラン変更できないケースもあります。そのようなときのワークアラウンドとしては悪くない程度の有用性に留まりますが、Claudeの使用量上限に悩まされている場合は一度お試し下さい。
