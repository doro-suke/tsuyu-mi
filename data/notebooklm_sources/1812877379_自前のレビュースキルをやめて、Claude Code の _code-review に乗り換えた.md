## 本文
Claude Code でのコードレビュー、私はレビュー用の自前スキルを作り込んで回していました。
ところが先日、久しぶりに公式の /code-review を叩いたら、指摘が重大度で色分けされて並ぶようになっていて、どれから直すかが見た瞬間に分かる。
これで十分では、となって、しばらく公式コマンドで進めることにしました。
ただ、effort 引数や --fix・--comment といったオプションを実測した情報はあまり見かけません。
そこで個人開発リポジトリの実 PR を題材に、effort の差・PR へのコメント投稿・自動修正をひととおり検証しました。
先に一番大きかった結果を書いておくと、同じ diff でも effort 次第で指摘は 1件と 10件に分かれました。

 /code-review の基本動作
/code-review は、いま作業しているブランチの diff をレビューするコマンドです。
対象は「upstream に対して先行しているコミット＋未コミットの変更」で、引数にファイルパス・PR 番号・ブランチ名・main...my-feature のような範囲を渡せば対象を変えられます。
実行すると、走るのはバックグラウンドのサブエージェント。
別のコンテキストウィンドウを持つので、レビュー中も手元の会話を続けられて、完了すると結果だけが会話に届きます。
届いた指摘には重大度のマーカーが付きます。
公式ドキュメントの定義はこの3段階です。

 effort 引数の実測比較
/code-review には low / medium / high / xhigh / max の effort を渡せます。
公式ドキュメントの説明では、low・medium は「確信度の高い指摘だけを報告する（偽陽性が少ない）」、high 以上は「網を広げる（確信度の低い指摘も含み得る）」という位置づけです。
同じ PR に /code-review low と /code-review high を1回ずつかけた結果がこちらです。

件数と時間だけでなく、実行のかたちまで変わりました。
low は1体のバックグラウンドエージェントがサッと見て終わり。
一方 high では Dynamic Workflow（複数のエージェントが役割分担して並列に走る Claude Code の仕組み）が立ち上がり、観点ごとの複数の finder と、指摘ごとに独立した verifier が同時に動いていました。
high の完了時には「候補として挙がった27件のうち5件は検証段階で反証されたため報告に含めていない」という内訳まで表示されました。
報告そのものにも件数の上限があり、残った候補をランク付けした上で絞り込む仕組みなので、27 − 5 = 22件が全部届くわけではありません。
今回手元に届いたのがその上位10件です。
網を広げつつ、怪しい候補は検証で落とし、確度の高い順に絞って報告する、という動きが画面から見て取れます。
中身の重さにも差がありました。
low が報告した1件は「将来のズレに備える防御的な指摘」で、現時点の実害はないもの。
しかも報告された行番号は :332 と、232行しかないファイルに存在しない位置で、本体セッションが訂正を添える一幕もありました。
対して high だけが拾った9件には、今回の PR で追加した CLI が、読み取り専用と明記しておきながら実際には DB に書き込んでいたという指摘が含まれていました。
この PR で持ち込んだ新規のバグなので、マージ前に捕まえられたのは大きいです。
なお low の1件は high の10件の中にも含まれていたので、今回の1回に関しては、low は「high の上澄みだけを最速で見る」という関係になっていたわけです。


レビュー結果は手元で読んで終わりにせず、GitHub PR に置いてくることもできます。
--comment を付けると、レビューの指摘が PR のインラインコメントとして投稿されます。
/code-review high --comment
検証では、high が報告した10件の指摘すべてが、PR の該当行にインラインコメントとして付きました（10件中10件成功）。
サマリーコメントは付かず、インラインのみなので、PR の会話タイムラインは汚れません。
動きとしては、レビュー完了後に本体セッションが対象の PR を自動検出し、gh コマンドで1件ずつ投稿していきます。
セルフレビューの結果をそのまま PR に残しておけるので、「あとで直す分」をレビューコメントとして積んでおく使い方ができます。
ひとつ注意点があります。
自分の環境（許可設定をゆるめにした auto mode）では、確認なしで公開 PR への投稿まで走りました。
公開リポジトリで試すときは、指摘が外から見える場所に残ることを頭に入れてから付けたほうがいいです。

 --fix での自動修正適用
指摘を読んで自分で直す代わりに、その場で直させる選択肢もあります。
--fix を付けると、レビューで見つかった指摘がそのまま working tree に適用されます。
/code-review high --fix
検証では、high が報告した10件が全件適用されました。
適用前の確認プロンプトはありません。
つまり --fix を付けること自体が「直してよい」の意思表示になります。
適用のされ方は、想像していた「機械的なパッチ当て」よりだいぶ丁寧でした。

修正と合わせて回帰テストを追加する
lint・テストスイート（1753件）・スモークテスト・ドキュメントビルドを通してから完了報告する
10件のうち1件は「この挙動は設計意図なので変えない」と判断し、挙動はそのままに検出可能性の問題だけを解消する

指摘に盲従せず、設計の文脈を読んで直し方を選んでいます。
最終的な diff は12ファイルで +705/−161。
自動コミットはされないので、内容を確認してからコミットする流れになります。


 /review・ultra との使い分け
レビュー系のコマンドは /code-review のほかに /review <pr> と /code-review ultra があります。
公式ドキュメントの比較表をもとに、対象と向き先を整理するとこうなります。



コマンド
対象・実行場所

/review <pr>

/code-review ultra
diff または PR・クラウド

ultra はクラウドのサンドボックスで多数のレビューエージェントを並列に走らせ、報告前に全指摘を独立に再現・検証するモードです。
所要は5〜10分程度、Pro / Max プランには1回限りの無料枠が3回あり、その後は1回あたり5〜25ドルの従量課金になります。
私はまだ実行していないため、ここは公式ドキュメントの情報です。
私自身のレビューは、いまのところローカルの /code-review をマージ前に1回だけ回す形に落ち着いています。

 まとめ
/code-review は重大度の色分けで着手順が決まり、effort で深さを選べて、--fix と --comment で修正・共有まで1コマンドで繋がります。
私の運用は前述のとおり「マージ前に1回だけ回す」です。
effort はその1回に何を求めるか次第ですが、実測で high だけが拾った指摘の重さを見ると、トークンと時間に余裕があるなら high を選んでおくのが安全だと考えています。
その後、欠陥をあらかじめ7件仕込んだ PR で low と high を3回ずつ測り直したところ、この結論は一段変わりました。
critical と high の欠陥は3回とも low が全部拾っていて、effort を上げて増えたのは medium と low の1件ずつだけです。

自前スキルからの乗り換えは、もうしばらく続けてみます。
