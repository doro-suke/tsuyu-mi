## 本文
はじめに
こんにちは！
株式会社エクスプラザのhyodoです！
最近は、台本もナレーションも図解も、ほとんどの工程をAIに任せて動画を量産できるようになりました。指示を一言投げれば、それっぽい動画が一本出てきます。
でも、いざ「自動で量産できる」状態になると、こんな不安が出てきませんか？

「AIが書いた台本、数字がしれっと間違ってないか？」
「ナレーション、固有名詞を変な読み方してないか？」
「未完成のテロップが残ったまま、間違って公開されたら……」

動画が作れるようになること自体は、もう難しくありません。本当の壁は別のところにあります。

速く作れるようになるほど、ボトルネックは「生成」から「信用して世に出すこと」へ移る。

私は情報処理安全確保支援士の監修付きで、セキュリティ解説のショート動画を運用しています。監修チャンネルでは、誤った情報や事故的な公開が一発で信用を失います。だから「速く作る」よりも、作ったものを信用して出すための仕組みに力を入れています。
この記事では、パイプライン全体の作り方ではなく、その中の 2枚のゲート に絞って書きます。


品質ゲート：生成したものが正しいか（中身のリスク）

安全ゲート：間違ったもの・未完成のものが世に出ないか（公開のリスク）


 前提とする構成
細部は本題ではないので、ここでは軽く触れるだけにします。司令塔は Claude Code、動画は React ベースのフレームワークでコードとして実装、ナレーションは Gemini の TTS、アップロードは YouTube Data API v3、レビュー管理は GitHub Issues、という構成を前提にします。動画を「コードで書く」話や図解の作り方はこの記事では扱いません。あくまで品質と安全の2点に集中します。

 なぜ「生成」より「公開」が難しいのか
手で1本ずつ作っていた頃は、作る過程で自然と中身を確認していました。台本を書きながら数字を調べ、ナレーションを録りながら読みを直し、書き出した動画を見てから公開する。工程が遅いことが、結果的にチェックを兼ねていたわけです。
自動化すると、この「遅さによるチェック」が消えます。そして残るのが2つのリスクです。


中身のリスク：AIが書いた台本の数値が古い、固有名詞の読みが間違っている、といった「内容の誤り」。

公開のリスク：レビュー前の動画、プレースホルダが残った概要欄、そういう「出してはいけないもの」がそのまま公開される事故。

監修チャンネルにとって、前者は信用問題に直結し、後者は取り返しがつきません。量産する以上、この2つは「気をつける」では守りきれません。仕組みで止める必要があります。

 設計の原則：生成物は「疑う」、危険な操作は「止める」
具体的なゲートの話に入る前に、土台にしている考え方を3つ挙げます。


生成物は人間の目だけで守らない。 全数を耳と目で確認するのは、量産と両立しません。機械的にチェックできるものは機械に任せます。

公開のような危険な操作は、人間承認か「構造」で止める。 「うっかり公開」が起きないように、運用ルールではなく仕組みで不可能にします。

チェックは安いうちに早く。 同じ誤りでも、台本段階で直すのと公開後に気づくのとでは、コストが桁違いです。リスクごとに、できるだけ前段にゲートを置きます。

この原則を、パイプラインのどこに当てはめているかを図にすると次のようになります。
ここから、2枚のゲートを順に見ていきます。

 品質ゲート：生成したナレーションをASRで「往復検証」する
まず中身のリスクです。「中身の正しさ」には、台本の 事実 が合っているかと、ナレーションの 読み が合っているか、という2つのレイヤーがあります。事実のほうは台本段階で別途チェックしているので、ここでは後者、音声の読みをどう自動検証するかを掘り下げます。

 TTSは便利だが、黙って読み間違える
Gemini の TTS にテキストを渡せば、自然なナレーションが返ってきます。ただ、固有名詞や略語は平気で読み間違えます。たとえば「情報処理安全確保支援士」を略した俗称をそのまま渡すと、まったく別の語として読まれることがあります。
問題は、TTSが間違えても何も言ってこないことです。音声ファイルは正常に生成されるので、再生して耳で聞かない限り誤読に気づけません。かといって量産する全本のナレーションを毎回フルで聞いていたら、自動化した意味がなくなります。

 出てきた音声を、もう一度文字に戻して照合する
そこで、生成した音声を ASR（音声認識）で文字起こしし、元の台本と照らし合わせて合否を判定します。AIが作ったものを、別のAIで検証するわけです。1セリフごとに、おおまかに次の流れで回します。


生成：Gemini TTS でセリフを音声化する。

無音トリム：前後の無音をカットし、末尾を軽くフェードする。

文字起こし：Gemini の ASR で音声を書き起こす。

照合：書き起こしと台本を突き合わせ、合否を判定する。

リトライ：不合格なら生成からやり直す（上限回数まで）。

照合のキモは「何をもって合格とするか」です。私は2つの条件を使っています。ひとつは、台本の 冒頭と末尾に必ず入るアンカー語 が書き起こしに含まれているか。もうひとつは、書き起こしと台本の 文字数比 が一定の範囲に収まっているか。これだけで「冒頭か末尾がごっそり抜けた」「丸ごと別物になった」といった大きな事故を弾けます。

tools/make_narration.py
def is_valid(script, transcript, head, tail):
    # 記号を落としてから比較する（句読点や括弧は誤差になりやすい）
    strip = lambda s: "".join(c for c in s if c not in "、。 　,.!?「」")
    body = strip(transcript)

    # 冒頭・末尾のアンカー語が書き起こしに含まれているか
    if head and head not in transcript:
        return False
    if tail and tail not in transcript:
        return False

    # 台本に対する文字数比が許容範囲か（極端な過不足を弾く）
    ratio = len(body) / max(1, len(strip(script)))
    return 0.55 <= ratio <= 1.6

合格したセリフからは、ついでに 合計フレーム数（フレームレート換算） が手に入ります。これは後段でシーンの尺を決めるときにそのまま使えるので、検証と尺計算を一度にこなせます。

 誤読は「読ませる前」に潰す
検証で弾くだけでなく、そもそも誤読されにくいテキストを渡すのも効きます。台本を書く時点で、次のような前処理を入れています。


英字・略語はカタカナにする：SMS →「エスエムエス」、AI →「エーアイ」のように、読みをそのまま文字で与える。

誤読しやすい固有名詞は正式名称で書く：俗称や略称は別の語に化けやすいので、フル表記にする。

「読みのゆれを後段で吸収する」より、「ゆれない形で渡す」ほうが、結果的にリトライ回数が減ります。

 実務の罠：偽陰性が出る
この検証、完璧ではありません。同音異義語や、かな表記と漢字表記のゆれ（たとえば「あやしい」と「怪しい」、「二段階」と「2段階」）で、正しく読めているのに不合格になる ことがあります。

機械の検証は「全部を耳で確認する作業を減らすため」のものであって、人間の最終判断を奪うものではない、というスタンスで運用しています。

 安全ゲート：間違っても「公開できない」構造を作る
次は公開のリスクです。ここでの方針は一貫しています。「気をつけて公開する」のではなく、「間違ったものは公開できない」状態を作ること。運用ルールは疲れていると破られますが、構造は破られません。3段階で守っています。

 (1) アップロードと管理で「鍵」を分ける
YouTube Data API のトークンを、用途で2つに分けています。


アップロード用：動画を上げることだけができる、権限の狭いトークン。

管理用：タイトルや概要の更新、公開状態の変更、削除など、影響の大きい操作ができるトークン。

日々のアップロードは前者だけで回し、公開状態を触る操作は後者に限定します。「動画を上げる権限」と「公開状態を変えられる権限」を同じ鍵に持たせない、という分離です。これだけで、自動化スクリプトが暴走しても、勝手に公開状態を切り替えるような事故が起きにくくなります。

 (2) そもそも「公開状態で上がらない」仕様を利用する
YouTube Data API には、審査を通していないプロジェクトからのアップロードは強制的に非公開（private）になるという挙動があります。これは普段は制約ですが、安全装置として見ると非常に都合がいい。
つまり、スクリプト側で公開状態に何を指定していようと、仕様のレベルで公開アップロードが起きない。設定ミスやコードのバグで「うっかり公開」が、構造的に発生しないわけです。

 (3) アップロード直前に「未完成サイン」を検出する
最後に、アップロードする直前で概要欄をチェックし、未完成を示す語が混ざっていたら処理を止めます。レビュー用のメモやプレースホルダが残ったまま世に出ることを防ぐゲートです。

tools/release_batch.py
def assert_publishable(description: str) -> None:
    # 未完成・レビュー用を示す語が残っていたら中止
    placeholders = ["レビュー用", "非公開", "placeholder", "TODO", "仮"]
    found = [w for w in placeholders if w in description]
    if found:
        raise SystemExit(f"中止: 概要欄にプレースホルダ語が残っています -> {found}")

    # 公開用フォーマットの最低条件（長さ・チャンネルの定型句）を満たすか
    CHANNEL_TAG = "@your-channel-handle"  # 自分のチャンネルの定型句に置き換える
    if len(description) < 40 or CHANNEL_TAG not in description:
        raise SystemExit("中止: 概要欄が公開用フォーマットになっていません")

公開予約は、この3段階を通り、かつ後述の人間レビューで承認された動画にだけ適用します。承認後は、指定した時刻に予約投稿（publishAt）するだけです。

アップロードは常に非公開で行い、公開は「GOが出たものだけ」。これを徹底すると、事故公開は「気をつける問題」ではなく「起きない仕組み」になります。


 どこを人間に残すか：自動と承認の境界線
ここまで自動化の話をしてきましたが、これは完全無人ではありません。むしろ、人間が握るべきところを明確に残すための設計です。人間がやるのは2つだけにしています。


ネタの方向性を決める（何を作るか）

公開GOを出す（出していいかを最終判断する）

レビューは GitHub Issue に集約しています。非公開URLとローカルファイルで中身を確認し、Issue 上で「承認」か「修正依頼」かを返すだけ。判断を非同期にできるので、作る側と確認する側が同じ時間に張り付く必要がありません。
そして、良かった点・直した点を フィードバックとして蓄積し、次回以降の生成に反映します。同じ指摘を繰り返さないようにしておくと、回を追うごとに人間が直す量は減っていきます。これは「人間承認」という安全の最後の砦を、回すたびに軽くしていく仕組みでもあります。
線引きの基準はシンプルです。退屈で間違えやすい工程は機械に渡し、創造性（ネタ選び）と最終責任（公開判断）は人間に残す。 自動化は人間を外すためではなく、人間が本当に見るべきところに集中するためのもの、という整理です。

 まとめ
AIで量産する時代に効くのは、「速く作る」より「信用して出す」ための設計です。私が置いている2枚のゲートを振り返ります。
生成物は信用しない前提で、機械が検証する。 ナレーションは ASR で往復検証し、合格するまでリトライ。固有名詞の誤読は、読ませる前の前処理で潰す。判定は目安なので、偽陰性は耳で拾う。
公開という危険な操作は、構造で止める。 トークンの権限分離、強制非公開の仕様の利用、概要欄の未完成サイン検出。事故公開を「気をつける」から「起きない」へ。
チェックは安いうちに早く。 台本→音声→公開と、リスクの種類ごとに別のゲートを置く。後段で気づくほど、直すコストは上がる。
人間は「ネタ」と「公開GO」だけ握る。 自動化するのは退屈で間違えやすい工程。創造性と最終責任は人間に残し、レビューのフィードバックで承認の負担を減らしていく。
「生成を疑い、公開を仕組みで守る」。この2点を入れておくと、量産してもチャンネルの信頼性は落ちません。動画に限らず、AIに何かを量産させて世に出すパイプラインなら、同じ考え方が使えるはずです。
