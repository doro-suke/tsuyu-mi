## 本文
この記事では2DドットブラウザゲームのプロトタイプをグラフィックやBGM・SEも含めて作成してくれるテンプレートプロジェクト browser-game-prototype を紹介します。

 こんな人に読んでほしい

ゲームを作ってみたいけど、何から手をつけていいかわからない人
簡単にブラウザゲームのプロトタイプを作りたい人
React や Phaser、TypeScript に触れたことがない初心者


 前提・環境
このテンプレートは以下のバージョンに対応しています。

Phaser 4
React 19.0.0
Vite 6.3.1
TypeScript 5.7.2

必要な環境は次のとおりです。


Node.js — 依存関係のインストールや npm 経由でのスクリプト実行に使います

uv — アセット生成スキルが Python（Pillow）スクリプトを実行するために使います

Claude Code — .claude/ 以下のルール・スキルを使った開発に必要です


 このプロジェクトで何ができるか
「○○なゲームを作りたいです」と Claude Code に伝えるだけで、要件定義・設計・実装・アセット生成までを AI が一貫して進めてくれるテンプレートです。

 AIがやってくれること

要件定義 → 外部設計 → 内部設計 → アセット生成 → TODOリスト作成 → 実装、という順序の提案と進行
背景画像・スプライト・BGM・SE といったアセットの自動生成
ReactによるUIとPhaserによるゲームロジックの実装


 使い方


リポジトリをクローンする
git clone https://github.com/aya7712/browser-game-prototype.git <game-name>-prototype


依存関係をインストールする
npm install


Claude Code を起動して、作りたいゲームを伝える
例えば以下のように伝えてみます。
植物を育てて楽しむゲームを作りたいです。
クリアーはありません。種を買い、育て、収穫し、売るというサイクルです。
植物を植えると、植えた状態、芽が出た状態、少し育った状態、花が咲いた状態、実がなった状態に成長していきます。
時間経過で成長します。
実がなると収穫できます。
植物はトマトとピーマンの二種類です。

 要件定義

 コンセプト
植物を育てる「育成サイクル」を楽しむ、まったり系の放置型農園ゲーム。
種を買い、畑に植え、時間経過で成長を見守り、実った作物を収穫して売る——というシンプルなループを繰り返す。
クリア（終了条件）は設けず、プレイヤーが自分のペースで畑を育て続けられることを目指す。

 ターゲットプレイヤー

勝敗や競争ではなく、ゆったりと植物の成長を眺めて楽しみたい人
スマホゲームの「放置・育成系」が好きな人
短時間の操作を1日に何度か行い、長期間にわたって遊び続けるプレイスタイルを好む人


 機能要件


 プレイヤーとして、お店で種（トマト・ピーマン）を購入したい

 プレイヤーとして、購入した種を畑の区画に植えたい

 プレイヤーとして、植えた植物が時間経過とともに自動で成長していく様子を見たい

成長段階: 植えた直後 → 芽が出た → 少し育った → 花が咲いた → 実がなった、の5段階



 プレイヤーとして、実がなった植物を収穫したい

 プレイヤーとして、収穫した作物をお店で売ってお金を得たい

 プレイヤーとして、得たお金で新しい種を購入し、サイクルを繰り返したい

 プレイヤーとして、各畑の区画が今どの成長段階にあるかをひと目で確認したい

 プレイヤーとして、ゲームを閉じて再度開いたときも、所持金・畑の状態・植物の成長が引き継がれていてほしい

成長は現実時間の経過に応じて、ゲームを開いていない間も進む




 デバッグシステム


 開発者として、ゲーム固有の初期状態（所持金・所持種・畑の植物の成長段階など）を設定してゲームを開始したい

 開発者として、デバッグ機能を本番ビルドでは無効化したい（開発ビルドのみ表示）


 非機能要件

スマートフォンでのプレイを前提とした縦長画面サイズ（例: 720×1280）で、シンプルな単一画面（畑＋お店UI）として完結させる
タップ操作だけで種の購入・植え付け・収穫・売却が行えるようにする
成長は現実の時間経過（数時間〜数日オーダー）に基づいて進行し、ブラウザを閉じている間も時間を計算して反映する
セーブデータは localStorage に保存し、ブラウザ再訪問時に状態を復元する


 スコープ外

クリア・エンディング・スコアランキングなどの「終了」を前提とした要素
トマト・ピーマン以外の作物の追加（将来的な拡張候補とするが、初期スコープには含めない）
マルチプレイ・他プレイヤーとの交流要素
サーバーサイドでのデータ管理（保存はブラウザのみ）


 完了条件 (Definition of Done)

種の購入 → 植え付け → 5段階の成長 → 収穫 → 売却、の一連のサイクルがUI操作で実行できる
成長段階がブラウザ上で視覚的に判別できる
ブラウザを閉じて再度開いたときに、所持金・畑の状態（植えている植物・成長段階）が正しく復元される
デバッグ機能（初期状態の設定）が開発ビルドでのみ利用できる

 ゲームルール

 ゲームループ

お店で種（トマト or ピーマン）を購入する
畑の空いている区画に種を植える
現実時間の経過とともに植物が成長する（5段階）
「実がなった」状態になったら収穫する
収穫した作物をお店で売り、お金を得る
得たお金で新しい種を購入し、1 に戻る

このサイクルに明確な終了条件はなく、プレイヤーは自分のペースで繰り返す。

 成長段階
植物は以下の5段階を順番に進む。各段階の滞在時間は balance-params.md で定義する。



#
段階名
説明




1
植えた直後
種をまいた直後の状態。土に何も生えていない


2
芽が出た
小さな芽が地面から顔を出した状態


3
少し育った
茎や葉が伸び、植物らしい見た目になった状態


4
花が咲いた
花が咲いた状態。もうすぐ実がなる


5
実がなった
収穫可能な状態。タップで収穫できる




段階の進行は現実時間の経過によって自動で行われる（プレイヤー操作は不要）。
ブラウザを閉じている間も時間は経過し、再度開いたときに経過時間に応じて段階を再計算する。
「実がなった」段階に到達した後は、収穫されるまでその状態を維持する（枯れる・腐るなどの劣化要素は持たない）。


 植え付けルール

空（何も植わっていない）区画にのみ、種を植えることができる。
植え付けには対象の種をプレイヤーが所持している必要がある。種を植えるとその分の所持数が減る。
植え付け時刻を記録し、その時刻からの経過時間で成長段階を判定する。


 収穫ルール

「実がなった」段階の区画をタップすると収穫できる。
収穫すると、その作物がインベントリに追加され、区画は空の状態（次の種を植えられる状態）に戻る。
「実がなった」段階に至っていない区画は収穫できない（タップしても「いまは収穫できません」のように案内する）。


 売却ルール

収穫した作物は、お店UIから売却して所持金に変換できる。
売却すると、その作物のインベントリ数が減り、対応する売却額分だけ所持金が増える。


 購入ルール

お店UIで、所持金の範囲内であれば種を購入できる。
購入すると、種の所持数が増え、所持金が購入額分だけ減る。
所持金が不足している場合は購入できない（「コインが足りません」のように案内する）。


 初期状態

新規プレイヤーは、初期所持金・初期所持種を持った状態でゲームを開始する（具体的な値は balance-params.md を参照）。
畑のすべての区画は空の状態から始まる。


 デバッグ機能（開発ビルドのみ）

所持金・所持種・各区画の植物の成長段階を、開発者が自由に設定してゲームを開始できる。
本番ビルドでは表示・利用できない。

 SE / BGM の方向性

BGM: アコースティックギター・バンジョー・フィドル・ハーモニカなど、フォーク／カントリー調の楽器を中心としたゆったりループ曲。納屋や牧場でのんびり過ごすような素朴な雰囲気。
SE:

種を植える: 軽く土を掘るような柔らかい音
成長段階が進む: 木製の鈴（カウベル風）が小さく鳴るような音
収穫: カゴに作物を入れるような、ことんと弾む音
購入・売却: 硬貨が木箱に触れ合うような素朴な音




 テキスト文体

敬体（です・ます調）で、プレイヤーに寄り添うやさしい口調にする。
例: 「トマトの種を植えました」「実が収穫できそうです」「150コインで売れました」
エラーや操作不可の通知も責めるような表現を避け、「いまは収穫できません」のように穏やかに伝える。

 初心者でも安心して使える理由

 きれいな実装になる仕組み
このテンプレートには、プレハブと ECS の使い分けや、React と Phaser 間の通信を EventBus に一本化するルール、フォルダ構成・命名規則の統一といった指針が .claude/rules/ にまとめられています。Claude はこれらに沿って実装を進めるため、できあがるコードの見通しが良くなります。
見通しの良いコードは、結果として「壊れにくく」「何かおかしくなったときに原因を探しやすい」コードでもあります。

 細かく確認しながら進める開発フロー
ワークフローは要件定義 → 外部設計 → 内部設計 → アセット生成 → TODOリスト作成 → 実装、と段階を踏んで進み、前のフェーズの必須ドキュメントが揃っていない状態で次に進むことはできません。実装も TODO リストを1タスクずつこなしながら、確認・承認・コミットを繰り返す形になっています。
一気に作り込んでから「動かない…どこから直せば」となるのではなく、小さく作って都度確認する。これを徹底しているおかげで、たとえ途中でうまくいかないことがあっても被害が小さく、後戻りしやすい開発フローになっています。

 注意点
本プロジェクトはあくまでゲームのプロトタイプを作ることを目的としており、本番相当の品質や著作権管理までは保証されていません。「とりあえず動くものを早く作ってみたい」という用途には強い一方、そのまま製品として公開するには別途見直しが必要になる、という点は理解した上で使ってください。
また、大規模なゲームの作成は想定していません。1～2時間で遊べる程度の2Dドットブラウザゲームの規模を想定してます。

 技術的な要素の紹介

 実装アーキテクチャ
ベースは Phaser 4 + React 19 + TypeScript で、Vite でビルドする構成です。React が HTML シェルと UI を担当し、Phaser がゲームキャンバスとロジックを担当する二層構造になっています。
Phaser 側のゲームロジックは、目的に応じて「プレハブ」と「ECS（Entity / Component / System）」を使い分けます。

配置

状態と描画が同一オブジェクト内で完結するもの（マップ上の固定オブジェクトなど）
src/game/prefab/


ECS
複数の System が協調するもの（プレイヤーキャラクター・敵・タイルなど）
src/game/ecs/



EventBus の使い方も決まっていて、Phaser シーン側では create() で購読し shutdown イベントで解除、React 側では useEffect で購読しクリーンアップ関数で解除する、という形に統一されています。

bg-generator は、canvas-design スキルで高品質な元画像を生成したうえで、専用のスクリプトでドット絵風に変換して保存する、という流れで背景画像を作成します。一方 sprite-generator は、アイテムアイコンやキャラクタースプライトといった64px以下の小さなドット絵を、ASCIIグリッドとパレット辞書でClaudeが直接描き、ネイティブ解像度のPNGとして書き出します。
bgm-generator は BeepBox の合成エンジンを、sfx-generator は ai-sfx の jsfxr ラッパーを、それぞれ MIT ライセンスのもとでビルド済みの形で同梱しています。Claude 自身が楽曲のコード進行や効果音のパラメータを設計してスクリプトに渡す形になっているため、外部 API を呼び出す必要がありません。
いずれもトンマナで決めたカラーパレットやビジュアルスタイルに沿って生成されるため、ゲーム全体で統一感が保たれます。

 雑感
プロトタイプを作るにも、まずアセットを準備するのに時間がかかると思っていた部分を今回Claude Codeで完結する形で解決してみました。リリースするゲームの品質としては足りませんが（特にBGMとSE）、プロトタイプであれば問題ないアセットを作成してくれます。
また雰囲気や面白さはアセットに依存するため、プロトタイプの時点である程度そろっていたほうが作りたいもののイメージが伝わりやすいと思います。
プロトタイプを作ることで操作感やどの部分の演出を凝ったものにすべきか、という検討がすすみます。また、アセットを含めAIが生成するため、アセットを作る（選ぶ）労力を考えて変更したくなくなるという心理的ハードルがなくなりました。
一方で今回はあまり実装のアーキテクチャにはこだわっていません。一応ECSやプレハブを設計する指示は入れましたが、素人の私が見てもまだ責務を分離できる余地のある実装が出力されます。AI特有の同じロジックが散見される現象も発生します。UIに至ってはゲームロジックと密結合です。
ただ、仕様変更が多発するプロトタイプでは綺麗に実装することにこだわりすぎる必要はないと考え、実装の指示は作りこみませんでした。プロトタイプが完成してみると、採用すべきアーキテクチャも変わってくるかもしれません。
