## 本文
書いた deny が、実は効いていませんでした
個人用のMacでAI開発環境を組み直していたとき、暴走削除を止める保険としてClaude Codeの permissions.deny に rm 系のルールを足しました。設定ファイルに書き込んで、「これで rm -rf の事故は止まる」と安心して次の作業に移りました。
数日後、別件の検証で使い捨てディレクトリに rm -r ~/work/sandbox を投げてみたら、ディレクトリは普通に消えました。deny は素通りしていたようです。
消えたこと自体は問題ではありません(使い捨てなので実害はゼロでした)。気になったのは、書いた deny が一度も効いていなかったのに、自分は「書いたから安全」と思い込んでいたことです。効いていない安全策は、無いよりむしろ危険かもしれないなと感じました。「もう対策した」という安心(false comfort)が、確認の手を止めてしまうからです。
そこから3セッションかけて、実測で原因を切り分けながら、効くdenyに組み直しました。踏んだ落とし穴は3つ。どれも「設定を書く」と「設定が効く」の間に潜む段差でした。この記事ではその記録と、効くdenyの作り方をまとめておきます。


 前提:deny に何を期待していたか
まず立ち位置を書いておきます。denyルールは最終防御のつもりではありません。最終防御は「破壊操作は人間が承認する」「削除は事前に予告する」という運用ルールに置いています。deny はその下の補助的な床、というイメージです。うっかり rm -r を実行させそうになったとき、最後にもう一段引っかかってくれたらいいな、くらいの位置づけでした。
止めたかったのは、再帰削除の経路です。代表的なのは次の3系統でした。


rm -r / rm -R(再帰削除)

find ... -delete / find ... -exec rm ...(find 経由の削除)

... | xargs rm(パイプで渡して削除)

これらを permissions.deny で塞ぐ、という素朴な方針です。素朴だったぶん、3回つまずきました。

 落とし穴①:ユーザー階層の settings.local.json は読み込まれないようです
最初に deny を書いたのは ~/.claude/settings.local.json でした。「.local はローカル上書き用だから、ここに追記すれば自分の環境にだけ効くはず」と考えたのですが、これがそもそもの勘違いでした。

 症状
settings.local.json に Bash(rm -r *) などを書いた状態で rm -r <ディレクトリ> を投げると、拒否されずに実行されてしまいました。

 切り分け
ここで「permission 機能そのものが壊れている」のか「このファイルだけ無視されている」のかを切り分けます。base の ~/.claude/settings.json(.local でない方)に元から入っていた deny を試してみました。
# base の settings.json にある deny を狙う
rm -rf ~/tmp/NOEXIST   # → 拒否される
# .local に書いた deny を狙う
rm -r ~/tmp/sandbox    # → 実行されて消える
base 側の deny は効いています。permission 層は生きているようです。どうやら、settings.local.json に書いたルールだけが無視されていたみたいでした。

 原因
公式ドキュメントの優先順位表で裏が取れました。settings.local.json はプロジェクト階層(<project>/.claude/settings.local.json)のための仕組みで、ユーザー階層(~/.claude/)に同名ファイルを置いても読み込み対象にはならないようです。設定の優先順位はこうなっていました。
Managed（管理ポリシー） > CLI > Local（プロジェクトの .local） > Project > User
deny は全階層が union でマージされ、deny が allow に優先し、Managed 階層は他から上書きできない、とのこと。つまり ~/.claude/settings.local.json という置き方が、そもそも読み込みの土俵に乗っていなかったわけです。

 対策:管理ポリシー階層へ置く
自分専用の固い床を作りたいなら、最優先かつ上書き不可の Managed 階層に置くのがよさそうです。macOS ではここでした。
/Library/Application Support/ClaudeCode/managed-settings.json
{
  "permissions": {
    "deny": [
      "Bash(rm -r *)"
    ]
  }
}
このファイルは root 所有なので、作成・編集に sudo が要ります。
sudo tee "/Library/Application Support/ClaudeCode/managed-settings.json" > /dev/null <<'JSON'
{
  "permissions": {
    "deny": [
      "Bash(rm -r *)"
    ]
  }
}
JSON
以下注意事項


sudo が要るので、AI エージェント自身には書き換えさせられません(これは安全側の性質でもあります。エージェントが自分の制約を勝手に緩められない、という意味で)。
反映は Claude Code の起動時です。書き換えても、今動いているセッションには効きません。検証は新しいセッションで行う必要がありました。
利点として、設定を自動更新する管理ツール(~/.claude/ を上書きしてくる類)を使っていても、Managed 階層は消されません。供給網リスクから床を切り離せる、というのは地味に大きいなと思いました。

これで「正しい場所」には置けました。ただ、まだ穴が残っていました。

 落とし穴②:コマンドは | や && で分割して判定されるようです
Managed 階層に7パターンを置いて、新セッションで再テストしてみました。rm -r も find -delete もきれいに拒否されます。ところが1つだけ素通りしてしまいました。
echo ~/tmp/sandbox/dummy.txt | xargs rm   # → 実行されて消えた
deny には Bash(* xargs rm*) を入れていました。正しい場所(Managed)に、xargs rm を狙ったつもりのパターンを書いたのに、捕捉できていません。

 切り分け:存在しないパスへの probe
ここで挙動だけを安全に確かめます。存在しないパスを狙えば、たとえ実行されても何も消えません。パイプの先に rm -r を置いて投げてみました。
true | rm -r ~/tmp/NOEXIST
返ってきた拒否メッセージがヒントになりました。
Permission to use Bash with command rm -r ~/tmp/NOEXIST has been denied.
true | が剥がれて、rm -r ~/tmp/NOEXIST だけが報告されています。どうやら Claude Code は、コマンドを | で分割して、各サブコマンドを個別に判定しているようです。&& でも同じ結果でした。

 本質:止めたいコマンドの「先頭語」を見誤っていた
分割を踏まえて echo X | xargs rm を見直してみます。これは2つのサブコマンドに割れます。

echo X
xargs rm

削除を実行しているサブコマンドは xargs rm です。ここで大事だったのは、コマンドは xargs であって、rm はその引数だ、という点でした。rm を起点にした感覚で * xargs rm* と書いても、分割後のサブコマンドは xargs で始まります。パターン先頭の * (末尾にスペースを要求する)は「xargs の前に何か + スペース」を求めるのですが、xargs rm の前には何もありません。だから一致しなかったのだと思います。
rm -r ~/tmp/x のような単独コマンドが Bash(rm -r *) で止まったのは、先頭語 rm から素直にアンカーできていたからでした。xargs 経由では先頭語が変わります。そこを取り違えていたわけです。

 対策:コマンドの先頭語からアンカーする
xargs rm を止めたいなら、xargs から書きます。
Bash(xargs rm:*)
末尾の :* は「このコマンドに任意の引数が続く(または続かない)」を表します。分割後の xargs rm に素直に一致してくれました。新セッションで再テストしたら、今度はちゃんと拒否されました。
Permission to use Bash with command xargs rm has been denied.

 副産物:rm 系 deny はパイプ/チェーン経由でも堅牢でした
この「分割して個別判定」という挙動は、こちらに有利にも働きます。true && rm -r ~/tmp/x や echo x | rm -r ~/tmp/x のように rm をパイプやチェーンの後ろに隠しても、分割された rm -r ... が単独で判定されるので、Bash(rm -r *) に引っかかって止まりました。前置きでごまかして deny をすり抜ける、という回避はできなかったわけです。穴は xargs のように「削除コマンドが別コマンドの引数になる」ケースに限られるみたいでした。

 落とし穴③:「書いた」と「効いている」は別物でした
①も②も、書いた時点では「効いているつもり」でいました。①は置き場所のせいで一度も読まれず、②は正しい場所に置いたのに書き方のせいで素通りしていました。どちらも、実際にコマンドを投げてみて初めて不発に気づいた、という流れです。
deny を書くたびに、頭の中ではこう考えてしまいがちです——「rm -r を deny に入れた。これで rm -r は止まる」。でもこの推論には、「ファイルが読み込まれている」「パターンがコマンドの解釈に一致する」という2つの暗黙の前提が挟まっています。前提が崩れていても、設定ファイルは何も警告してくれません。静かに不発になるだけでした。
なので、deny は書いたら必ず実測する、というのを今回の教訓にしました。

 検証レシピ
使い捨てのサンドボックスを作って、deny したいコマンドを実際に投げて、拒否されるか/対象が消えるかを見る、というだけです。
# 1. 使い捨てディレクトリを作る
mkdir -p ~/tmp/deny-test/t1 && echo dummy > ~/tmp/deny-test/t1/dummy.txt

# 2. Claude Code に deny したいコマンドを投げる
rm -r ~/tmp/deny-test/t1
#   → 拒否されれば床が効いている
#   → ディレクトリが消えたら、その deny は不発（穴）

# 3. 挙動だけ安全に確かめたいときは存在しないパスを狙う（何も消えない）
true | rm -r ~/tmp/deny-test/NOEXIST
Managed 階層を書き換えたら、新しいセッションで確かめてみてください(起動時にしか読まれないので)。後始末も、これから作る床に合わせて素の rm <file> と rmdir で消すことになります(rm -r は自分で deny したので使えません。床が日常運用にどれくらい摩擦を与えるかの確認にもなりました)。

 効く deny の作り方
3つの落とし穴を裏返すと、こんなチェックリストになりました。
① 置き場所

自分専用の固い床なら、macOS の Managed 階層 /Library/Application Support/ClaudeCode/managed-settings.json(最優先・上書き不可・要 sudo)がよさそう。
ユーザー階層に settings.local.json を置いても読まれません。.local はプロジェクト階層用なので。
チームに配るなら、各自の Managed 階層は MDM などの管理で、個人は配布される settings.json で制御、と層を分けるのがよさそう。

② 書き方

止めたいコマンドの先頭語からアンカーします。xargs rm を止めたいなら Bash(xargs rm:*)。rm 起点だと届きませんでした。
表記揺れも個別に塞ぎます。大文字フラグ(rm -R)やフラグの組み合わせ(rm -Rf / rm -RF)は、別の文字列として扱われるようです。
別経路も個別に塞ぎます。find ... -delete と find ... -exec rm ... は別構文です。

手元で落ち着いた7パターンはこうなりました。base の settings.json に元からあった rm -rf * / rm -fr * の隙間(-f なしの -r、大文字変種、find/xargs 経由)を埋める補強として置いています。
{
  "permissions": {
    "deny": [
      "Bash(rm -r *)",
      "Bash(rm -R *)",
      "Bash(rm -Rf *)",
      "Bash(rm -RF *)",
      "Bash(find * -delete)",
      "Bash(find * -exec rm*)",
      "Bash(xargs rm:*)"
    ]
  }
}
③ 検証

書いたら使い捨てサンドボックスで実投下して、拒否されるか実測します。
Managed を変えたら新セッションで確かめます。


 限界も書いておきます
denyは文字列マッチなので、完全網羅はできません。rm --recursive(ロングオプション)、alias 経由、シェル変数に逃がす書き方など、すり抜ける経路はいくらでも作れてしまいます。なので deny は最終防御にはならない、と割り切っています。あくまで補助の床という位置づけです。最終防御は「破壊操作は人間が承認する」「削除は事前に予告する」という運用に置いて、deny はその手前でうっかりを一段止めるためのもの、と考えるとしっくりきました。

 まとめ

効いていない安全策は、無いよりむしろ危険かもしれないなと思った。「書いた=安全」という思い込みが、確認の手を止めてしまう。
Claude Code の deny は、置き場所(ユーザー階層の .local は読まれない / Managed 階層へ)と書き方(| && で分割される / コマンドの先頭語からアンカーする)を押さえておかないと、静かに不発になることがある。
なので、書いたら実測すべき。サンドボックスにコマンドを投げて、拒否されるのを目で確かめる。存在しないパスを狙えば、ゼロリスクで挙動だけ確認できる。

ツールの安全機能は、設定ファイルに書いた瞬間ではなく、実際にブロックされたのを見た瞬間に、ようやく「効いている」と言えるのかなと思いました。
