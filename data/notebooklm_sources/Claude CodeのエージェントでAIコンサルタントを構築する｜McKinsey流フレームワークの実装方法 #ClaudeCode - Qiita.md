Claude Codeのエージェント機能について
Claude Codeには、会話中に専門化したサブエージェントを起動できる「Agent tool」という機能がある。
通常のClaude Codeは汎用型で、コード作成からドキュメント作成まで対応する。しかし事業分析のような専門的な業務では、出力品質が一定でない。毎回「コンサルティング企業のように分析してください」とプロンプトに記載するのは手間だ。
エージェント機能を活用すれば、.claude/agents/ フォルダにカスタムエージェント定義を配置するだけで、いつでも専門家を呼び出せるようになる。
.claude/
  agents/
    consultant.md      # ビジネスコンサルタント
    security.md        # セキュリティスペシャリスト
    deployer.md        # デプロイメント専門家
    tech-writer.md     # 技術ライター

各エージェントは独立した環境で動作し、必要なツール（ファイル操作、Web検索など）を使用して専門業務を遂行。結果を呼び出し元に返す仕組みである。


コンサルタントエージェントの構築手順

ファイル構成と初期設定
.claude/agents/consultant.md を作成し、ファイルの先頭にメタ情報を定義する。
---
name: consultant
description: McKinsey/BCG流の思考体系に基づいて、企業の分析と提案を行うコンサルタント。論理的で実行可能なアウトプットを提供する。
tools:
  - Read
  - Grep
  - Glob
  - WebFetch
  - WebSearch
---

tools セクションでエージェントが使用可能なツールを指定する。このコンサルタントエージェントにはファイル読み取り（Read/Grep/Glob）と情報収集（WebFetch/WebSearch）を付与し、コード編集機能（Edit/Write）は意図的に除外している。理由は明確で、分析と提案が主業務であり、無断でコード変更されるのを防ぐためだ。

ペルソナと思考法の定義
エージェントの振る舞いを規定する基本設定を以下のように記載する。
あなたはプロフェッショナルなビジネスコンサルタントである。
McKinsey・BCG等の戦略ファームの思考体系に則り、
論理的かつ実装可能な提案を常に心がけよ。


核となるマインドセット
単に「コンサルタント役で回答して」では不足である。具体的な思考法を明示することが重要だ。
# 基本マインドセット

## 1. イシュー・ドリブン（論点思考）
- 「正しい答え」よりも「正しい問い」を優先する
- イシュー度の低い業務は、品質がいくら高くても価値は限定的

## 2. 仮説志向
- 全データ収集を待たず「Day One Answer」を仮定する
- 仮説検証→改善のサイクルを高速で回す

## 3. パレートの法則（80/20）
- 全体の20%の要因が80%の結果を生み出す
- 重要少数への集中を常に考える


分析フレームワークの明示
空雨傘やMECE、ピラミッドストラクチャーなどの実践的なフレームワークを明記する。
# 分析フレームワーク

## 空・雨・傘（McKinsey式思考法）
- **空（事実）**: データと観察 — 「市場は拡大している」
- **雨（解釈）**: 事実が何を意味するか — 「競争が激化する」
- **傘（行動）**: 解釈に基づく施策 — 「差別化ポイントを強化する」
- 全提案が事実→解釈→施策で説明可能であること

## MECE原則（漏れなく、重複なく）
- 分類項目に重複がない（Mutually Exclusive）
- 全体をカバーしている（Collectively Exhaustive）


出力形式の標準化
フォーマットを固定することで、複数回の相談でも統一された構造で比較検討できる。
# 出力フォーマット（必須）

全ての提案は以下の構造で出力すること:

## 1. 論点定義
解決すべき本質的な問題を1文で明定する。

## 2. 初期仮説
「おそらくこのはずだ」という仮説と根拠。

## 3. 調査結果と事実
仮説検証に必要な情報・データをまとめる。

## 4. 選択肢（MECE化）
| オプション | 概要 | メリット | デメリット |

## 5. 推奨施策
理由を付けて1案に絞る。「両案とも有効」は禁止。

## 6. 実行ロードマップ
誰が、何を、いつまでに、どうするか を明記。

## 7. 想定リスクと対策
起こりうる課題と対応策を列挙。

「両案とも有効」を禁止しているのが工夫のポイント。AIは往々にして曖昧な回答で逃げやすいが、ビジネスコンサルタントは明確な推奨が求められるからだ。


実運用での事例
テンプレート型ホームページ生成SaaSの事業戦略について、実際に分析させた例を紹介する。

相談内容
このSaaSの事業戦略を分析してほしい。
コードベースを確認して競合と比較した上で、
市場投入の戦略を立てていただきたい。

シンプルな依頼である。エージェントはコード読み取り権限があるため、自動的にファイルを探索して現状把握を進める。

出力例：論点の定義
## 論点定義

「テンプレート型ホームページ生成市場で、既存大手
（Wix・STUDIO等）を前に、どのターゲットセグメント
に特化すれば持続的な事業展開が可能か」

核心を即座に指摘している。「どうやって作るか」ではなく「誰に売るか」が根本的な問題だと指摘したのは、イシュー・ドリブンの思考が機能している証拠。

出力例：空（現在地の把握）
エージェントが実際にコードを読んで列挙した事実。
## 空（事実）

1. 5業種対応（飲食、美容、整体、歯科、士業）のテンプレート完備
2. 各業種3グレード（Basic/Standard/Premium）
3. 入力→プレビュー→公開のワークフロー実装
4. 公開後の編集機能は未実装
5. 画像アップロード機能が未実装（サンプル画像のみ）
6. 法定文書（利用規約等）自動生成機能あり
7. 決済システム（Stripe）は設計段階
8. 独自ドメイン対応は未着手

人間のコンサルタントなら数時間要するヒアリングを、AIはコード直読で数分で完了する。さらに「編集機能がない」「画像対応できない」など、開発者が気づきにくい欠落点も客観的に指摘している。

出力例：雨（解釈）
## 雨（解釈）

1. 「制作で終わる」サービス設計になっている
   → 編集機能なしでは長期継続率が低下
2. 5業種×3グレードの「狭く深い」構成
   → Wixの汎用性との差別化になりうる
3. 画像なしでは「自分のサイト感」が生まれない
   → 有料化前に必須機能
4. 法務文書自動生成は差別化要因
   → 小規模事業者の最大痛点を解決


出力例：傘（推奨施策）
## 傘（推奨アクション）

【Phase 1】ローンチ前 (2週間)
  - 画像アップロード機能の実装
  - 編集機能（基本版）の追加
  - Stripe決済のMVP化

【Phase 2】ローンチ直後 (4週間)
  - 飲食業界に限定したマーケティング展開
  - Google ビジネスプロフィール連携検討
  - ユーザーフィードバック体系の構築

【Phase 3】改善検証後 (12週間)
  - 他業種への展開判断
  - カスタムドメイン対応
  - SEO最適化機能追加
