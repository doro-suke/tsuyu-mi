# 生成は雑でいい、検証器が全部拾う：採択率0.26%で成立する『生成→検証』ループ

## 本文
🎯 はじめに
LLMを実務に組み込むほど、「たぶん合ってる」出力をどう扱うかに悩まされる。
コード生成にせよ、SQL生成にせよ、構造化データにせよ、
「モデルが確信を持って返してくる誤り」を人間側で拾い切るのは現実的ではない。
このとき効くパターンが、生成と検証を分離するという考え方だ。


生成側は正しさを一切保証しなくてよい

検証器が「正しい」と言い切る責任を全部持つ
生成が安いなら、雑に量産して検証で絞ればいい

これをLLMで議論する前に、古典的なパズル生成でこの型を素朴に実装したツールを作った。verigen という Go 製の CLI で、覆面算(SEND + MORE = MONEY のようなパズル)を「生成→検証→再生成」ループで作る。

実測した採択率は 0.26%、つまり生成した種の 99.7% を検証器が捨てている。
それでも5問あたり84msで出せる。
この記事では、このループの構造と、なぜそれがLLM時代の設計として効くのかを書く。


 🗺️ 全体像
先に構造を図にする。
要点は一つだけ。

生成は正しさを一切保証しない。保証はすべて検証器にある。

生成側は乱数で「それっぽい種」を投げるだけ。
検証器は全探索で「解が存在し」「解が一意である」ことを厳密に確認する。
通らなければ捨てて次の種を作る。それだけのループを回す。
このループ自体はドメインに一切依存しない。
覆面算だろうが、別のパズルだろうが、Domain インターフェースさえ実装すれば同じループに載る。


 📊 実測：生成のほとんどはゴミである
覆面算で5問生成したときの実測ログはこうなる。

実行ログ
$ verigen -n 5 -seed 7

── 問題 2  [難]
   HAIKU + BONSAI = KOKORO
   答: 96542 + 378165 = 474707
   （この種に辿り着くまでの試行: 624回）


統計
=== 生成→検証ループの実績 [alphametic] ===
seed=7  出力=5問  総試行=1947回  所要=84ms
採択率 = 0.2568%  (1問あたり平均 389 回の生成が必要)
--- 棄却理由の内訳 ---
  解が一意でない                          770  (39.55%)
  解なし                              695  (35.70%)
  文字数>10（解が存在し得ない）                 477  (24.50%)
  ok                                 5  ( 0.26%)

採択率 0.26%。生成した種の 99.7% は「解が無い」か「解が一意でない」かで、検証器が全部捨てている。
それでも所要は 84ms。人力では絶対にやれない選別を一瞬でやっている、というのがこの仕組みの本体だ。
難易度で絞るとさらに厳しくなる(-level 易 で採択率 0.03%、1問あたり約3200回)。
それでも一瞬で終わるので、生成が安いなら検証で殴れるという設計が成立する。
ここで重要なのは、生成側のコードを賢くして採択率を上げようとしていないことだ。
賢くするコストより、雑に回して検証器に選別させるコストの方が安い、という判断がある。


 🧩 検証器が「言い切る」ために何をしているか
このループが成立するかどうかは、検証器がどこまで厳密に保証を貼れるかにかかっている。
verigen の覆面算 Domain では、検証器がこれだけの保証を持つ。



保証
方法




解が存在する
列ごとに桁上がりを持って全探索


解が一意である
2つ目の解が見つからないことを全探索で確認


文字数が11以上なら解なし
鳩ノ巣原理。探索する前に弾く


先頭が0にならない
2文字以上の語の先頭文字を制約




 「保証を貼る」を成立させる設計判断
書きながら効いた判断が3つある。
1. 検証器を最初にテストした
検証器が壊れていたら「保証」がまるごと嘘になる。
そこで、答えが世界的に知られている定番問題を正解データにした。


SEND + MORE = MONEY → 9567 + 1085 = 10652


CROSS + ROADS = DANGER → 96233 + 62513 = 158746

「解なし」「一意でない」「文字数11以上」も個別にテスト

生成器のテストは後回しでいい(壊れても採択率が下がるだけ)。検証器が壊れていると全体が崩れる。
2. 事前枝刈りは"効く事実"だけ入れる
覆面算では相異なる文字が10以下でないと、鳩ノ巣原理で解が存在し得ない。
これは全探索する前に弾ける。実測でも棄却理由の 24.5% がこれで、探索コストを大きく削る。
生成側を賢くするのではなく、検証器の入口で明らかにダメな種を高速に弾く方向で最適化している。
3. 難易度は代理指標だと明示する
Score(分岐点の数)を難易度の指標にしているが、これは「試行錯誤の量の代理」であって、
人間の体感難易度そのものではない。相関はするはずだが未検証。
保証できることと、そうでないことを分けて書くのは、
検証器が「言い切る」ためのお作法として重要だ。


 🤖 LLM への接続：既にやられていること、まだ空いていること
ここまでの構造は、そのまま LLM 応用に置き換えられる。
verigen で乱数が担っていた「生成器」を LLM に差し替えるだけだ。
ただ、これは 2026 年時点でもう新規性のあるパターンではない。
LLM 応用の主要な領域では、この型は既に業界標準として実装されている。
以下ではまず「もう普及した側」を素早く並べ、次に「まだ空いている側」を掘る。

 既に業界標準になっている領域
コード生成 — Claude Code の hooks や Devin 2.0 に代表される「Loop Engineering」として定式化済み。「テスト・型・lint を通るまでエージェントを終わらせない」が当たり前の実装になっていて、Cognition の 2025 年年次レビューでは Devin が生成する PR のマージ率が 67%(前年 34%)まで来ている。
ただし裏を返せば、3件に1件はそのままではマージされていない。検証器が拾えるのは「通るか落ちるか」までで、レビューで直される部分はその外側にある。
SQL生成 — Snowflake Cortex Analyst が verified queries の自動最適化を 2025 年 12 月に Preview 投入。Vanna AI も dry-run エラーからの自己修正を標準機能として持つ。EXPLAIN・スキーマ照合・実行結果でのリトライは、text-to-SQL 系プロダクトのお約束になっている。
構造化出力 — もはや「検証」ですらなく、decoding 時に schema 違反トークンを出させない方向まで進んだ。XGrammar が vLLM / SGLang / TensorRT の標準バックエンドになり、OpenAI Structured Outputs も同じ方向。「JSON をパースしてリトライ」は過去の話に近い。
数式・証明 — 一番派手なのはここだ。そして、ここで型が一度分岐している。
AlphaProof は 2024 年に AlphaGeometry 2 と組み合わせて IMO(国際数学オリンピック)で銀メダル水準のスコア(28/42点)を取った。
仕組みは verigen と地続きで、「候補となる証明を生成 → Lean 4 という証明支援系(=機械的な検証器)にかけて通るかを見る → 通るまで回す」というループを、途方もない計算量で回している。DeepSeek-Prover-V2 も同じ方向。
ところが翌 2025 年、Gemini Deep Think が同じ IMO で 35/42点(6問中5問完答)の金メダル水準を、Lean を使わず自然言語のまま取った。
2024 年の AlphaProof が1問に最大3日かけていたのに対し、Deep Think は人間と同じ4.5時間の制限内に収まっている。1問あたりに直すと1〜2桁の開きだ。
つまり試験問題は、検証器なしで勝てた。
だが未解決問題はそうではない。
2026 年 5 月、DeepMind の AlphaProof Nexus が Erdős の未解決問題を9件(全353件中)、OEIS の予想を44件解いたと報告している(arXiv:2605.22763)。
こちらは Lean での形式検証を外していない。1問あたり数百ドルの計算を、検証器が通るまで回している。
差は答え合わせができるかどうかにある。
試験問題には採点者がいて、正解が存在することも分かっている。だから生成器が強ければそれで足りる。
未解決問題にはどちらもない。「解けたと言っている」を「解けた」に変えるものが、Lean 以外にない。
覆面算で全探索が「解の一意性」を言い切ったのと同じことを、Lean が「数学の証明」でやっている、と読める。
verigen で "生成は雑でよく、検証器が全部拾う" と書いた。だが検証器が要るのは、生成が雑だからだけではない。誰も答えを知らないからでもある。
いずれも共通するのは、「検証器が厳密に判定できる」ことがすべての前提という点だ。
逆に言うと、創作文の"良さ"のような機械的に判定できないものには、そもそもこの設計は効かない。

 まだ空いている領域
一方で、「検証器そのものの設計」に踏み込む方向はまだ余地がある。
round-trip 検証 — データ変換や翻訳で「逆変換して元に戻るか」を確認するタイプの検証。schema 検証は普及したが、意味等価性まで見る round-trip は仕様設計として未成熟で、ETL やコード移行(言語間、フレームワーク間)のような領域で効きそう。
「一意性」に相当する保証 — 覆面算の検証器は「解が存在する」だけでなく「解が一意である」まで言い切っている。LLM 応用でも、単に「動くコードが出た」で終わらせず、入力仕様に対して振る舞いが一意に定まっているかまで検証器で貼れると強い。プロパティベーステストで反例が出ないことまで見る、といった方向にあたる。
「良問フィルタ」に相当するもの — verigen で「解けるが面白くない問題」を弾けていないのと同じで、LLM 応用でも「テストは通るが良い設計ではないコード」を弾く検証器は薄い。これはメトリクスの設計そのものが未解決に近く、簡単には言い切れない。
「生成→検証」ループ自体はもう普及した型だが、どこまで厳密に何を保証するかの詰め方は、いまも設計者ごとに答えが違う。verigen で古典パズルを題材にしたのは、その"検証器そのものの設計"を最小コストで手を動かして考えるためだった、というのが後付けの整理でもある。


 💡 設計原則：生成が安ければ検証で殴れる
このパターンが成立する条件を整理しておく。

 条件1: 生成コストが十分に低い
verigen の場合、5問で総試行1947回でも 84ms で終わる。
LLM 生成はこれよりずっと高い(APIコール1回で数百ms〜数秒)。
なので LLM で同じ採択率0.26%を狙うのは非現実的で、
採択率を上げるプロンプト設計と、検証器の厳密さの両方をチューニングする必要がある。

 条件2: 検証コストが生成コストと釣り合う
verigen の検証器は全探索だが、それでも生成と合わせて 84ms に収まっている。
LLM への応用では、「テスト実行」「型チェック」など、
検証側もそれなりのコストがかかるものが多い。
検証が生成より重くなるなら、そもそもこの設計は成立しない。

 条件3: 検証器が厳密である
一番効くのはこれ。
検証器が「実は保証していないこと」を保証しているように見せると、
このループ全体が嘘になる。**「言い切れないことは言い切らない」**を徹底する。
verigen で難易度を「代理指標です」と明示したのはこの理由で、
LLM 応用でも「テストが通った=正しい」とは限らないことは分けて扱う必要がある。


 👋 おわりに
verigen で古典パズルを題材にしたのは、検証器が全探索で厳密に保証を貼れるという、極端に扱いやすい条件で「生成→検証」ループを実装してみたかったからだ。実際に採択率 0.26% というログが出ると、「生成側を賢くする」より「検証器を厳密にする」方に投資する判断が、感覚として腑に落ちる。
この型自体は、既に業界標準になっている(Claude Code の hooks、Snowflake の verified queries、XGrammar での decoding 制約、そして AlphaProof)。
だからこそ、これからの設計の勘所は「LLM の出力をどう信じるか」ではなく、**「検証器で何を、どこまで厳密に保証するか」**に寄っていく。verigen の一意性保証や、今回挙げた round-trip 検証・良問フィルタあたりは、その"検証器そのものの設計"を考えるうえで、まだ手を動かせる余地がある領域だと思う。
次にやりたいことはいくつかある。

別題材の追加(ポリオミノ敷き詰めは実装済み。結び目、不定積分、虫食い算あたりを検討中)
「良問フィルタ」の実装(いまは「解ける」だけを保証していて、面白いかは見ていない)
難易度の代理指標を人間の体感と突き合わせる
