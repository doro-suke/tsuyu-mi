## 本文
こんにちは。エクスプラザの Unsu です。
最近 "Loop Engineering"という言葉をよく目にするようになりました。
また新しいかっこいい名前の何かしらエンジニアリングが出てきたな、くらいに思いつつ、
Addy Osmani の Loop Engineering という記事を読んでみました。

内容は、こんな感じでした。

Loop Engineering とは、


人間が手動でAIエージェントにプロンプトを打ち込むのをやめ、代わりに「プロンプトを自動生成・実行・検証するシステム（外側のループ）」を設計すること


ユーザーは一度だけ目標を定義し、システム内のエージェントがその目標を達成するまで自律的に繰り返し続ける仕組み



これを読んで思いました。「もしかしたら、うちのチームで4月からやっていることと似ているかも？」
Palma 開発チームでは、AI駆動開発をチームでもうまく回したいと思い、
2ヶ月前から interview-dev-loop という Agent Skill を作り、チーム全員で使うようにしました。
この記事では、個人のプロンプト術に寄っていた AI駆動開発を、チームで回る開発ループに変えようとした2ヶ月の出来事を紹介します。

 解決したかったこと
私たちのチームは、少人数で自社 AI Workflow SaaS「Palma」を開発しています。

開発では Codex や Claude Code を使っています。最初はそれぞれが自分のやり方で使っていました。
でもチームで見たとき、課題は2つありました。
1つ目は、使い方も、成果も、バラバラになっていたこと です。
AIに何を渡すか、どこまで調べさせるか、どこで人間に確認させるか。このあたりが人によって違うと、同じようなタスクでも品質や速度に差が出ます。
2つ目は、人間がループを回す係になっていたこと です。
PR を出す。Codex Review がコメントする。人間が対応要否を見て、修正プロンプトを自分のローカルのエージェントに書く。エージェントが直す。もう一度レビューする。繰り返す。
人間が見るべきところと、エージェントが自分で回すところを分けて、人間の介入を減らしたいと思いました。

 As-is: 人間がループを回していた
最初の状態は、だいたいこうでした。
青が人間、緑がエージェントです。
実装前のプロンプトは人によって違う。
後半のレビュー対応ループでは、エージェントが1往復ごとに止まって人間の指示を待つ。
これがもったいないと思いました。

 作ったもの: interview-dev-loop
interview-dev-loop では、「As-is: 人間がループを回していたの図」のPRを出すまでの部分を、調査、質問、計画、実装、レビューという1つの流れ にしました。
人間がやることは、主に3つです。

質問に答える
計画を承認する
動作確認する

残りはエージェントが回します。

イメージとしては、以下のようなループが一つのスキルになったと思うとわかりやすいかもです。

より今のプロジェクトに特化した形でインタビュー・プランモードを実施する
その後、レビュー指摘がなくなることをゴールとして、その達成までループし続ける

実際には途中で人間が見ることもあります。完全放置ではありません。それでも、人間が毎回プロンプトを書いてループを進める状態からは、かなり離れました。

 いちばん大事だったのはインタビュー
この Skill の中心は、実装ではなくインタビューです。
最初に、AI駆動開発をチームのものにするために出たアイデアは、"良いプロンプトのベストプラクティスをチームで揃える"でした。でも途中で、そこを標準化するのは難しいと思いました。
タスクによって必要な情報は違います。実装場所も違う。リスクも違う。
それなら、人間が最初から良いプロンプトを書くのではなく、エージェントがいいと思うプロンプトを欠かせばいい。
そう考えました。
たとえば、Webサービスに新しい外部連携 Provider を追加するタスクがあるとします。
人間の指示はこのくらいで始めます。
$interview-dev-loop 外部連携機能に、新しい Provider（ここでは仮に Notion とします）を追加する
Skill はいきなり実装に入りません。
まずコード、docs、テスト、過去の plan を読みます。そのうえで、まだ決まっていないことを整理して、質問を返します。
たとえばこんな感じです。
収集した調査結果

- code: `Notion` は provider 一覧の定数には存在するが、有効 provider の定数には入っていない。
  一覧、route、UI は既存 Provider 2つ前提で分岐。
- docs: 外部連携は組織 credential と project scope の fail-closed 境界が重要。
  本番コードの変更には coverage ownership と型チェックが必須。
- tests: 現状テストは Notion を inactive として期待。
- existing plans: 過去 plan に「active provider は既存の2つのみ、それ以外は UI に出さない」方針が残る。
- local instructions: 編集前の plan ファイル必須、coverage ownership 必須、型チェック必須。

まだ決まっていないこと

- Notion を active provider として UI に出すか、catalog 上の未提供として整理するだけか
- 出す場合、接続画面を「未対応」表示にするか、credential 保存 / API まで作るか
...

Q1. Notion の初回追加スコープはどれにしますか？

現状: Notion は inactive なので画面に出ず、route は `501 この Provider はまだ利用できません` を返す。

なぜ聞くか: 「Provider として追加」が内部 catalog の整理なのか、UI に出す準備なのか、実接続まで含むのかで、実装量、UX、テスト、fail-closed 境界が変わるため。

- A) active にしない: 未提供扱いをテストと docs で明確化するだけ。
  UI には出ない。
- B) UI に出すが未実装表示: 一覧、アイコン、詳細 route まで通すが、詳細は「準備中」。
  credential 保存や同期は動かさない。
- C) credential / API まで実装: 組織 credential 保存、scope、API handler、テストまで作る。
  認証方式や対象 API scope の設計が必要。

推奨は B。
Provider として追加されたことが UI / route で確認でき、未実装の接続を動くように見せずに fail-closed を保てるからです。
この例では、どこまでを今回のスコープにするか、未実装の機能をUI上でどう扱うか、失敗時に安全に閉じる境界をどこに置くかを聞いています。
普通の Plan Mode が「どう作るか」を整理してくれるものだとすると、interview-dev-loop では、その前に「今回は何を作るべきか」を詰めにいきます。

 作りながら直したこと

 質問していい曖昧さを決めた
最初は「曖昧な点は全部質問して」と書いていました。
でも、この指示だと、毎回の挙動が結構ブレる形になりました。
かなり曖昧な指示なのに質問せず plan に入ることもある。逆に、細かいことまで質問してきて、いつまでも plan が出ないこともある。
そこで、質問していい曖昧さを定義しました。
実装の方向、検証、ロールアウト、データ処理、権限、ユーザーに見える動作。このどれかが変わりうる不確実さだけを、 実在する曖昧性（Material Ambiguity） と定義して、質問の対象にしました。
ここを決めてから、質問の質がかなり安定していきました。

 明らかに選ばれない選択肢を禁止した
エージェントは、ときどき答えがほぼ決まっている質問をしてきました。
正解っぽい選択肢と、明らかに選ばれなさそうな選択肢を並べて、
「どれにしますか」と聞いてくる。
「もう決まってるだろ」と思いました。
個人的には、CodexやClaude Codeのプランモードでもかなり遭遇していた問題でした。
なので、選択肢は以下の場合になるように限定しました。

選択して実装・設計の方向が変わる、現実的に成り立つものだけ
最大3つまで
推奨案を書くのはよい。ただし、他の選択肢も実際に選べるものでなければならない

これで、すでにエージェントがBest Practiceだと思う方向性は質問しないようになり、質問は数問で収まりやすくなりました。

 実装は別の agent に渡した
実装フェーズでは、調査と plan を作ったメインエージェントにそのまま実装させない形にしたら、より正確に作業を終えるようになっていると感じました。
おそらく、実装作業時にAIエージェントが持っているコンテキストの質と量が違うからだと思いました。
調査中には、捨てた案、読んだが使わなかったファイル、候補から外した実装方針も混ざります。 そのため、メインエージェントに実装をそのまま指示したら、その情報を持ったまま実装に入ると、エージェントが不要な前提を引きずることがあると感じました。
人間がAIエージェントに実装指示をするように、メインエージェントが実装役のサブエージェントに実装指示を作る形になり、実装エージェントは、不要なコンテキストを捨てて、採用された方針、変更対象、完了条件、必要なテストだけに全力に集中できるようになった と思います。

 2ヶ月使って変わったこと
いちばん変わったのは、プロンプトを頑張る時間が減った ことです。
前は、最初の指示に必要な前提をどこまで書くかで悩んでいました。今は、やりたいことを短く伝える。足りないところは向こうから聞いてくるようになりました。
この差は、思ったより大きかったです。
もう1つ大きかったのは、個人の工夫がチームのものになっていったことです。
誰かが「このプロジェクトで開発するときは、この指示を入れたほうが良さそう」と思ったら、Skill や AGENTS.md に改善 PR を出す。すると、次から全員がその改善を使える。
AIの使い方が、個人のメモや個人の設定ではなく、そのプロジェクトを開発するチームの資産になっていく感じがありました。
メンバーからは、こんな声がありました。

指示だと抜け漏れていた部分が、インタビューで整理されて手戻りが減った
途中で口を出す回数が減ったので、別の作業と並行で回せるようになった
実装そのものより、仕様やユーザー価値を考える時間が増えた

最後の声は、個人的にかなりうれしかったです。
AI駆動開発で人間がAIに指示する・介入する手間が減り、人間の時間が「何を作るべきか」「どう確認するか」「ユーザーにとって何が正しいか」によりフォーカスできる ようになったと感じました。

 レビュー指摘は本当に減ったのか
体感だけで終わるのは少し怖かったので、マージ済み PR の初回 Codex Review を集計してみました。

ローカルで先に使っていた私を除く、他メンバーを対象

チャートで見ると、前後で実際PR作成後のレビュー指摘が減っていったことがわかりました。
もちろん、この結果だけで「すべて Skill の効果だった」とは言えません。
チーム全体が AI駆動開発に慣れてきた影響もある。
変わったのは、PR を出したあとに人間が割り込んで直していた問題の一部を、PR 前の実装、レビュー、修正のループで吸収できるようになったことだと思います。
その結果、毎回いいプロンプトを書き直したり、途中で人間が細かく介入したりする時間が減りました。
だから、変更が大きくなっても、人間が途中で止める回数を増やさずに済み、結果としてマージ済みの変更行数も同期間で増えたのだと思います。

 PR の後ろもループにした
その後、PR後の指摘対応も、チームメンバーが作った codex-review-loop で自動 polling できるようになりました。

今の流れは、だいたいこうです。
interview-dev-loop で実装
-> E2E で動作確認
-> PR 作成
-> codex-review-loop で指摘対応
-> E2E で動作確認
-> Merge Ready
人間が触るのは、作りたいものを伝える、計画を承認する、動作を確認するところが中心です。
調査、設計、実装、レビュー、指摘対応は、できるだけエージェント側で回す。
最後の責任は人間にあります。動作確認も必要です。仕様判断も必要です。
それでも、人間が毎回プロンプトを書いてループを押し進める状態からは、かなり変わりました。

 公開版を作りました
社内ルールを除いた、汎用版の interview-dev-loop を GitHub に出してみました。

Codex / Claude Code のどちらでも使えるように、できるだけエージェント非依存にしています。
使うときは、タスク開始時に明示的に呼び出すのがおすすめです。
$interview-dev-loop XX画面で◯◯機能を新しく追加する
インストールしたい場合は、使っている開発エージェントに次のように伝えると進めてくれると思います。
https://github.com/unsu0707/interview-dev-loop の Skill をインストールして

 これから試したいこと
今は、さらに前段のチケット作成や、後段の E2E テストまで含めて、どこまでループを広げられるかを試しています。
エンジニア各自のための開発エージェントを作り、それらがNotion、Slack、GitHub を定期的に見て、自分の環境上にインストールされた Codex に指示を出す。そうやってまずバグ修正・小さな改善タスクなどを任せるようにしてみたい。
人間が判断すべきところと、人間が毎回止めなくていいところをきちんと考えて、AIネイティブな開発が実現できるかを実験しています。

 最後に
AI駆動開発をチームで機能するようにすることは大変だったけど、いろいろと学びがありました。

チームで同じ判断基準を持つ。
使いながら、どこを直せばチームで使えるようになるのかを考える。
次の人が、それをまた使う。

その繰り返しで、AIの使い方そのものがチームの資産になっていくのだと思います。
もちろん、これが正解だとは思っていません。
最近は、AIネイティブな開発を組織でどう進めるかについての記事や事例も増えてきました。
そうした知見も学びながら、自分たちの開発ループを更新していきたいです。
interview-dev-loop は、その最初の形でした。
個人では回る AI駆動開発を、チームでどう回すか。
同じことを考えているチームの参考になればうれしいです。
