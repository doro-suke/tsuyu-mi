## 本文
Claude Code が出力する 200 行の Markdown レポートは、承認されたのかどうかすら一目でわかりません。本記事は HTML/CSS を書けない非デザイナーが、claude.ai の「Design」機能で「確定事項と検討経緯を色温度で分けた」HTML レポートテンプレートを作り、それを Claude Code 経由で、編集会議を自動化する自作のスラッシュコマンド /editorial（Claude Code のカスタムコマンド。記事の企画・構成・SEO 戦略を対話で固める筆者のワークフロー）へ統合するまでの実装手順を、再現可能な 5 ステップと公開中の実例つきで解説します。
本記事は、AI に HTML を直接生成させる「不当な有効性」を Markdown と比較した前作（理論編）の 実装・実証編 です。理論的背景と Markdown / HTML の役割分担は前作で詳述しています。


本記事は、Claude Code でマルチエージェントワークフロー（/editorial 等）を運用していて、前作で HTML 出力に興味を持ったものの、HTML/CSS は書けない非デザイナーの方を対象にしています。

 なぜ Markdown レポートでは限界なのか
結論から: Markdown は「狭いキャンバス」であり、長くなるほど人間に消費されなくなります。AI エージェントが量産するレポートは、まさにこの「長くなる」性質を持っています。
筆者のワークフローでは /editorial（編集会議）・/analytics・/review が、それぞれ企画書・GA サマリ・レビュー結論をすべて Markdown で吐き出します。200 行の Markdown レポートを前にしたとき、「結局この企画は承認されたのか」「どのセクションがボリューム的に重いのか」が、スクロールしても頭に入ってきません。承認ステータスもボリューム感も、テキストの行列に埋もれてしまうのです。これが消費効率（Consumability）の欠如です。Markdown が苦手なもの——空間レイアウト、信号機のような状態表現、ボリュームを面積で示すバー——を、テキストの1次元で代用しているために起きます。
Anthropic の Claude Code チームのエンジニアである Thariq Shihipar 氏は、Claude Code に「Markdown の壁」の代わりに 20 個の自己完結型 .html ファイルを作らせた事例を公開し、こう述べています。

Twenty self-contained .html files an agent produced instead of a wall of markdown. Each one trades a document you'd skim for one you'd actually read.
（Markdown の壁の代わりにエージェントが生成した 20 個の自己完結型 .html ファイル。そのどれもが、斜め読みする文書を、実際に読まれる文書へと取り替えている）
— Using Claude Code: The Unreasonable Effectiveness of HTML


同じ時期、Andrej Karpathy 氏も「AI への入力は音声が便利だが、出力は視覚が圧倒的に効率がいい」「視覚は脳への 10 車線の情報スーパーハイウェイだ」という趣旨の提案をしています。なお「10 車線の高速道路」は氏の比喩を二次情報経由で要約したものです（出典: Quasa による Karpathy 解説、dsebastien.net 2026-05-12）。
理論編を公開したあと、読者から最も多く返ってきた「次の問い」はこうでした。

理論はわかった。で、デザインできない自分はどう作るのか。

本記事はその問いに、実際に動いているワークフローで答えます。


 非デザイナーは Claude に何を頼んだのか
結論から: デザインを「描く」のではなく、情報構造と見せ方の意図を言語化して渡すだけで、テンプレートの初稿（叩き台）は生成できます。あとは試行と微調整で詰めます。非デザイナーに必要なのは、CSS の知識ではなく「何をどう見せたいか」の解像度です。

筆者が claude.ai の Design 機能に渡した要件は、大きく 3 つの方向性で構成しました。


ペルソナと文脈の付与:「あなたは編集会議の意思決定を支援する情報デザイナーです」と役割を与え、誰が・どの場面で・何を判断するために読むのかを明示する

数値での具体指示:「いい感じに」ではなく、確定事項と検討経緯の差を「背景色・罫線の実線/破線・不透明度」という具体的な視覚属性で指定する

構成のブロック化: レポートを 10 個のブロック（A〜J）に分割し、各ブロックに「何を載せるか」と「推奨する視覚効果」を表で渡す

特に 3 番目が肝でした。長大な指示を一度に渡すと AI の出力精度は落ちます。「10 ブロックを A〜J で構造化し、ブロックごとに視覚効果を指定する」という分割統治にすることで、各ブロックの完成度を1つずつ詰められます。実際に渡した構成表が以下です。

この表自体が「非デザイナーが claude.ai の Design 機能に渡した仕様書」です。「同心円状の関連度マップを SVG で」「信号機の比喩でステータスを最上部固定に」と意図だけを言語化すれば、実装（CSS の border-radius、SVG の座標計算、@media print）は claude.ai の Design 機能が引き受けます。デザインスキルではなく、情報を構造で捉える力が成果物の質を決める——これがデザインの民主化の実体です。

 HTML レポートを「色温度」で設計する—確定事項と検討経緯の分離
結論から: このテンプレートの核心は「色温度による情報の分離」です。確定事項は濃色・実線、検討経緯は淡色・破線、GA データは別レイヤー。読み手は色温度だけで「決まったこと」「考えた経緯」「データ根拠」を瞬時に見分けられます。なお本記事でいう「色温度」とは、背景色の濃淡・罫線の実線/破線・不透明度をひとまとめにした視覚的な温度差の比喩です。
編集会議のレポートには、2 種類の情報が混在します。ひとつは「タイトルは A 案に確定」のような結論。もうひとつは「当初案は B だったが、自己カニバリ（前作と検索キーワードが食い合うこと）のリスクで却下した」のような検討経緯です。Markdown ではこの 2 つが同じ太さの文字で並ぶため、読み手は毎回「これは決定事項か、それとも途中で消えた案か」を文脈から判断させられます。
そこで Claude に、この区別を CSS のデザイントークンとして固定するよう依頼しました。実際に生成されたスタイル定義の核心部分が以下です。

styles.css
:root {
  --bg-card:     #ffffff;  /* 確定事項: 不透明な白カード */
  --bg-process:  #faf8f4;  /* 検討経緯: 淡い背景 */
  --bg-data:     #f1efe7;  /* GA データ: 別レイヤー */
  --line:        #e3dfd5;  /* 確定事項: 実線罫線 */
  --line-dashed: #c4bfb5;  /* 検討経緯: 破線罫線 */
}

/* 確定事項 — 濃色・実線・不透明 */
.card        { background: var(--bg-card); border: 1px solid var(--line); }

/* 検討経緯 — 淡色・破線（“まだ揺れている情報”であることを視覚化） */
.card.process { background: var(--bg-process); border-style: dashed; border-color: var(--line-dashed); }

/* GA データ — 別レイヤーで囲い、根拠であることを示す */
.card.data    { background: var(--bg-data); }

承認ステータスは信号機の比喩で最上部に固定し、属性 1 つで色が切り替わるようにしました。これにより「いま条件付き承認なのか、再検討なのか」がページを開いた 0.5 秒で伝わります。

styles.css
.status-chip[data-status="approved"]    { --chip-fg: var(--ok);   --chip-bg: var(--ok-bg); }   /* 緑: 承認 */
.status-chip[data-status="conditional"] { --chip-fg: var(--warn); --chip-bg: var(--warn-bg); } /* 琥珀: 条件付き */
.status-chip[data-status="rejected"]    { --chip-fg: var(--bad);  --chip-bg: var(--bad-bg); }  /* 赤: 再検討 */

そして意思決定プロセスのブロックでは、却下された案をあえて消さずに残すよう指示しました。採用案は実線・濃色、却下案は破線＋取り消し線です。

styles.css
.opt.chosen   { border-style: solid; border-color: var(--ink); background: var(--bg-card); }
.opt.rejected { border-style: dashed; text-decoration: line-through; opacity: 0.7; } /* 透明性のため削除しない */

「却下案を残す」のは単なる装飾ではありません。なぜその企画になったのか、どの選択肢を捨てたのかが第三者（編集長・将来の自分）に追跡可能になり、意思決定の透明性が担保されます。確定事項の原本性と、検討経緯の透明性を、色温度という 1 つの軸で両立させる——これが非デザイナーが見つけた設計の答えでした。


 /editorial ワークフローへどう統合したか
結論から: テンプレートを /editorial の最終出力レイヤー（Phase 4.5）に組み込み、編集会議の完了時に Issue / Markdown / HTML の 3 アウトプットが同時生成されるようにしました。前作で「統合案」として予告した構想を、ここで実証します。
/editorial 完了時に生成される 3 つの成果物は、それぞれ「次に誰が読むか」で役割が分かれています。
HTML を生成する LLM には、データを正しく配置させるための「分析ブリーフ」を渡しています。これは「どのデータを 10 ブロックのどこに、どう変換して置くか」を仕様化した指示セットです。


スクラップ分析: テーマ・技術スタック・要点を抽出し、構成ツリー（ブロック C）の出発点としてマッピング

ライブラリアン調査: 既存記事との関連を直接/強い/間接の三層に分類し、同心円マップ（F）へ配置

GA データ分析（任意）: 実データがあれば KPI スコアカード・ヒートマップ（G）へ。無ければ <section id="sec-g"> を丸ごと削除

対話型提案: AskUserQuestion の全ステップを保持し、採用/却下案を区別して縦型ステッパー（I）へ

編集長承認: 最終判定を最上部の信号機チップ（A）に最優先で反映し、承認印（I）と必ず連動

実装上は index.html / styles.css / script.js の 3 ファイル構成としつつ、CDN やビルドツールなどの外部依存を一切持たない自己完結型にしました。「自己完結」とは単一物理ファイルの意味ではなく、外部依存ゼロでそのまま動く、という意味です。index.html をダブルクリックするだけで動き、ローカルで即プレビューでき、配布も容易です。この設計は Claude Code 公式ドキュメントが「ブラウザで開けるインタラクティブな自己完結型 HTML ファイルを生成させる」をベストプラクティスとして推奨している方向と一致しています。
なお、このワークフローは /editorial（編集会議）固有のものではなく、GA4 月次レポート・提案書・調査サマリなど、任意の定常 Markdown レポートにも転用できます。/editorial を 12 エージェント体制で運用するに至った経緯は１週間で最強の編集チームを作った話で詳述しています。

なお /editorial の「複数エージェントによる協調」を Agent Teams で実行する場合、Agent Teams は 実験的機能でデフォルト無効であり（2026 年 5 月時点）、CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 の有効化と Claude Code v2.1.32 以降が必要です（Orchestrate teams of Claude Code sessions）。本テンプレート自体はサブエージェント単体でも、Agent Teams でも生成できます。


 非デザイナーが今日から始める 5 ステップ
結論から: 既存の Markdown 出力ワークフローを HTML 化するのに必要なのは、企画→テンプレート作成→組み込み→ブリーフ注入→継続改善の 5 ステップだけです。デザインスキルは要りません。

 Step 1: 企画と要件定義
対象を 1 つに絞ります。筆者は「編集会議（/editorial）の成果物」を選びました。次に課題を言語化します——「長大な Markdown で承認ステータスが埋もれる」「ボリューム感がわからない」。最後にゴールを「確定事項と検討経緯を色温度で分離し、一目で把握できるダッシュボード」と定義します。ここまでは 1 文字も CSS を書きません。

 Step 2: Claude を用いたテンプレート作成
前章の「10 ブロック構成表」と「色温度の数値指定」を claude.ai の「Design」機能に渡し、テンプレートの初稿を生成させます。ここがこのワークフローの肝で、デザインの実作業はすべて claude.ai の Design 機能が担います。要件提示 → プレビュー確認 → 微調整のループを数回回すのがコツです。AI に一度頼んで完成、とはなりません。試行回数と人間の最終調整を前提にしてください。出来上がった初稿を report_templates/editorial/ 配下に取り込み、メンテナンス性のため HTML・CSS・JS は独立ファイルに分けつつ、CDN 等の外部依存は持たせません（前述の自己完結型）。

 Step 3: ワークフローへの組み込み
既存のスキル/コマンド定義（.claude/commands/editorial.md）に、成果物生成の必須工程として「HTML レポートの作成（Phase 4.5）」を追加します。出力先は slug ベースで一貫させます（editorial-reports/<slug>/）。これで「普段どおり実行すれば HTML も付いてくる」状態になります。

 Step 4: 分析ブリーフ（Context）の注入
AI がデータを正しく配置するための「仕様書」を書きます。スクラップ・ライブラリアン調査・GA データ・対話ログを、テンプレートの A〜J のどこに置くかを具体化し、条件分岐（GA が無ければ G ブロック削除、単発なら連載 UI 削除）も明記します。前章のブリーフがそのまま雛形になります。

 Step 5: 適用と継続的改善
普段どおり /editorial <scrap_path> を実行し、生成された index.html を各デバイスの実機で確認します。レイアウト崩れ・モバイル非対応が混じることがあるため、生成物は「叩き台」と捉え、CSS やブリーフの指示を微調整します。最後に、生成レポートをライブラリ目録と連動させ、リポジトリ全体の可視性を高めれば知的資産になります。
実際にこのワークフローで生成・公開しているレポートの実例を 2 つ挙げます。どちらも 200 行を超える検討経緯が、スクロールせずに「承認ステータス・構成ボリューム・却下案」まで一目で把握できます。ぜひ実物で確認してください。

 実例 1: 本ブログで最も読まれている記事の編集会議レポート
Anthropic の 5 パターンで Claude Code エージェント設計を分類するは、本ブログで群を抜いてアクセスの多い cornerstone 記事です。その企画がどう決まったのか——ペルソナ・構成・SEO 戦略・編集長の承認判断までの全プロセスが、この HTML レポートに凝縮されています。


 実例 2: いま読んでいる「この記事」自身の編集会議レポート
本記事もまさにこのワークフローで企画されました。あなたがいま読んでいる記事が、どんな対話を経て・どの案を却下して生まれたのか——その意思決定プロセスがそのまま HTML 化されています。記事と編集会議レポートを見比べると、「色温度による分離」が実データ上でどう機能するかが体感できます。



 まとめ：Markdown と HTML の耐久性層別化
本記事では、非デザイナーが claude.ai の「Design」機能に「情報構造と見せ方の意図」だけを渡してテンプレートを作り、色温度で確定事項と検討経緯を分離した HTML レポートを、Claude Code 経由で /editorial の Phase 4.5 に統合するまでを実証しました。


狭いキャンバス問題: Markdown は長くなるほど消費されない

意図の言語化: 10 ブロック構成表と数値指定で、デザインスキルなしに品質を引き出す

色温度分離: 確定＝濃色・実線、検討＝淡色・破線、GA＝別レイヤー

3 アウトプット統合: Issue / Markdown / HTML を「次に誰が読むか」で使い分ける

逆に言えば、HTML 化はタダではありません。テンプレートの保守コスト、生成時のトークン増、Git diff でのレビューや全文 grep のしにくさといった負債を伴います。頻繁な差分レビュー・全文検索・原本性が最優先の成果物は Markdown のままにすべきで、HTML が報われるのは「人間が一目で意思決定する」局面に限られます。
Zenn 記事は「永続原本」の層なので Markdown のままが正解です。一方、毎回更新され消費効率が問われる編集会議レポートは HTML の層に置きます。「Markdown は長すぎて読まれない」という本記事の主張の証拠は、記事の文字数ではなく、先ほどリンクした 2 つの実例 HTML が長大な検討経緯を一目で消費可能にしていることそのものです。両者は対立しません。原本性は Markdown が、消費効率は HTML が担う——この役割分担こそが結論です。
冒頭の問いに戻ります。承認されたのかすら一目でわからなかった 200 行の Markdown レポートは、色温度と信号機チップを得て、開いた瞬間に意思決定できるダッシュボードに変わりました。HTML/CSS を書けなくても、「何をどう見せたいか」を言語化できれば、その変換は今日から始められます。
