## 本文
このページの話をざっくり言うと、「AI に直接プロンプト打つんじゃなくて、“自走する仕事ループ”を設計しよう」 って話だよ。

 まず「ループエンジニアリング」って何？
ふつうの使い方だと、キミが AI にプロンプト書いて、返ってきたの読んで、また指示して…って人力ターン制チャットじゃん？
ループエンジニアリングはそれをやめて、

「キミの代わりに “AI をプロンプトして動かし続ける仕組み” を作る」

って発想だよ。
イメージとしては:

前: キミ＝マネージャー兼作業者で、AI に一手ずつ指示出してた
今後: キミ＝ループの設計者で、「仕事を見つけて→割り振って→チェックして→記録する」ミニ工場を組む

で、そのミニ工場（ループ）が自動で回り続ける、みたいな感じだね。

 ループを構成する5つ＋1のパーツ
著者は、ループにはだいたい5つの部品＋記録用のメモリがいるって言ってる。


Automations（自動実行）

一定のスケジュールで勝手に走るジョブ。
例: 毎朝「昨日の CI 失敗まとめて、気になるのを洗い出す」とかを自動でやるやつ。



Worktrees（作業用の別チェックアウト）

複数のエージェントが同じリポをいじってもコンフリクトしないようにする箱。
Git worktree で、エージェントごとに別ディレクトリ＆別ブランチを割り当てるイメージ。



Skills（プロジェクト知識の固まり）


SKILL.md みたいなファイルに、「このプロジェクトのルール」「ビルド方法」「やっちゃダメなこと」を書き溜めた再利用できる説明パック。
これを毎回読むことで、AI が毎回ゼロから推測しなくて済む。



Plugins / Connectors（外部ツールとの接続）

GitHub / Linear / Slack / DB / CI など、AI が“本番の作業環境”に手を伸ばせる窓。
ここがあると、「直しました」→終わり、じゃなくて「PR 作って、チケット紐づけて、CI グリーンになったら通知」まで自動でいける。



Sub-agents（サブエージェント）

「作る人」と「チェックする人」を別の AI に分ける。

同じモデルに「自分の宿題を自分で採点させる」より、役割・指示の違う別エージェントにレビューさせたほうがマジで安全って話。



State（外部の記録・メモリ）

Markdown ファイルとか、Linear のボードとか。

「何を見つけたか」「何を試したか」「どこまで終わったか」 を会話履歴じゃなくディスク側に書いておく。
モデルは毎回忘れるけど、リポとファイルは忘れないからね、っていう発想。




 Codex と Claude Code でほぼ同じ部品が揃ってる
Addy は、「ツールごとの違いより、ループの“形”のほうが大事だよ」って言ってる。

OpenAI の Codex App も
Anthropic の Claude Code も

名前は違うけど、上の 5+1 パーツをほぼ全部内蔵してるから、「どのツールを使うか」より、「どうループをデザインするか」が重要だよね、っていう主張。

 Automations: ループの心臓（勝手に動く部分）
ここが「ただの一回きりの実行」と「ループ」の一番の違い。

スケジュールで走る
何か発見したら「Triage inbox」や Markdown/Linear に投げる
何もなかったら静かに消える
その中で $skill-name みたいなスキル呼び出しもできる

Claude 側だと /loop とか cron、hooks、GitHub Actions で同じニュアンスを実現してる。
さらに /goal ってコマンドは、

「この条件になるまで続けて」っていうゴール駆動モード

例: ‎⁠"test/auth のテスト全部パスして lint もクリーン"⁠
各ターンのあとに別モデルが「もう終わった？」ってチェックする
→ 作業した本人じゃなくて、別のヤツが「ゴール達成したか」を見る感じ

Codex も /goal を持ってて、ノリはほぼ同じ。

 Worktrees: 並列作業の地獄を回避するクッション
AI エージェントが2体以上同時に動き出すと、

同じファイルを同時に編集 → コンフリクト地獄
片方が上書きしてもう片方の成果が消える

みたいな、ふつうの人間チームでも起きるやつが発生する。
そこで git worktree を使って:

各エージェントを別チェックアウトの世界線に隔離

終わったらマージ・レビューだけ人間がやる

ってスタイル。
ツールが勝手にコンフリクトを防いでくれても、「その結果をレビューする人間の帯域」がボトルネックだよね、っていう話もしてる。

 Skills：毎回 “自己紹介・プロジェクト紹介” するのをやめる
AI って、プロジェクトに対する記憶を基本持たないから、毎回「このリポはこうで〜」「この会社では〜」って説明しがちでしょ。
それを一回ちゃんと SKILL として書き出して、何度も再利用するのがスキル。

プロジェクトのコンベンション
ビルド／テストの流れ
地雷・避けたい設計（過去の事故とか）

これをスキルとして外部化することで、

AI が毎回テキトーに想像で補完する（＝変なクセのコードを書く）
「意図の借金（intent debt）」が積み上がる

みたいなのを防ぐ、っていう主張。

 Plugins / Connectors：ループを “現場” に繋ぐ手足
ファイルシステムだけ見えてる AI って、言ってみれば部屋の中でコードだけ書いてる人みたいな感じ。
Connectors を使うと、AI が:

Issue Tracker（Linear とか）を読める
DB を叩ける
ステージング API をテストできる
Slack に通知を飛ばせる

みたいな、「ちゃんとエコシステムに参加してる開発者」っぽく振る舞える。
で、Plugins は Skills と Connectors をまとめた配布パックみたいなイメージで、「これ入れたらこのチーム用のループ一式が使えるようになるよ」ってやつ。

 Sub-agents：作る人とチェックする人を分けようぜ
ここが一番重要って言ってる。

コードを書いた本人（＝モデル）が、自分でレビューすると甘くなる
だから別のエージェントを「ツッコミ役」専任にする


構成例としては:

1体目: 仕様を読み解いて「どう実装するか」設計する
2体目: 実装を書く
3体目: テストと仕様を元にチェックする

みたいな「AI オーケストラ」構造。
もちろんエージェント増える分、トークンコストはゴリゴリ増えるので、全部を多重チェックするんじゃなくて「ここは絶対ミスれない」ってとこに集中投入しようね、って感じだね。

 1つのループが実際どう動くかの例
本文の例を人間向けに言い換えると、こんな流れのループだよ：

毎朝、Automation がリポに対して走る
Triage 用の Skill が以下を読んで、「今日やる価値あるやつ」を Markdown or Linear に書き出す

昨日の CI 失敗
Open な Issue
最近の commit


その「やる価値あるタスク」ごとに

別 Worktree を作成
Sub-agent A が修正案を書く
Sub-agent B がプロジェクト Skill とテストを使ってレビュー


Connectors 経由で

PR 作成
チケット更新
CI 状況によって Slack に通知


途中経過や結果は全部 State（Markdown / Linear） に追記

次の日の朝、その状態からまた続きが自動で走る



で、キミは「そのループそのものを一回設計した」だけ。
各ステップを毎回手でプロンプトしてないのがポイントだね。

 でも「ループ任せで OK」って話じゃない
著者はかなりハッキリ、

ループを組んでも検証は人間の仕事のまんまだよ
コードをレビューしないでループだけ回してたら品質は確実に落ちる

自分が理解してないコードがどんどん増える「理解の借金（comprehension debt）」が加速する

って警告してる。
あと、

ループがいい感じに動き始めると、
→ 「よくわかんないけど動いてるからヨシ！」って思考停止しがち（認知の降参/cognitive surrender）

まさにそこが危険ポイントで、
→ 「ちゃんと理解した上でテコ入れに使う人」と「理解避けるために丸投げする人」で結果が真逆になる


って話をしてる。

 結論: プロンプトから「ループ設計」へレバレッジポイントが移動した
最後のメッセージはこんな感じ:


これからは「うまいプロンプト一発」より 「うまいループ設計」のほうがレバレッジ高い


でもそれは「楽になった」じゃない

「エンジニアとしての責任の持ち方が変わった」ってこと



ループを回しつつ、以下の姿勢がないとマジで危ない

自分でコードをレビューする
仕様と動きを理解し続ける
どこに自動化を効かせてどこは人間が見るかを設計する



ざっくり言うと、

「ループは組め。でも“スタートボタンを押す人”じゃなくて、“ちゃんとコードを理解してるエンジニア”でい続けろ」

ってメッセージだね。
