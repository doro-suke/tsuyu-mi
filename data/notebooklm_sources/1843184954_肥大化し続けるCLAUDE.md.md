## 本文
はじめに
TOKIUM でエンジニアをしているちっちです。26卒として入社し、現在は2ヶ月の研修を経て開発に取り組んでいます。
突然ですが、今お使いのCLAUDE.mdは何行ありますか？
以前、中身を整理した方も気づくと膨れ上がっていませんか？
かくいう自分も研修を終えて数週間後、ふとCLAUDE.mdを開いてみると378行ありました。しかも、そこに書いてあることを自分でも半分くらい覚えていません。
書き足すたびに便利にしているつもりが、実際にやっていたのは自分でも把握できていないものを Claude に毎回読ませることでした。

 整理しても、静かに崩れていく
公式ドキュメントには、CLAUDE.md の大きさの目安について、次のように書かれています。

CLAUDE.md ファイルあたり 200 行以下を目標にします。より長いファイルはより多くのコンテキストを消費し、遵守を減らします

このような背景から、CLAUDE.mdの整理術を検索すると数多くの記事やサイトがヒットします。
公式にもv2.1.206から/doctorコマンドが導入され、CLAUDE.mdから「コードベースを読めば判断できること」を削る提案をしてくれます。
それでも自分のCLAUDE.mdは378行になりました。やり方が分からなかったからではありません。
書き始めた時点では87行でした。積み上げている最中、自分に肥大化している自覚はありません。どの追記もその時は正しい判断で、間違って足した行は一行もない。それでも合計だけが増えていきます。 そして合計を見る機会は、意図しない限り訪れません。
整理は一度で終わりますが、CLAUDE.mdの成長は続きます。必要だったのは、整備してくれる誰かではなく、膨らむ前に止めてくれる仕組みでした。

 書き込んだ瞬間、機械的に測らせる
やったことは単純です。ファイルに書き込んだ瞬間にフックで大きさを測り、決めた上限を超えていたら知らせる。 それだけです。

 そもそも「フック」とは
ひとことで言うと、特定の出来事が起きた瞬間に、自分で決めた処理を割り込ませる Claude Codeの設定です。
「ファイルに書き込んだら、このコマンドを走らせる」と登録しておけば、あとは書き込みのたびに、こちらが何もしなくても勝手に走ります。Git を使っている方なら、コミット前に自動でチェックが走る仕組みとほぼ同じ発想です。
実は公式ドキュメントも、この使い分けを勧めています。

特定の時点で実行する必要がある指示（例えば、すべてのコミット前またはファイル編集後）の場合は、代わりに hook として記述してください。Hook はシステムコマンドとして固定されたライフサイクルイベントで実行され、Claude が何をするかに関係なく適用されます。

つまりこれは「綺麗になったCLAUDE.mdのリバウンドを防ぐ」うえで、ルールを強制する絶好の仕組みです。

 割り込ませた処理
書き込みの直後に走らせているのは、35行ほどのシェルスクリプト1本だけです。測る部分は単純で、効いているのは上限超過したときに何を返すかのほうでした。
フックのスクリプト#!/bin/bash
# 書き込まれたファイルの情報は、標準入力に JSON で渡ってくる
payload=$(cat)
# jq は JSON を読むための小さなコマンド。これが無いと読めないので、黙って素通りせず先に知らせる
command -v jq >/dev/null || { echo "🚨 このフックには jq が必要です" >&2; exit 1; }

# Edit / Write は、書き込み先のパスがそのまま渡ってくる
path=$(printf '%s' "$payload" | jq -r '.tool_input.file_path // empty')
# Bash には渡ってこないので、その場合は作業ディレクトリ直下の CLAUDE.md を見る
if [ -z "$path" ]; then
  cwd=$(printf '%s' "$payload" | jq -r '.cwd // empty')
  [ -n "$cwd" ] && path="$cwd/CLAUDE.md"
fi
[ -n "$path" ] && [ -f "$path" ] || exit 0

# 上限を決めたファイルだけを対象にする。決めていなければ何もしない
case "$(basename "$path")" in
  CLAUDE.md) limit=12288 ;;
  *)         exit 0 ;;
esac

size=$(wc -c < "$path" | tr -d ' ')
[ "$size" -le "$limit" ] && exit 0

cat >&2 <<EOF
🚨 上限を超えました: ${size}B（上限 ${limit}B）
   🚫 削るのではなく、置き場を変えてください
   ⚠️ 常に効いている必要があるルールは移さない（移した時点で読まれなくなる）
   1. その時だけ必要な手順 → docs/ へ移動。残す1行は「いつ開くか」を動詞で書く
      ✅ PR を作る前に docs/xxx.md を読む
      ❌ 全文＝docs/xxx.md（〜について）
   2. 特定のファイルを触るときだけ効くもの → .claude/rules/ へ（paths: frontmatter が要る）
   3. 失効したルール → docs/archive/ へ移動（🚫 削除しない）
EOF
exit 2   # この終了コードにすると、メッセージが AI 側に返る

これを ~/.claude/hooks/claude-md-size-guard.sh として保存し、実行権限を付けます。
chmod +x ~/.claude/hooks/claude-md-size-guard.sh
あとは ~/.claude/settings.json に、書き込みのたびに呼ばれるよう登録するだけです。
settings.json への登録{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|Bash",
        "hooks": [{ "type": "command", "command": "/絶対パス/claude-md-size-guard.sh" }]
      }
    ]
  }
}

matcher は、どのツールが動いたときにフックを走らせるかを、ツール名で指定する欄です。ファイルが書き換わるのは Edit と Write、それにシェル経由の追記があるので、Bash まで含めて指定しています。
なお、上限はコンテキストを実際に食っているバイト数で決めています。これは、行数では「1行が10文字なのか300文字なのか」データ量の区別が難しいからです。自分が眺めるときは行数、機械に測らせるときはバイト、と分けています。

 捨てるのではなく、置き場を変える
上限を超えると、Claudeはフックから次のメッセージを受け取ります。
🚨 上限を超えました: 25147B（上限 12288B）
   🚫 削るのではなく、置き場を変えてください
   ⚠️ 常に効いている必要があるルールは移さない（移した時点で読まれなくなる）
   1. その時だけ必要な手順 → docs/ へ移動。残す1行は「いつ開くか」を動詞で書く
      ✅ PR を作る前に docs/xxx.md を読む
      ❌ 全文＝docs/xxx.md（〜について）
   2. 特定のファイルを触るときだけ効くもの → .claude/rules/ へ（paths: frontmatter が要る）
   3. 失効したルール → docs/archive/ へ移動（🚫 削除しない）
これをもとにClaudeは内容を削るのではなく、CLAUDE.mdに置く必要がないものを判別して、指示された行き先へ移してくれます。
実際に上限を意図的に超えさせてみると、次のように動きました。本体にべた書きしていた運用手順が docs/ へ丸ごと移り、本体には見出しと1行のリンクだけが残っています。
 ### 記録ファイルとスプリントの運用

-#### 進捗ログの運用
-（中略：この節の手順本文）
+**記録を書く前・新スプリント開始時に [docs/記録ファイルとスプリント運用.md](…) を開く。**
+（進捗ログの置き場と書き方／スプリントの区切りとフォルダ規約／`temp/` の使い分け／フォルダ全体図）
CLAUDE.md は 25,147B から 10,281B（241行 → 127行）になりました。移動先の docs/記録ファイルとスプリント運用.md は 16,629B です。移動元にあった実質94行は一字一句そのまま存在し、削除は1件も起きていません。
移した先は常に読み込まれるわけではなく、残した1行に書いた場面——この例なら「記録を書く前」と「新スプリント開始時」——になったときに開かれます。
削除ではなく移動なので、判断を間違えても戻せます。そのため承認は挟まず、そのまま実行させています。

 フックによりリバウンドを防げる？
CLAUDE.mdを整理して130行まで落とし、その上限を約12KBに決めて、フックを導入した前後7日間で比較してみました。

導入前は7日間で170行から378行へ、データ量にして約2.8倍に膨らんでいました。導入後は130行から131行、データ量で1.2%の増加に収まっています。2週間経った今も131行のままで、公式の目標である200行は余裕で守れています。
ただ正直に言うと、対策後の7日間は 10,979B から 11,114B までしか動いておらず、上限の 12,288B には一度も届いていません。つまり +1.2% はフックが止めた結果ではなく、整理した直後だから保てている数字と見るのが正確です。フックはこの数字を作るためのものではなく、次にまた膨らみ始めたときに気づかせる予防線として置いています。

 おわりに
今まで/doctorや記事の整理術を参考にCLAUDE.mdを整理しても、数週間後に元通り大きくなっては再び整理することを繰り返していました。
そこで今回はClaudeのフックを活用することで、気づかぬ間に肥大化していたCLAUDE.mdを一定の大きさに保ち続けることができる仕組みを構築できました。効いているのは「上限を決めたこと」ではなく、「書き込んだ瞬間に鳴ること」のほうでした。
もし同じようにCLAUDE.mdのリバウンドに悩んでいる方は、ぜひ試してみてください。
