## 本文
Claude Code のセッションを、VSCode の拡張機能で5つほど並べて使っている。
Markdown が見やすく、コードも見られて、VSCode から離れなくて済むからだ。
ただ、パネルの見出しは短く、5枚並べるとどれが何をしているのか分からなくなる。
使用枠があとどれくらい持つのかも気になる。
そこで、動いているセッションを1枚で見るダッシュボードを自分用に作った。
いま動いているセッションの状態、その日の作業履歴、使用枠の推移、引き継ぎ台帳、
過去の会話の検索、毎朝の「今日やること」までが入っている。

架空のデータで作った画面
作るときに1つ決めたことがある。コードは一切読まない。
1年前にもバイブコーディングの連載を書いたが、そのときはコードを読みながら AI と作っていた。
今回は読まずに作るとどうなるかを試したかったので、画面の動きだけを見て「こう動いてほしい」と伝え、
直させることを繰り返した。見た目だけは途中で気に入らなくなり、AI と相談して
余白・文字の大きさ・色の意味の決まりを作った。
初期版は1週間ほどで固まり、1か月足らずでほぼ今の形になった。コードは約12,000行ある。
速さは想像以上だった。
この記事は、その読まなかったコードの中に何があったか、という話だ。
しかも AI は、それに気づいていた。


 この記事を書くために調べさせたら、まだあった
記事を書く前に、Claude に「同じ数字なのに、画面ごとに取り方が違うところはまだあるか」と調べさせた。
以前に一度リファクタリングをしていて、そのときに整理は済んだと思っていた。
あった。「1日に使ったトークン」の数え方が、画面によって2通りあった。
使用枠の推移の画面は、サブエージェントが使った分を親のセッションに足して数えている。
サブエージェント（重い調査を任せる子のエージェント）の記録は親とは別のファイルに書かれるので、5時間枠ごとに見ると、実際の 1/9 ほどに見える回があった。その対策だ。
ところが作業履歴とセッションカレンダーは、親のセッションの記録だけを数えていた。
見つかった後、別のセッションに直させた。直す前と後を並べると、こうなる（単位は百万トークン、1日の始まりは7時）。

サブエージェントをよく使った日ほど、作業履歴の数字が小さく出ていた。
直した後は、2つの画面の数字がどの日も一致している。
人が作るなら、同じ「使ったトークン」を2か所で別々に数えることはまずしない。
数える関数を1つ作って、両方の画面から呼ぶ。

 気づいていなかったわけではない
Claude Code の会話の記録は既定では約30日で消えるが、このダッシュボードは依頼と返答の文を自前で控えている。
それを遡ると、経緯はこうだった。
使用枠の推移の画面を作った日、Claude はこう報告してきた。

これまでの5時間枠の按分は、サブエージェントの消費を1つも数えていませんでした。（中略）8.8倍の過小評価でした。今回から親に合算しています。

同じ報告の中には作業履歴の画面にも手を入れたと書いてある（見出しの付け方を直した）。
同じ日に同じファイルを触っていながら、作業履歴のトークンの数え方には一言も触れていない。
10日後のリファクタリングでは、作業履歴とセッション一覧の組み立てを1つにまとめた。
確かめ方は「直す前と後で、画面のデータが一致するか」。作業履歴は前から親の記録だけを数えていたので、
一致して通った。ずれも一緒に、そのまま守られた。
その4日後、詳細ページの設計を相談していたとき、Claude は回答の途中にこう書いていた。

前の回答で保存を推した一番の理由は「サブエージェントの分が控えに入っていない」でした。これは1時間ごとの欄とは別の問題で、改善案の文書には制限7として載っています（「急がない」の扱い）。今回の PR からは外します。作業履歴でサブエージェントを多く使った作業が小さく見えて困ったときに、別の作業として取り上げます

自分の返事は「外しましょう」だった。ただしこれはそのとき聞かれていた1時間ごとのトークンの欄への返事だ。
外すと書かれた1文は回答の途中にあり、その1文について自分が何か答えた記録は無い。


 記録を遡ると、同じ型が何度も出てくる
ほかにも同じような場面がないか、ダッシュボードを触った48本のセッションの記録を調べた。
大きく3つの型に分かれた。

 1. 分かっていて、後回しにする
上のトークンの件がこれにあたる。
同じ「後回し」でも、別の日には、返事待ちの判定が遅い原因（画面の作り直しに約10秒かかる）を
Claude が見つけ、「これ以上は直さず、別の作業として扱う」かどうかを、表にして聞いてきたことがある。
こちらは自分で「いったん良い」と決めた。
違いは判断を求める場所に書かれていたかどうかだけだ。
回答の途中に書かれると、人は読み流す。

 2. 見ていないのに、言い切る

他ツールとの比較で、自分のダッシュボードに無い機能を3つ挙げた。実装を読み直すと2つはあり、
訂正の中でもう1回同じ誤りをした
詳細ページに「最後の依頼」の欄が欠けていると言った。実際は出ていた
画面の新しい表示を説明されたが、3つとも、どこに出ているのか分からなかった。
Claude が説明していたのは、まだ配備していない試験用の写しの画面で、自分が開いていたのは普段の画面だった
画面の作り直しにかかる時間を「数秒」と見積もった。測ると約10秒だった
この記事のために直す前の数字を数えたとき、Claude は1日の区切りを0時として表を作った。
ダッシュボードの既定は7時で、設定ファイルが無いことを0時と読み替えていた。
直しを担当した別のセッションが、画面の数字と突き合わせて見つけた

どれも、Claude は自分が書いたもの・作ったものを根拠に話していて、
実物（実装・人が見ている画面・測った数字）を見る前に言い切っていた。

 3. 言葉の意味が、人の想定と違う

「返事待ちなのに音が鳴らない」と聞いたら、原因は、Claude の決めた「返事待ち」に
実行許可の確認で止まっている状態が入っていなかったことだった。
画面の説明にも「止まっている」の例として書いてあったが、自分にとってはどちらも「自分の番」だった
「使用枠の％にワークフロー（何体ものエージェントをまとめて動かす仕組み）の分も入っているか」と聞くと、
「入っている」と返ってきた。後で、入っていたのは画面上部の全体の数字だけで、
セッションごとのカードの数字には入っていなかったと訂正された
そして冒頭の「使ったトークン」は、画面によって意味が違っていた

自分は「みんな同じ数え方だよね」と確かめていたつもりだった。控えを遡ると、聞いていたのはこうだ。

これってここに表示されている%分が5hに加算されているという感じですか？

Claude の答えは「全セッションを足すと5時間枠の%そのものになります。定義上ぴったり足し合わさります」。
これは正しい。ただ、確かめたのは「カードの％を足すと上の帯の％になるか」で、
作業履歴の数字は話に出ていない。自分は「みんな」のつもりで聞き、Claude は聞かれた範囲に正しく答えた。

付け加えておくと、どの場面でも Claude は最後には自分で誤りを認めて直している。
ただ、訂正のきっかけは毎回、こちらの「分からない」「通知も出てない」という返事か、Claude が実際に測った数字だった。
何も言わなければ、そのまま進んでいた。

 コードを読まない代わりに、決まりを足した
コードを読まないと決めた以上、こちらにできるのは Claude への指示を変えることだけだった。
上の型に当たるたびに、Claude Code の指示ファイル（CLAUDE.md）に決まりを足していった。

後回しにする
判断してほしいことは、回答の決まった見出しの下に書く。途中に混ぜない


言い切る
「無い」と書く前に、探し方を2通り以上変える。「ある」「同じ」と書く前にも、確かめた実物を1つ挙げられなければ「未確認」と書く


意味が違う
数字を出すときは、何を数えたか（どこからどこまで・何を除いたか）を一緒に書く



それでも今回、トークンのずれは残っていた。決まりは Claude のこれからの書き方を変えるが、
すでに作られた部分を見直させるきっかけにはならない。

 割り切るところと、割り切れないところ
Claude はセッションが変われば別の AI のようにふるまう。今回は調べてもらったら見つかったが、
聞き方が違えば「ありません」と返ってきたかもしれない（これは確かめていない）。
聞き方を変えて何度も聞けば見つかるのかもしれないが、それはコストの無駄だ。
人なら、こういう作り方はしない。人の想定とは違う判断を AI はする。
個人のツールなら、それは「そういうもの」と割り切れる。
このダッシュボードも、日によって数字が2割以上小さく出ていたのに、困ってはいなかった。
ただ、しっかりしたプロダクトなら話は別だ。
今回の経験から、自分なら次の3か所を読む。

同じ数字を複数の画面で出している箇所。数える処理が1つにまとまっているか
AI が回答の途中で「外す」「別の作業として」と書いた箇所。何を外したのか
リファクタリングの確かめ方。「直す前と後で一致する」は、元からあったずれもそのまま通してしまう
