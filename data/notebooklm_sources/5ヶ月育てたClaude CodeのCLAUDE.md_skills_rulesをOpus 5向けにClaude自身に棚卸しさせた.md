## 本文
対象読者

Claude CodeでOpus 5を使っている人
以前のモデル向けにCLAUDE.md / skills / rulesを育ててきた人
Opus 5では既存設定を読み込ませない方がうまく動く気がするが、全部捨てるのも違うと思っている人


 モチベーション

5ヶ月ほどかけて、Claude Code用のCLAUDE.md / skills / rulesを育てていた
Opus 5では、それらを読み込ませない方が期待通り動くことが増え、一時的に読み込ませない運用にしていた
毎回それをやるのも面倒なので、Opus 5でも必要なものだけ残せないかと考えた


 結論

既存のCLAUDE.md / skills / rulesをOpus 5向けにClaude自身に棚卸しさせるのは、かなり楽だった


/claude-api prompt-auditコマンドでサクッとやってくれる


各ファイル内の指示については、残す・削る・書き換えるをかなりよしなに判断してくれた
ただし、「そもそもこのskillや仕組み自体がまだ必要か？」までは自発的には踏み込んでくれなかった
自前の自律開発ループも、こちらから「/goalで置き換えられない？」と提案して初めて、不要という判断になった
結果、skillは40個から6個、常時ロード量は32,694文字から9,465文字（72%減）になった

Opus 5向けに既存設定を棚卸しするなら、「今のモデル向けにどう書き換えるか」だけでなく、「そもそもこの仕組みは今も必要か？」から見てもらうのがよさそう。

 Opus 5では既存設定を読み込ませない方が期待通り動いた
自分の~/.claudeには、5ヶ月ほどかけて育てたClaude Code向けの設定があった。
内容はざっくり以下。

CLAUDE.md 308行

skills/ 40個

commands/ 6個
カスタムサブエージェント 2個
個人Decision Record 7件

単発のユーティリティだけでなく、要件定義、ADR、NFR、トレーサビリティ、DoRゲート、自律開発ループなども作っていた。
要件を整理して、設計して、テスト戦略を作って、実装して、検証する。
そういった開発フローをClaude Code上で回すために、かなり細かく仕組みを作っていた。
ところがOpus 5を使うようになってからは、これらを読み込ませない方が自分の期待通り動くことが増えた。
Opus 5では、以前より細かく指示せず任せる方向がよさそうということもあり、とりあえず既存のCLAUDE.md / skills / rulesを読み込ませないようにして使っていた。
ただ、毎回それをやるのは正直面倒くさい。
そもそも、読み込ませない方がいいなら、
「今のOpus 5に必要なものだけ残したらよくない？」
となった。
とはいえ、5ヶ月かけて作った設定を自分で1つずつ読み返して判断するのも面倒くさい。やってられない。ぶっちゃけ判断できない。
Claude Codeの設定なのだから、Claude自身にOpus 5向けに棚卸ししてもらうことにした。

 各ファイルの中身はかなりよしなに整理してくれた
まず、既存のCLAUDE.md / skills / rulesに書かれている指示をOpus 5向けに監査してもらった。
具体的には、/claude-api prompt-auditコマンドを使用し、ユーザーレベル設定のCLAUDE.md / skills / rulesをClaudeに監査してもらった。
自分の設定には、以前のモデル向けに書いた以下のようなものが残っていた。

このあたりはかなりよしなに整理してくれた。
単純に文章を短くするだけではなく、「この指示は今のモデルにも必要か？」という単位で判断して、残す・削る・書き換えるを選んでくれた。
Claude Code側ですでに持っている内容と重複しているなら削るし、逆に、Opus 5の挙動を踏まえて明示した方がよいものは残してくれた。
CLAUDE.md / skills / rulesの中に書いてある個々の指示を棚卸しするところは、かなり任せられるという印象だった。

 整理したのはいいものの、そもそもの必要性の検討が必要だと気付いた
自律開発フローで使っていたskillの1つをClaudeに監査させ、92行ほど圧縮した。
その30分後、そのskill自体をアーカイブした。
が、ここで順序を間違えていることに気づく。
使わないskillの文面をOpus 5向けにいくら整理しても意味がない。
Claudeは「このskillに書かれている指示は今も必要か？」はかなり細かく見てくれた。
一方で、「そもそもこのskillという仕組み自体、今も必要なのか？」までは自発的には踏み込まなかった。
ここで、「内容が適切か」と「仕組み自体が必要か」は別問題だと気づいた。
そして、見るなら後者が先だった。

 「そもそも使っている？」もClaudeに調べてもらった
そこで、既存のskillsを実際に使っているのかも調べてもらった。
Claude Codeの場合、自分の環境では~/.claude/projects/*/*.jsonlにツール呼び出しを含むtranscriptが残っていた。
ここからskillの発火実績を集計できるとのことで、Claudeに集計を依頼した。
結果、直近1ヶ月では40個中35個のskillがゼロ発火だった。
発火していたのも、GitHub Issue作成やユニットテスト実装など、単発で目的が明確なskillが中心だった。
一方、要件定義から実装までをつなぐ多段パイプライン系のskillは使われていなかった。
さらに、そのパイプラインから生成していたrequirements.mdやarchitecture.mdなどが後工程でReadされているかも確認した。が、自分の環境で確認した範囲では0件だった。
作る仕組みは残っていたが、実際には使っていなかったということになる。。。
ちなみに、transcriptの保持期間は環境によって異なる可能性がある。
自分の環境で確認できたのは約1ヶ月分だったので、ここから言えるのはあくまで「直近1ヶ月で使っていなかった」まで。
だが、この数字を見て、以前作った仕組みを残す理由はかなり薄くなった。

 自律開発ループも「/goalでよくない？」と聞いて初めて消えた
不要なskillを整理していくと、以前作った自律開発ループの一部だけが残ったが、これも「/goalで代替できない？」と考え始めた。
Claudeに聞いてみたところ、/goalで代替できる上に、細かくフローを制御するよりそっちの方が良いと回答してきたので、自前の自律開発ループもアーカイブへ退避することになった。
今回、ここが一番面白かった。
Claudeは既存のCLAUDE.md / skills / rulesを渡すと、その中身についてはかなり細かく要否を判断してくれた。
ただ、「この仕組みを作った当時にはなかった現在の機能で、仕組みごと置き換えられないか？」というところまでは、自発的には踏み込まなかった。
少なくとも今回の自分の環境では、そこはこちらで考える必要があった。

常時ロード量は32,694文字から9,465文字まで減った。
文字数からの概算では、約10.6k tokens/セッション相当の削減になるらしい。
不要と判断したskillも、いきなり削除はしていない。
Claudeからの提案に従い、Claude Codeから読み込まれないarchive/へ退避し、必要になれば戻せるようにした。
退避なら、「本当に困らないか？」をそのまま試せるので気が楽だった。

 今やるなら「Opus 5向けに直して」だけでは頼まない
今回やったことを振り返ると、最初の頼み方が雑だったと思う。
今回の振り返りから、もう一度やるなら、最初から例えば以下のように頼む。
既存のCLAUDE.md / skills / rulesについて、
中身を書き換える前に「仕組み自体が現在も必要か」を監査してほしい。

利用履歴から実際に使われているか確認し、
現在のClaude Codeの機能で代替できるもの、
使われていないもの、
生成物が後工程で利用されていないものを洗い出してほしい。

その後、生き残ったものだけOpus 5向けに内容を調整してほしい。
自前で大きな仕組みを持っているなら、これも聞く。
この仕組みを作った当時にはなかった現在のClaude Codeの機能で、
仕組みごと置き換えられないか？
繰り返しになるが、今回の経験では、「既存の仕組みをどう改善するか」と「既存の仕組みを捨てられないか」は別の話だった。
Claudeは前者についてはかなりよしなにやってくれた。
後者については、こちらから問いを立てた方がよさそう。

 やってみた所感

その後、軽く適当なものを開発させたが、期待・想定通りに動いてくれたため、仕組みが壊されることもなかった。
今後、新しいモデルが出るたびに、Claude自身に棚卸をさせるのが良さそう。

と、新たな疑問が湧き出てきた。
