## 本文
はじめに
AI 時代になって、コードを「書く」コストはずいぶん下がりました。
その一方で、「読む・理解する」コストはむしろ上がっている気がしています。
AI が一気に生成した大量の Markdown、巨大な PR の diff、初見のリポジトリ、長い設計メモや仕様書……。
こうした「理解しないといけない対象」の量と速度が増えて、認知負荷の高まりがあちこちで叫ばれていますよね。
もちろん「AI に要約させればいい」のですが、これにも地味な不満がありました。

出てくる見せ方が毎回似偏る（AI 臭い文章）。箇条書きのテキスト、など。
あとで別の角度から見たくなると、また同じ対象を丸ごと AI に食わせ直す必要がある
そもそも頭への入り方は人によって違う。マインドマップが刺さる人もいれば、シーケンス図でスッと入る人もいる

そこで、この認知負荷を少しでも下げるアイデアとして、解析対象の情報を YAML として起こし、それを元に HTML で図解化する Claude Code スキルを作ってみました。

この記事では、その設計の「ミソ」を中心に紹介します。

 この記事を読むと得られること

ドキュメント理解の認知負荷に対する、その軽減アプローチ
「意味（YAML）」と「見せ方（HTML）」を分離する設計の利点

yaml-to-html スキルの具体的な構成と使い方


 何が「しんどい」のか
理解の認知負荷を、もう少し分解してみます。
1. 対象が大きく、どこから読めばいいか分からない
ファイルが何十個もある PR やリポジトリを前にすると、まず「読む順番」を決めるところでエネルギーを使います。
2. AI 要約の見せ方が「AI 臭い文章」で、負荷がそこまで下がらない
「要約して」と投げると毎回それっぽいテキストが返ってきますが、表現はだいたい同じ。あとで「依存関係だけ図で見たい」「テーブルで一覧したい」と思っても、また対象一式を読み込ませ直すことになります。入力コンテキストが毎回膨らむわけです。
3. 頭への入り方は人それぞれ
同じ内容でも、

ある人はマインドマップ的な見た目の方が頭に入る
ある人はシーケンス図表記でカチッと並んでいる方が頭に入る
（エンジニア）レビュアーは読む順番とリスクが見たいが、PdM は目的と影響が見たい

同じ「意味」を、読み手に合わせて「見せ方」を変えたい。でも毎回 AI に最初から説明し直すのは、コスト的に割に合いません。

 作ったもの：yaml-to-html explainer
作ったのは、2 つのスキルから成る Claude Code プラグインです。理解したい対象を、オフラインで開ける HTML の「図解バンドル」に変換します。

パイプラインにすると、こういう流れです。
ポイントは、間に YAML という中間表現を 1 枚はさんでいることです。ここが今回いちばん伝えたい設計の核です。

 ミソ：「意味」と「見せ方」を分ける
このスキルの肝は、対象を「意味（core.yaml）」と「見せ方（view.yaml）」の 2 枚に分けて YAML に閉じ込めることです。

 core.yaml ＝ 意味（読み手に依存しない）
core.yaml は、対象が「何を意味するか」だけを書き起こしたものです。UI の話は一切含みません。
概念・関係・重要度・難易度・確信度・出典（ファイル:行）・リスク・疑問といった、意味の構造を持ちます。
version: core/v1

target:
  type: pull_request
  title: "Add rate limiting to the public API"

concepts:
  - id: c_store
    label: "TokenBucketStore"
    summary: "クライアント＋ルート単位のトークンバケットをメモリに保持"
    importance: high
    difficulty: high
    confidence: 0.85
    source_refs:
      - { path: "src/api/middleware/token_bucket.py", lines: { start: 1, end: 120 } }

relations:
  - from: c_middleware
    to: c_store
    type: depends_on
    label: "トークンを要求する"

risks:
  - label: "プロセスごとの制限"
    description: "実効的な制限がインスタンス数に比例して増える（グローバルな保証ではない）"
    severity: high
注目したいのは、ここに「マインドマップで見せる」とか「シーケンス図にする」といった見せ方の情報が一切ないことです。あくまで意味だけ。だから、読み手が誰であってもこの core.yaml は変わりません。

 view.yaml ＝ 見せ方の戦略（読み手に依存する）
一方 view.yaml は、その意味を「この読み手に、どう見せると速く理解できるか」という戦略を書きます。
version: view/v1

audience:
  role: engineer
  familiarity: intermediate

presentation:
  preferred_forms:    # この読み手が好む表現
    - worktree
    - reading_path
    - review_checklist
  avoid_forms:
    - dense_table     # 詰まったテーブルは避ける
  density: medium
  tone: technical

focus:
  emphasize:          # 何を強調するか
    - dependencies
    - reading_order
    - risks
ここを差し替えれば、意味（core.yaml）はそのままで、見せ方だけを別の読み手向けに切り替えられるわけです。

この「意味を一度 YAML に固定してしまえば、表現はいくらでも派生できる」というのが、認知負荷の軽減に効いてくる部分です。

 できあがる HTML バンドル
generate-explainer-html が出力するのは、1 枚の HTML ではなくディレクトリ（バンドル）です。
<bundle>/
  index.html      … 外枠（ヘッダ＋ライト/ダーク切替＋左ペイン＋右ペイン）
  views.json      … ビューの一覧と順序
  core.yaml       … コピーされて同梱（プロンプトから絶対パスで参照される）
  view.yaml       … 同上
  views/
    01-engineer.html  … 切り替わる各ビュー（それぞれ完結した HTML）
    02-table.html
画面は以下のような2ペイン構成です。



右ペイン：タブでビューを切り替えられる iframe。ここに図解本体が表示される

左ペイン：ビューを追加するためのプロンプトのカードと、core.yaml / view.yaml のビューア

そして地味に大事なのが、ビューが「追加式（additive）」なこと。新しい表現を頼んでも既存ビューは書き換わらず、タブが 1 つ増えるだけです。エンジニア向けビューの隣にテーブルビューを足す、という増やし方ができます。


 見せ方は「読み手が」増やせる
ここが記事冒頭の「マインドマップ派 vs シーケンス図派」への答えになっています。
左ペインのプロンプトカードは、別のローカルファイルを読める AI に「YAML を読んで新しいビューを 1 つ返して」と頼むためのテンプレートです。最初から以下のような“追加ボタン”が用意されています。


テーブル：概念・重要度・難易度・関係・根拠を一覧で

ワークツリー：リポジトリ構造・読む順番・影響箇所を階層ツリーで

初心者向け：用語解説と 3 ステップの導線、例え話

エンジニア向け：依存・読む順番・レビュー観点・リスク・テスト観点

PdM / Biz 向け：目的・影響・意思決定ポイント

自由記述：「こういう表現にしたい」を自分で書く

カードのプロンプトは、YAML の中身を本文に貼り付けず、絶対パスで参照させる設計になっています。
# 参照（必ず読み込む）
- core.yaml: {{core_yaml_path}}
- view.yaml: {{view_yaml_path}}
これらのファイルを開いて意味構造と見せ方の方針を把握してから作ってください。
yaml の中身はこのプロンプトには貼り付けていません。
つまり、「テーブルで見たい人」はテーブルのカードをコピーして実行するだけ。AI が読むのは YAML 2 枚なので軽く、できたビューはタブとして増えていきます。
「自由記述」カードに {{希望する表現}} として「マインドマップ風で」と書けば、マインドマップビューも足せます。意味は固定したまま、見せ方は読み手側がいくらでもカスタマイズできる、というわけです。

 使い方

 インストール
Claude Code 内で以下を実行します。
/plugin marketplace add hirokita117/yaml-to-html-skill
/plugin install yaml-to-html@yaml-to-html-skill

 生成する
1 つのプロンプトで、2 つのスキルが正しい順番（YAML → HTML）で走ります。
この PR を、レビューするエンジニア向けに分かりやすく説明する HTML バンドルを作ってください。
まず generate-explainer-yaml で core.yaml と view.yaml を生成し、
続けて generate-explainer-html でその YAML（絶対パス）から
ライト/ダーク切り替え付きのビュー HTML バンドルを ./explainer-bundle に組み立ててください。

--- 対象 ---
<ここに PR / ドキュメント / リポジトリ概要 / README / 設計メモを貼る、またはパスを指定>
「まず YAML だけ作って中身を確認 → 良ければ HTML 化」とステップを分けて進めることもできます。

 開く
./explainer-bundle/index.html を開きます。
iframe 読み込みがブロックされる場合、以下のようにバンドル内で簡易サーバを立てるのが楽です。
cd explainer-bundle && python3 -m http.server

 サンプル（図解イメージ）
ここでは「このスキル自身のリポジトリ」を題材に、実際に生成したバンドルを載せます。スキルが自分自身を図解しているかたちです。
まず全体像については、上記で添付したように左ペインに「ビューを追加する」プロンプトカード、右ペインにタブで切り替わる図解ビューが並びます。

ここからが本題です。まったく同じ core.yaml から、見せ方だけが違うビューを切り替えられます。
「関係をたどって把握したい人」にはマインドマップ。

そして「処理の流れで理解したい人」には、シーケンス図。
この図自体を、マインドマップと同じ core.yaml から後づけで1タブ追加しました。

ちなみに、ライト/ダークの切り替えにも対応しています。


 まとめ
今回は、ドキュメント理解の認知負荷を下げるアイデアとして、対象を「意味（core.yaml）」と「見せ方（view.yaml）」に分けて YAML に閉じ込め、それを元に HTML で図解するスキルを紹介しました。
設計のミソを改めてまとめると、

意味を一度 YAML に固定することで、見せ方を何度でも派生できる

だから個々人が理解しやすい形で、図解化に対応できる


再生成時に AI が読むのは YAML だけで済み、入力コンテキストを小さく保てる
出力はオフライン・自己完結で、ビューは追加式に増やせる

「AI に丸投げ要約」から一歩進んで、意味は固定し、見せ方は読み手が選ぶ。そんな理解支援の形を試してみたい方は、ぜひ触ってみてください！
