## 本文
はじめに
最近は簡単なゲーム程度なら Claude code などの生成 AI だけで作れるようになってきました。例えば画像・動画生成、3D モデル生成を行う AI と組み合わせてデモゲームを作成する godogen などのプロジェクトもあります。

godogen では用途に応じて複数の AI サービスを組み合わせてロジックやゲームに必要なアセットを作る構成になってます。

コーディング全般: Claude Code / Codex
画像生成: Gemini
画像・動画生成: Grok
3D モデル生成: Tripo3D

youtube に生成されたゲームのデモも公開されています。

もちろん現時点で AI が自律的に作成できるのはごく単純なゲームやプロトタイプのみで、複雑な作品や創造的なアイデアを人間抜きで作るのは依然として困難という点はあります。とはいえ、シンプルなロジックの実装などコードで完結できる部分は AI だけでかなりの範囲をカバーできそうに感じました。
そこで、今回は Godot と Claude code を活用してゲームを作るというコンセプトのもと、インディーゲームの Party hard をオマージュしたゲームを作ることにしました。
Party Hard を選んだのは好きなゲームというのもありますが、特に以下の特徴があるのでゲームとして再現しやすそうという理由もありました。

アートスタイルがピクセルアートなので再現しやすい。
ゲーム性がシンプルでそこまで複雑なロジックがない。

この記事では実際にゲームを開発した際の進め方や開発記録を書いていきます。
ゲームはすでに完成して itch.io/gototplayer で公開しているので、興味のある人はプレイしてください。


 Party Hard とは
オマージュ元である Party Hard について簡単に紹介しておきます。
Party Hard は 2015 年にリリースされた見下ろし型 2D ステルスアクションで、立ち回りやトラップを駆使し、人目につかないようにパーティーの参加者を排除していくゲームです。にぎやかなパーティーの雰囲気と対照的なダークなゲーム性、攻略の自由度の高さが評価され、Indie Prize Europe 2015 の受賞や DevGAMM Moscow 2015 でのノミネートもしています。2018 年には続編の Party Hard 2 もリリースされました、ピクセルアートなのでそれほどリアルではありませんが、作品は全体的にゴア表現を含むので注意。


この記事は Party Hard を知っていることを前提に書いていくので興味があればプレイしてみてもいいかもしれません。

 使用するツールなど
今回の開発にあたって使ったツールをまとめて紹介します。

 Godot 4.6
ゲームエンジンは今まで触ってきて慣れている Godot を利用しました。現時点で最新版の 4.6 を使用。
開発には Godot の知識もある程度必要となります。コードは基本的に claude code が書いてくれますが、たまに細かい修正ができず無駄な変更を繰り返してトークンを浪費することがあるので、そういった場合に手動で修正できるぐらいの知識があると良いです。

 Claude Code (max 5x plan)
生成 AI は claude code max 5x plan を使用しました。モデルは基本的に opus 4.6 を使いましたが、 5 時間の上限/weekly 上限のどちらにも抵触することはありませんでした。pro plan でも可能ですが上限に達する可能性はあります（もちろん 1 回の作業量による）。
この記事を書いている時点では claude code が最もコーディング用途に適しているという雰囲気がありますが、codex とかでもできるかもしれません。

 Aseprite (ドット絵ツール)
party hard はシンプルなピクセルアートのゲームなので、生成した画像やアセットの加工・修正に aseprite を使用しました。aseprite である必要はなく、ピクセルアートを書いたり編集できるツールであれば何でも良いです。

 ChatGPT (画像生成 AI)
レベルの背景やエフェクトの画像を作成する際に ChatGPT の画像生成機能（無料枠）を使いました。特に ChatGPT である必要はないので好みの AI でも良いです。無料枠では 1 日に生成できる画像数に上限がありますが、ロジックの実装などと並行してやれば無料枠の範囲で十分だと思います。

 Gimp (画像編集)
画像の透過や編集に使用。画像編集できるツールであれば何でも良いです。

 MCP Server

 Coding-Solo/godot-mcp
Godot 公式の MCP Server は現時点で存在しませんが、ユーザーが作ったものはいくつかあります。今回は以下の mcp server を使いました。

Feature にあるように claude code 経由で以下のようなことができます。

godot プロジェクトの実行
コンソール出力の取得
シーンの作成・編集
uid の管理
etc

ただ godot のシーンファイル.tscn や GDScript、tres はいずれもテキストなので、mcp server を使わなくても claude で直接作成・編集することはできます。また godot は headless で特定のシーンを実行してコンソール出力を取得できるので、claude に明示的に支持すればシーン実行時の出力やエラーを確認することもできます。この mcp server があっても作業効率が劇的に変わるというわけではないですが一応使用しました。

 Skill
この記事を書いている時点で Godot 開発において必須の超有名な skill はないので、特に godot 向けのパブリックな skill は使っていません。ただ機能実装時の詳細を決める際に以下の grill-me が便利なので使用しました。

 grill-me

詳細などは以下の記事を参照。

今回の開発では、claude に機能やロジックを実装させるときに要件や実装内容の詳細を決めるときに使用しました。要件や指示が曖昧だと既存の実装や責任分離を無視したガバガバコードを書く確率が高くなるので、まずは grill-me で要件や変更点を明確にしてから機能を実装させることで上記の失敗をかなり抑えることができます。

 実装範囲
Party hard ではレベルは 10 以上、プレイアブルキャラクターは 5 以上、NPC のバリエーションは数十種類あります。これを全て実装するのは現実的ではないので、とりあえず遊べるゲームになるように以下の最小構成にします。

レベル数: 1
プレイアブルキャラクター: 1
NPC: 数種類



 グラフィック関連の実装
作るもの・作る範囲が固まったので実際にゲームを作っていきます。
進め方は色々考えられますが、まずは claude code だけでは実装が難しいグラフィック関連の表現から実装していきます。

 レベルの実装

 レベル背景画像の実装
party hard はパーティー会場・キャンプ場・カジノといった様々なロケーションのレベル上をプレイヤーや NPC が自由に動き回るゲーム性なので、まずはロケーションに対応する背景画像を作ります。今回は 1 レベルのみ作ることにしているので、 Party hard の 最初のレベルに対応するパーティー会場風のレベルを再現します。参考として実際のゲーム画面を切り抜いてきました。

Party hard の最初のレベル
レベルの特徴は以下。

建物の中と外に分かれている
建物の構造はメインのダンスフロアといくつかの小部屋に分かれている
キッチンやバスルームがある
部屋は扉で区切られている

このあたりの特徴を踏まえて、レベル背景として使用できる画像を ChatGPT 画像生成で作成します。何回かプロンプトを調整しながら画像ガチャを回すと以下のような画像ができました。

細かく見ると構造にいろいろツッコミどころはありますが、メインの部屋といくつかの小部屋で構成されている・建物内外に分かれているといったようにレベルの背景画像として使用できる要素は十分に備わっています。ただメインの大部屋がログハウス風でパーティー感があまりないので、もうすこしナイトクラブの雰囲気を出すように修正していきます。
ChatGPT 画像生成では「画像内の特定部分のみ xxx に変えて、他の部分は一切保持して」というように指示すると、指定した範囲の雰囲気やオブジェクトを変更して部屋の構成や配置は保持することができます（もちろんプロンプトや返信次第ではありますが）。部屋のレイアウトは変えずにオブジェクトや装飾をナイトクラブ風にするように何回か修正を重ねたところ、最終的に以下のような画像になりました。

建物や部屋の構成は維持したまま全体的にナイトクラブ風になり、だいぶゲームの雰囲気が出るようになりました。バー風の部屋が庭と直通しているなど相変わらずツッコミどころはありますが、完璧にするには難しいのでこのあたりで妥協します。

 当たり判定の設定
作成した背景画像にはまだ当たり判定がないので、プレイヤーや NPC が壁や地形を無視して自由に動けます。Godot では CollisionShape2D を使って壁や侵入不可の領域を定義します。
AI を使ってコリジョンを設定することもできますが、AI は画像内の壁や区画の境界を認識するのがあまり得意ではないようで微妙にずれたりするので、手動で CollisionShape2D を配置して地形の当たり判定を設定していきます。
Godot でレベルに対応するシーンを作成し、Sprite2D などで画像を取り込み、壁や柱が存在する場所に地道にコリジョンを配置していきます。部屋の壁の他、ゲームでは特に使用しない林の部分、キャラクターが侵入できないテーブルや柱、プール等にもコリジョンを設定し、最終的に以下のようになりました。色がついている領域にはプレイヤーや NPC が侵入できません。

コリジョンの設定。青：壁、ピンク：テーブルや柱など、緑：侵入不可領域

 ナビゲーション領域の配置
party hard では NPC はランダムに動き回るので、NPC が移動可能な領域を設定します。Godot 2D では NavigationRegion2D を利用することで容易に設定できます。

実際はプレイヤーや NPC の当たり判定の大きさも考慮する必要があるので実装しながら適宜調整することになりますが、まずはざっくりと設定しました。

色のついた領域が NPC が動き回れるエリア
ただ Party hard の NPC は指定した領域すべてを自由に動き回るわけではなく、事前に定義されたポイント間を移動するようになっています。このゲームでも後述する waypoint により移動先を制限しています。画像では上の方に孤立した領域が存在していますが、waypoint を配置しなければ NPC はその地点に移動しないので問題ありません。


 ドアの実装
party hard ではいくつかの部屋の境界はドアで区切られていて、プレイヤーや NPC が近づくと自動で開閉するアニメーションが実装されています。ドアが開いているときは NPC の視線が通るので NPC kill が目撃されたら発見判定となりますが、閉じている際は kill しても視線に入らないので発見状態にならないといったようにゲーム性にも影響しています。
生成した画像では部屋のドアは描写されていないのでどう実装するか悩みましたが、ドアの開閉画像を書いて元ゲームと同様の挙動で実装する方法にしました。
まずゲームの画面を見ながらドアの画像を Aseprite などで書きます（開閉・縦横で 4 パターン）。あとはレベルの背景画像上に door をノードとして配置し、プレイヤーや NPC が近づいたときに画像の切り替えや、NPC 視線の遮断などのロジックを実装することで元ゲームと同じ挙動を再現しています。


 NPC 隠しポイント
party hard ではレベル内に排除した NPC を隠せるポイントがいくつか配置されています。
このゲームでは浴槽、プール、冷蔵庫、ゴミ箱など、画像内で既に描写されている使えそうなオブジェクトを隠しポイントに設定することにしました。隠し場所の具体的な動作はロジック実装時に実装します。

青い領域が NPC 隠しポイント
これである程度レベルの実装ができてきました。
実際にプレイ可能にするにはまだいくつか機能の追加や調整が必要になりますが、いったん置いといて次はプレイヤー・NPC のグラフィックを実装してきます。

 キャラクターの Sprite
Party hard のキャラクターや NPC は歩行、ダンス、攻撃、死亡モーションなどの動きがあるので、これらの動作を表現するための立ち絵画像（Sprite）とアニメーションを用意する必要があります。ピクセルアートなので立ち絵数枚程度なら自作できるものの、アニメーション用の差分画像をすべて準備するのは骨が折れるのでアセットを利用します。
いくつか探したところ、itch.io で公開されている以下の Pixel Art Character in the style of Party Hard が今回の用途に合いそうでした。

静止状態、歩行、攻撃、ダンスなどゲームで使用できるアニメーションが一通り含まれており、aseprite ファイルも含まれているので NPC のベースには上記のアセットを使用します。ただ NPC としては 1 種類しか含まれていないので、これをベースにいくつか変更を加えていきます。

まずはじめに、Party hard の主人公であり、プレイアブルキャラクターのひとりでもあるダリウスを作成します。ダリウスは汎用 NPC とは異なる見た目なので、party hard ゲーム本編を見ながら アセットに含まれる aseprite ファイルの 1 フレーム目の NPC を上書きしながらを書いていきます。ピクセルアートでドットを打つだけなので絵心がなくてもできるはず。

作成したダリウスの待機アニメーションの 1 フレーム
アニメーションを置き換えるには他のフレームの NPC 画像もすべて上記のダリウスで置き換える必要がありますが、手動で書き換えるのは現実的ではないので aseprite の Lua で API を実行する機能を利用します。

aseprite API を利用し、作成した 1 フレーム目のダリウスの立ち絵で他フレームの NPC を置き換えるよう claude に指示して実行させます。おそらく 1 回ではうまくいきませんが、何回か試行錯誤を繰り返すとほとんどの立ち絵を置き換えた aseprite ファイルを生成してくれます。

生成された aseprite ファイルの全てのフレームを 1 つの画像にまとめたスプライトフレームとして保存します。Godot ではスプライトフレーム内の指定したフレームからアニメーションを作成できるの機能があるので、これを利用してゲームで使用するアニメーションを作っていきます。詳細は以下を参照。

作成したアニメーションの一部が以下のようになります。Godot ノードとして実装しているので、これをそのままゲーム内で使用できるアニメーションになっています。

待機、歩行、攻撃、ダンス、打撃、やられアニメーション
NPC のパターンもいくつか欲しいので、同様の手法で 1 フレーム目のみ手動で作成して残りのフレームを置き換える方法で作成します。配色を変えるだけでもパターンの差分としては有効なので、以下のようにいくつかパターンを生成しました。

NPC 差分。元アセットの配色を変えたパターンと、ダリウスをベースにしたもの
その他、元アセットの NPC と異なる見た目としてカウボーイ風の NPC の立ち絵を作成しました。また、Party Hard ではプレイヤーを追跡する特殊な NPC として police が存在するのでこちらも実装します。元アセットでは帽子やスカーフなどがないので始めのうちは claude でうまく生成できませんでしたが、試行錯誤させることで無事にアニメーションを生成してくれました。

カウボーイ風 NPC と police NPC
プレイヤーはダリウスの 1 種類、NPC は色違いも含めて 10 種類、特殊 NPC は police 1 種類作成できたので、とりあえずゲームとして遊べるぐらいのキャラクター立ち絵+アニメーションが用意できました。

 NPC の AI (ビヘイビアツリー)
party hard の NPC の AI は基本的に繰り返しのルーチン行動と、特定の行動に応じてルーチン行動を中断して固有のアクションを行う行動で構成されています。

繰り返しのルーチン行動：レベル内の決まった地点まで移動 → ダンスなど NPC 固有の行動を実行 → 別の地点に移動
それ以外の行動： 死体を見つけたら police に通報、プレイヤーのダンスに反応など。

これらの行動はビヘイビアツリーで制御されているので、このゲームでも NPC の AI の実装にはビヘイビアツリーを使うことにしました。
Godot でビヘイビアツリーを実装する場合、自作するか既存のフレームワークを使う選択肢があります。Godot 用の既存のフレームワークでは LimboAI, Beehave あたりが有名なので、主な候補は以下 3 つとなります。

 Waypoint (WP)
NPC の BT で制御しているように特殊行動していない NPC は付近の Waypoint (WP) に移動 → ダンスなどの行動をランダム実行 → 次の WP に移動というルーチン行動を繰り返すようになっています。WP ノードとしてレベル上に散らばるように配置しています。

マーカーがついているのが WP。同じ WP には同時に NPC が占有しないようになっている。
WP は割と適当に配置していますが、ダンスフロアとキッチンには多め、建物外には少めという傾向にしています。これによりダンスフロアには常に多数の NPC が存在するため排除するタイミングが少ない、建物外や小部屋などは NPC が孤立しやすいため排除しやすいといったようにゲームバランスの調整に結びついています。

 テスト
テストは AI を使って効率的に実行する方法が特に思いつかなかったので、実際にシーンを再生してプレイする、godot のデバッグ機能などを使って地道にバグがないか確認していきます。

 デバッグメニュー
テストでは同じシーンや同じ動作を何回も実行することになるため、特定の動作を瞬時に呼び出せるデバッグ用のメニューを実装すると便利です。このあたりも claude に指示することで実装できます。このゲームでは NPC の生存状況、特定の画面への遷移、police の任意の出現・退場など頻繁に使う機能をデバッグメニューから呼び出せるようにしています。

デバッグメニューの一部
デバッグメニューは Godot シーンとして実装し、シーンに設定した gdscript では以下のように設定します。
  func _ready() -> void:
      if not OS.is_debug_build():
          process_mode = Node.PROCESS_MODE_DISABLED
          return
OS.is_debug_build() はゲームがエディター上から実行されている時、および debug export されているときのみ true になるので、本番リリース用の release export では自動的に無効化されます。

 まとめ
この記事では Godot + Claude code を活用してゲームを作るというコンセプトの元、インディーゲームの Party hard のオマージュゲームを作った際の開発記録をまとめました。
Claude Code と GDScript は相性が良く、Godot シーンや GDScript のみで実現できるロジック実装は claude code だけでかなり効率良く開発を進めることができました。もちろんゲームの規模が大きくなるにつれて、追加や修正による影響範囲を厳密に確認して実装する、適宜リファクタリングを実行すると言った工程は必要になりますが、それを踏まえてもコーディング部分の開発スピードは従来より大幅に上がったと感じます。
一方、レベル背景画像や UI アイコン、キャラクターの立ち絵・アニメーションといったグラフィック関連は対応が難しいので、ChatGPT 画像生成や既存アセットを駆使する必要がありました。ゲームに特化したグラフィックを生成する AI というのもまだ確立されてなさそうなので、このあたりは依然として人間を作ったものの価値が高そうです。とはいえ、画像生成や既存アセットを利用すれば自分で絵がかけなくてもグラフィック関連をカバーできるようになっており、個人開発のハードルはだいぶ下がってきていると思います。
